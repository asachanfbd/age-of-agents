# Blueprint

**What this document is**: a living snapshot of what currently exists in "Age of Agents", written and updated by its assigned Worker at the end of every Task — not a changelog. See agent-visual-os's own docs/glossary.md for the full definition.

Test commands and daemon-test conventions live in [testing.md](testing.md). Rules for planning a task live in [planning-notes.md](planning-notes.md).

## What currently exists

The Project Workspace header shows a single GitHub icon link that opens the Project's repository in a new browser tab. It is shown only when the Project has a linked repository URL its Git provider recognises, and sits immediately before the branch selector. There is no pull-request button or popover. Open pull requests are listed in the **PR** tab, placed right after **Code**; it is hidden for a Project without a recognised repository, and its label carries the open-PR count ("PR 3", accessible name "PR, 3 open"; just "PR" when the count is unknown, so a real zero shows "PR 0").

**Git provider.** Each Project has a `gitProvider` setting (Settings → Git provider), default and only value `github`; a Project stored before the setting existed reads as GitHub. Server code reaches the host only through the `GitProvider` interface in `server/src/projects/gitProvider.ts`, looked up with `gitProviderFor(project.gitProvider)`; a new provider is one more registry entry. Its operations are repository-link resolution, `listOpenPullRequests` and `describeFailure` for the list, and `readPullRequest`, `mergePullRequest`, `fetchPullRequestHead` and `describeActionFailure` for the row actions described under "PR tab actions" below. `PATCH /api/projects/:id/git-provider` with `{ gitProvider }` validates the value (400 with `{ error }` if unsupported). The web mirror is `web/src/lib/gitProvider.ts` (`gitProviderOf`, `repositoryLinkOf`, `GIT_PROVIDERS`). The GitHub provider converts validated HTTPS and SSH remotes, including SSH aliases, to `https://github.com/owner/repo` browser links and an `owner/repo` CLI identity (`githubRepository` in `server/src/projects/git.ts`).

**GitHub accounts (per project).** Accounts come from the machine's GitHub CLI: the app lists the github.com accounts `gh auth status` reports (Settings → GitHub accounts, `GET /api/github/accounts`, which re-detects every time it is called: on opening the settings, on Refresh and on Re-check) and stores no token, password or key of its own. `gh` 2.40 or newer is needed for several accounts; with `gh` missing or older, only "Machine default" is selectable. A Project's `githubAccount` (the `gh` login; absent or null is Machine default, so existing projects are unchanged) is set with `PATCH /api/projects/:id/github-account` (400 for a non-github.com or missing repository, an invalid login or one `gh` does not list) and checked with `POST /api/projects/:id/github-account/check` (OK, no access, signed out, unavailable; an owner or organisation matching none of the signed-in accounts is a warning only). Per account the commit author name and email can be overridden (`PUT`/`DELETE /api/github/accounts/:login/identity`, stored in `github-identities.json`); the defaults are the GitHub profile name (or login) and the `<id>+<login>@users.noreply.github.com` address. The identity never changes the user's global git config or `gh`'s active account.

**Project name and deletion (task 37.013).** Settings → General (first section, default, for every Building type) holds **Project name** and a **Danger zone**. `PATCH /api/projects/:id` takes `{ name }` and/or `{ position }` (400 `{ error: 'name or position is required' }` when neither; with both, both apply). A name is trimmed and must be 1 to 80 characters, counted as characters (an emoji is one): else 400 `{ error: 'Name must be 1 to 80 characters.', field: 'name' }`; an unknown project is 404, also when it is deleted while the rename waits (the rename runs under the Project lock). Names need not be unique (only slugs are). A rename changes only `name` and `updatedAt`: the slug, folder, repository and worktrees keep their names, and the form says "The folder name stays the same." It broadcasts the existing `project` event, so every open view updates live. Content Studio's own Settings rename calls the same `renameProject` (`server/src/projects/projectService.ts`), so both paths share the rule and the event. `DELETE /api/projects/:id` stays as it was (204; 404 unknown; 409 with `ProjectHasActiveTaskError`'s message when a task is active, nothing touched) and now also stops the Project's task and Agent-session terminals and removes its Tasks, task contexts, plan items, queued plan-item entries, workflow and step runs, saved commands and command runs (running ones are stopped first), notifications and Agent sessions with their counter, besides the folder, worktrees, step outputs, secrets, building data, scheduled jobs and links it already removed. It then broadcasts the new `/ws` event `{ type: 'projectDeleted', projectId }`; the web store drops the Project and everything it holds for it and closes its popup (the delete action does the same on success, so the event arriving second is a no-op). The Delete dialog names the project and `projects/<slug>`, requires the exact name typed, shows the server's 409 reason with only a Close button, and toasts "Project deleted". A read-only Building (type unavailable or newer data) shows both controls disabled with the reason as text. Replaced: the old `PATCH /api/projects/:id` error "position is the only field this endpoint updates". Not covered by tests: real Remotion or render processes at delete, real simultaneity of a rename and a delete in two tabs, and anything rendered in a browser.

*What receives the account.* `withProjectGithub` (`server/src/github/accounts.ts`) fetches the account's token with `gh auth token --user <login>` once per operation and runs the operation inside an async scope (`server/src/github/context.ts`); `git()` and `gh()` read that scope, so concurrent operations on different projects never mix identities. Inside it the child process gets `GH_TOKEN`, `GH_HOST=github.com`, prompts disabled, `GIT_AUTHOR_*`/`GIT_COMMITTER_*` set to the account's identity, an inline credential helper that reads `GH_TOKEN` from the environment (existing `GIT_CONFIG_COUNT` entries are extended) and, for a `git@github.com:` remote, an `insteadOf` rewrite of just that project's remote to HTTPS. Ambient `GITHUB_TOKEN`, `GIT_ASKPASS`, `SSH_ASKPASS` and `GIT_SSH_COMMAND` are removed. The stored remote is never rewritten. This covers task commits and pushes (Complete step, step "inspect changes" commit-and-push, interim commits, testing-setup and docs-bootstrap runs), PR creation and lookup, the open-PR count, the PR tab's list, merge and conflict-resolution actions, the stack-merge check, the branch list fetch, the sync poller, and the Sync command run. Claude and Codex terminal sessions of the project (execute, planning, workflow steps and read-only reopened steps) get the same variables in their environment (`githubSessionEnv`); sessions already running keep the account they started with. Inherited ambient credentials are removed from sessions too (the terminal start takes an `unsetEnv` list). Project without an account: nothing is added. Local-only worktree commands (`git worktree add`) are not scoped because they never reach GitHub; creating a project clones before any account can be chosen. A `github.com` remote in an unsupported form (`http://`, `ssh://`, embedded credentials) fails with a clear message for a project that has an account.

*Failures.* A chosen account that is signed out, expired or without access never falls back to another account: the action fails with a message naming the project, the account and the action, plus the fix (`gh auth login -h github.com`). Background failures (sync poller, open-PR count) also raise a `github.account_failed` notification under the project. If the repository URL later stops being a github.com URL the stored account is ignored (Machine default behaviour).

*Redaction.* Tokens are never placed in argv, URLs, stored remotes, files or API responses. A fetched token is registered with `server/src/redaction.ts`, which scrubs it (plain, Basic-auth base64, URL-encoded and JSON-escaped forms) from daemon logs, error messages, command-run output and terminal output before it is stored or sent over `/ws`, using a stream redactor that holds back only a tail that could be the start of a secret so a token split across chunks is still caught. Task transcript turns and step output files are redacted before they are persisted.

**Endpoint contract.** `GET /api/projects/:id/open-pull-requests` runs `gh api --paginate` for every open pull request page (drafts included) and returns `{ count, pullRequests, truncated, checkedAt }`. Each pull request has `number, title, headBranch, baseBranch, author (null for a deleted account), url, isDraft, createdAt, updatedAt`. The list is sorted newest first by `createdAt` (ties: higher number first) and capped at 100; `count` is the true total and `truncated` is true only when more than 100 are open. If `gh` fails the route still answers 200 with `{ count: null, pullRequests: [], truncated: false, checkedAt, error }`, so a real zero (`count: 0`) is never confused with unavailable data. An unknown Project returns 404 and a Project without a repository its provider recognises returns 400, both with an `{ error }` body. The PR tab lists rows as `#12 Add login page` with a Draft badge, `head → base`, author and an "Open on GitHub" link, under a "Newest first" caption, with a footer "Showing newest 100 of more than 100" when truncated.

**Polling and cache.** `createPrReadings` in `web/src/lib/pullRequests.ts` holds one reading per Project for the whole app, so the tab label and the list share one data source and a tab switch never resets it. It fetches when the workspace opens (reusing a successful reading under a minute old), then `startPolling` forces a check every 60 seconds while the page is visible. Hiding the page stops the timer; showing it checks immediately and restarts the minute. Requests in flight for a Project are shared, including by a manual Refresh, which otherwise bypasses the cache. A failed check keeps the previous list and count, shows the error and the last good check time, and is not cached, so the next open or poll retries. Changing the Git provider clears the Project's reading and drops any response still in flight for the old provider. When classifying `gh` errors, only explicit authentication evidence means signed out; a 403 can also mean a rate limit or denied access. Keep these cases distinct and verify them with fake CLI output in `server/tests/openPullRequests.test.ts`; `web/tests/pullRequests.test.mjs` covers the reading store, polling with an injected environment, tab order and source wiring.

**PR tab actions (task 10.002).** Every row has Check out and Merge beside "Open on GitHub". The routes are `GET /api/projects/:id/pull-requests/:number/merge-state`, `POST …/:number/merge` (`{ confirmBlockers?, executorId? }`), `POST …/:number/checkout` and `POST /api/projects/:id/pull-requests/return` (`{ branch? }`), all in `server/src/projects/pullRequestService.ts`. A PR number that is not a positive integer is a 400 before any `git` or `gh` runs. Refusals are 409, a provider failure on merge, checkout or Return is 502 with the provider's reason, an unknown Project or PR is 404 and a Project without a recognised repository is 400. The merge-state read is the exception: a provider failure answers 200 with `{ number, checkedAt, mergeState: null, error }`, like the list route, so one row can show it with Retry.

*Provider operations.* GitHub implements them in `server/src/projects/pullRequestMerge.ts` with `gh`. `readPullRequest` is one `gh api graphql` call returning a provider-neutral `PullRequestReading` (state, draft, mergeable, each check with GitHub's `isRequired` flag for this PR (`statusCheckRollup.contexts`, first 100), review decision, protection and behind-base flags, whether the account may merge, head and base branches, whether the head branch still exists, fork URL, default branch). Output it can't parse throws; it never reads as clean. `mergePullRequest` runs `gh pr merge <n> --repo <slug> --merge`, always a merge commit. It adds `--admin` only for a merge the person confirmed over its blockers (`bypassProtection`), because `gh` otherwise refuses a PR the base branch's protection blocks before asking GitHub; a clean merge and the conflict run's automatic merge never pass it. `fetchPullRequestHead` fetches `refs/pull/<n>/head` from `origin` into `refs/agent-visual-os/pull/<n>` and resolves it, so a fork's head works and a same-named branch on `origin` is never used. `describeActionFailure` names `gh` missing, signed out, rate limited and unreachable, and otherwise returns the provider's own text.

*Merge-state classification.* `classifyMergeState` turns a reading into one of four classes, and Merge acts on the class the daemon reads at click time, not on what the row showed:

| Class | When | Merge does |
| --- | --- | --- |
| `clean` | mergeable, nothing flagged | merges at once |
| `conflicts` | the PR conflicts with its base | starts a conflict-resolution run with the chosen agent (400 without `executorId`) |
| `blocked` | draft, *required* checks failing or still running, changes requested, review required, behind its base, protection rules not satisfied, or merge state unknown | returns `needs-confirmation` with the blockers; merges only with `confirmBlockers: true` |
| `unmergeable` | closed, already merged, the account can't merge, or the head branch is gone | refused with the reason; the row shows it in place of the button |

`unmergeable` wins over everything. `conflicts` wins over `blocked` and keeps the blockers, which are confirmed after the run. An unknown merge state is a blocker. Only required checks block (task 19.002): the blocker names them ("Checks are failing: build, lint"), checks that are not required come back as `warnings` ("Optional checks failing: Vercel") and never change the class, and when required-ness is unknown every non-passing check blocks with "(could not tell which checks are required)". The field is `isRequired(pullRequestNumber:)` on `CheckRun` and `StatusContext`, chosen from the GraphQL schema as remembered, not from a real answer; if GitHub refuses it the PR is read again without it. `mergeStateStatus` `UNSTABLE` is never used as a blocker. The row reads its merge state per PR, so one unreadable PR shows its own error with Retry and the list stays.

*Branch deletion.* After a successful merge the remote head branch is deleted with `gh api -X DELETE …/git/refs/heads/<head>`; `gh`'s own `--delete-branch` is not used because it would also delete the local branch and switch the checkout. It is skipped, with a note, when the head is the base branch, the repository's default branch, or lives in a fork. Open PRs whose base is the head branch are retargeted to the merged PR's base first, because deleting a branch through the API closes them. A failed deletion or retarget leaves the merge a success (200) with `branchWarning`, shown as a warning strip above the list. A head branch that is already gone when the delete runs (GitHub answers "Reference does not exist", as when the repository deletes head branches on merge) is not a failure: it is reported as deleted, with no warning. Local branches and worktrees are never touched.

*Checkout rules.* Check out switches the Project's own folder to the PR's branch under the branch switcher's rules: refused when tracked files have uncommitted changes (untracked files don't count) and when the folder is busy (`assertProjectFolderFree`). A same-repository PR is checked out as its head branch name, a fork PR as `pr-<n>/<head>`. A new local branch is created at the PR head. An existing one is switched to and fast-forwarded when behind, kept as is when it is only ahead, and refused when it has diverged, with nothing changed. The branch is at the PR head exactly, so a conflicting PR has no conflict markers. Checkout never merges, pushes, changes the PR or starts an agent, and like any switch to an existing branch it leaves paused tasks on the branch they were started on. A closed or merged PR is refused (409) saying so. The Project record stores `prCheckout: { number, branch, previousBranch }`; the row then shows "Checked out" and "Return to <previous branch>", which is also the first item of the header branch menu while that branch is current, including after the PR was merged. `previousBranch` is whichever branch was current just before the latest checkout. If it is gone, Return answers 409 with `defaultBranch`, and both the row and the menu explain it and offer that branch instead. The default branch is read from the local `origin/HEAD`, or asked of the remote when that is not recorded. Any other refused Return (uncommitted changes, folder in use) shows its message on the checked-out row and in the menu. An ordinary branch switch or branch creation clears `prCheckout`. A checkout or Return is refused as busy (409) while another one, or a merge of any PR of the same Project, is in flight; two merges of the same PR at once give the second a 409.

*Conflict-resolution run.* The dedicated workflow is defined in code in `server/src/worker/conflictResolution.ts` (id `pr-conflict-resolution`, one write-capable step, no approval gate), not in the Catalog. The run belongs to a PlanItem with `prConflict`, titled "Resolve conflicts: #<n> <title>", so it appears on the Tasks board with a "PR conflicts" badge and opens the same run from the board and from the row's View. Its worktree is on a run-local branch `pr-conflicts/<n>-<run id>` created at the fetched PR head, so it works while the PR's own branch is checked out in the Project folder. It starts at once: it skips the concurrency cap and never holds or joins the plan-item queue. When the step completes, `finishConflictRun` in `workerManager.ts` commits what is left, pushes HEAD to the PR's head branch without force (to the fork's URL for a fork PR), waits for the provider to report the pushed commit with a known merge state (`recheckPullRequest`: up to 15 readings 2 seconds apart by default, after which a still-unknown state counts as a blocker), and then: merges when clean (`outcome: 'merged'`), completes as `resolved` when only blockers remain (the row shows "Conflicts resolved" and Merge opens the confirmation), or fails with the reason when the PR still conflicts, can no longer be merged, the push was refused or the merge was refused. The worktree and the run-local branch are removed in every case. One run per PR at a time: Merge during an active run returns that run. A stopped or failed run leaves the PR unmerged; Retry asks for an agent again, archives the old card and starts a fresh run. A row finds its run by PR number (`latestConflictRun`, `conflictRunFor` on the web), which survives a reload and a daemon restart; a run the previous process left mid-merge is reported failed at startup. `skip_step`, Interim commit and "mark complete" never push a conflict run's work.

*Web.* `web/src/lib/pullRequestActions.ts` holds every row decision as pure functions (`prRowModel`, `mergeClickTarget`, `runPhase`, `mergeNotice`, `returnMenuItem`, `withHeldRows`). The store keeps `prActionsByProject` and the actions `loadPrMergeStates`, `mergePullRequest`, `checkoutPullRequest` and `returnFromPullRequest`. A row's merge state is read again only when the PR's `updatedAt` changes, on Refresh, after an action and when a conflict run changes status. A row whose merge is in flight is held as it was against poll responses. The Resolve conflicts dialog (`PrDialogs.tsx`) uses the shared coding-agent picker (see below), asks every time and remembers no agent.

Tests: `server/tests/pullRequestMerge.test.ts`, `pullRequestCheckout.test.ts`, `pullRequestMergeApi.test.ts`, `conflictResolutionRun.test.ts` (shared harness `tests/helpers/pullRequestHarness.ts`: real git against a local bare remote, a scripted `gh` on `PATH`, scripted terminal sessions) and `web/tests/pullRequestActions.test.mjs`.

Not yet implemented or verified for the PR tab actions: no run with the real `gh` CLI has been made (checkout of a normal and a fork PR, clean merge with branch deletion, conflict run, blocked by checks), so the GraphQL field names and `gh` argument forms are checked only against fakes. The fetch does not use a per-Project GitHub account, since that task has not landed. `--admin` on a confirmed merge is sent for every kind of blocker, and how `gh` answers for an account that may not bypass protection has not been tried. The run view has no link back to the PR tab. Starting a conflict run's card again from the Tasks board, in place of Retry on the PR tab, has not been traced. A row keeps showing an old failed run's status after the PR was fixed by hand and reads clean. Nothing was checked in a browser.

**Auto-merge (task 10.017).** Product behaviour (states, agent rule, blocker policy, API) is in [auto-merge](../docs/auto-merge.md). Implementation facts that are easy to miss: the switch lives on the plan item (`autoMerge`, set by `PUT /api/projects/:id/plan-items/:itemId/auto-merge`) and follows its latest run's PR link, not a `TaskRecord`. `autoMergeService.ts` runs one look at a time per project (FIFO queue in `autoMerge.ts`), re-evaluates every 60 s and at start-up, and waits on a conflict run inside that turn for at most `maxRunWaitMs` (six hours). Failed and Can't-be-merged tasks are only read on the poll (to notice a manual merge) and never act or change on a failed read. The conflict run is `workerManager.startConflictRun` with an optional auto-merge owner; the manual PR-tab flow still requires an executor. Merging/resolving chips use a still dot because looping animations are banned (`web/tests/gpuFriendlyUi.test.mjs`). Board placement (bug 10.017.001): server statuses stay `completed`/`done`; the web holds an Auto-merge task back from Completed until `merged` (`autoMergeHoldOf` in `web/src/lib/autoMerge.ts`, used by `buildCompletedRows`, `taskProgress` and `buildTaskGroups`, whose `prNotMerged` group feeds the lower Needs you row). Placement rules are in the [auto-merge doc](../docs/auto-merge.md#where-the-task-sits-on-the-board). Task 19.002: the stored record also carries `warnings` (non-blocking checks), a merge raises the info notification `automerge.merged`, and the web plays the chime on the merge rather than at run end and the horn when Auto-merge needs the person (`web/src/lib/taskSounds.ts`); see the [auto-merge doc](../docs/auto-merge.md#which-checks-block). "Merge state unreadable" was reported once for the HR Fin Pay project but not reproduced with an SSH-alias remote and the project's account (`server/tests/pullRequestAccount.test.ts`), so no fix was made for it. Task 10.022 extends the hold to Auto-merge-off tasks: `pullRequestStateService.ts` (injected lookup, `gh` GraphQL `ghBranchPullRequests` in `git.ts`, one call per batch with branch names as variables) stores `PlanItemRecord.pullRequest` only on change, so a failed lookup leaves the last reading; it runs on a 60 s timer, on run completion and after a PR-tab merge, and `completedAutoMergeHold` (`web/src/lib/autoMerge.ts`) reads it, so board, progress, details header (`detailStatus`) and PR-tab tag (`prRowAutoMergeTag`) agree. Held-only rows are ordered in `orderPrNotMerged`. Not verified: a real `gh` answer for closed and reopened PRs, and the move after a PR-tab merge in a real browser. Not verified: a real `gh` run with clean, conflicting and blocked PRs on a throwaway repository, and the switch, panel, chip and two-row Needs you column in a browser (both themes, narrow width).

**Per-step notes.** A person can leave a free-text note for one workflow step of a task, running or not yet started. Notes are stored on the task (`PlanItemRecord.stepNotes`, keyed by step id), not on a run, so they work before any run exists and apply to every later run of that task. `PUT /api/plan-items/:id/step-notes/:stepId` with `{ note }` sets one; an empty or `null` note clears it, a missing or non-text `note` is 400, and so is a trimmed note over 4,000 code points, a step id that is not a kebab-case slug, or (once a run exists) one outside the latest run's workflow snapshot; an unknown task is 404. `GET /api/workflow-runs/:id` returns `stepNotes`. Rules live in `server/src/projects/stepNotes.ts` (the web mirror is `web/src/lib/stepNote.ts`; a web test pins the two limits and `codePointLength` together, since the packages cannot share code). `startStepTask` appends the note, unlabelled, to the end of a fresh step prompt and to the resume, rerun and "Continue." messages. It clears the note only after `runTerminalTask` reports a successful launch and only if the stored note is unchanged since the prompt was built, so a failed launch keeps it. A note saved on a running or finished step is not sent to the live session; it waits for the next round or retry. Starting a run drops notes for steps the chosen workflow lacks. `setStepNote`, `consumeStepNote` and `dropStepNotesOutside` run through a per-task queue (`withStepNotesLock`). UI: `StepNoteControl.tsx` in the run view and a marker in `WorkflowRunStepper.tsx`. Current limitation: a task that has never run has no screen for adding a note (the accepted mockup is the run view only). Not verified: a real CLI session receiving the note, a daemon restart (persistence is checked from the stored JSON), the regression-run message carrying it (no test), and layout in a browser. Tests: `server/tests/stepNotes.test.ts`, `stepNotesApi.test.ts`, `web/tests/stepNote.test.mjs`.

**Dependent tasks (task 10.018).** Product behaviour (satisfaction rule, waiting and blocked states, API, the decision that dependent tasks never stack) is in [dependent tasks](../docs/dependent-tasks.md). Implementation facts: `dependsOn` and `waiting` live on the plan item; the pure rules (validation, cycle and depth checks, `evaluateParent`, start order, the chain builder) are in `server/src/projects/dependencies.ts`, the service (evaluation, start, cancel, notifications) in `dependencyService.ts`, the git and provider reads behind an injectable `DependencyGit` in `dependencyGit.ts`. The service evaluates one project at a time through the same keyed queue as auto-merge, on parent run/plan-item events, project sync readings, dependency changes, daemon start and a 30 s timer (`schedule` and `now` are injectable). `acceptWorkflowRun` clears `waiting` in the same write that moves the item out of Planning, and restores it when a start is rejected; `findStackTarget` returns no target for a task with dependencies. Tests: `server/tests/dependencies.test.ts`, `dependencyService.test.ts`, `dependencyApi.test.ts`, `dependencyGit.test.ts`, the I34 case in `instantStart.test.ts`, and `web/tests/dependencies.test.mjs`. Waiting cards have no `progress`. Card-to-card link drops are handled in `useBoardDnd.ts` (middle 50% of a card, `stopPropagation` and clearing the column's reorder target, independent of `canDropOn`), with the new parent list from `planLinkDrop`; both helpers are in `web/src/lib/dependencies.ts`. Its tests assert source text, so the rendered popovers are unchecked in a browser. Outstanding: the manual three-task run on a throwaway repository and a browser look at the new screens.

Syncing a Project's checked-out branch from origin and switching to an existing branch (`BranchMenu.tsx`'s Sync action and branch list, `checkoutProjectBranch`/`runProjectSync` in `server/src/projects/projectService.ts`/`server/src/commands/commandRunner.ts`) are refused only while something is really working in the Project's own folder — the same rule `executePlanItem` already used to decide whether a new in-place Task may start, pulled out into `server/src/worker/projectFolderGuard.ts` (`isProjectFolderBusy`/`assertProjectFolderFree`/`isLiveTask`) so both call sites and `workerManager.ts` share one answer instead of two. A running planning session, and a coding Task or WorkflowRun isolated in its own worktree, never block either action; only a live, non-`plan` Task with no `worktreePath` or an unsettled WorkflowRun (`running`/`awaiting-approval`/`needs-attention`/`completing`) with no `worktreePath` does, and a stale `activeTaskId` left on the Project record is never counted. A busy folder fails with 409 (`ProjectFolderBusyError`); uncommitted changes now also answer 409 (a `GitError`, where they used to surface as a 500), and a missing repository still refuses exactly as before. Creating a branch is unaffected by any of this — always allowed, folder-busy or not. The web mirrors the rule live rather than guessing: `TaskRecord` carries `worktreePath` on the wire (mirroring `WorkflowRunRecord`'s existing field), and `web/src/lib/branchMenu.ts`'s `isProjectFolderBusy` recomputes it from the store's already-live `tasksById`/`workflowRunsByProject`, so `BranchMenu.tsx` no longer gates its Sync button or existing-branch entries on the Project's overall `status`. Project status, the building dot and footer counts are unchanged — a planning session still shows a Project as working, it just doesn't block git actions. See `docs/architecture.md`'s "Amended 2026-10-04" note for the full rationale. **Auto-pull (task 10.014).** When a Project's checked-out branch is `behind` `origin/<branch>`, the daemon fast-forwards it by itself (`server/src/projects/autoPull.ts`, driven from `gitSyncPoller.ts`). It pulls only when all hold: the reading is `behind` (never ahead, synced, diverged, no-remote or unknown); nothing uses the main folder (the same `isProjectFolderBusy` rule as the branch switch and manual sync, so planning sessions and worktree work never block); no local change overlaps the incoming commits (the **overlap rule**, `server/src/projects/incomingOverlap.ts`: the paths changed between `HEAD` and `origin/<branch>` are compared with the local status; only a staged, modified, deleted or renamed path in that set, or an untracked file the commits would add, blocks; other local changes and ignored files never do, and if the incoming paths cannot be read every tracked change blocks, with the reason said); no merge, rebase, cherry-pick or revert is unfinished (a detached HEAD is read as `unknown` by the poller, so it never pulls and shows "could not check" rather than a reason); no branch checkout, PR checkout or merge, or task start/stop holds the Project lock; and the Project's **Auto-pull upstream changes** setting is on (Settings, Git; `ProjectRecord.autoPullEnabled`, absent reads as on, `PATCH /api/projects/:id/auto-pull`, only for a Project with a repository). The only pull command is `git fetch origin && git merge --ff-only origin/<branch>`, run as a tracked command run in the Project's command log, marked `automatic` (History shows an "Automatic" badge). It is evaluated on every sync check (the one-minute poll) and straight away after a task or run releases the folder, a branch or PR checkout, a PR merge, or the setting being switched. The Project is claimed (`claimProjectPull` in `git.ts`) before the conditions are read, so a task starting meanwhile waits for the pull in `withProjectLock` and a pull never starts once a task start holds the lock; pulls for different Projects run in parallel, for one Project serialized. A deferred pull is explained in the sync indicator's tooltip and the out-of-sync notification ("not pulled: a task is running in the main folder", "...you have uncommitted changes to files the update also changes: a, b, c and N more" (also `ProjectSyncState.blockingFiles`/`blockingFilesTotal`), "...your branch has diverged from origin", "...a merge is in progress", "auto-pull is off for this project") and happens by itself once the reason clears. Success raises nothing: the reading returns to synced, the tooltip says "Pulled N commits automatically at <time>" (`ProjectSyncState.lastAutoPull`), the out-of-sync notification resolves, and the Code tab reloads (`mainFolderReloadKey`). A failure (including git refusing at apply time because the folder changed after the check: the message names the files and nothing is applied) raises one `git.auto_pull_failed` notification per distinct reason and is not retried until `origin/<branch>` moves; the sync icon always works. Not covered by tests: real network, auth and timeout failures, a daemon killed mid-pull, real simultaneity (the race is forced at the lock), and anything rendered in a browser (see `.docs/testing.md` known gaps). The manual sync button runs the same fetch and `merge --ff-only` with no pre-check, so git itself refuses only on overlap and unrelated local changes never stopped it (task 10.016 pinned this in tests; no code change). Nothing the app does discards local work: the pull never uses `reset --hard`, `checkout -f`, `clean` or `stash`. Covered by `server/tests/autoPull.test.ts`, `server/tests/incomingOverlap.test.ts`, `web/tests/gitSync.test.mjs`, `worldStore.test.mjs`, `serverApi.test.mjs`.

**Terminal view reconnects on its own (bug B.031).** Every embedded terminal (`TaskTerminal.tsx`: Task, planning, step, Agent and Content Studio panes) gets its socket from `createTerminalConnection` in `web/src/lib/terminalReconnect.ts`. A remount, such as a changed React `key`, is not needed and is not how reconnection works; the old `terminalKey` remount in `TaskDetailsView.tsx` is gone. Ordering facts the controller relies on:
- The daemon emits `task`/`stepRun` events **before** it registers the PTY (`launchDeferredSession`, `continueTask`, step start into `runTerminalTask` in `workerManager.ts`), so a view that mounts on those events can attach too early. `ws.ts` then sends `error` and closes with 1008.
- The `terminalSessions` snapshot (store: `liveTerminalSessions`) is broadcast only after the PTY is registered or has exited, so it is the reconnect signal. Broadcasts go through `createOrderedDelivery` (`server/src/api/orderedDelivery.ts`), so they arrive in request order. A client's first snapshot on connect is still sent on its own.
- On PTY exit the terminal socket's `ended` frame arrives **before** the snapshot of that exit, so the snapshot in hand at `ended` can still list the id.
- `attach()` replays the session's whole buffer, and a socket attached to an ended session never hears a PTY restarted under the same id.

The rule: a socket that **failed** (attach refused, error or close) reconnects on the next snapshot that lists the id during that connection. A socket that got **`ended`** reconnects only after a snapshot shows the id not live, then live again. So a normal end never clears the view. Each reconnect calls `terminal.reset()` first and uses a fresh `connectionId`, and input and resize go through `link.send` to the current socket. Task ids that are expected live (`isTaskExpectedLive`: `developing`, `blocked` or `runtimeStatus: 'starting'`) also get a bounded fallback retry (`FALLBACK_RETRY_DELAYS_MS`); ids with no Task record rely on snapshots only. `TaskTerminal` must feed **every** snapshot to `link.setLive` through `useWorldStore.subscribe`, not a render selector, because React batching can hide a quick not-live/live flip. Some behaviour is easy to get wrong when changing this code:
- Finishing a run (`finalize`) happens once per run, never rejects, and only releases the queue slot it owns.
- A run settles 2 seconds after its command exits even if a background child keeps the output pipes open.
- Stop is ignored once the command has ended.
- The daemon signals running tests on SIGINT/SIGTERM/exit (`index.ts`), because each test runs in its own process group.
- Deleting a Project first discards its runs (`discardProjectRuns`, via `deleteProject`'s `beforeRemove`).
- Latest results count only runs on the primary working tree.

**Turn-end while waiting on a Test Run.** A Task's testing-tool calls with `waitSeconds > 0` (`runAction`, `runAll` including joined `skipped` runs, `getRun`) record the run ids they hand back on the Task (`awaitedTestRunIds`, deduped, last 20) through `recordAwaitedTestRuns` in `server/src/worker/workerManager.ts`. Any other hook clears the flag. Known limits: an agent that waits on a run, times out and then asks a person is silenced until the run ends plus 60 s; `dispose()` (clears timers) is only called from tests. The grace delay must stay above `RECENT_COMPLETION_MS`. Covered by `server/tests/workerManager.test.ts` and `agentTestingApi.test.ts`; not yet verified against a real CLI session.

**Command-capable read-only steps (task 22.002).** A workflow step may set `canRunCommands` ("Can run commands" in the workflow editor; absent reads as off, validated as a boolean like `canEditCode`, 400 on the workflow routes). It lets a step that may not edit code run shell commands (install dependencies, run tests, build) and use the registered testing tools; it gets no file-editing tools and is not a write step: never committed or pushed, no change to what Complete does, and its prompt keeps the read-only wording but says it MAY run commands, that files those commands create or change are not committed, and that it must not use commands to edit source files. With `canEditCode` also on, the step is an ordinary write step. Planning, bug report and testing-setup proposal sessions cannot get it (a setup run ignores the field and stays fail-closed read-only; if its working tree changes, the run still needs attention).
- **Claude:** `--disallowed-tools Edit,Write,NotebookEdit` only; the shell stays allowed. **Codex:** `--sandbox workspace-write -c sandbox_workspace_write.network_access=true --ask-for-approval never` (the plain read-only sandbox cannot install or use the network), whatever the autonomy.
- **Not enforced:** a shell can write anywhere the user can, so "don't edit source files" is guidance in the prompt plus denied edit tools, not a guarantee. Tracked-file changes made by commands (for example a lockfile) are ignored: nothing resets, flags or blocks them. They stay in the run's working copy and the next write step's commit may include them; installed dependencies and build output also remain for later steps.
- **Reopened sessions:** a settled command step offers the same with-permissions or read-only choice as a write step; read-only stays fully read-only (no shell, no tests), "with permissions" means shell, no edit tools and the testing tools. `sessionSetup.canRunCommands` records the option; a stored setup without it stays read-only.
- **Shipped Bug Fix workflow:** the RCA step has the option on and is told to install dependencies, run the tests to reproduce and to establish which fail before the fix, and record the commands and results in "Reproduction" and "Tests". Catalog workflows are read live from `catalog/workflows` by id; Projects do not keep their own copy, so the change reaches every Project's next run (runs in progress keep their snapshot). A locally edited `bug-fix.json` is changed only by merging the new file, never overwritten by the daemon.
- **Headless Codex turns** (`runCodexTurn` in `codexProcess.ts`, used by the plan titler, the Complete-stage summarizer and the SEO keyword agent) always use the read-only sandbox; workflow steps never reach it (they run as interactive terminal sessions), so the option does not apply there.
- **Open limit (owner: the person):** a manual check with the real Claude and Codex CLI that RCA installs dependencies, runs the test action and edits nothing by tool. Tests cover argument lists only.

- A queued run closed out as `interrupted` after a restart, or one whose action was disabled while it waited, can become the suite's latest `error`.

### Typing into a live Content Studio session

Two features type into a running Studio CLI as if the owner did: Confirm assets (`videoStudio.confirm`) and line comments (`studioSessions.comment`, task 36.002). Both run inside the Building's write queue (`ctx.exclusive`) and call `typeIntoSession(host, id, text, videoDeps().submitDelayMs)` in `server/src/content/typeIntoSession.ts`: one `write` of `ESC[200~` + `terminalSafe(text)` + `ESC[201~` (a bracketed paste), a wait through `setTimer`, then a lone `'\r'`. The paste markers are the delivery guarantee: an unbracketed write over one 1,024-byte terminal read reached Claude Code as a paste block plus typed text, and 2.1.317 submitted only the typed tail (bug 36.002.001). A size cap cannot replace them, since a comment alone may be 2,000 code points. `terminalSafe` (same file, the only sanitiser) turns line breaks and tabs into spaces and drops escape sequences and C0/C1 controls, so text cannot end the paste, press Enter early or send Ctrl-C. "Live" means the newest session record has the asset's current `round` and `host.has(id)`; otherwise refuse with 409 and tell the owner to Resume, never queue. Nothing from the CLI confirms delivery; the comment route returns `sentChars` (code points pasted), and a paste sent mid-turn was queued by Claude Code 2.1.318 until the turn ended (Codex mid-turn unchecked). A new caller uses the helper rather than calling `host.write` itself. ### In-app application update

Implemented (task 7.001). Detail lives in code: `server/src/appUpdate/`, `server/bin/run-app-update.mjs`, `web/src/lib/appUpdate.ts`, `web/src/ui/AppUpdate*.tsx`, `AppReconnectBanner.tsx`; the longer prose is in `docs/blueprint.md` ("App update"). Not yet verified in a real prod-started instance with a local test remote (acceptance item 11 was left as a manual check).

- **Availability**: the app's own checkout (not a registered Project) is fetched quietly on a recurring poll and on "Check now", then compared with `origin/<branch>`. Applicable only when fast-forward-only is possible. Local changes block only when they overlap the update (task 10.016, same overlap rule as auto-pull: a local change to a path the incoming commits change, or an untracked file they would add); unrelated local changes, including generated JSON files, leave the update available and are left exactly as they are, for the web-only and server paths alike. The popover lists the blocking files (path and kind, up to 10 and "+N more") with a plain explanation and a "Copy file list" button; the app never discards or stashes anything for the person (a discard action was considered and declined). If the incoming paths cannot be read, any tracked change blocks and the reason says why. Local-ahead commits or divergence (which take precedence over overlap) report "Can't update automatically" with a reason. No network, no remote, detached HEAD or a non-git checkout is "Couldn't check"; a failed check keeps the previous result, notes the failure, and never raises a notification itself. Zero behind is "Up to date", which stays visible so "Check now" always has an entry point.
- **Classification**: `web-only` only if every changed file is under `web/`; anything else, including root `package.json`, `scripts/` and `server/src/appUpdate/`, is `server`. A web manifest/lockfile change only adds a web dependency install.
- **Idle definition** (`appUpdateBlocking.ts`, each count must be zero on its own): live execute Tasks / running WorkflowRuns; planning sessions mid-turn or with a live CLI process (one waiting for the user with no live CLI does not block); queued or running TestRuns; running CommandRuns of every origin including `sync`; open interactive terminal sessions, counted as sessions not yet ended. The counts deliberately overlap (a running Task also holds a terminal session), and the terminal count catches inspect sessions on settled Tasks.
- **Paths**: `web-only` applies immediately in the daemon (pull, optional web install, build into `web/dist.new/`, atomic swap), never touching the daemon or running work; a failed build keeps the previous build served. `server` is held until idle (new work is not blocked, no timeout, Cancel any time) and then runs a detached process (own process group, so it outlives the daemon) doing stop, pull, install, start. Every failure after the old processes stopped checks the previous commit back out and restarts, then records the failure in the log and `.run/app-update-result.json`.
- **Rollback**: a failed server-path update (install or start fails) restores the previous commit with `git reset --keep`, never `--hard`, so local changes survive. If git cannot restore it (a file the update changed was edited after the pull), the failure message says so and the checkout stays on the new commit. A pull git refuses because the folder changed after the check fails cleanly naming the files, with nothing applied. `server/src/appUpdate/updateGitSteps.ts` holds both steps so they are tested against real temporary repositories; `server/bin/run-app-update.mjs` stays a thin, manually checked caller.
- **API**: `GET /api/app-update` (now with `blockingFiles` and `blockingFilesTotal`), `POST /api/app-update/{check,apply,cancel}` plus an `appUpdate` WebSocket event. Apply while held or running is 409; apply when not updatable (dev mode, not behind, overlapping local changes, ahead, diverged) is rejected with a reason; cancel with nothing held is a 200 no-op. Dev mode (no `prod:start`) reports availability but cannot apply.
- **State lifetime**: a hold does not survive a daemon restart. The new daemon consumes the result file once and shows `updated`/`failed`; that terminal phase reverts to idle after `TERMINAL_PHASE_DISPLAY_MS` (5 minutes) so later updates are discovered without a restart.
- **Web**: footer item and popover reuse `FooterCountPopover`; one `app.update_available` notification (`{ type: 'app' }` subject) on first detection, resolved when applied or up to date. Open tabs compare the baked-in `__APP_BUILD_COMMIT__` with the live commit and show a persistent dismissable reload banner (never auto-reload, so a half-typed message survives); a disconnect during an `updating` phase shows a reconnect banner instead, and the reload banner is suppressed while it shows.


### Workspace layout rules

Applies to the Project Workspace popup (`web/src/ui/ProjectWorkspaceModal.tsx`) and the Settings tab.

- **One declaration.** `web/src/lib/workspaceLayout.ts` declares every top-level tab (`TAB_DECLARATIONS`: label, `selfGuarded`). Settings sections are declared in `web/src/lib/settingsSections.ts` (`SETTINGS_SECTIONS`, `settingsSectionsFor`) with icon and label in `ui/project-popup/SettingsPanel.tsx`. Icons and panels are exhaustive `Record`s keyed by the tab union, so a missing one fails the type check.
- **Top-level tabs:** Tasks, Documents (Notes in the Notes type), Testing, Code, PR (GitHub repository only), Settings, and Archived while there are archived tasks. Schedules, Connections and Activity are Settings sections (order: Workflow, Git provider, Commands, Schedules, Building links, Activity, Storage; a type shows the ones that apply). The generic Connections section is labelled "Building links" because the SEO Building's tasks plan their own external-services "Connections" area in its Settings; the SEO Building (10.006) has its own Settings → Connections (Google Search Console, Analytics 4, Ads, Bing, IndexNow) and Settings → Data, so the two labels differ on purpose.
- **Old values.** `normalizeWorkspaceTab` maps the former tab values `schedules`, `connections` and `activity` to Settings plus that section (used by `setWorkspaceTab`, so deep links, stored values and notifications still land); an unknown value opens Tasks. A section the type does not offer falls back to the first offered one.
- **The read-only wrapper.** `ReadOnlyFieldset` (in `ui/WorkspaceBody.tsx`) disables every control inside it while a Building is read-only. It grows to fill the popup (`flex-1`), like each panel.
- **Self-guarded panels** (`selfGuarded: true`; Settings and everything inside it, including Schedules, which keeps history readable and disables only its changing controls) must not be drawn inside the wrapper, or the wrapper's own disabling would defeat their guard and it would take a share of the height.
- **Never empty.** `WorkspaceBody` takes the tab's panels and `panelPlacement` decides: no panel draws nothing, a self-guarded panel is drawn bare, any other goes inside the wrapper. Every shell (Software, Notes) uses `WorkspaceTabBar` and `WorkspaceBody`; none keeps its own tab-name list. The unavailable shell has no tabs.
- **Checklist for a new tab:** add it to `WORKSPACE_TABS` and `TAB_DECLARATIONS` (choose `selfGuarded`); add its icon in `WorkspaceBody.tsx` and its panel in the Software shell's `panels` (the `satisfies Record<WorkspaceTab, ReactNode>` check enforces it); list it in `workspaceTabs` or `notesTabs`; run `web/tests/workspaceLayout.test.mjs`.
- **Checklist for a new Settings section:** add it to `SETTINGS_SECTIONS` and `settingsSectionsFor`, give it an icon/label in `SettingsPanel.tsx`, render a panel that fills the content area itself (`min-h-0 flex-1 overflow-y-auto`) and guards its own read-only state.

#### Known pitfall: content starts half way down the popup

- **Symptom:** a tab's content starts roughly half way down the popup, with an empty band under the tab bar. It happened for Schedules/Settings (task 10.004.001) and again for Connections/Activity.
- **Cause:** the growing read-only wrapper was drawn empty beside a panel that renders outside it, because "tabs that show a panel" and "tabs that skip the wrapper" were separate hand-kept lists (plus a third in the Notes shell), and a new tab was added to one but not the other.
- **Prevention:** one declaration per tab; `WorkspaceBody` derives placement from it and cannot draw an empty wrapper; the Software shell's `satisfies Record<WorkspaceTab, ReactNode>` forces a panel per tab; the three former tabs no longer exist as top-level tabs.
- **Guarding tests:** `web/tests/workspaceLayout.test.mjs` (declaration completeness, placement for every tab of every shell, no per-shell tab lists, Settings panels fill the content area) and the source checks in `web/tests/schedulesPanel.test.mjs` and `web/tests/buildingStorage.test.mjs`. A real-browser pixel check of each panel's top edge is still a manual step.

## Connections between Buildings

Capabilities (request and response), events, links a person makes, and an Activity log of every call and event. Software offers `get-open-tasks`, `get-task-details` (one task's description, status, phase, current activity, step-by-step summary, delivery and outcome; input `id` or board `number`, exactly one), `list-completed-tasks` (newest first; `limit` default 20 max 100, `cursor`, `since`, `search`; returns `total` and `nextCursor`) and `start-planning-session`. Status words: ready, waiting, running, waiting-for-input, awaiting-approval, needs-attention, failed, stopped, completed, archived; phase: not-started, in-progress, completed. Long text is cut and flagged `truncated` (description 20,000 characters, step summary 2,000, outcome 5,000, 100 steps); input limits are rejected. A new link starts with every capability checked (none pre-approved; the person unchecks what to withhold), and links that existed get the two task capabilities switched on once at startup (`grantsVersion`), keeping every other choice; events and approval gates are unchanged. The mechanism, validation contract and numbers are in `docs/connections.md`. Connections ("Building links") and Activity are sections of the Settings tab in the Building popup, and links are drawn between Buildings in the 3D scene. Not yet implemented: see the last section of `docs/connections.md`; nothing has been looked at in a browser (`.docs/testing.md`, Known gaps).
