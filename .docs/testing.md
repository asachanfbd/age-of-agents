# Testing

## Commands

| Where | Check | Command |
| --- | --- | --- |
| `server/` | Types | `npx tsc --noEmit` |
| `server/` | Tests (every `tests/*.test.ts`, run concurrently) | `npm test` |
| `web/` | Types | `npx tsc -b --noEmit` |
| `web/` | Tests (`tests/*.test.mjs`) | `npm test` |
| `web/` | Lint (`oxlint`; there is no ESLint config, so `npx eslint` is the wrong tool) | `npm run lint` |

Both packages use Node's built-in test runner. Server tests never touch the real data directory: `AGENT_VISUAL_OS_DATA_DIR`, `AGENT_VISUAL_OS_PROJECTS_DIR` and `AGENT_VISUAL_OS_EXECUTORS_PATH` point at temp folders and `server/tests/fixtures/executors.json` (see `server/README.md`, "Environment variables"). Tests that create Catalog items also point `AGENT_VISUAL_OS_CATALOG_DIR` at a temp copy of `server/tests/fixtures/catalog`. If `tsc` or `oxlint` is missing, the dev dependencies weren't installed; `npm install --include=dev` in that package fixes it without changing the lockfile. In a WorkflowRun worktree, `npm run install:all` and `npm ci` have been seen to skip devDependencies because the shell had `NODE_ENV=production`, so check for `node_modules/.bin/tsc` before the first check and install with `npm ci --include=dev` if it is missing. A missing `server/node_modules` also shows up as ~100 failures with 503 `The storage worker stopped: Cannot find package 'better-sqlite3'` on every Building create (task 10.006.001); the fix is the same install, and `scripts/prod-start.sh` now exits early with that hint (`server/tests/prodStartScript.test.ts`).

## Writing daemon tests

- **Starting a second Task in the same Project:** wait until the Project is idle (`(await projectService.getProject(id)).status === 'idle'`), not until the first Task reads `done`/`stopped`. `workerManager.ts`'s settle functions write the Task's status before `removeActiveTask` frees the Project. A test that starts the next Task in between gets `TaskConflictError` under the CPU load of the full concurrent suite, even though it passes on its own. The same applies before `followUpTask`, `completeTerminalTask`, or anything else that re-checks the Project's active-task cap.
- **Concurrency in tests:** `projectService.createProject` makes a Project with no `repositoryUrl`, so its cap is one file-writing Task and no worktrees are created. Planning sessions don't count toward that cap, which is what lets a test run one beside a held coding Task.
- **Planning sessions are CLI-only:** start them with `executorId: 'test-claude-cli'` (or `'test-codex-cli'`) and a `fakeTerminalHost()`. Finish them with `terminal.starts[i]?.onExit(0)`. A structured executor (`test-claude`, `test-codex`) is refused with `PlanningRequiresCliError`.
- **Events versus reads:** A `FileDatabase` change becomes visible to reads only when its file write finishes (`#persist` swaps the cache after the rename), and services usually store before they emit, so a read can see a change before its `/ws` event is emitted, while a write still awaited after an event is invisible until it lands. When a test asserts on emitted events, wait for the event, not for the stored value. This matters most when asserting that an action emits *nothing*: subscribe before the step that settles earlier work (such as `onExit(0)`), wait for that settle's last event, then clear the array. `settleStopped` stores `stopped` before it emits `project` and `task`, so a subscription started after the stored status flipped caught both and failed with `2 !== 0` under load (B.013, "failed planning completion leaves the session…"). The reverse also happens: work that runs after an event is emitted may not have finished when the test sees the event. For example, Test Run pruning happens after a run's final `testRun` event. Wait on that side effect itself with `waitUntil`, such as a pruned run's log file reading `''`. A run's completion Notification is the exception: `testRunner.ts`'s `recordOutcome` (like `commandRunner.ts`) writes it before the final event, so a test may read notifications right after `settled()`. Keep that order when changing either runner; `withSlowNotificationInserts` in `testRunner.test.ts` delays the insert by 50 ms so a reorder fails every time instead of only under load (B.017).
- **Test Runs never spawn a real command:** build the runner with `createFakeHarness()` from `server/tests/helpers/testRunFakes.ts`. It fakes spawn, artifact directories and git, and uses the real per-run files under the test's temp data dir. Its `FakeProcess.exit()` emits `exit` then `close`, as Node does. `exitKeepingPipesOpen()` emits only `exit`, which simulates a background child holding stdout. A fake `kill()` fires `exit` again after the run has settled, which catches code that re-arms timers after settling. That once made the whole suite hang.

- **Import `src/` only after setting the env:** `src/config.ts` reads `AGENT_VISUAL_OS_*` once, at first import. A test file that sets them in `before()` may have only `import type` lines, or value imports of modules that never load `config.ts`, at the top; everything else is `await import(...)` inside `before()` (see `server/tests/workerManager.test.ts`). One top-level value import once made that file's skill fixtures land in the real `catalog/`. After a full `npm test`, `git status --porcelain catalog server/data` must print nothing.

- **Tests of environment-diffing code must clear the ambient values they compare against.** `githubSessionEnv` (`server/src/github/accounts.ts`) puts a variable in `set` only when its value differs from `process.env`, and `githubEnv` forces `GH_HOST=github.com`, `GH_PROMPT_DISABLED` and `GIT_TERMINAL_PROMPT`. A shell that already exports `GH_HOST=github.com` made "session env carries token, identity and git auth config…" fail (B.007) while passing on CI. `server/tests/githubAccounts.test.ts` wraps such tests in `withoutAmbientForcedEnv`, which clears those variables and restores them. When a test asserts that a variable appears in `set`/`unset`, clear it first. To reproduce this class of failure, run the file with the suspect variable exported (`GH_HOST=github.com node --test tests/githubAccounts.test.ts`).
- **Scripting a failed turn:** make the fake `runClaudeTurn` throw, or reject a promise only after `runTurn` has awaited it. A promise rejected before the fake returns it gets no handler in time and fails the test as an unhandled rejection.
- **`fakeTerminalHost()` tracks liveness (`server/tests/helpers/terminalStepFakes.ts`).** `has(taskId)` is true from `start` until that session's `onExit` fires, and the host exposes a `live` set. A test that needs a live Task without starting a session adds its id with `terminal.live.add(id)`; a test of `reopenStepSession` must end the first session with `onExit(0)` first. `workerManager.test.ts` and `autoAdvanceTerminalSteps` have their own hosts with `has: () => true`.
- **A failure seen only in the full concurrent run is usually a race inside one file's daemon, not two files sharing state.** Each test file runs in its own process with its own temp directories (the Catalog's too, when the file sets `AGENT_VISUAL_OS_CATALOG_DIR`); `--test-concurrency=4` adds CPU load, which shifts background timers into later tests. Example (B.014, since fixed by removing the timer in 37.012): `POST /api/projects` used to schedule the docs-bootstrap Task 1.5 s later, and its Catalog read landed inside a later skills test. `POST /api/projects` now creates the 'Set up project documentation' item and starts it before responding, so tests that create a repository project over HTTP and then start their own tasks use `server/tests/helpers/quietProject.ts` (service-level create) to avoid the extra item. Reproduce such a race with a burst of concurrent service calls, as the concurrent-create tests in `server/tests/catalogService.test.ts` do, instead of rerunning the suite until it fails.
- **Hold a fake at a signal, not after a fixed sleep.** To assert state while a fake is mid-operation, have the fake resolve a `reached` promise and then await a `release` one (`deferred()` in `server/tests/videoPure.test.ts`), and create fresh pairs before each retry. `ensureProject` scaffolds files before it calls the installer, so the setup test's 10 ms sleep read `percent: null` instead of `40` whenever disk writes were slow, and a retry's `release()` resolved the previous attempt's promise and hung until the 120 s timeout (B.033).
- **Assert a pruned or settled count with `waitUntil`, not right after the final event.** The test runner's `finalize` prunes old runs after the last `testRun` event, so a count read straight after `settled()` can be one too high (`testRunner.test.ts` retention test).
- **Simulating a genuinely-live folder Task without a real CLI process:** insert a `TaskRecord` straight into `tasksDb` with `runtimeStatus: 'starting'`. `isLiveTask` treats that as live even though no terminal session is registered yet — the same state a Task is really in for the instant between being created and its CLI session registering — so it counts toward the concurrency cap and the Project-folder-busy check (`assertProjectFolderFree`/`isProjectFolderBusy` in `server/src/worker/projectFolderGuard.ts`) without spawning `claude`/`codex`. Giving the record a `worktreePath` instead makes it count as worktree-isolated (never folder-busy).

- **API tests never start a real Task:** `test-claude` in `server/tests/fixtures/executors.json` runs the real `claude` binary. To get a running, stopped or failed Task, insert a `TaskRecord` straight into `tasksDb` (see the plan-item queue tests in `server/tests/api.test.ts`). When a test moves the queue on, delete the next queued item first. The dequeue then drops its entry instead of spawning a CLI.

- **Scripting a `gh` failure:** use text copied from a real failure where one is known, and say so when it is a guess. The real `gh api` form is `gh: <message> (HTTP <status>)`; the wrapper in `server/src/projects/git.ts` puts `gh command failed: Command failed: …` on the line before it. The first "already gone" case in `server/tests/pullRequestMerge.test.ts` used an invented `HTTP 422: Reference does not exist` and asserted a warning, while GitHub really answers `gh: Reference does not exist (HTTP 404)`. Code that sorts provider failures matches the message text, not the status, and each kind of answer needs a case for the outcome it should give (already-gone is success; a bare `Not Found (HTTP 404)` still warns). Most other failure strings in the pull request tests are still in the unconfirmed `HTTP <status>: …` form.
- **Test runs are throttled.** The Testing tab's runner starts at most 2 runs at once across all Projects (`AGENT_VISUAL_OS_TEST_MAX_CONCURRENT_RUNS`) and stops any run after 15 minutes (`AGENT_VISUAL_OS_TEST_RUN_TIMEOUT_MS`, status `error`, diagnostic `timed-out`). The server test command also passes `--test-concurrency=4 --test-timeout=120000`, so a stuck test fails after 2 minutes instead of holding the run. Several agents each running a full suite at once pushed the load average past 300 and made timing-sensitive tests fail; a run that sits `queued` is waiting for a slot, not stuck. Direct `npm test` from several worktrees is not throttled, so run one at a time.
- **A run that seems to hang:** bound it with `perl -e 'alarm 200; exec @ARGV' npm test` (from `server/`). macOS has no `timeout` command. `timeout 110 npm test | grep …` fails with "command not found", and the pipe hides that error, so it looks like a hang with no output.

- **Analytics tests use fakes on an injected clock.** `server/tests/helpers/analyticsFakes.ts` has `analyticsHarness()` (history in memory, the real poller over a fake provider, recorder, sampler and service) and builders for Tasks, runs and readings. `server/tests/analyticsApi.test.ts` drives real Task and WorkflowRun events through the recorder over HTTP. Task events carry real timestamps while readings use the injected clock, so the one test that needs both to line up runs before any test advances the clock. A manager used there must pin `listExecutors` and `getExecutorLimits`, or the headless summariser picks its executor from the machine's real usage.
- **End shared registry state in `finally`.** Module-level registries such as `contentJobs` (`server/src/content/jobs.ts`) survive `afterEach` resets, so a job a test begins and never ends shows up in every later test's snapshot in that file. B.034: the Remotion setup test slept 10 ms, assumed the fake install had started, failed under load before its `cancelSetup`, and SU45/SU47 then saw the leaked job. Hold the fake at a signal (the rule above), make fakes reject on their abort signal so cleanup cannot hang, and put the cleanup in `finally`. A test that snapshots a registry asserts it is empty first (SU45/SU47), so a leak names its cause. To reproduce such a race, run about 16 copies of the file in parallel; before the fix 8 to 16 of 16 failed, after it 0.
- **A stored default coding agent leaks between tests.** With none stored, a run with no agent choice uses the first CLI agent in the fixture `executors.json` (`resolveFallbackExecutor`), so most tests get agent A. A test that stores one (`defaultExecutorStore.set` from `src/executors/defaultExecutorInstance.ts`) clears it in `finally` (`server/tests/testingSetup.test.ts`). A router test that calls `GET /api/executors` runs the real re-check, which can store a default in that file's database; pin the agent in later starts rather than weakening the assertion. Never let a start path reach the real `getExecutorLimits` (`fallbackExecutor.test.ts` counts quota reads).
- **A fake that returns instantly hides timer drift.** When a test checks a repeating schedule on an injected clock, make the fake operation advance the clock before it returns (the slow provider in `server/tests/quotaSampler.test.ts`, U19), and test the value just past any threshold derived from the interval. With a zero-duration provider read, the sampler's tests passed while the real daemon skipped every other five-minute tick.

## Testing Building Types and the bulk data layer

- **Real SQLite, never mocked.** `server/tests/bulkStorage.test.ts` drives `BulkStore` (the worker-thread client in `server/src/buildings/bulkClient.ts`) against real database files in a temp folder, because crash safety, isolation and query correctness are the behaviour under test. A crash is simulated with `store.terminateForTest()`, which kills the worker thread mid-ingest. Generated data is 5k to 600k rows; the 10M-row benchmark is the separate script `server/scripts/benchBulk.ts` (`node scripts/benchBulk.ts [--metrics N] [--lists N] [--dir <folder>]`) and is not part of `npm test`.
- **Fault injection is opt-in.** A disk-full error is injected with `AGENT_VISUAL_OS_TEST_FAULTS=1` (set before the Building's storage first opens) and `store.setFault({ code: 'SQLITE_FULL', atRow? })`. Without the variable the worker refuses `setFault`.
- **Content Studio finalize starts a retro.** Any test that finalizes a `script`, `post-text` or `article` must pass a `createRetros({ agent })` with a fake agent (`server/tests/studioSessions.test.ts` does), or the shared `assetFinalized` hook reaches for the default agent. Retro API cases hold that fake at a latch to prove finalize does not wait and to race Run retro, accept and deletion (`server/tests/contentRetroApi.test.ts`).
- **Dev-only types:** set `AGENT_VISUAL_OS_DEV_TYPES=1` before a test creates a Notes Building through the API.
- **Registering a throwaway type:** `registerBuildingType` / `unregisterBuildingType` (`server/src/buildings/registry.ts`) share one registry with the running test server, so a test can bump a type's version to run a migration (`server/tests/buildingLifecycle.test.ts`) or remove one to see a Building become "type unavailable".
- **Timing assertions are lenient on purpose.** The responsiveness and memory tests (`I32`, `I36`) assert that the daemon stays responsive and its heap does not grow with the data, with margins wide enough for the concurrent full suite.
- Files: `buildingTypes`, `buildingQuery` (pure), `bulkStorage` (worker), `buildingApi` (HTTP), `buildingLifecycle` (restart, migration, maintenance), `buildingRuns` (workflow runs for a non-repository type). Web: `buildingTypes`, `buildingStorage`, `buildingTypesSettings`, `newBuildingDialog` tests, with Building routes added to `web/tests/serverStub.mjs`.

## Testing the scheduler

- **Injected clock, never a real timer.** Build the scheduler with `fakeClock`, `fakeStarter` and `fakeSources` from `server/tests/helpers/schedulerFakes.ts` (`server/tests/schedulerEngine.test.ts` has a `world()` helper that also gives a Building and a `restart()`). Move time with `w.at(time)`, which sets the clock, ticks once and waits until nothing is in flight. A timer fires only when the test calls `clock.fire()`.
- **Settle runs by hand.** A fake run stays `running` until `runs.settle(runId, status)`; then `await scheduler.idle()` before asserting.
- **Jobs created at the same instant have no fixed order** (the tie is broken by a random id). Advance the clock between creates, or look runs up by job id, when a test depends on which started first.
- **Slots follow the Building's timezone.** An hourly job in `Asia/Kolkata` fires on the half hour in UTC.
- **Real worker manager:** `server/tests/schedulerRuns.test.ts` drives runs with a fake terminal host and a script per step. A Building with no repository keeps its folder while a run needs attention or approval, so wait for the Building to be idle, and expect a second start to queue.
- **HTTP:** `createDaemonServer({ scheduler })` takes the scheduler, so `server/tests/schedulerApi.test.ts` never starts a run.
- **Prove a gate at run level.** A pure function's answer (`approvalGateIndex` returning a step index) shows what the code decided, not that the decision is right: the first version returned "no gate" for a workflow ending in an approval step and its unit test agreed. For a rule about when something may happen, also assert in `schedulerRuns.test.ts` which steps had run when the run paused.
- **Test a limit with an input that exceeds it, against the real source.** A fake source hands back a finished value, so it cannot show whether a size cap or timeout is applied before the cost is paid (the 1 MB cap was first checked after the whole body had been downloaded, and a timed-out folder read kept running). `schedulerPollSources.test.ts` uses an endless chunked body, an oversize `content-length` and a read that outlives the timeout.
- Files: `schedulerCron`, `schedulerValidation`, `schedulerPoll`, `schedulerGuardrails` (pure), `schedulerPollSources` (the real file and HTTP sources, against a temp folder and a loopback server), `schedulerEngine`, `schedulerRuns`, `schedulerCommandStarter` (the command target through a real command runner and real shell commands), `schedulerApi`. Web: `schedules`, `schedulesStore`, `schedulesPanel`, with the routes in `web/tests/serverStub.mjs` (`stub.schedules`, `stub.settleRun`).

## Testing connections between Buildings

- **A fixture type with gates.** `server/tests/helpers/connectionFixtures.ts` builds a type with a read, a slow read, a write held for approval, a write that waits at a latch, a run-starting write and a handler that calls back into the service. `makeProbe()` holds the counters and gates; `Object.assign(probe, makeProbe())` resets it between tests. It only imports types from `src/`, like the scheduler fakes.
- **Races are forced at a gate, in one process.** The same-key race (`I67`) and the link or Building deleted during a call (`I68`, `I69`) hold the handler at `probe.latch` while the test acts; the hourly limit with events published together (`I70`) uses `Promise.all`. Real simultaneity across two clients is not tested.
- **The service takes its clock, limits and job starter.** `connectionsApi.test.ts` builds `createConnections` with a short timeout, a tiny event limit and a `startJob` that calls the test's own scheduler, which uses `fakeStarter`, so no run is ever started. Capability jobs go through the real `createManagerRunStarter` with a fake manager.
- **A session needs only a Task record.** Insert a `TaskRecord` with `status: 'developing'` (and a `workflowRunsDb` row for a step) and call `/api/agent-capabilities/...?taskId=` with the CLI token (`CLI_HOOK_TOKEN`). Which sessions get which tools is tested through the offers route and `capabilityMcpServer`'s arguments, not through a real CLI.
- **A write is held for approval**, so Software's `start-planning-session` is tested by approving the call with `workerManager.startTask` swapped for a fake; nothing starts a real planning session.
- Files: `connectionsPure` (field checks, declarations, approval, depth, rate limit, tool offers, filters), `connectionsApi` (links, calls, approvals, idempotency, events, scheduler, sessions, deletion, privacy), `connectionsDocs`. Web: `connections` (the store through `serverStub.mjs`, view logic, line geometry, source checks); the stub has `stub.connections` with links, subscriptions, `busy` and `requests`.

## Writing web tests

- **No DOM harness, but a static render path.** `web/tests` runs plain Node with no jsdom, so there is no click, drag or focus. `web/tests/renderHelper.mjs` bundles a TSX module with rolldown and renders it with `react-dom/server`; `web/tests/componentRender.test.mjs` uses it to assert markup (roles, `aria-*`, classes, read-only state) of the design components, the CRM board, Customers and the contact detail. Use it for what the markup shows. Behaviour (drag, undo, rollback) still goes into pure functions such as `web/src/lib/crmBoardActions.ts`. The rest of this section applies when a case needs more than static markup. Put UI behaviour in pure view-model functions and test those directly, for example `buildPlanningQueue`/`planningTaskHistory` in `web/src/lib/projectTasks.ts` (see `web/tests/projectTasks.test.mjs`). Component wiring is pinned with source-level checks in `web/tests/taskBoard.test.mjs`. A change that deliberately rewires pinned code updates the pin and any test helper that mirrors it in the same change: commit `9433b76` moved the Running column to `boardRunning` (running plus waiting tasks) without updating the `taskBoard` pin or its `boardFor()` helper, nor `U35b` and `WU20`, and the stale failures were then carried as "known" for many tasks (bug B.010). `web/tests/planningTaskPanel.test.mjs` shows all three kinds for one feature: pure helpers, the store against the stub, and source checks. A source check only proves that a call is written, not that it decides correctly, so a decision made inside a handler (where Back leads, what a click opens) also belongs in a pure helper with its own cases: `detailBackTarget` in `web/src/lib/planningTaskPanel.ts` exists because a pattern check passed on a Back handler that went to the wrong place. A source check goes stale when a later task makes an intended change to the text it pins (B.012: 22.003 added `|| isToastTarget(...)` to the footer guard in `dialog.tsx`/`sheet.tsx`, 22.001 added a legitimate `Textarea` to `TaskDialogs.tsx`). Before changing a file, grep `web/tests` for checks that read it, run those test files, and update any it breaks in the same task instead of recording the failure as a known gap. Bug B.024: `92bdd7b` rewrote the yard click in `ProjectYard.tsx` and ran only `villageYard.test.mjs`, so `villageScene` C08 (which reads that file) failed on `main` for several tasks, carried as a known gap under the wrong file name. Pin the specific identifier (`isRejectReasonValid`), not a generic one (`Textarea`).
- **Text overflow in grid and flex parents is pinned by classes, not pixels (task 10.021.001).** The Start task dialog and the shadcn `Alert` are grids whose `1fr` track has an automatic minimum, so a long task title in `TaskConflictAlert.tsx` set the minimum width of every ancestor and `truncate` never applied. The fix needs `min-w-0` (or `minmax(0,1fr)` columns) on every ancestor between the scroll or width limit and the truncating element, not on the element alone. `web/tests/taskConflictAlertLayout.test.mjs` pins those classes and renders very long titles; the render cannot measure width, so a real-browser check of the dialog at `sm:max-w-md` and phone width was not done. Apply the same chain when adding long, user-written text to any alert or dialog; keep the fix in the caller, since `alert.tsx` and `dialog.tsx` are shared.
- **Workspace layout is pinned by `web/tests/workspaceLayout.test.mjs`.** TSX can't be loaded in node tests, so it checks the pure `panelPlacement` decision for every tab of every shell, the declaration against the tab union, and source patterns (no per-shell tab lists). Whether a panel's top edge sits directly under the tab bar, focus after a deep link, double scroll bars and the narrow sidebar need a real browser (see the real-browser recipe below) and are not automated; run them by hand when changing tabs or Settings sections.
- **Local-time code is tested in a zone ahead of UTC.** A host in UTC hides every "UTC instead of local" bug (21.001.005: `toISOString().slice` fed a `datetime-local` input, `timeZone: 'UTC'` day labels). Set `process.env.TZ` on the first line of the test file, before any import; `node --test` gives each file its own process, so the zone stays in that file. Use an instant just after local midnight so the UTC day differs, and pass the Building timezone explicitly where the code takes one. Example: `web/tests/crmLocalTime.test.mjs` (`Asia/Kolkata`, 00:30 boundary cases).
- **Feed new plan-item fields through the store, not by hand.** View-model tests that build `PlanItemData` directly skip `toPlanItemData`, so they pass even when the store drops the field (bug B.005). When a feature reads a plan-item field on the web, add one test that sends the daemon's shape through `mergeWorkerEvent` or `loadPlan` and asserts the result of the consuming helper, as `web/tests/worldStore.test.mjs` does for `reportSessionNumber` and `relatedBug`.
- **Store tests go through `web/tests/serverStub.mjs`.** It is a hand-written copy of the daemon's routes. A new daemon endpoint the store calls needs a matching stub route that mirrors the server logic, or store tests fail with 404s. Mirror the route's refusals (409/400) too: the stub's `/execute` accepted tasks with parents, so no store test could catch bug 10.018.005; `C2d` in `web/tests/dependencies.test.mjs` now pins the 409.
- **Checking UI changes in a real browser:** from `web/`, run `npx vite --port 5199 --strictPort` (any free port). The page calls the daemon at `http://localhost:4500` directly, so it shows live Projects. localStorage is per origin, so preferences set on the spare port don't change the user's normal app. When a check changes state and then reloads, run the two steps as separate, sequential tool calls. Run in parallel, the reload can win and throw the click away.
- **Checking Agent Analytics in a browser needs its own daemon.** The page's default daemon on port 4500 runs whatever is checked out there. Start one from the working tree on a spare port with `PORT`, `AGENT_VISUAL_OS_DATA_DIR`, `AGENT_VISUAL_OS_PROJECTS_DIR`, `AGENT_VISUAL_OS_EXECUTORS_PATH` and `AGENT_VISUAL_OS_CATALOG_DIR` pointing at temp paths, and start Vite with `VITE_SERVER_URL=http://localhost:<port>`. Give the executors file profiles whose `CLAUDE_CONFIG_DIR` is an empty temp folder so no real account is read; their checks then fail with "no account access". Seed readings and activity through `createAnalytics` from `server/src/analytics/index.ts` before starting the daemon. A session left open in seeded history is closed at startup, so a live band cannot be seeded.
- **A hidden browser tab does not lay out.** The chart draws nothing until its width is measured, and automated clicks sent in the first seconds after a page load can be dropped. Take a screenshot first, then act.
- **Socket lifecycles are tested through a pure controller with a fake socket.** With no DOM, WebSocket reconnect logic lives in a module that takes an `openSocket` factory, timers and callbacks (`createTerminalConnection` in `web/src/lib/terminalReconnect.ts`). `web/tests/terminalReconnect.test.mjs` drives it event by event (attach refused, `ended` before a stale snapshot, out-of-order snapshots). Source checks then pin the component wiring. Follow the same shape for other socket code.
- **View state that must follow live data is a pure transition helper.** A `useState` initializer runs once per mount, and the store patches records in place, so a mode or selection chosen in an initializer goes stale while the view is open (bug B.032). Put the transition in a pure function taking the previous value, the new data and a manual flag (`followRoundMode`, `followRoundIndex` in `web/src/lib/workflowRunView.ts`), table-test it, and pin with a source check that the component calls it and that no control sets the state directly (`web/tests/workflowRunView.test.mjs`).
- **Check that a new test file actually ran.** A registered run picks up only `web/tests/*.test.mjs` and `server/tests/*.test.ts`. In bug B.031 a new file written with a relative path while the shell was in `web/` ended up in `web/web/tests/`, and the first registered run silently skipped it. After adding tests, confirm the run's total rose by the number of new cases.
- **three.js stays out of the main bundle:** after `npx vite build`, `grep -c WebGLRenderer dist/assets/index-*.js` must print `0`. The 3D scene is only reached through the lazy `web/src/ui/WorldView.tsx` chunk.

A server error emitted after a task start is accepted (`planningCompletionError`) becomes an error notification: `web/tests/errorNotifications.test.mjs` covers the store patch and the toast/drawer wiring by source checks. ## Testing the SEO Pages and Sitemaps tabs

## Testing the SEO Building

- **Fakes, not Google.** `server/tests/helpers/seoFakes.ts` is a scriptable stand-in for Google and Bing (`createFakeSeo()`): deterministic days, queued failures (`fail('queryDay', quota())`), call counters and a `gate` awaited at the start of each GSC day, which lets a test hold a sync mid-way. Inject it with `configureSeo({ services, now, sleep, dayPauseMs: 0 })` from `src/seo/deps.ts`; `now` is the injected clock and `sleep` records back-off waits instead of waiting.
- **Never await a sync from inside the gate.** `stopSync` waits for the running sync, which is waiting for the gate; call `void sync.stopSync(id)`.
- **Stop background SEO work before teardown.** `startSeoMaintenance` returns an async `stop` that clears the timer and waits for any loop already running; await it, then call `stopInspection(id)` for each Building, before `closeAllStores()` and removing the temp dir. `seoApi.test.ts` `after()` stops every project's inspection first. Skipping this left a loop re-opening stores after teardown, so the server suite never exited (bugfix B.008). `pass()` in `src/seo/inspection.ts` treats a Building with no settings as nothing to inspect (`stoppedBecause: 'finished'`).
- **Windows:** with the clock at 2026-03-15, one month back fetches 28 days and two months 59 (the newest fetched day is the 14th); 12 months is 365. 06:30Z on the 15th is still the 14th in Pacific time (UTC-7 in March).
- **Roll-up consistency** is checked by `assertRollupsMatchRows`, which rebuilds month and week totals from the raw rows and compares.
- **Scale:** `server/scripts/benchSeo.ts` is the 10M/1M benchmark (not in `npm test`); `seoApi.test.ts` I51 runs 120k rows. Test files: `seoPure.test.ts`, `seoApi.test.ts` (server), `seoWorkspace.test.mjs` (web, with `seo` routes in `tests/serverStub.mjs`).
- **App-wide Google client (task 37.011).** `server/tests/seoGoogleClient.test.ts` sets `AGENT_VISUAL_OS_DATA_DIR` to a temp folder before its dynamic imports, so the app-wide `<data>/secrets.json` is never the real one. Other SEO API tests save the client through `PUT /api/settings/google-oauth-client` (their helpers), not per Building. `seoFakes` records `exchangeArgs` and `refreshArgs` to prove which client a call used. Web: `googleSeoSettings.test.mjs`; Radix dialogs render nothing in `renderToStaticMarkup`, so the Remove confirm and the panel's open tab are source checks.

### Keywords tab
