# Architecture decisions

Every architecture decision made for agent-visual-os, with the reasoning behind it. Source of truth: [`docs/spec.md`](spec.md), "Architecture decisions." Terms below (Agent, Worker, Template, Task, etc.) are defined in [`docs/glossary.md`](glossary.md).

## Real agents, not a simulation

Workers in the scene are backed by real `claude` CLI processes doing real work from the first version, not a mocked visualization layered on top of fake status. This was chosen over a phased approach (mock first, wire up real execution later) because the whole point of the tool is to watch and direct actual work.

## Standalone tool, not scoped to any one project

agent-visual-os is a general tool that can manage any project on the machine. Its own file conventions (catalog, per-project `.docs/` folders) are independent of any single managed project's structure.

## Local, single-user, no hosting

Runs as a local server on the machine, opened in a browser. No authentication, no multi-user access, no deployment target. If sharing status with clients or teammates becomes a goal later, that is a separate, larger piece of scope not covered here.

## CLI subprocess orchestration, not the Agent SDK

Agents are launched as `claude -p` subprocesses managed directly by agent-visual-os's backend, using:

- `--output-format stream-json` for structured, streamable state
- `--permission-prompt-tool` and `PreToolUse` hooks with the `defer` decision to detect and pause on a blocked tool call or clarifying question
- `--resume <session_id>` to continue a paused session

This was chosen over the Claude Agent SDK specifically to avoid separate API-key billing: the CLI path can run against the existing Claude Code subscription. Research found that the Agent SDK is, underneath, a typed wrapper that spawns the same CLI subprocess, so no orchestration capability is lost by going directly to the CLI; the tradeoff is doing the stream-json parsing and hook wiring by hand instead of getting typed message objects for free. Full research: [`docs/research/real-agent-orchestration-options.md`](research/real-agent-orchestration-options.md).

**Known gray area:** Anthropic's stated policy reserves subscription login for ordinary individual use of Claude Code, and describes API-key billing as the expected path for "developers building products or services" on top of Claude. A tool that programmatically spawns CLI processes sits closer to that second case, even when the only user is the person who owns the subscription. Not a blocker for personal, single-user use as currently scoped — see [`docs/risks.md`](risks.md) — but worth rechecking against Anthropic's terms before this goes beyond personal use.

### Confirmed by spike (2026-09-12)

A spike run against the actual CLI build available at the time (v2.1.269) confirmed the mechanism this depends on, and found it works differently from what desk research assumed:

- `AskUserQuestion` is **not available as a tool at all in headless (`-p`) mode** on this build. A session instructed to use it searched for it and found nothing.
- What works instead, confirmed end to end: prompting a worker to end its turn with a clear question — optionally enforced with `--json-schema` so the response is reliably parseable as `{"status": "blocked", "message": "..."}` rather than free text — then running `claude -p --resume <session_id> "<the user's answer>"` as a fresh invocation. The resumed session picks the task back up correctly, with full context of what it had already asked and why.
- This is **not a live, frozen process being unblocked**; it is a completed turn followed by a fresh one carrying the same session ID. This happens to be exactly the shape the manager/sub-agent relay design (below) already assumed, so no design change was needed — just a more concrete implementation path.

**Permission mode is not a soft setting.** With the default permission mode, a file-write attempt was not paused or asked about — it was denied outright, and the worker's turn ended by explaining the write had been refused. With `--permission-mode bypassPermissions`, the same task actually created its files with no denials. In other words, "full autonomy by default" (below) has to be wired through as an actual `--permission-mode bypassPermissions` (or equivalent) flag on the worker's process, or every tool call that would normally need approval will quietly fail instead of doing anything.

Full test log: [`docs/research/real-agent-orchestration-options.md`](research/real-agent-orchestration-options.md), "Empirical spike, 2026-09-12."

## Background daemon, not session-bound

A background server process keeps running independently of the browser tab, so agents keep working with the tab closed and the UI just reconnects to live state when reopened. The alternative — agents only run while a tab is open — was rejected because it undercuts the point of an ambient status view.

## Manual project registration only

Projects are added one at a time, not through automatic scanning or discovery of directories. This was chosen over auto-discovery specifically because a discovered project would get real, potentially fully autonomous agent access the moment it was found, which is not something that should happen without a deliberate step.

**Amended, 2026-09-13:** the original version of this decision had agent-visual-os point at an arbitrary existing folder path anywhere on the machine. That was changed before any server code was written: creating a Project through agent-visual-os now creates a real, fresh folder under its own git-ignored `projects/` directory (`server/src/projects/projectService.ts`), rather than registering a pre-existing path. The "manual, deliberate step, no autodiscovery" reasoning above still holds — a Project only exists once a person explicitly names one — but agent-visual-os now owns the folder's whole lifecycle (creation, its `.docs/` scaffold, deletion) instead of only ever pointing at something that already existed. Pointing at an arbitrary pre-existing path on disk is not supported in this pass; it's a plausible later addition if managing an already-existing repo turns out to matter, but it isn't needed for the tool's current, self-contained use.

## Its own git repository

agent-visual-os is real, ongoing software with its own git history, kept separate from every project it manages.

## Full autonomy by default, switchable per task

An assigned Worker can edit files, run commands, and commit without per-action approval by default. A setting can flip a given Task to approval-gated instead, and that setting can be changed both when the task is created and while it is running. A single global switch was rejected as too blunt given this will run against real client repositories as well as low-stakes personal projects.

## Home base shows Templates, not live processes

The Catalog at the home base lists agent personas as configuration, not as running processes sitting idle. A real process only exists once a Template is assigned to a Task. An idle LLM process with nothing to do would have no purpose and would visually misrepresent what is actually happening.

## Catalog lives in its own repo-root `catalog/` folder

**Amended, 2026-09-16.** The Catalog is a separate, repo-root `catalog/` folder — `catalog/agents/` and `catalog/skills/`, read and written directly by `server/src/catalog/catalogService.ts` — never this project's own real Claude Code config (`.claude/`) and never the *user's home directory* `~/.claude/` either. A Template or Skill authored in-game is therefore not a real, invocable Claude Code subagent/skill for this repository; it is game content, format-compatible with Claude Code's own agent-markdown / `SKILL.md` shape (so it stays portable and easy to hand-author or export) but otherwise inert outside the game. This repo's own dev-tooling agents/skills (`server-daemon-architect`, `threejs-scene-artist`, `ui-interaction-engineer`, `agent-visual-os-domain`, `roadmap-runner`, `threejs-scene-conventions`, `web-interaction-conventions`) never surface in the Catalog — they live only in the real `.claude/`, which this daemon never reads or writes.

An earlier pass briefly moved the Catalog directly into this repo's real `.claude/agents/`/`.claude/skills/` to avoid keeping two near-identical folder shapes in sync. That turned out to be the wrong call in practice: game-authored agents became real, invocable Claude Code subagents in this repo's own dev sessions, and this repo's actual dev-tooling agents/skills leaked into the game's Catalog UI as if they were game content. This decision reverts to the original design — a genuinely separate `catalog/` folder — with every capability already built (CRUD, enable/disable, skills, zip upload, `npx skills add` registry install, Task/Worker template+skill wiring) unchanged; only the storage location moved back.

The extra metadata the game needs (avatar, manager flag, default autonomy, enabled, triggers) is tracked in a sidecar `catalog/catalog-index.json` alongside the agent/skill files rather than added into the files themselves, so the agent markdown and `SKILL.md` files stay ordinary and portable. Auto-discovery still applies within `catalog/`: any `.md`/`SKILL.md` file not yet indexed gets a synthesized default entry the first time anything reads the Catalog (`syncCatalogIndex` in `server/src/catalog/catalogIndex.ts`, run by every `catalogService.ts` read), which is how a hand-dropped or `npx skills add`-installed file surfaces with no manual migration step — it just no longer scans anywhere near the real `.claude/`. Every read-modify-write of the index, including that sync, goes through `server/src/catalog/catalogIndex.ts`, which runs them one at a time on a single in-process promise chain and writes the file atomically (temp file, then rename), the same guarantee `FileDatabase` gives its collections. New writers must call those functions rather than touch the file: an unqueued background sync used to reset a just-created skill to its default entry, and overlapping writes left the JSON permanently unparseable (bug B.014).

`npx skills add <owner/repo>` is a real third-party CLI with no output-directory flag — it always writes into whatever `.claude/skills/` it finds relative to its own `cwd`. To keep that CLI from ever touching this repo's real `.claude/`, `skillInstall.ts` runs it with `cwd` set to a fresh temp directory it creates and owns exclusively, then copies the resulting skill folder(s) from `<tmpdir>/.claude/skills/` into `catalog/skills/` once the process exits successfully, and removes the temp directory afterward regardless of outcome.

## Manager and sub-agent flow: native delegation, with a relay for questions

A Manager Template spawns sub-agents through Claude Code's own built-in delegation (the Agent/Task tool) rather than agent-visual-os launching a fully separate OS process per sub-agent. This has a real consequence: native sub-agent delegation has no true mid-task pause. When a delegated sub-agent hits something it needs clarified, its current call ends, reporting what it finished and what it is blocked on. The Manager — being the only one of the two with native access to ask the user a question — is the one that raises the question through the wave-and-popover-and-chat interaction. Once answered, the Manager makes a fresh delegated call carrying the answer, continuing the remaining work.

**Visual consequence:** the blocked sub-agent's Worker keeps showing a working animation through the gap between its call ending and the follow-up call starting. That is a deliberate simplification in the visual layer, not a literal frozen process kept alive in the background.

## Blueprints are agent-authored

The assigned Worker writes and updates its Project's `.docs/blueprint.md` automatically at the end of each Task, following a fixed template covering what was built and what is proposed next. The user is not required to write these by hand, though the files are plain markdown and can be edited freely at any time.

## Project plan documents and the Tasks breakdown

**Added, 2026-09-13**, alongside the Full-fledged Project Popover. Every Project gets five fixed, always-present plan documents under `.docs/plan/` (Specifications, Requirements, Test Cases, End-to-End Testing, Performance Testing — `server/src/projects/plan.ts`). They are plain Markdown, stubbed at creation and editable in the workspace or by hand on disk. Planning conversations create and edit structured tasks; they do not currently write these plan documents.

The Tasks breakdown (the popover's default Tasks tab) is **not** parsed out of a Markdown checklist. It is structured `PlanItemRecord` data in the central file-based store (`server/data/plan-items.json`). Stable item IDs retain status, execution Task/WorkflowRun links, and planning-session provenance across edits. Numbered planning conversations are Task records; their ready linked items nest beneath them on the Planning board, while manual tasks and released children are standalone. Planning groups and standalone tasks share persisted `planningQueueOrder`, changed atomically through `PUT /api/projects/:id/planning-queue/order`; a group's ready tasks keep their own `planningGroupOrder`, changed through `PUT /api/projects/:id/planning-queue/sessions/:sessionId/order`. This keeps identity and ordering in runtime state rather than reconciling an agent-edited checklist by regex. Executing an item creates a `WorkflowRunRecord`; `workerManager.ts` synchronizes run state back to the item. Completing a planning conversation archives only the conversation, not its linked tasks, and restoration regroups only still-ready children.

## Sequential plan-item execution queue

**Historical note (2026-09-16 to 2026-09-27):** an execution queue and priority swimlanes once governed pending items; neither is used by the current board. A task remains in **Planning** until `POST /api/plan-items/:id/execute` accepts its start. The start picks the executor, Catalog Workflow, and `createBranch`: `true` assigns a new `task/<ref>-<slug>` branch and worktree off the Project's branch, while `false` uses the Project's current folder and branch. A start refused only because the Project is at its task limit is no longer an error: it waits in line (see "Added, 2026-10-26 (task 31.003)" below). A busy in-place folder on a repository Project still returns 409, and failed validation or launch leaves the task at its exact Planning position. The four current columns are Planning, Running, Needs you, and Completed; completed planning conversations and archived tasks share Archived. A planning conversation becomes auto-completion-eligible only after creating a task and completes when no linked task remains ready and the session is idle. A live session defers that check; manual completion releases ready children as standalone Planning cards without changing their state or provenance. Restoring a completed conversation makes it resumable and regroups only still-ready children. Legacy `priority` data is ignored on read; it has no bearing on the persisted mixed Planning order.

**Added, 2026-10-26 (task 31.003): waiting list for a full Project.** The execution queue is back, as a waiting list gated on the Project's free task slots rather than on one executor-holding item. `POST /api/plan-items/:id/execute` calls `workerManager.enqueuePlanItemExecution`: it starts the task at once unless the Project is at its task limit (6 with a linked repository, 1 without; `claimConcurrencySlot`), in which case it persists a `PlanItemQueueEntry` and answers **202 `{ started: false, entry }`** instead of 409 `task_limit_reached`. The entry keeps the dialog's executor, workflow, `createBranch` and skipped steps; the Auto-merge choice is saved on the task when the start is accepted, as for `start-when-ready`. A repository-less Project's one slot is also held by an unsettled run keeping the Project folder, so a busy folder queues there too. Refusals that are not the limit (400 bad options, 409 `session_still_running`, a read-only Project, unmet dependencies) are unchanged, and planning sessions (`kind: 'plan'`) never use a slot or wait.

- **One gate.** The old `executorHolder` rule (one queue-managed item at a time, a stopped run keeps holding it) is removed. The only gate is `claimConcurrencySlot`, so a Project with free slots runs several tasks at once. A stopped or paused task keeps its slot exactly as long as `liveTasksOf` counts it live, and no longer.
- **Order.** First come, first served by when Start was pressed, changeable with `queueIndex` or `reorderPlanItemQueue`. A start while others wait joins behind them.
- **Advancing.** `advanceQueueIfIdle` runs under the per-Project `withQueueLock` whenever a task settles, stops, fails or is deleted, a waiting-for-input task resolves, or a plan item is completed or deleted. It starts entries in order until the slots are full; one that still hits the cap is put back at the front. An entry whose task no longer exists is dropped. On daemon start `advanceAllQueues` advances every Project once, after interrupted runs have settled.
- **Dependent tasks.** `start-when-ready` answers 202 `{ started: false, item, entry }` when every parent is satisfied but the Project is full; the task leaves its waiting-for-parents state and joins the list. The same happens when parents are satisfied later.
- **Notification.** One `task.limit_reached` notification per Project while entries wait; it resolves when the list empties or an entry is removed.
- **Routes.** `GET /api/projects/:id/plan-item-queue` lists the entries in order; `DELETE /api/plan-item-queue/:entryId` removes one (404 when it already started), and the task goes back to unstarted. The `planItemQueue` live event carries the Project's whole ordered list.
- **Web.** The Start dialog closes on a queued answer and toasts "<title> is waiting for a free slot (3rd in line)"; when the Project is already full it notes "All 6 slots are in use; this task will wait in line and start on its own." The card shows "Waiting for a free slot · #n" in the waiting group of the Running column (counted with dependency-waiting tasks by the shared grouping, so footer counts agree) and offers "Remove from waiting list".

Not yet implemented: the entry does not itself carry the Auto-merge choice (it lives on the task), and "Remove from waiting list" is a button on the card rather than a card-menu item.

## Fetch before listing or switching a Project's branches

**Added, 2026-09-16**, for the same popup redesign — clicking "switch branch" should show a fresh branch list, not whatever this checkout's local refs happened to be the last time anyone fetched. `projectService.ts`'s `projectBranches` (`GET /api/projects/:id/branches`) now runs a quiet `git fetch origin` (`git.ts`'s new `fetchOrigin`, the same quiet full-remote fetch `gitSyncPoller.ts`'s background sweep already used — factored out so both go through one place) before reading `refs/heads`/`refs/remotes/origin`, so a branch a teammate pushed after this Project was cloned (or after the last background sync tick) shows up immediately rather than up to `GIT_SYNC_REFRESH_MS` later. A fetch failure (no network, remote gone) surfaces as an ordinary `GitError` — 409, same as any other git operation this router exposes — rather than silently falling back to a stale local list; unlike `gitSyncPoller`'s passive background reading, this one is a direct response to a person opening the branch picker, so a clear failure is more useful than a quietly-stale one. `commands/commandRunner.ts`'s `runProjectSync` needs its own `git fetch origin` to run as *part of* one trackable, user-visible `CommandRun` shell command (`git fetch origin && git merge --ff-only origin/<branch>`) rather than a separate awaited step, so it couldn't reuse `fetchOrigin` directly; `git.ts` also exports `FETCH_ORIGIN_COMMAND`, the shell-command spelling of the same fetch, so the two never drift out of sync independently.

`checkoutProjectBranch` already handled checking out an *existing local* branch or creating a brand-new one (`create: true`); it now explicitly handles the third case `projectBranches`' fresher listing surfaces more often — a branch that exists only on the remote, with no local ref yet. Modern git's `git switch <name>` will DWIM a local tracking branch for a uniquely-matching remote branch on its own, but that behavior is gated on the `checkout.guess` config and git version, not guaranteed — so `checkoutProjectBranch` checks explicitly (`hasLocalBranch`, a `for-each-ref refs/heads/<branch>` emptiness check, the same pattern `gitSyncPoller.ts` already uses on the remote side) and, when there's no local ref, runs `git switch -c <branch> --track origin/<branch>` itself rather than depending on git's default-guessing behavior.

**Amended 2026-09-26: creating a branch is allowed over uncommitted work and during an active Task.** Someone who started work on main/develop and forgot to branch needs a way to move that work onto a branch of its own. `git switch -c` never touches the working tree, so `checkoutProjectBranch` with `create: true` now skips both the clean-tree check and the folder-busy check (see the next amendment for what that check became). Inside the same project lock, its `onBranchCreated` callback (wired by the router to `workerManager.retargetPrimaryTasks`) moves every unsettled Task (not done or failed) running in the Project's own directory from the old branch onto the new one. Without that step, the Task's branch-drift check and its final `commitAndPush` would fail against the old branch. Worktree Tasks have their own checkouts and aren't touched. Switching to an existing branch still requires a clean tree, because it would swap files out from under work really happening there.

**Amended 2026-10-04: switching to an existing branch and syncing are gated on the same "is the Project's folder free?" rule as starting a new in-place Task, not on "is there an active Task?".** A running planning session never touches project files and needs no branch; a coding Task or WorkflowRun isolated in its own worktree never touches the Project's own folder either. Neither should ever have blocked a branch switch or a sync, but both did, because `checkoutProjectBranch` (`createBranch: false`) and `commandRunner.ts`'s `runProjectSync` each checked the crude `project.activeTaskId` truthy flag — which also only reflects the most recently *started* active Task, so its answer depended on start order. Both now call the same `assertProjectFolderFree`/`isProjectFolderBusy` that `executePlanItem`'s `createBranch: false` path already used (moved out of `workerManager.ts` into `server/src/worker/projectFolderGuard.ts` so `projectService.ts` and `commandRunner.ts` can share it without a circular import), which counts only a live, non-`plan` Task with no `worktreePath`, or an unsettled WorkflowRun (`running`/`awaiting-approval`/`needs-attention`/`completing`) with no `worktreePath` — the same liveness check (`isLiveTask`) that already discards a stale `activeTaskId` left over from a settled or legacy Task. A busy folder still fails with a 409 (`ProjectFolderBusyError`); uncommitted changes and a missing repository are refused exactly as before, unchanged by this amendment. `TaskRecord` gained `worktreePath` on the wire (`web/src/lib/serverApi.ts`'s `ServerTask`, mirroring `WorkflowRunRecord`'s existing field) so the web never has to guess: `BranchMenu.tsx` computes the same rule client-side (`web/src/lib/branchMenu.ts`'s `isProjectFolderBusy`, over the store's already-live `tasksById`/`workflowRunsByProject`) instead of gating its sync button and existing-branch entries on the Project's overall `status`. A planning session still makes a Project show as "working" at the Project-status/building-dot level — that aggregate is unchanged — it just no longer disables branch switching or sync. Creating a branch is unaffected: it's still always allowed, folder-busy or not.

## Milestones: a Project's target states, broken into Tasks

**Added, 2026-09-14.** A Milestone is a target state for a Project with its own definition of done — distinct from the Blueprint (a present-tense snapshot of what exists) and from a single Tasks-breakdown item (one unit of work). One plain markdown file per Milestone, `.docs/milestones/milestone-N.md`, numbered rather than named so a new one never collides; Project creation no longer stubs `milestone-1.md` (the helper module was removed in 37.012), so files are written by hand. This was chosen as plain files rather than a new DB-backed record (no new API route or UI tab this pass) because a Milestone's own narrative — its goal and definition of done — is exactly the kind of freeform, human-editable content the Blueprint/Plan docs already model well; only its *task breakdown* needs the Tasks-breakdown's structured identity, and that already exists.

A Milestone's tasks are ordinary Tasks-breakdown items, not a parallel list. `PlanItemRecord.milestoneId` is nullable and remains on items linked by earlier planning sessions. **Historical implementation note:** the original planning JSON mutation (`planTasks`/`PLAN_STATUS_SCHEMA`) could set this field and rewrite milestone files; that mutation was removed when planning became CLI-only and task-first. Milestone Markdown remains a human-editable snapshot, while task status and planning provenance live in structured records.

**Historical implementation note:** planning once allowed restricted writes under `.docs/plan/` and `.docs/milestones/`. The current planning agent does not edit those files; its task-creation tools update structured PlanItems instead.

## Project Commands: user-defined shell commands, not Tasks

**Added, 2026-09-14.** A Project Command (`server/src/domain/types.ts`'s `ProjectCommandRecord`) is a named shell command a person defines against one Project, run on click from that Project's own root directory — build/test/lint/deploy scripts, and the like. Deliberately **not** a Task: no Template, no Worker, no LLM turn, no session, no autonomy setting — just `child_process.spawn(command, { shell: true, cwd: projectAbsolutePath(project) })`. It gets its own small module, `server/src/commands/` (`commandService.ts` for CRUD, `commandRunner.ts` for execution), parallel to but independent of `worker/workerManager.ts`, rather than being folded into the Task machinery, since a shell command shares none of a Task's actual concerns (persona, permission mode, blocked/resume, transcript turns) — bolting it onto `workerManager.ts` would mean threading a pile of Task-only fields through a code path that never uses them.

Up to 3 Commands per Project can be **highlighted** (`commandService.ts`'s `MAX_HIGHLIGHTED_COMMANDS`, enforced server-side — a client-side disable is only a convenience, not the real cap), shown as one-click buttons on the Project Popover's header; the rest are reachable through a "⋯" menu. Defined and managed from the Popover's own top-level **Commands** tab (alongside Actions/Documents/Testing/Code), whose left sidebar has two entries, **Manage** and **History** — the latter listing every past **Command Run** (`CommandRunRecord`: status, exit code, full output, start/end) — the same file-based-store pattern (`server/data/project-commands.json`, `server/data/command-runs.json`) every other runtime record uses, see "One central runtime-state store" above.

**Amended, 2026-09-15 (Commands tab restructure):** originally this was a generic **Settings** top-level tab whose only sidebar entry, "Commands," toggled between Manage and History with two buttons inside the panel's own header. Since Commands was Settings' only content, that indirection was pure overhead — renamed the top-level tab itself to **Commands** (`TopTab`'s `'settings'` key became `'commands'`), and promoted Manage/History from an in-panel toggle to the tab's own two left-sidebar entries (`COMMANDS_ITEMS`, replacing the single-entry `SETTINGS_ITEMS`) — the same "each top-level tab owns its own left sidebar" shape every other tab (Actions, Documents, Testing, Code) already uses, rather than a one-off toggle pattern unique to this tab. `WorkspaceTab`'s single `'commands'` key split into `'commandsManage'`/`'commandsHistory'` to match; `CommandsSettingsTab` (the old toggle-owning wrapper) became `CommandsPanel({ view: 'manage' | 'history' })`, a thin `.document-panel` shell picking `CommandsManager` or `CommandsHistory` — both unchanged internally.

A run's live output/status streams over the daemon's existing single `/ws` connection: `commandRunner.ts` has its own small event bus (`CommandEvent`, structurally parallel to `workerManager.ts`'s `WorkerEvent`), and `api/ws.ts` broadcasts both over the one WebSocket rather than opening a second one — the frontend's existing `WorkerEvent` union and `mergeWorkerEvent` reducer just gained more event types to handle. Command *definitions* (create/update/delete) don't need this live feed — like PlanItem CRUD, the store folds the HTTP response straight into local state — only a running command's asynchronous output/status needs one.

A running command can be stopped (mirrors a Task's "Stop task"): `commandRunner.ts` tracks in-flight child processes in its own `runningProcesses` map, keyed by command id so the same command can't be started twice concurrently (`CommandAlreadyRunningError`) — a narrower, simpler version of the one-Task-per-Project limit, with no worktree/branch concept to isolate since a Command Run touches no git state agent-visual-os itself manages.

Closing a Command's log popup never stops it — the run keeps going and logging in the background exactly like a Task does, per "Background daemon, not session-bound" above; the popup is a pure view over live store state, not the thing keeping the run alive.

**Known simplification:** no cap or rotation on a Command Run's stored output, and stdout/stderr are interleaved into one `output` string in whatever order they arrive rather than kept as separate streams — acceptable for this tool's local, single-user, "a handful of Projects" scale (see server/README.md's "Known simplifications").

**Amended, 2026-09-26 (task 3.012):** Commands is no longer its own top-level tab. It moved under the new **Settings** top tab as one of its two sections (alongside Workflow — see "Configurable task Workflows" below), reachable the same way (the header's "Manage commands" action lands on Settings → Commands). `CommandsPanel` itself is unchanged; only where it's mounted from moved.

**Amended, 2026-09-15:** added a "Run a custom command" entry point (`ProjectCommandBar`'s always-present "▶ Run…" button, even with zero Commands defined) for a one-off shell command that's never saved unless asked — `commandRunner.ts`'s `runAdHocCommand`, sharing the exact same `startRun` execution core as `runCommand` and `runProjectSync`, just with a fresh synthetic `adhoc:<uuid>` `commandId` per call rather than one fixed id (unlike a branch sync, several one-off commands, or the same one twice, can reasonably run at once — nothing to dedupe against). Its log popup offers "Save as command", opening the same create-command form prefilled with the run's own command text.

This is also why `CommandRunRecord` gained `origin: 'saved' | 'sync' | 'adhoc'`: the log popup and History need to tell a saved command's run apart from a sync's or an ad hoc one's without guessing from `commandId`'s string shape, since "Save as command" only makes sense for `'adhoc'` (a `'saved'` run already is one; a `'sync'` run is a fixed system action). `CommandForm` (the "+ Add command"/row-"Edit" form, and now the "Save as command" dialog) also gained a **"Show in header"** checkbox — the same `highlighted` field the row-level ★ toggle already exposed, just settable at creation/edit time too instead of requiring a separate step afterward; `createCommand` now accepts an optional `highlighted` and enforces the same `MAX_HIGHLIGHTED_COMMANDS` cap `updateCommand` already did (factored into one shared `assertCanHighlight` check).

**Amended, 2026-09-15 (long-running background commands):** a Command Run was always allowed to outlive its log popup (see "Closing a Command's log popup never stops it" above), but nothing let the workspace *notice* one still going once its popup was gone — no problem for a quick `npm run build`, but a real gap for a deliberately long-lived one like `npm run dev`. Three pieces closed it, all reading the same underlying fact (a `CommandRunRecord` with `status: 'running'`) rather than adding a separate "is it running" flag anywhere:

- `commandRunner.ts`'s `listCommandRuns` gained an optional `status` filter (`GET /api/projects/:id/command-runs?status=running`), so the workspace can ask "what's still going on this Project?" without pulling every past run's full accumulated output over the wire just to find the handful still running — `FileDatabase.find` is an in-memory scan either way (see "One central runtime-state store" above), so the filter is free server-side; the payload savings are what matter here, since an unbounded `output` (see this section's own "Known simplification") makes fetching full history for this purpose pathological.
- `worldStore.ts`'s `loadActiveCommandRuns` calls that filtered endpoint and merges the results into `commandRunsById` — deliberately *not* into `commandRunIdsByProject` (History's own full-list cache), since overwriting that with a running-only subset would corrupt History the next time it's opened. `ProjectCommandBar` (always mounted in the workspace header) and `CommandsManager` (Commands → Manage) both call it on mount, so either surface reflects a command left running from a previous session, not just ones this session itself started.
- `findRunningRun(commandRunsById, commandId)` — a pure lookup, same testable-without-a-store precedent as `mergeWorkerEvent` — finds the in-flight run for a command, if any. The header button and each Manage row use it to show a small glowing blue dot (a static glow — looping animations are banned for GPU cost) and, in Manage, replace Run/Edit/Remove with a single "Running…" status button back to the log popup (editing, removing, or double-running a command mid-flight isn't a choice worth offering). Clicking an already-running header button reopens that popup rather than calling `runCommand` again, which would 409 (`CommandAlreadyRunningError`).

The log popup itself gained an explicit **Minimize** button alongside Stop, shown only while `status === 'running'` — functionally identical to the header's existing × (both just clear the locally-held open-run id; the run itself is untouched either way), but named so a person watching a long-lived process isn't left guessing whether dismissing the popup might kill it.

**Amended, 2026-09-15 (ANSI output rendering):** most CLIs (webpack, npm, and nearly everything else run via a Project Command) color their own output whenever they believe they're writing to a color-capable terminal — `spawn`'s pipes often fool that detection into staying "on" — so a run's raw `output` frequently contains real ANSI SGR escape codes. Rendered as plain text, `CommandLogPopup`'s `<pre>` showed these as literal noise (`ESC[1mESC[32mmain.jsESC[39mESC[22m`) rather than bold green text. `web/src/lib/ansi.ts`'s `parseAnsi` (a small hand-rolled parser, not a dependency — this tool already prefers small owned utilities over adding a package for something this scoped, the same call `FileDatabase.ts` makes) turns the accumulated output into an array of `{ text, style }` segments, each rendered as a `<span style={...}>` — React's own text-child escaping means this needs no `dangerouslySetInnerHTML` and has no injection surface. Only SGR sequences (`ESC [ params m`, covering bold/dim/italic/underline/strikethrough, the 16 standard colors, 256-color, and truecolor) are turned into styling; every other escape sequence a CLI emits (cursor movement, erase-line, OSC window titles) is recognized and silently dropped rather than rendered as garbage, since this is a static top-to-bottom scrollback with no cursor to move — full terminal emulation (a spinner repainting in place, say) is a deliberate scope cut, not a bug. Re-parsed from the full accumulated `run.output` on every render (memoized on it) rather than incrementally per streamed chunk, so a multi-byte escape sequence split across two WS `commandRunLog` chunks is always whole by the time it's parsed.

## Remote git sync: a background poller, not a webhook

**Added, 2026-09-15.** Checking out a branch is a snapshot — nothing in this daemon otherwise notices if someone pushes new commits to that same branch on GitHub afterward. A webhook would be the usual fix, but this tool is deliberately "local, single-user, no hosting" (see above): there's no public endpoint for GitHub to call. So `server/src/projects/gitSyncPoller.ts` closes the gap the same way `executors/claudeUsage.ts` already does for usage limits — an in-memory poller (`GIT_SYNC_REFRESH_MS`, 60s) that sweeps every git-backed Project, running a quiet `git fetch origin` and comparing `HEAD` against `origin/<branch>` (`git rev-list --left-right --count`) to land on one of `synced`/`ahead`/`behind`/`diverged`/`no-remote`/`unknown` (`GitSyncStatus`, `server/src/domain/types.ts`).

The reading (`ProjectSyncState`) is kept in memory only, never persisted — like a Command Run's live output, it's a point-in-time fact the next fetch immediately supersedes, not state worth writing to `projects.json`. It's attached to every `GET /api/projects[/:id]` response computed fresh from the cache (`api/router.ts`'s `withSync`) and pushed live the moment a fetch completes as a `projectSync` event, structurally the same event-bus shape as `CommandEvent` and broadcast over the same one `/ws` connection (see "Project Commands" above) — the frontend's `WorkerEvent` union and `mergeWorkerEvent` reducer just gained one more case.

The same reading doubles as an action: the branch picker's sync button (`web/src/ui/ProjectWorkspaceModal.tsx`'s `BranchSyncButton`, styled and positioned as an ordinary `.btn` alongside the checkout button, not a bare icon) fetches and fast-forwards the checked-out branch up to its remote when clicked — but rather than a bespoke REST call whose only feedback is a boolean/error, it runs through the exact same machinery as a user-defined Project Command: `commandRunner.ts`'s `runProjectSync` spawns `git fetch && git merge --ff-only origin/<branch>` as a real, trackable `CommandRun` (`POST /api/projects/:id/sync`, 201), and the click opens the very same log popup a Project Command's "Run" button does, so the person sees the actual command, its live output, and its real exit code — not just a toast. It's never a persisted `ProjectCommandRecord` (a synthetic `commandId` of `sync:<projectId>` only reuses `startRun`'s "can't run the same thing twice concurrently" guard, `CommandAlreadyRunningError`), so it never shows up in the Commands tab's list of *defined* commands — but its runs do land in that same tab's History alongside real ones, since `listCommandRuns` has no reason to filter them out and a sync is a real run worth keeping a record of. Deliberately `git merge --ff-only`, never a real merge or `--hard` reset: a diverged branch (local commits of its own) fails the run outright — a real, non-zero exit shown in the log — rather than silently rewriting or losing anything. Once the run settles, `runProjectSync` refreshes `gitSyncPoller`'s cache and rebroadcasts immediately, so the sync button and the rooftop dot both catch up right away instead of waiting for the poller's next scheduled tick. `behind`/`diverged` are surfaced as the same red, glowing "needs attention" state a failed Task's rooftop dot already uses (`web/src/lib/buildingVisualStatus.ts`) — one visual vocabulary for "this Project wants a person to look at it," regardless of whether the cause is a failed Task or a branch that fell behind.

**Added, 2026-10-13 (task 10.014): automatic pull.** The poller no longer only reports. After each reading, `gitSyncPoller.ts` hands a `behind` branch to `autoPull.ts`'s auto-puller, which fast-forwards it when that is safe and otherwise records a plain-words reason (`ProjectSyncState.deferredReason`) that the tooltip and the `git.out_of_sync` notification show. The decision (`decideAutoPull`) is a pure function of the reading and the blockers: setting off, detached HEAD, an unfinished merge/rebase/cherry-pick/revert (`git.ts`'s `detectGitOperationInProgress`), the Project lock held, the folder busy (`isProjectFolderBusy`, the one rule shared with branch switch and manual sync) or local changes overlapping the incoming commits (see the overlap rule below), reported in that fixed priority. To keep a task start from racing the pull, the auto-puller first claims the Project synchronously (`claimProjectPull`, refused while a lock holder or another pull has it) and only then reads the conditions; `withProjectLock` waits for a pull in flight instead of refusing, so a task starting meanwhile proceeds the moment the (short) pull ends, and a pull can never begin while a task start or stop holds the lock. The pull is `commandRunner.runAutoPull`, the same command text, per-Project command id (so it cannot overlap a manual sync) and History as `runProjectSync`, with `automatic: true` on the run. A failure is remembered with the remote commit it failed against and raises one `git.auto_pull_failed` notification per distinct reason; it is retried only after `origin/<branch>` moves, and the manual sync is always available. Re-evaluation without waiting for the poll: a task or WorkflowRun event reuses the last reading (no fetch) when the pull was deferred (`reevaluate`), and the branch checkout, PR checkout, return and merge routes refresh the reading after they finish. The setting is `ProjectRecord.autoPullEnabled` (absent reads as on) set by `PATCH /api/projects/:id/auto-pull`.

**Amended, 2026-10-13 (task 10.016): the overlap rule.** A local change no longer blocks the automatic pull or the app self-update just by existing. `server/src/projects/incomingOverlap.ts` lists the paths changed between `HEAD` and `origin/<branch>` (`git diff --name-only -z --no-renames`, streamed, so renames count on both sides and nothing is quoted) and the local status (`git status --porcelain=v1 -z`, streamed; ignored files never appear). An update is blocked only by a staged, modified, deleted or renamed local path in the incoming set, or an untracked file the commits would add (including a file/folder clash). Paths compare case-insensitively, trimmed and Unicode-normalised, so a case-insensitive filesystem cannot hide an overlap. Identical content still counts, because git would refuse. If the incoming paths cannot be read, the old conservative rule applies (any tracked change blocks, untracked files do not) and the reason says so. The check runs again at apply time inside the same flow; if the folder changed meanwhile git itself refuses (`merge --ff-only` never overwrites), the failure names the files and nothing is applied. Ahead, diverged, detached HEAD, an unfinished operation, a busy folder, auto-pull off, and dev mode keep their order and wording; ahead and diverged are reported before overlap. The manual sync button has no pre-check (it runs `git fetch && git merge --ff-only`), so git already refuses only on overlap there. The blockers reach the web as `ProjectSyncState.blockingFiles`/`blockingFilesTotal` and `AppUpdateStatus.blockingFiles`/`blockingFilesTotal` (capped at 10, exact total); the popover lists them with a "Copy file list" button. The app never discards, stashes or cleans local work to clear a blocker.

**Rollback guarantee (task 10.016).** A failed server-path app update restores the previous commit with `git reset --keep <sha>` (`server/src/appUpdate/updateGitSteps.ts`), not `--hard`: files the update changed return to their old content and every local change is kept. If a file the update changed was edited after the pull, git refuses, the failure message says the previous version could not be restored without discarding local changes, and the checkout stays on the new commit with the edit intact. The pull and rollback steps are shared by both update paths and by `server/bin/run-app-update.mjs`, which stays a thin, manually checked caller.

## Notifications are not triaged by an LLM agent

**Added, 2026-09-25.** Milestone 5 (`docs/milestones/milestone-5-notification-system.md`) first shipped a Notification Agent: on every new Notification the daemon ran one throwaway `claude -p` turn that picked actions from a closed catalog and wrote an `agentDecision` back onto the record. It was removed on purpose. One claude turn per Notification spent usage on every event, including noisy low-severity ones, and the decisions it made were not useful enough to justify that. The `NotificationChannel` interface and WhatsApp adapter (`server/src/notifications/channels/`) are kept with no caller as plumbing for a future rule-based escalation, not an LLM one.

## Notifications are keyed by subject, not a single status field

**Amended, 2026-10 (task 1.002).** A Notification's old `status: 'open' | 'acknowledged' | 'resolved' | 'dismissed'` conflated two independent questions: has the user seen this (their call), and is the condition that raised it still true (the system's call). It's now two fields, `readAt`/`resolvedAt`, both nullable timestamps — resolving also marks read, since a thing that's no longer true doesn't need a separate "seen" step. Every Notification also carries a `subject` (`{type:'task'|'command'|'project'|'skill', ...}` — see the milestone doc's data model) that's both what it's about and where clicking it goes; its identity (type plus whichever field names the thing itself, never the `taskId`/`runId` used only for the deep link) is what `raiseNotification`/`resolveNotifications` dedupe and resolve against, replacing each producer's own hand-rolled find-or-create. The building dot counts only unread-and-unresolved Notifications; the topbar bell counts every unread one regardless of resolved state; the old Notification Center dialog is now a right-side drawer (`web/src/ui/NotificationCenter.tsx`) with deep links and a quick action per kind where one exists (reply, retry, run again, sync) instead of generic status-transition buttons.

## Cloning a repository bootstraps its docs from what already exists

**Added, 2026-09-14.** Creating a Project from an existing repository (`repositoryUrl` set) auto-starts a `'plan'`-kind Task the moment the clone finishes (`projectService.ts`'s `startCloneDocsBootstrap`, called from `api/router.ts` — never from `projectService.ts` itself, which workerManager already imports, to avoid a cycle). Its prompt (`CLONE_BOOTSTRAP_PROMPT` in `plan.ts`) asks the Worker to read whatever documentation the repository already has — README, an existing `docs/` folder, package manifests, code comments — before replacing the plan docs' and first Milestone's placeholder stub text, so a real, already-documented codebase starts from a first draft informed by what it actually is rather than five blank stubs. A brand-new, empty Project never gets this Task — there is nothing yet to read.

This runs as an ordinary, visible Task (pollable, shown developing/blocked/done like any other) rather than a hidden setup step, and its own failure never fails Project creation, which has already succeeded by the time it's kicked off.

Scaffolding a Project's `.docs/` never clobbers what a clone already ships: every stub file (`writeStubBlueprint`/`writeStubPlanDocs`) is written create-exclusive, so a repository that already has its own `.docs/` — say, one a previous run of this tool already set up and committed — is preserved untouched. The bootstrap Task still runs in that case too; redrafting docs that already look right is a harmless, if occasionally redundant, planning turn.

## Agent-driven planning: a restricted Task kind, not a separate agent

**Added, 2026-09-13.** The popover's persistent chat defaults to "planning": the message runs as an ordinary Task (a real Worker, shown developing/blocked/done like any other) but with `kind: 'plan'` instead of `'execute'`. A `'plan'` Task's prompt is composed differently (`PLAN_INSTRUCTIONS` in `plan.ts` in place of the coding/blueprint instructions), and — the actual enforcement, not just a prompt request — it runs with `--disallowed-tools Bash,BashOutput,KillShell`, so it cannot run build/test/deploy/git commands regardless of what the prompt says or what the model decides. It may still read the codebase (Read/Grep/Glob) for context and write only the plan docs and Milestones (see below); nothing stops it writing outside `.docs/plan/`/`.docs/milestones/` at the tool-permission level, so that boundary is enforced by instruction, not sandboxing — a known simplification, see `server/README.md`. Checking "Skip planning" in the chat runs the same message as an ordinary `kind: 'execute'` Task instead — real coding work, exactly like the "Start a task" flow already had.

**Revised, 2026-09-24.** Planning is now CLI-only and task-first. A planning session runs only on an interactive CLI executor (`PlanningRequiresCliError` otherwise); the structured `claude -p` / `codex exec` planning path, its `planTasks` final-JSON contract (`PLAN_STATUS_SCHEMA`) and the `.docs/plan/task-changes.json` file are gone. The prompt is the user's message plus a short `PLAN_INSTRUCTIONS`: research the topic, question the user until the requirement is unambiguous, then create ordered tasks whose descriptions stand on their own. It no longer asks the session to edit plan docs or milestones, or injects the current breakdown.

**Amended (task 38.003).** Short requests used to become tasks with no questions asked, so Test Case Planning kept going back to the owner for facts nobody had gathered. Both planning-capable prompts (`PLAN_INSTRUCTIONS` and `PLAN_AND_BUGS_INSTRUCTIONS`) now embed one shared block from `server/src/projects/planningInterview.ts`: an interview first, even for a short request, walking the decision tree one decision at a time (independent decisions may share a round) with a recommended answer for each and facts taken from the code and git history; a confirmation round (scope, decisions, open assumptions, explicit go-ahead) before the first filing call; and a specification completeness checklist written into each task (testing expectations, schemas and API contracts, environment and baseline, UI decisions, wording that stays, criteria verifiable here). The session has no shell, so its baseline check reads `.docs/testing.md`, `.docs/planning-notes.md` and the package scripts. These are prompt rules only: the filing tools and routes are unchanged and enforce no confirmation. The earlier bug report session's prompt is unchanged.

**Revised, 2026-09-26.** A planning session now writes feature specifications, not implementation plans: one task per feature (its backend, frontend, UI, tests and docs together, in sections if large), each describing the problem, user-visible behaviour, rules, decisions, edge cases, scope and acceptance criteria. It must not prescribe file paths, code names, data structures or coding steps — the coding agent picks those. Splitting a feature into small implementation-step tasks produced fragmented work, and naming files locked the coding agent into the planner's guesses. The same wording is in `create_task`'s description.

The session manages tasks live through four MCP tools (`list_tasks`, `create_task`, `update_task`, `delete_task`) served by a session-scoped stdio MCP server, `server/bin/plan-task-mcp.mjs` (launch config in `server/src/terminal/planTaskTool.ts`, CLI flags in `terminalSessionManager.ts`'s `interactiveCliArgs`), relayed to the token-protected `/api/agent-tasks` routes. `workerManager.ts` only accepts calls from a `'plan'` Task that is still `developing`, only touches items in that Task's own Project, and never edits or deletes an item with a Task running. It also never edits a completed (`done`) item (`PlanItemCompletedError`, 409): a done item only lists under Completed, so reworking it into new work would hide that work from the open Tasks list. **Revised, 2026-09-26.** **Revised, 2026-09-25.** A planning session is read-only; its only output is tasks, so it never needs branch or change management. Claude CLI denies every shell and file-editing tool (`PLAN_DISALLOWED_TOOLS`: `Bash`, `BashOutput`, `KillShell`, `Edit`, `Write`, `NotebookEdit`); Codex CLI has no per-tool deny flag, so it runs in `--sandbox read-only --ask-for-approval never` whatever the session's autonomy, since an approved escalation would run outside the sandbox.

The channel is MCP rather than a plain HTTP call because a planning session's shell tools are denied, and an MCP tool is the one extension point both the Claude and Codex CLIs expose.

Tasks a session creates are numbered `<session>.<task>` (task zero-padded to three digits, e.g. `3.002`) so they read in execution order: the session number is per Project and shared by a conversation's follow-ups (`TaskRecord.planningSessionNumber`), and the task number is stored on the item (`PlanItemRecord.planningRef`). Nothing sets `PlanItemRecord.milestoneId` any more; items linked by older sessions keep theirs.

## Agent terminal sessions: an interactive coding agent per Project, not a Task

**Added, 2026-10-19.** The Project popup header has an "Agent" dropdown, right after the Commands controls, for working step by step in a real interactive CLI when the person is not yet clear enough to write tasks. "Start new" is its first, low-key item; the other rows are the Project's sessions (running or ended), each renameable, endable and deletable. Starting asks which coding agent to use (the shared `CodingAgentPicker`, with its usage-limit status). The session fills the popup body under the tab bar; Back returns to the tabs and leaves the session running.

A session is **not a Task**: it has no branch, worktree, concurrency slot, commit or completion step, so it never appears on the board. It is a record in its own store (`agent-sessions.json`, `terminal/agentSessions.ts`) that runs in the Project's own folder through the same `TerminalSessionManager`, keyed by the session's id (the `/terminal` socket accepts it). It runs with the broad `auto` permissions (`--dangerously-skip-permissions` for Claude, the sandbox bypass for Codex) and no read-only or denied-tool restriction; planning, bug-report and workflow-step sessions are unchanged. It does not report CLI lifecycle hooks (`reportHooks: false`), so it never moves a Task's state and records no usage analytics.

Names default to "Terminal 1", "Terminal 2", ... from a per-Project counter that only increases, so a deleted number is never reused. The system prompt asks the agent to call `rename_session` (`bin/agent-session-mcp.mjs`, relayed to `POST /api/agent-session/name` with the CLI hook token and the session id) after two or three exchanges; the person can rename too. Both paths trim, strip control characters and allow at most 80 characters.

Resume relaunches the same agent conversation from the stored setup (system prompt, binary, environment, `auto` autonomy): Claude with `--resume <id>`, Codex with `resume <id>`. If the agent no longer has the conversation, or none was ever recorded, the session starts afresh under the same name. A daemon restart marks sessions it left running as ended.

The app tools a session gets are the planning task tools (`list_tasks`, `create_task`, `update_task`, `delete_task`, on the Project directly, so tasks created this way carry no `<session>.<task>` number) and the testing tools (`list_test_actions`, `run_test_action`, `get_test_run`, `run_all_tests`, run in the Project's own folder). **Not yet implemented** for these sessions: filing bugs (`report_unrelated_test_failure` answers 409), starting tasks, running Project commands, and the GitHub-account environment that Task sessions get. The web record never carries the agent's conversation id, the launch environment or the folder path.

## Follow-up Tasks continue a session, not mutate a finished one

**Added, 2026-09-13.** A Task's own lifecycle stays terminal once it settles (`done`/`failed`) — "Interactive task-specific chat ... to provide further instructions" (roadmap) is a **new** TaskRecord (`workerManager.ts`'s `followUpTask`) that resumes the same CLI session (`--resume`, full prior context) with a fresh instruction, staying linked to the same PlanItem if the original was running one. ## Building Types are coded, not configured

**Added, 2026-10-09 (task 10.003).** A Building has a **Building Type** chosen from a list registered in code (`server/src/buildings/registry.ts`). Software, the existing Project, is the first (`types/software.ts`); Notes (`types/notes.ts`) is a developer-only skeleton that exercises the whole contract. `GET /api/building-types` lists every registered type with `devOnly` flagged (the web needs them all for a Building's tint and storage); creating a dev-only type needs `AGENT_VISUAL_OS_DEV_TYPES=1` on the daemon, and the web create dialog also hides it outside `vite` dev. Later Buildings (SEO, Sales and Marketing) are written as further types against the same contract, each in its own task.

Types are code rather than a declarative definition because each Building will have its own server logic, tools, 3D look and workspace popup, and most of a Building's plumbing is fixed. A schema language or generic tab and panel kinds would have to be as expressive as the code they replace. The contract (`buildings/contract.ts`) is therefore plain data plus a validator:

- **Identity:** stable id (lowercase kebab-case, matched exactly), name, description, category, version, 3D look (`software` model or a generic building with a tint) and the web workspace to open.
- **Create inputs:** `validateCreate` returns the validated value or the field it rejects. Software checks only the name here; the repository URL is still validated and cloned by `createProject`, so its errors read exactly as before.
- **Data storage:** an optional `StorageSpec` (tables, roll-ups, retention rule, versioned SQL migrations). A type without one (Software) keeps using the central store.
- **Workflow slots:** named places where the type uses a workflow, each with a built-in default (`software`: "Build a feature or change", "Fix a bug"). **Agents** it uses, and the tools its sessions get, come from the workflows' steps.
- **Scheduled jobs:** default jobs each Building of the type starts with, run by the scheduler ([scheduler contract](scheduler.md)).
- **Capabilities and events**: capabilities offered to other Buildings (with inputs, outputs, read or write, approval and the code that runs them) and events published. Linked Buildings call and subscribe to them; see [connections](connections.md).
- **Repository flag.** A type that declares a repository gets a clone, a worktree and a branch per run, and the commit, push and pull-request stage. Any other type runs its workflows in the Building's own working folder with the same run, step, approval and notification behaviour and none of the Git wording (`web/src/lib/buildingTypes.ts` `repositoryWording`; the Settings panel hides Workflow, Git provider and Commands). Repository-only features: branches, worktrees, commit and push, pull requests, the Code and PR tabs.

**What every type gets from the platform:** runs, steps, approvals and notifications; the Tasks board and Planning sessions; the scheduler and the generic Schedules area; the status footer; Settings basics; secrets storage; owner and tenant fields.

**A stored Project reads as Software.** `normalizeProject` (`buildings/normalize.ts`) is applied on every read and every `project` WebSocket event: a record with no `typeId` is Software version 1, owned by the local user, and is not rewritten until its next save. A record whose type is not registered stays listed and openable but **read-only** with a "type unavailable" notice, as does a Building whose data is newer than the code or whose last migration failed. Every non-GET request under `/api/projects/:id` for a read-only Building answers **409** `{ error }` with the reason, except moving and deleting it and exporting a backup; starting a Task, a run or a planning session is refused at the same 409 wherever the request comes from (`assertWritable`, called where the work claims its slot in `workerManager.ts`). The app has no screen for deleting a Building yet; deletion is `DELETE /api/projects/:id`.

**Unknown type** on create is 400 `{ error, field: 'typeId' }`; invalid input is 400 naming the field; an unknown Building is 404.

**Configuration is per type, not per Building** (an assumption in the task, kept): `GET /api/building-types/:id/config`, `PUT` and `DELETE /api/building-types/:id/slots/:slotId`, stored in the central `building-type-configs.json`. Per slot the person picks which Catalog workflow fills it and, per step, which Catalog agent runs it. A new run snapshots the result (the explicit workflow, else the Project's own, else the type's first slot, else the Catalog default), so a later change never touches a run already started. A configured workflow or agent that is deleted falls back to the default and the Catalog screen shows a notice; the delete itself still succeeds. Switching a slot's workflow clears that slot's step agents.

**Tenancy is design constraints only.** Projects and Tasks carry `ownerId` and `tenantId` (defaults `local-user` and `local-tenant`, `buildings/ownership.ts`). Credentials go through one `SecretsStore` (`buildings/secrets.ts`): one file per Building with owner-only permissions, plus one app-wide file (`<data>/secrets.json`, `appSecrets()`) for credentials every Building shares, never copied into a record, never returned (the API reports `hasSecret` only), and scrubbed from the daemon's console output. There is no login, locking or deployment.

**The CRM Building** (`types/crm.ts`) deliberately does not use the bulk layer: it needs row updates and multi-step transactions, so it keeps `crm.sqlite` in the Building's folder and runs it synchronously in the daemon thread, with one writer at a time per Building. See `docs/crm-building.md`.

**The Content Studio Building** (`types/contentStudio.ts`, task 32.001) also keeps its own SQLite file (`content.sqlite`) in the Building's folder, like the CRM, plus plain files agents can read and edit (`knowledge/`, `concepts/<id>/`), guarded by a version on every save. It plans Concepts with per-platform Posts, a calendar, Business knowledge and a Writing style for one business. See `docs/content-studio-building.md`.

**The SEO Building** (`types/seo.ts`, task 10.006) is the first product type on the contract: one site per Building, Google/Bing connections, daily snapshots in the bulk store and a per-Building retention window. It added three generic pieces to the foundation: `replaceRows` (replace matching rows and fix roll-ups in one transaction), a retention that can span several tables with a per-Building window, and the type hooks `onCreated`, `onDeleting` and `retentionPlan` (the last gates automatic and generic retention). See `docs/seo-building.md`.

## Bulk data layer: one SQLite file per Building

**Added, 2026-10-09 (task 10.003).** The central store (`FileDatabase`, one JSON file per collection, loaded whole) stays for small records. A Building type with large data (daily per-page and per-query metrics, link graphs, keyword and backlink lists, customer histories) declares a `StorageSpec` and gets its own embedded database.

- **Engine: SQLite via `better-sqlite3`, one file per Building** at `server/data/buildings/<id>/bulk.sqlite`, with `secrets.json`, `backups/` and `exports/` beside it. Node here is v25.2.1, whose built-in `node:sqlite` still prints an `ExperimentalWarning`, so the maintained native add-on was used as the task asked; the storage code sits behind `BulkStore` (`buildings/bulkClient.ts`) so a hosted engine (Postgres, for the later multi-tenant server) can replace it without changing any type's screens. No second engine is built or planned.
- **Isolation.** Deleting a Building removes its folder (a failed cleanup is logged and does not block deletion); one Building's size or corruption cannot affect another; a Building exports on its own (`POST /api/projects/:id/storage/export` writes a standalone SQLite file).
- **A worker thread per Building** (`buildings/bulkWorker.ts`) owns the connection, so synchronous database work never blocks the daemon. Long operations (synthetic ingest, retention) run as jobs: short transactions of 5,000 rows (20,000 for retention) with a yield between them, which is where progress, cancel and other queries get through. `POST` returns 202 with a job; `GET /storage/jobs/:jobId` reports `done`/`total`; `POST .../cancel` stops between batches (404 unknown, 409 finished). If the thread dies, pending calls reject and the next call restarts it.
- **Crash safety.** WAL mode; each batch is one transaction that writes the rows and their roll-ups together, so a crash or a failure on row K leaves none of the batch. A large load into an empty table drops the table's secondary indexes and builds them once at the end (random index inserts into a multi-million-row table were the bottleneck), also after a cancel.
- **Queries happen in the store.** Lists are keyset-paginated (`(sort column, id)` cursor, opaque, so ties are stable), default page 50, maximum 200 (an over-large `limit` is clamped; zero, negative or non-numeric is 400; there is no way to ask for all rows). Sort and filter columns, operators and roll-up names come from per-table allow-lists in the type's spec; every value is bound as a parameter; `LIKE` wildcards are escaped. A bad request is a 400, never an SQL error. `total` is `null` (counting 10M rows per page is not worth it). Aggregates (period totals, top-N, group-by) read **maintained roll-up tables**, never raw rows.
- **Retention.** A type declares one rule (`table`, `timeColumn`, `months`, `mode`). The cutoff is the first day kept (UTC): rows dated before it are removed in chunks, a row dated on it is kept; `discard` also reduces the roll-ups, `rollup` keeps them so totals still cover the discarded period. It runs on demand (`POST /storage/retention`) and every six hours for each Building (`startStorageMaintenance`). Deleting rows frees pages for reuse but does not shrink the file; `compact: true` runs `VACUUM`. The rule is shown in Settings in plain words. Nothing else is ever dropped.
- **Size and warning.** `GET /api/projects/:id/storage` reports bytes (database plus WAL), the warning threshold (default 2 GB, `PATCH` to change), the level, the rule, the last backup and any read-only or ingestion-stopped reason. Crossing the threshold raises one `storage.problem` notification per crossing; dropping back under resolves it.
- **Storage errors.** Only a genuine storage fault (`SQLITE_FULL`, `SQLITE_IOERR*`, `SQLITE_READONLY`, `SQLITE_CORRUPT`, `SQLITE_CANTOPEN`) stops ingestion; a row the table refuses (a duplicate of its unique key, `onConflict: 'fail'`) is a 409 for that request and leaves ingestion running. The supported conflict modes are `fail` and `ignore`. A storage fault stops ingestion for that Building only, raises a notification and leaves the data valid; further writes answer 409 until the person resumes (`POST /storage/resume`).
- **Migrations.** `version` is 1 plus the number of `migrations` steps. Opening a Building whose stored version is lower takes a backup (`db.backup` into `backups/pre-migrate-v<N>-<ms>.sqlite`), applies the SQL steps in one transaction and records the version. On failure the backup is restored byte for byte, the Building is read-only with the error shown, and the next start retries. A version newer than the code opens read-only untouched. Migrations also run for every Building at daemon start. A current Building takes no backup.

### Benchmark (the task's scale targets)

`node server/scripts/benchBulk.ts` generates 10,000,000 metric rows (365 days, 3,000 pages, 50,000 query strings) and 1,000,000 list rows in one Notes Building, then times each query (15 runs). Run on an Apple-silicon laptop (darwin arm64), Node v25.2.1, `better-sqlite3`, 64 MB page cache:

- Ingest: 10M metric rows in 61 s (about 165,000 rows/s, five indexes and two roll-ups), 1M list rows in 3 s. Database file: 1,457 MB for both.
- Daemon process RSS: 98 MB at start, 354 MB at the peak during ingest, 263 MB after the queries (the worker thread's fixed page cache and the in-flight batch; it does not scale with the row count, and `bulkStorage.test.ts` asserts the JS heap stays flat for 20 times the data). Worst event-loop lag in the daemon thread while ingesting and querying: 44 ms.
- Retention: 1,068,522 rows older than the cutoff removed in 26.8 s, roll-ups reduced to match.

## One central runtime-state store, docs stay per-project

Live orchestration state — process status, Task status, transcripts, pending questions — lives in one store at `server/data/`, covering every registered Project at once. This was chosen over a separate store per project because the background daemon already manages every Project centrally, and a single store makes a cross-project view a single query instead of a scan across many small databases.

**Amended, 2026-09-13:** built as a small dependency-free file-based JSON database (`server/src/db/FileDatabase.ts` — one JSON file per collection, atomic writes, mutations serialized per instance) rather than SQLite. SQLite was the original "most likely" guess in this decision; a plain file-based store turned out to be simple enough for v1's scale (a handful of Projects, one active Task each) and keeps the daemon dependency-free. Revisit if querying or concurrent-write needs outgrow it. **Amended, 2026-10-09:** that need arrived for Building types with large data, which get a per-Building SQLite file instead (see [Bulk data layer](#bulk-data-layer-one-sqlite-file-per-building)); this store keeps the small records, and Software Projects are unchanged.

Human-readable documentation (notes, blueprint, decision logs) stays as per-project markdown inside each Project's own `.docs/` folder, kept apart from the runtime store. See [`docs/file-structure.md`](file-structure.md).

## Project testing contract: one framework-neutral config per Project

**Decided 2026-09-25.** A managed Project may be Python, PHP, Node.js, React, Astro or anything else, so the Testing tab can't know about any one framework. Each Project declares its Test Suites, Test Actions and Collectors in `<project>/.docs/testing/config.json` (schema version 1), and the web UI consumes only the normalized model the daemon returns. Framework-specific knowledge stays in the command a Project runs and the standard report it writes: JUnit XML, LCOV, Cobertura XML, SARIF, or the Agent Visual OS result JSON for anything else.

This follows the same split as [the runtime-state decision above](#one-central-runtime-state-store-docs-stay-per-project). The config is committed project knowledge, so it lives in `.docs/`. Test Run history and logs are mutable runtime state, so they live in the daemon's central data directory (`test-runs.json`). The daemon never caches or writes the config. It reads it fresh on each request because an agent or a person may edit it on disk at any time.

A missing config is a normal state (`absent`), not an error. A broken one comes back as `invalid` with every issue listed, so the UI can offer to repair it rather than just fail. Validation rejects absolute or `..` paths, invalid or duplicate ids, a missing or non-result primary action, and unknown schema versions or formats. Every report read is resolved inside that run's own artifact directory, symlinks included, so a config can't make the daemon read a file elsewhere on disk. The full schema, with examples, is in [`docs/testing-contract.md`](testing-contract.md).

### Test Run engine: one serialized test queue per Project

**Decided 2026-09-26.** `server/src/testing/testRunner.ts` runs Test Actions as plain shell subprocesses, like Project Commands, and adds what testing needs on top:

- **One queue per Project, one run at a time.** Unit, E2E, load and security suites are often heavy and may share ports, databases or browsers, so letting two overlap by accident costs more than waiting does. Project Commands stay unqueued, because a long-lived `npm run dev` must not block anything. The queue is in memory. Persisted `queued`/`running` records from a previous process are closed out as `error` (`interrupted`) at startup rather than resumed, since their results can't be collected any more and re-running a suite without being asked isn't safe. Finishing a run is idempotent and never throws, so a failure while saving one can't leave the queue stuck or start two runs at once. A run settles shortly after its command exits even when a background child holds its output open.
- **Own process group, killed on shutdown.** Each command gets its own process group so Stop reaches the whole tree it forks. That also hides it from a Ctrl-C to the daemon, so the daemon signals every running test itself on SIGINT/SIGTERM/exit. A hard crash can still leave one running.
- **Latest results describe the primary tree.** Agent runs in a Task's worktree go through the same queue and History, but never become a suite's latest result, since a half-finished change being red says nothing about the Project.
- **A result is only what a report says.** Collectors parse declared reports after the process exits. The exit code is kept next to the result instead of replacing it, because a failing runner almost always exits nonzero. A missing or malformed required report is `error`, not `failed`, so "tests failed" and "we don't know" are never mixed up.
- **Agent runs use the Task's own tree.** A run given a Task id executes in that Task's cwd/worktree and reads the config from there, so an agent tests the code it changed, not the primary checkout.
- **Small records, per-run files.** `FileDatabase` holds a whole collection in memory and rewrites the file on every change, so `test-runs.json` keeps only each run's metadata and a result summary. The log and the full result go to `server/data/test-runs/<id>.log` and `<id>.result.json` (`runFiles.ts`), appended or written once, and deleted with the run when it's pruned. That lets a log or a report be large without slowing every other write or bloating WS events. Only runaway output is cut (a 5,000,000-character head plus a 200,000-character tail), cases and findings have sanity caps of 20,000 and 5,000, and each Project keeps its newest 100 finished runs.
  *Amended 2026-09-26:* the first version stored logs and results inside `test-runs.json`, which forced much tighter limits (a 1,000-line / 64,000-character log tail, 500 cases, 200 findings).
- **Injectable side effects.** Spawn, artifact directories, report reads and git lookups are passed in (`TestRunnerDeps`), so tests never start a real process.

The status rules, REST endpoints and events are in [`docs/testing-contract.md`](testing-contract.md#test-runs).

**Amended 2026-10-03 (task 2.006, the Testing tab UI):** `mergeWorkerEvent`'s `testRunLog` case now actually streams, the same `commandRunLog`/`skillInstallLog` convention described above — a chunk appends onto `testRunLogsById[runId]` once that run's detail has been fetched (`loadTestRunDetail`), and is dropped for a run the client hasn't fetched yet (a WS reconnect gap; the next fetch picks up the full log fresh). The run drawer renders that live buffer through `lib/ansi.ts`'s `parseAnsi`, exactly like `CommandLogPopup` does. This replaces the tab's earlier 2-second poll of `GET /api/test-runs/:runId` while a run was active: the detail view now only refetches once, when the run's status (carried live by the ordinary `testRun` event) actually transitions, to pick up the full `result` a status-only event doesn't carry.

### Testing setup: an approval-gated Open Task

**Decided 2026-09-28 (task 2.005).** The Testing tab's "Set up testing" (config absent), "Reconfigure testing" (valid) and "Repair testing" (invalid) all start the same thing: an ordinary PlanItem, marked with `testingSetup: { mode }`, run through the built-in **testing-setup** workflow (`server/src/testing/setup.ts`) instead of the Project's own. It shows up in Open Tasks and goes through the ordinary plan-item queue, so it starts now or, when the Project is at its task limit, waits in the Project's waiting list. A second click while one is queued, running, awaiting approval or needing attention returns that one (serialized per Project, so a double click can't make two). A stopped (rejected) setup doesn't hold the queue, and a new one can be started.

The rule is that an agent never changes a Project's testing setup before the person has seen the consequences and approved them. The daemon enforces that; it does not rely on the prompt alone:

- **Read-only discovery.** The first step, Setup Proposal, is `canEditCode: false` with `requiresApproval: true`. Its session gets the planning-session denial list (Claude) or the read-only sandbox with no approval escalation (Codex), and no testing tools, because running a test action runs arbitrary project commands. This holds whatever autonomy the executor normally has. The step can't be skipped, and `complete_step` is refused without a non-empty proposal output. After it completes, the run's worktree must still be clean (`git status`). If it isn't, the run goes to `needs-attention`, nothing is committed, and nothing is offered for approval.
- **Only an explicit approval unlocks writes.** The implementation step is write-capable only while the latest proposal round carries an `approved` decision (`resolveStepPermissions`/`stepCanEditCode` in `workerManager.ts`). A testing setup fails closed: if the step can't be resolved or the approval is missing, the session is read-only. Only `POST /api/testing-setup/:runId/approve {proposalRound}` records that approval, and it must name the round the person was shown; an older round is refused. The generic `/workflow-runs/:id/approve` refuses a setup run. Feedback (`/revise`, the same request-changes resume) starts a new proposal round that is still read-only and has no approval, so writes stay locked until that round is approved. Reject (`/reject`) is a stop: nothing was committed before approval, so the Project is unchanged.
- **Approval covers the displayed proposal.** The implementation step's prompt carries every proposal round with its decision ("APPROVED by the person" on the approved one), and tells it to do only that. If a materially different change turns out to be necessary, it calls `complete_step` with verdict `issues`. The step is a loop origin back to the proposal step (up to 3 times), so this re-runs discovery read-only and pauses for a new approval, while the earlier approved round stays in history. "Continue anyway" past that loop is refused for a setup run.
- **Evidence before success.** `complete_step` with verdict `pass` runs `evaluateSetupEvidence` against the step's own working tree. The config must be valid, and every enabled suite's primary action must have a settled `passed` or `failed` run with a normalized result. That run must be an agent run from this setup's implementation step, so manual runs and other Tasks' runs don't count. A failed-but-parsed result counts, because it proves the action produces results, and its counts are shown. `error`, `stopped`, still-running and summary-less runs don't count. The evidence is saved on the run (`testingSetup.evidence`) either way, and the refusal tells the agent what is missing. A valid config with no suites is accepted; that is the "record that no tests are configured" choice, which the proposal must offer alongside "add a test foundation" when the Project has no tests. A retry after the implementation session ends early reruns it under the approval that round already has.

The workflow is defined in code, not in the Catalog, so a Catalog edit can't loosen it. `assertSetupWorkflowSafe` also refuses to start one whose approval gate is missing or comes after a write-capable step. The approved change is committed and pushed to the run's own branch like any other run, so the Testing tab, which reads the Project's checked-out branch, shows the new config once that branch is merged or checked out.

## Concurrent tasks per project

This section started as "one task per project in version 1". Originally: only one active Task was allowed per Project at a time, full stop. Multiple Workers sharing one project's working directory at once is a real source of file and git conflicts, and the standard fix — an isolated git worktree per Worker — was deferred until concurrent Tasks on one Project were actually supported.

**Amended, 2026-09-14:** implemented via isolated `git worktree`s, following the conceptual pattern of two existing tools found during research, `claude-squad` and `crystal` — one git worktree + branch per concurrent agent session on the same repo. The restriction that remains is deliberately conservative, not "gone":

- A git-backed Project's **first** concurrently active Task still runs directly in the Project's own primary working directory (`projectAbsolutePath`), on whatever branch is already checked out there — no worktree overhead for the common single-Task case, unchanged from the original v1 behavior.
- Only once a Project **already has** an active Task does starting another one create a fresh isolated worktree (`git worktree add -b task/<taskId> <worktreePath> <baseBranch>`, branched off whatever the Project's own directory currently has checked out) instead of refusing the start — up to a fixed cap (`MAX_CONCURRENT_TASKS_PER_PROJECT` in `server/src/worker/taskConflicts.ts`, currently **6**, raised from 3 on 2026-10-13) per Project. The cap is one value in one place; it is not configurable per Project. What counts toward it: coding Tasks that are live (developing, or waiting for the person's answer or approval, which still hold their slot) and runs still starting up. Planning sessions and conflict-resolution runs do not count, and a stale record that claims a slot but is not live is never counted or listed.
- A Project with **no linked repository** has no git repo at all (`git worktree` needs one), so it keeps the original strict limit of **one** Task unconditionally — running Tasks side by side needs the isolated per-Task working copy a repository provides, and there is no way to isolate a second concurrent Task's working directory there.
- Each worktree Task's own working directory (`TaskRecord.worktreePath`) is threaded through everywhere a running Task's cwd matters — the turn itself, the branch-drift check, and `commitAndPush` — instead of always assuming `projectAbsolutePath(project)`.
- **Interim commits (2026-09-25):** `interimCommitTask` (`POST /api/tasks/:taskId/interim-commit`) runs the same `commitAndPush` against an ongoing (`developing`/`blocked`) Task's own working directory with the message `Interim Commit <ISO timestamp>`, without settling the Task. It is refused (409) for a settled Task, whose worktree may already be gone, and for a Project with no repository.
- **Cleanup policy:** once a worktree Task settles (`done` or `failed`), its worktree *directory* is removed (`git worktree remove --force`) to free disk and avoid an orphaned worktree entry, but its *branch* — and anything already pushed to it — is left exactly where it is. Nothing auto-merges a worktree Task's branch into the Project's main branch; a human (or a future roadmap item) reviews and merges it, the same way the original single-Task flow already just pushes a named branch rather than merging it. This matches claude-squad/crystal's "isolated, reviewable work" model, not silent auto-integration.
- A Project's aggregate `status` (`idle`/`developing`/`blocked`) is now computed over however many Tasks are currently active on it — `blocked` wins if any of them is, `idle` only once none are. It's derived from each listed Task's live `status`, not from list membership alone: every settle/refresh (`reconcileActiveTasks` in `server/src/worker/workerManager.ts`) drops ids whose Task is no longer `developing`/`blocked` (or no longer exists), so a stale entry can never pin a Project in development. `ProjectRecord.activeTaskId` is kept, meaning "the most recently started Task that is still active," for backward compatibility with UI built around "the" one active Task per Project; the full set now lives on `ProjectRecord.activeTaskIds` for any future UI to use. **No such UI was built as part of this change** — the existing single-Task UI (the Tasks tab, footer counts, the `project.status === 'idle'` gating on "Assign a task"/"Start a new planning session") is untouched, and since it never offers a way to start a second concurrent Task in the first place, it keeps behaving exactly as it did before this change; the new capability is reachable today only by calling `startTask`/the API directly. A Task-list-per-project view and per-worktree diff/merge UI remain explicitly open follow-up work.
- **Known open risk, not resolved here:** `followUpTask` resumes a settled Task's CLI session (`--resume`) but is assigned a *fresh* workspace (the Project's own directory if free, otherwise a new worktree) since the original worktree — if the prior Task had one — is already gone by cleanup time. Whether the `claude` CLI's session storage is keyed in a way that tolerates `--resume` running from a different working directory than the one the session originally ran in was not verified against real CLI behavior (no network access during this change). This was always a non-issue pre-worktree, since every Task on a Project shared the exact same directory for the Project's whole lifetime; it is a new edge case introduced by this change, worth a dedicated look before leaning on it.


**Amended, 2026-09-25:** only file-writing Tasks count. A `'plan'`-kind planning session never changes project files, so `claimConcurrencySlot` in `workerManager.ts` lets it start (or follow up) while any number of coding Tasks run, even on a Project with no linked repository. It always reads the Project's own directory, never gets a worktree, and never counts toward the cap or pushes a later coding Task into a worktree. It still joins `activeTaskIds`, so the Project's aggregate `status` shows it as active. The Planning prompt (`web/src/ui/project-popup/PlanningPrompt.tsx`) no longer waits for the Project to go idle.

**Amended, 2026-10-13: refusals have their own identities.** `TaskConflictError` is now the base of two errors, each answered as HTTP 409 with the usual `error` message plus a `code` and `details` the web reads instead of parsing text:

- `task_limit_reached` (`TaskLimitReachedError`): the Project is at its cap. Starting a task through `POST /api/plan-items/:id/execute` or `start-when-ready` no longer answers it (the start joins the waiting list); other starts, such as resuming a run, still do. `details` has the limit, how many are in use, whether the Project has a repository, and the occupying Tasks (task id, plan item id, number, title, state `starting`/`running`/`waiting_input`).
- `session_still_running` (`SessionStillRunningError`): archiving or completing a planning session (or deleting one) while one of its Tasks is live. `details` names that Task.

Completing or archiving a planning session that is already complete or archived, and restoring one that is not archived, succeed without changing anything. A waiting task that cannot start because of the cap stays on the waiting list at the front and is retried when the next slot frees; it also raises one project-scoped `task.limit_reached` notification, which resolves when a queued start succeeds or the queue empties. No user-facing message links to documentation.

See [`docs/roadmap.md`](roadmap.md#scale-out--multi-project).

## Read-only terminal transcript in version 1

Each Worker's terminal-style output pane is built by rendering the parsed `stream-json` event stream as formatted text through `xterm.js` used purely as a display widget. There is no live, interactive PTY (`node-pty`) session behind it in this version, so there is no way to type directly into a Worker's session. A real interactive escape hatch is a plausible later addition, deferred partly because it would also require deciding how typed input interacts with the autonomy setting, which is not resolved for that mode. Full rationale for the rendering and streaming choices: [`docs/research/game-rendering-and-terminal-streaming-options.md`](research/game-rendering-and-terminal-streaming-options.md).

**Amended, 2026-09-13:** built as a chat thread, not an `xterm.js` terminal pane. Once the wave-and-popover-into-chat flow and the Task Details view were actually built, rendering `stream-json` as raw terminal text turned out to fight the "this is a conversation with an agent" framing those interactions need — a person answering a blocked question, or replying to a finished Task, reads that exchange as chat turns, not a scrollback log. The transcript's `'prompt'`/`'answer'`/`'result'` turns render as chat bubbles (`ProjectWorkspaceModal.tsx`'s `TaskDetailsView` — see the amended "A Building's click opens its full Project Workspace directly" entry above for why this is the only place that renders them now); `'raw-event'` turns (the full parsed `stream-json` stream — tool calls, thinking, intermediate assistant text) are still recorded in the transcript in full and still "read-only" per the original decision, but surfaced as a plain count ("N tool/status events not shown") rather than rendered inline, since a live terminal-style playback of every tool call added noise without adding to what a person actually needed to decide something. No `xterm.js` dependency was added.

The backend and frontend both use Node.js and TypeScript, avoiding a two-language stack for a tool built and maintained by one person.

## Three.js and React Three Fiber for the scene

The scene is rendered in Three.js, with React Three Fiber for the React integration layer, populated with free, stylized-but-three-dimensional low-poly asset packs (Kenney's city and character packs, Quaternius, or similar) rather than flat pixel sprites, with real lighting and shadows. This was chosen over 2D sprite frameworks like Phaser or PixiJS specifically because the goal is a scene that reads as dimensional and clean, not as 2D pixel art, and true 3D rendering is the only one of the options considered that can deliver that regardless of art quality. This will look like a clean, modern 3D city-builder scene, not photorealistic visuals; genuinely photorealistic rendering would need an art budget this project does not have. Full comparison of Phaser, PixiJS, and Three.js: [`docs/research/game-rendering-and-terminal-streaming-options.md`](research/game-rendering-and-terminal-streaming-options.md).

## The 3D village shows work, not buildings: a warehouse per Project in its own yard

**Added, 2026-10-18 (task 13.001).** The village used to show each Project as an office tower with a ring of up to six robots, one per Running or Needs-you task. It told the person that something was happening, but not what was in flight, at which step, what was waiting on a merge, or which commands were running. Each Project is now a warehouse with a tinted roof in a yard with three fixed areas: work (a box per task, a machine per command run), merge-wait (robots holding finished work whose PR is open) and planning (robots at laptops). The rules live in pure helpers (`web/src/lib/villageYard.ts`, `villageLayout.ts`) so they are unit-tested without a WebGL harness; the scene only draws what they return. The cards view stays the accessible, non-3D overview and is unchanged.

Decisions behind it:

- The yard derives its state from the Tasks board's own grouping (`buildTaskGroups`) but splits it differently. A task with Auto-merge failed or can't merge is in the board's Needs you, but its PR is still unmerged, so the yard shows it as merge-waiting; a failed or stopped run is also Needs you on the board but a red box in the yard. The spec's merge-wait rule wins over the board's grouping wherever they differ.
- Areas are fixed and always reserved, and slots are sticky: priority decides which items show, but an item keeps its slot until it leaves, so nothing shuffles while work comes and goes.
- Plots are streets, not blocks. The village used to be 32 plots in a grid of blocks with domes, hills and a fixed 8-groups-of-4 cards view, which capped the number of Projects and looked nothing like a town. It is now 12 streets with a left and a right side of 10 yards each (240 plots, generated from street, side and slot in `townLayout.ts`), a flat grass plain with fences, trees, rocks and water, and a world much larger than the camera frame. A Project is a rectangular warehouse with a pitched roof; the tint (Building Type) is on the roof and the status colour on the eave trim and lamp. Instancing keeps the scenery to a few draw calls and nothing uses per-plot lights or shadows. Saved block-grid positions are moved once to the street plots nearest City Center in their old order (the daemon at startup, the web app on load) rather than left unreachable, which is why the old and new coordinates are guaranteed never to coincide. The 2D view follows the same street model (`townGroups.ts`), so a move in either view shows in the other.
- A failed run's red machine stays until someone opens its log, which needs a stored per-run flag (`failureUnopened`) so every browser and a reload agree. That, and the agent-supplied `short` checklist label behind the tag's step summary (`currentLabel`), are the two read-only-in-spirit server additions the redesign needed; neither changes how runs, tasks or merging behave.
- Each yard reads only its own Project's command and test runs, compared field by field on what the yard shows (`sameYardCommandRuns`/`sameYardTestRuns` in `useYardModel.ts`). A command's streamed log replaces its run on every chunk; comparing whole runs would re-derive every yard per chunk.
- The yard robot is the animated RobotExpressive glTF model (`web/public/models/`), as before the redesign. `robotClips.ts` maps each `RobotPose` to one of its clips (`Walking`, `Wave`, `Sitting`, `Idle`; a working robot plays `Idle` while a small wrench in its right hand turns slowly); holding a box reuses `Idle` with the box placed in front of the robot, and a waiting robot adds an amber ring and light.

## Configurable task Workflows replace the docs-and-retro completion step

**Added, 2026-09-26 (task 3.012).** Every executed PlanItem now runs through a **Workflow** — an ordered list of **Steps**, each run by exactly one Catalog agent, each getting every earlier stage's outputs as input and producing its own summary + output. A Step that can edit code (Development, Docs & Retro) changes code; every other Step is read-only. Workflows are defined in the Catalog (`catalog/workflows/<id>.json`, `server/src/catalog/workflowService.ts` — same CRUD/validation/sidecar-metadata shape as Templates and Skills) and each Project selects one (`ProjectRecord.workflowId`, null meaning "the Catalog default," `software-development` if enabled, otherwise the first enabled Workflow). This supersedes the classify/gates/rca-review/retro-FIFO-queue proposal in `docs/milestones/milestone-9-workflow-catalog.md` (now marked superseded) — that document's mechanism was never built; this is the mechanism that shipped instead.

The seeded default, **Software Development** (shipped as editable configuration; the steps below are its current shape, not a contract): UI Planning (approval) → Test Case Planning → Development (edits code) → Code Review (loops back to Development, max 3 rounds) → Docs & Retro (edits code) → Complete (built-in: commit, push, raise PR). Since task 38.003, UI Planning's summary lists every change to existing wording, labels, states or behaviour with a reason (anything the spec does not call for keeps today's text), an "Owner decisions" section from the UI review, and any difference from the task specification, which wins unless an Owner decision says otherwise. Test Case Planning is told those, the spec and `.docs/` are its sources of truth and where the spec states testing expectations, contracts and baseline; it can still ask the owner and raise `planningGap`. Development treats the Owner decisions as binding.

The built-in **Bug Fix** workflow (task 5.009, `catalog/workflows/bug-fix.json`, enabled but never the default): RCA (read-only; its main output is an "RCA report" Markdown artifact) → RCA Review (loops back to RCA, max 3 rounds) → Fix (edits code; regression tests where they apply) → Bugfix Review (reviews the diff against the RCA report; loops back to Fix, max 3 rounds) → Docs & Retro (edits docs only) → Complete. It reuses the software-engineer and documentation-n-retro-agent agents. The RCA report reaches later steps through the normal earlier-stages history, which shows every RCA round in full because RCA is a loop target.

**Requirement analysis is the planning session, not part of a Workflow.** (Revised, 2026-09-27: Workflows used to carry a fixed `requirementAnalysis` stage config and runs a `requirementSource`; both were removed.) A Workflow is only its configurable steps. A `'plan'`-kind Task runs with the agent/skills/executor chosen at session start, or the Catalog defaults, plus `PLAN_INSTRUCTIONS` and the resolved Workflow's step list; its output, each plan item's description, is the specification the first step receives as its input. `PlanItemRecord.planningTaskId` still records which planning Task created an item, for the Tasks board's provenance label. Older Workflow files and runs that still carry the removed fields load normally: `workflowService.ts` strips `requirementAnalysis` on read (so the next save writes the file clean), and nothing reads a stored run's `requirementSource`. The planning prompt (`PLANNING_SESSION_PURPOSE` in `plan.ts`) also now states the one-task rule: one task when the work is related, several only when genuinely distinct features are being discussed — and tells the planner which Workflow steps each task it creates will go through, so descriptions serve those steps directly.

**The run engine** (`server/src/worker/workerManager.ts`, extended rather than given a parallel module, since it already owns Task lifecycle/worktree machinery a WorkflowRun reuses wholesale): `executePlanItem` creates a `WorkflowRunRecord` instead of a bare execute Task. The run snapshots its Workflow (`workflowSnapshot`) at creation so a later Catalog edit never changes an in-flight run. By default it gets its **own branch in its own git worktree** (`createBranch: true`; `false` works in place, see the amended queue section above), named `<type>/<ref>-<slug>` (or `<type>/<item id>` for a task added by hand) off the Project's current branch, where `<type>` is the Workflow's optional `branchType` (a lowercase slug; `bugfix` for Bug Fix) and defaults to `task` — reusing exactly the worktree/branch machinery "One task per project in version 1" (above) already built, just keyed to the run instead of a single Task. **No stacking (B.020):** every run branches from the Project's own branch and its PR targets that branch. A task that has dependencies (task 10.018, [dependent tasks](dependent-tasks.md)) waits until its parents' work is merged into the checked-out branch and starts from there. A run stacked before this change keeps its parent's branch as `baseBranch` (and as the PR base on a retry), and fails to open its PR if that branch is gone. A repository-less Project runs with no worktree/branch/PR machinery at all, same as today's no-repo Task path. A running step takes one of the Project's concurrency slots like any Task; an in-place run also keeps the project folder to itself until it settles.

Each Step becomes a `StepRunRecord` (`round` starting at 1, incrementing whenever the step runs again in the same run: a loop re-run, Request changes, a resumed stop, or a manual retry — every round kept, never overwritten, so later prompts and the UI's stepper see the full history) and one Task, reusing the run's own worktree/branch rather than allocating a fresh one or taking a second concurrency slot. The **prompt** is built by a pure module, `server/src/worker/workflowPrompt.ts` — task title/description, the Step's instructions, every earlier stage's latest summary and outputs (all rounds for a loop's target step, so Development sees the full review history; outputs are referenced by file path, see below), the branch/base, and whether the Step may edit code. Permission enforcement for a non-code-editing Step reuses `PLAN_DISALLOWED_TOOLS`/Codex's read-only sandbox verbatim — a Step is, mechanically, the same restricted-session shape a `'plan'` Task already was.

**The MCP relay generalizes the planning session's own** (`terminal/planTaskTool.ts` → `terminal/stepTaskTool.ts` + `bin/step-task-mcp.mjs`, same session-scoped-stdio-server-behind-a-bearer-token pattern, wired into both `claude -p --mcp-config` and `codex exec`'s existing `codexMcpArgs`). A Step session calls `complete_step({summary, outputs?, verdict?})` (verdict required only when the Step is a loop origin) or `skip_step({reason})` (no approval needed even on an approval-required Step), and can page through the branch diff with `diff_summary()`/`diff_file({path})` rather than having the whole diff pasted into its prompt. A session that ends without calling either is marked failed/stopped and the run goes `needs-attention` — a real behavior change from a plain Task's stop semantics, since a Step's own session ending isn't itself a valid way to finish a Step.

**Required outputs (B.036):** a Workflow step may set `requiredOutputFormat: "html"` (the seeded Software Development's UI Planning does). `complete_step` on such a step is refused with 422 (`StepOutputRequiredError`, `worker/requiredOutputs.ts`) unless at least one output has `format: "html"` and `content` that, trimmed, contains `<!doctype html`, `<html` or `<body` (any case), is at least 100 characters, and is not a placeholder (`PLACEHOLDER`, `TODO`, `TBD`, `...` or `…`, any case, alone or wrapped only in tags). A mockup whose markup has no visible text at all (for example SVG only) is refused as a placeholder too. The refusal is checked before anything is recorded: the round stays `running`, the run does not advance, no approval is requested and the session stays open, so the agent sees the message (which names each rejected output and how to send a mockup) as a tool error and retries in the same conversation. `skip_step` is not affected, and a step without the field keeps outputs optional. Separately, `POST /api/workflow-steps/complete` answers 400 when `outputs` is not an array of `{name: non-empty string, format: "markdown" | "html", content: string}` (`api/stepOutputs.ts`); a JSON string holding such an array is parsed and accepted. Read-only step prompts say the read-only rule covers project files only and that `complete_step` outputs are not files.

**Live progress (task 5.017):** the same relay also carries `report_progress({checklist?, currentActivity?, estimate?})` — a checklist, a one-line current activity, and an optional time estimate, wholly replacing the round's previous progress on every call (never merged, never kept as history). It is authorized the same way as `complete_step`/`skip_step` (the calling round must still be its Project's running, active Task — settled, stopped or reopened-for-inspection sessions are refused) and writes only `StepRunRecord.progress` plus a denormalized `WorkflowRunRecord.currentStepProgress` summary (cleared whenever a new round starts), so the Running board card can show "N/M · ~estimate" without loading the run's full detail. Both updates ride the existing `stepRun`/`workflowRun` WorkerEvents, so the run view's live split (progress panel beside the session while a round is running, or beside a finished-without-summary session that has any) and the board card update the same way any other live field does — no new event type.

**Advancing, approvals and loops:** after a code-editing Step, its changes are committed (`<ref> <step name>: <summary line>`). A Step with `requiresApproval` pauses the run `awaiting-approval`; `POST /api/workflow-runs/:id/approve` continues exactly like an ordinary completion; `/request-changes` records the decision and comment on the approval step's round, then starts a new round of the step named by that approval step's optional `requestChangesToStepId` (which must be an earlier step, validated when the Workflow is saved), or of the approval step itself when unset. From that step the run carries on forward as usual, through any review loop in between, and the approval step waits for a decision again. Code already committed on the run's branch stays; new fixes are added on top. A testing setup run ignores the setting and keeps its own proposal rules. A loop-origin Step's `verdict: 'issues'` jumps `currentStepId` back to `loopBack.toStepId` and lets ordinary forward advance replay every step up to and including the loop step again — an emergent property of the same linear-advance code path, not a separate replay queue — up to `loopBack.maxRounds` before the run pauses `needs-attention`; `POST /api/workflow-runs/:id/loop {action: 'another-round'|'continue'}` resolves it, `another-round` bumping a `loopRoundAllowance` human-override budget (deliberately not part of the public Workflow definition — a fixed cap the person can consciously override, not a soft limit). `/retry-step` and `/stop` round out manual recovery.

**Later rounds continue the step's session.** Whenever a step starts round 2 or later in the same run, `startStepTask` continues the CLI session of that step's latest earlier round (`--resume`) and sends only what is new (builders in `workflowPrompt.ts`): the step making a fix gets only the feedback, meaning the reviewer's latest issues (`buildReviewFixMessage`, plus the comment of a "run another round" override) or the person's Request changes comment (`buildChangesRequestedMessage`); any other re-run step gets a short note plus the latest round of each earlier step that ran again since (`buildRerunMessage`). A reviewing step's note asks it to re-review the current changes and give a new verdict. A stopped run's resume sends a plain "Continue." The rule is generic, not tied to step names. The session can't be continued when the earlier Task has no session id, ran on a different executor, or the CLI no longer has the conversation on disk (`cliSessionExists` in `terminalSessionManager.ts`, checked through the host's optional `sessionExists`). The round then starts a new session with the full step briefing and the same message appended to the instructions ("Continue." is not appended), so the run still progresses. Retry continues the latest round's session with a short "previous attempt was interrupted or failed … Continue." message when that round ended unfinished (failed, stopped, or still running with a pending question, whose live session is stopped quietly first); after a finished round, or when the session can't be continued, it starts fresh with the full briefing. Tools, permissions, verdict rules, round numbering and the loop budget (every round of the loop step in the run counts, including rounds after going back) are unchanged. An inspect session reopened on that conversation is stopped and its process exit is awaited before the later round starts; live process ownership is checked by CLI session ID across Task records. Each Task captures its launch prompt, permission and executor settings; a later round that continues its conversation reuses those settings even if the Catalog or executor configuration changed.

**Earlier outputs are referenced by file path, not pasted (task 5.020).** Every step output (HTML mockups, Markdown lists and reports, from any Workflow including Catalog ones and testing setups) is saved once, when a later prompt first references it, by `server/src/worker/stepOutputFiles.ts` at `<data dir>/step-outputs/<projectId>/<runId>/<stepId>/round-<n>/<output slug>.<html|md>` (slugged names, `-2` for a clash, `output-<n>` for an empty one, files mode `0444`). That's the daemon's data directory, never a project repository or worktree, so the files are never committed or in a branch diff. The full briefing and the re-run message list each output's name, format, approximate size (lines, plus KB when large) and `Absolute path:`, with a hint to read it only if relevant and partially when large; summaries, verdicts, decisions and planning gaps stay inline. The review-fix and Request changes messages carry no outputs. If a file can't be written the step still starts, that output is pasted inline as before, and the failure is logged. Every step session (and a reopened one) may read its run's folder without prompting: Claude gets `--allowed-tools Read(//<run folder>/**)` and `--disallowed-tools Edit(//<run folder>/**)` (deny rules hold even with `--dangerously-skip-permissions`); Codex needs no flag, since every sandbox mode reads the whole disk and the folder is never a writable root. With Codex's sandbox bypassed (auto autonomy) or Claude's Bash, only the read-only file mode stands in the way of a write. Deleting a task removes its runs' folders, deleting a Project its whole folder, and a rolled-back start its run's folder; a failed removal is logged and never blocks the deletion. The run view keeps reading outputs from the StepRun records, so it never depends on these files.

**The Complete stage is built-in, not a WorkflowStep**: commit any remainder, push, `gh pr create` (base = the run's saved `baseBranch`, the Project's own branch, or `main` if unset; title `<ref> <title>`; reusing an already-existing PR for the branch rather than erroring; skipped entirely for a repository-less Project). Its body (a TL;DR line, then Requirement / What's done / Review highlights) comes from a headless summarizer, `server/src/worker/workflowSummarizer.ts`, in the same "build a prompt, run a non-interactive turn, parse structured JSON" style `planItemTitler.ts` already established — falling back to stitching Step summaries together directly, one `###` heading per Step, if the summarizer's turn fails or its JSON doesn't parse. **This subsumes and replaces the old docs-and-retro completion flow entirely** (`COMPLETION_DOCS_RETRO_QUESTION`/`runDocsRetro`/`DocsRetroState`/the Yes/No completion prompt and its dedicated route are gone): the same "does this Task's finished work get documented and retro'd" question is now just the Docs & Retro Step, an ordinary code-editing stage in the Workflow like any other, and finishing a run always ends at the same built-in Complete stage rather than a special per-Task confirmation dialog.

**One house style for every agent-written summary**: step summaries, skip reasons, Markdown step outputs, an approval step's brief, and the completion report/PR body all follow the rules in `server/src/worker/summaryStyle.ts` (TL;DR first, short `###` sections, lists, tables, blockquotes for what must not be missed, plain language). The rules are injected by the daemon — appended after every step's own instructions in `buildStepPrompt`, plus review and approval-brief rules for loop-origin and approval steps, and given to the summarizer — rather than written into each Workflow step, so Catalog Workflows the person wrote get them too.

A run's status maps onto its PlanItem the same way a bare Task's status always did: `developing` while `starting`/`running`/`held`/`completing` (`held`: an early UI Planning run waiting for its parents, see [dependent tasks](dependent-tasks.md#early-ui-planning)), `blocked` while `awaiting-approval`/`needs-attention`, `done`/`failed` once terminal. `workflowRun`/`stepRun` events broadcast over the existing single `/ws` connection, the same "one event bus, more variants" pattern every other producer here uses; a run entering `awaiting-approval`/`needs-attention` raises a `workflow.awaiting_approval`/`workflow.needs_attention` Notification (`domain/types.ts`'s `NotificationKind` — two of the three kinds that extend the notification redesign's own spec to cover this pre-existing producer), resolved once it leaves that state. Restart recovery treats a `running` run whose current Step's Task is gone as an orphan → `needs-attention`, the same spirit as the pre-existing Task restart recovery, not a silent resume.

**Where this leaves the Project Workspace UI:** Tasks opens by default as a four-column board: **Planning**, **Running**, **Needs you**, **Completed**. Planning has **Plan & bugs** and **+ Task**; its numbered conversation groups and standalone tasks share a persisted top-level order. Ready tasks created by a conversation nest beneath its card, in the user's group order (new ones last), with ready and history counts; started and completed work appears only in its actual execution column. Cards open their detail views, where applicable start, stop, edit, completion, archive, restore, and delete actions live. Archived is one mixed view of completed planning conversations and archived tasks, with planning clearly labelled and each restored independently. Opening a row with a WorkflowRun shows the full run detail view: a Stepper across every stage (with round counts on a looping one), each stage's Summary/Output/Session tabs (an HTML output artifact rendered in a sandboxed `srcdoc` iframe **without** `allow-same-origin`), and the approve/request-changes/loop/retry/stop actions. The Catalog has a Workflows tab (list/create/edit/delete/enable), and Project Workspace has a **Settings** top tab for Workflow selection and Commands.

## Starting a task returns at once; the slow setup is visible start-up steps

**Decided 2026-10-11 (task 11.001).** `POST /api/plan-items/:id/execute` used to hold the Start task dialog until a headless model had named the branch, the worktree had been checked out and the agent had launched. It now returns after only the fast local checks (the Workflow has a runnable first step, the agent exists and is supported, required skills are usable, the concurrency cap and the "project folder is busy" rule, a repository when a branch is asked for). A refusal there behaves as before: the dialog stays open with the reason and the task keeps its exact place in Planning.

An accepted start records the run as **Starting**, moves the item out of Planning and returns the run. Its `startup` field lists the steps, each `pending`, `running`, `done` or `failed`: *Choosing branch name*, *Creating worktree*, *Installing CLI hooks*, *Launching agent*. A start with no new branch (the project folder, or a repository-less project) has only the launch step; a conflict-resolution run has worktree, hooks and launch. Once the agent is launched the run is an ordinary Running run on its first step. The Project lock covers only the checks and the slot claim, so two starts never wait on each other's slow work. A Starting run holds a concurrency slot (and, for the waiting list, that slot) from acceptance.

- **Branch names have no model call.** `<type>/<ref>-<title slug>`, with `-2`, `-3` suffixes for a clash; the type is the Workflow's fixed branch type or `feature`. A retry reuses the item's existing branch.
- **The base branch is read in the naming step** under the repository lock and saved on the run with the branch name, so a resumed start-up creates its worktree from the saved base. A start-up saved by an older version with a `stack` step is read without it (`normalizeStartup`).
- **Naming and worktree creation run one at a time per Project**, so two starts can neither pick the same branch name nor race inside one repository. They do not hold the Project lock.
- **A failed step ends the run Failed**, with the step name and reason on the card and detail. The attempt's worktree, its branch (never one reused from an earlier run), its first-step task rows and its active-task bookkeeping are removed, and the slot is released. A "Task failed to start" attention notification is raised. The item stays out of Planning. Retry sets the same run up again from its first step.
- **Stop during Starting** marks the run Stopped at once and frees the slot; the in-flight step finishes and its work is undone. If the agent had already launched, it is stopped like a running run's and its worktree is kept. Resume of a run stopped while starting sets it up again from the first step.
- **A daemon restart while Starting** settles the run as Needs attention ("The daemon restarted while this task was starting."), with its partial worktree and branch removed rather than reused. Retry sets it up again.
- **Records from before this change** have no `startup` field and read as they did.

## A finding that may reduce how much of this needs to be hand-built

While running the Phase 0 spike, `claude --help` turned up native commands for managing background sessions, not just the `-p`/`--resume` primitives the design above is built on:

- `claude --bg` — starts a session in the background and returns immediately
- `claude agents --json` — lists every active session, interactive and background, with pid, working directory, and status
- `claude logs <id>` — prints a background session's recent terminal output
- `claude attach <id>` — opens one in the current terminal
- `claude stop` / `claude rm` — end one
- `-w`/`--worktree` — creates a git worktree for a session directly (the exact mechanism Phase 4 expects to build by hand)

This was not part of the original research and was not exercised deeply — `claude agents --json` was only used to confirm the command works and check for stray sessions, not to build against. **This needs a dedicated, deeper look before Phase 1 starts**, since if `claude logs <id>` gives usable structured output and `claude agents --json` gives reliable status polling, a meaningful chunk of the planned `server/` subprocess pool, status polling, and possibly the read-only terminal transcript might already exist as CLI primitives to build on rather than reimplement.

**Caveat:** this build (v2.1.269) is a customized build with several tools (background session management, cron, remote triggers) not part of the plain open-source Claude Code CLI. Don't assume these commands exist on a different install without checking `claude --help` first.

## Per-project GitHub account

A Project can be tied to one `gh` account (`ProjectRecord.githubAccount`, absent or null = machine default). The daemon never switches the global `gh` account or edits global git config. `server/src/github/context.ts` holds an `AsyncLocalStorage` scope with the account's token and commit identity; `withProjectGithub` (`github/accounts.ts`) opens it per operation, and `git()`/`gh()` in `projects/git.ts` build the child environment from it, so two operations on different projects at once cannot see each other's credentials. Agent sessions get the same variables through `githubSessionEnv`. Failures classify into signed-out, no-access and private-email messages; nothing falls back to another account. `server/src/redaction.ts` is the dependency-free list of secret values scrubbed from logs, errors, command output and terminal output. Details of what each operation receives are in `.docs/blueprint.md` under "GitHub accounts (per project)".

## Read-only workflow steps may run commands (task 22.002)
A workflow step may set `canRunCommands` ("Can run commands" in the workflow editor; absent reads as off, validated as a boolean like `canEditCode`, 400 on the workflow routes). It lets a step that may not edit code run shell commands (install dependencies, run tests, build) and use the registered testing tools; it gets no file-editing tools and is not a write step: never committed or pushed, no change to what Complete does, and its prompt keeps the read-only wording but says it MAY run commands, that files those commands create or change are not committed, and that it must not use commands to edit source files. The shipped `software-development` Code Review step and `bug-fix` Bugfix Review step set it (task 39.001, still not edit-capable): they install dependencies, run the registered test suites and the diff's own tests themselves, and compare their counts with the earlier step's claimed counts; a mismatch, failure or missing planned case is an "issues" verdict. Browser checks are not part of Code Review yet. With `canEditCode` also on, the step is an ordinary write step. Planning, bug report and testing-setup proposal sessions cannot get it (a setup run ignores the field and stays fail-closed read-only; if its working tree changes, the run still needs attention).
- **Claude:** `--disallowed-tools Edit,Write,NotebookEdit` only; the shell stays allowed. **Codex:** `--sandbox workspace-write -c sandbox_workspace_write.network_access=true --ask-for-approval never` (the plain read-only sandbox cannot install or use the network), whatever the autonomy.
- **Not enforced:** a shell can write anywhere the user can, so "don't edit source files" is guidance in the prompt plus denied edit tools, not a guarantee. Tracked-file changes made by commands (for example a lockfile) are ignored: nothing resets, flags or blocks them. They stay in the run's working copy and the next write step's commit may include them; installed dependencies and build output also remain for later steps.
- **Reopened sessions:** a settled command step offers the same with-permissions or read-only choice as a write step; read-only stays fully read-only (no shell, no tests), "with permissions" means shell, no edit tools and the testing tools. `sessionSetup.canRunCommands` records the option; a stored setup without it stays read-only.
- **Shipped Bug Fix workflow:** the RCA step has the option on and is told to install dependencies, run the tests to reproduce and to establish which fail before the fix, and record the commands and results in "Reproduction" and "Tests". Catalog workflows are read live from `catalog/workflows` by id; Projects do not keep their own copy, so the change reaches every Project's next run (runs in progress keep their snapshot). A locally edited `bug-fix.json` is changed only by merging the new file, never overwritten by the daemon.
- **Open limit (owner: the person):** a manual check with the real Claude and Codex CLI that RCA installs dependencies, runs the test action and edits nothing by tool. Tests cover argument lists only.


## Workflow steps may use a headless browser (task 39.002)
A workflow step may set `canUseBrowser` ("Can use browser" in the Catalog workflow editor, a "Uses browser" badge on the project Settings step row; absent reads as off). It is validated as a boolean like `canRunCommands`, and `true` is refused (400 on the workflow routes) unless the step also has `canEditCode` or `canRunCommands`, because starting the app needs a shell. The flag travels in the run's `workflowSnapshot`; the shipped `code-review` step in `catalog/workflows/software-development.json` has it on (no other shipped step does). A testing-setup run never grants it.
- **Server:** `server/src/terminal/browserTool.ts` registers the Playwright MCP server (`@playwright/mcp`, pinned exactly in `server/package.json` `optionalDependencies` and as `PLAYWRIGHT_MCP_VERSION`) as session MCP server `agent_visual_os_browser`, run from the daemon's own install with `--headless --isolated`, so it never touches the owner's Chrome profile. `--output-dir` is `<data dir>/browser-output/<task id>` (screenshots, traces), never the worktree. Its tools are an explicit list (navigate, snapshot, click, hover, type, fill_form, press_key, select_option, wait_for, take_screenshot, resize, console_messages, network_requests, handle_dialog, tabs, close) added to Claude's `--allowed-tools` and to Codex's per-tool approvals; arbitrary-code, file-upload and storage tools are not offered.
- **Install:** `cd server && npm install` (the package is an optional dependency) and `npx playwright install chromium`. If either is missing or the version differs, `sessionMcpServers` logs a warning, leaves the server out and the session still starts; the step prompt then says the browser is unavailable and tells the agent to report browser checks as unverified. The check runs at session launch, never at catalog save.
- **Prompt:** `buildStepPrompt` adds a "# Browser" section for a flagged step: start the app from the documented run command or saved Commands on a free port, wait for the URL, drive the browser, check every mockup-described screen and state (empty, error, loading, a narrow width when breakpoints are named), report what was checked, treat missing behaviour as an issue, mark checks unverified when the app cannot start, and skip with one line when there is no UI.
- **Cleanup:** the instructions require stopping the dev server before `complete_step`. As a backstop, a flagged session starts with `killProcessGroupOnExit`, and `terminalSessionManager` calls `terminateProcessGroup` (`commands/processGroup.ts`, SIGTERM then SIGKILL after `STOP_GRACE_MS`) on the CLI's PTY process group when the CLI exits. A server the CLI moved into its own session or group (for example with `setsid`) is not reached.
- **Code Review:** when the diff touches UI it starts the app and checks the changed screens against the approved UI Planning mockups and the summary's "Owner decisions" and "Changes to existing UI" lists; a mismatch is an `issues` item naming the screen, the state and the difference.
- **Not yet implemented:** attaching browser screenshots to step outputs or the run view, and the browser on steps other than Code Review.

## A run with no agent choice uses the owner's default coding agent (bug 19.001.001)

Every daemon path that starts work without a chosen agent resolves it through one injected helper, `resolveDefaultExecutor` (default `resolveFallbackExecutor`, `server/src/executors/fallbackExecutor.ts`): the stored default coding agent, else the first configured interactive CLI agent. Precedence is unchanged: the request's `executorId`, then the item's saved one, then a step's own `executorId`, then the helper. It reads only the stored id and `executors.json`, never quota, so tests that start runs read no real usage. It replaces a fallback that always took the first entry in `executors.json`. Details: [default coding agent](default-coding-agent.md#runs-started-with-no-agent-choice).
