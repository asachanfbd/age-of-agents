# Content Studio Building

The Content Studio Building (type id `content-studio`, `server/src/buildings/types/contentStudio.ts`, code in `server/src/content/`, routes in `server/src/api/contentRoutes.ts`, web in `web/src/ui/ContentStudioWorkspace.tsx` and `web/src/ui/content/`) plans and produces social content for **one business**: scripts, videos, images and carousels, post texts, captions and blog posts for LinkedIn, Instagram, X (Twitter), Facebook and a Blog. A second brand is a second Building. This is task 32.001, the foundation: Concepts and their Posts, the List and Calendar views, the Concept tab bar, Business knowledge and the Writing style. Task 32.002 added the shared agent pane and the Script tab. Task 32.003 added manual Publish and stats snapshots; task 32.004 the Post content, Captions and Blog tabs; task 32.007 the Video tab and the shared Remotion project; task 32.005 the writing-style retro; task 32.008 the Remotion tab (Remotion Studio); task 32.006 the Images tab; task 37.004 the thumbnail asset of a video (server and Publish dialog); task 37.005 the Thumbnail tab (web).

Tabs of the Building, first to last: **Content** (opens on the List, with New; a List / Calendar toggle that is not remembered), **Knowledge**, **Writing style**, **Settings**. `CONTENT_TABS` (web `lib/contentWorkspace.ts`) is the declaration. A Concept opens in place of the Content tab's list, with a back button, never as a top-level tab.

## Creating one, storage, deletion

`POST /api/projects` with `typeId: "content-studio"`, a name (trimmed, 1 to 80 characters, else 400 `{ error, field: 'name' }`) and a `timezone` (an IANA name; invalid is 400 field `timezone`; omitted is `UTC`). The new-Building dialog shows a time zone dropdown with the browser's zone preselected. The type has no repository, no workflow slots and no capabilities; category Marketing; version 1; generic 3D look tinted `#8e6bbf`.

- **Records** are in `<data>/buildings/<id>/content.sqlite` (SQLite through `better-sqlite3`, WAL), opened on first use by `content/runtime.ts`. Tables: `meta` (time zone, writing-style version, settings, each Concept's composition id), `concepts`, `posts`, `assets`, `studio_drafts`, `style_history` (an `autoApplied` column is added on open to an older database), `retros`, `style_proposals` (see [Writing-style retro](#writing-style-retro)), and for the Video tab `media`, `video_rounds` (per round: `confirmedAt`, `scriptChanged`), `video_checklist_items` (per round: id, label, detail, ticked, linked media ids) and `video_renders`, and for the Images and Thumbnail tabs `image_renders` (one row per `render_images` or `render_thumbnails` call, keyed by asset id), and for Performance `target_history` and `insights_history` (targets and the owner notes live in `meta`). The CRM precedent, the same reasons: row updates and multi-step transactions.
- **Content files** are plain files agents can read: `<building>/knowledge/` (below) and `<building>/concepts/<conceptId>/` (one folder per Concept, created with it). Inside it, `script/script.md` holds the finalized script (written on finalize, removed on Reopen) for the post tabs' agents to read (a script finalized before task 32.004 has no file until it is reopened and finalized again; until then post sessions are told there is no finalized script); `posts/<postId>/` belongs to one post (the Images tab writes `images/round-<n>/image-NN.png` there; deleting the post removes it); `video/round-<n>/render-<k>.mp4` holds the renders, `thumbnail/round-<n>/thumb-NN.png` the rendered thumbnails and `media-thumbs/` the video poster frames; later tasks put `media/` there. `<building>/remotion/` is the shared Remotion project (Video tab, below), created on the first video session.
- **Deleting the Building** stops its Remotion Studio, closes the database (`onDeleting`) and removes the folder. Deleting a Concept removes its row, posts, assets (the thumbnail and its render rows included) and folder (its thumbnail PNGs included), stops its renders, and removes its code (the thumbnail stills included), media and archives from the Remotion project (the registry follows).
- **One writer at a time per Building:** every write route runs through `ctx.exclusive`, a promise queue per Building.
- Ids of Concepts, Posts and assets are random UUIDs; a route id that is not a UUID is 404 and is never joined into a path.

## Closed sets

- **Platforms** (exact wire values, case-sensitive): `linkedin` "LinkedIn", `instagram` "Instagram", `x` "X (Twitter)", `facebook` "Facebook", `blog` "Blog". Anything else is 400 field `platform`.
- **Formats per platform** (else 400 field `format`): linkedin `text`, `image`, `carousel`, `video`; instagram `image`, `carousel`, `reel`; x `text`, `image`, `video` (an X carousel is `image` with 1 to 4 images); facebook `text`, `image`, `carousel`, `video`; blog `article`.
- **Assets a post needs** (`rules.ts`, duplicated in `web/src/lib/contentRules.ts` and pinned by `server/tests/contentRules.test.ts` SU28): every non-blog format needs the post text (named Caption on Instagram, Post on LinkedIn and Facebook, Tweet on X); `image` also needs an image set (exactly 1 image, X 1 to 4); `carousel` also needs an image set; `video` and `reel` need the Concept's video and its thumbnail (LinkedIn, X and Facebook video and Instagram reels all use the one thumbnail); `article` needs the blog article. The script is per Concept and never required.
- **Carousel limits** recorded here and in `imageRange`: LinkedIn 2 to 20, Instagram 2 to 20, Facebook 2 to 10. They are the platforms' published limits at the time of writing; the Images tab's Finalize enforces them (below).
- **Asset kinds** `script` and `video` (one each per Concept), `thumbnail` (one per Concept that has a video or reel post: created with the first such post, never a second one; it stays when the last video post is deleted, in no post's needs, and is reused by the next; `CONCEPT_ASSET_KINDS` in `rules.ts`), `post-text`, `image-set` and `article` (one each per Post, where the format needs it). A database from before thumbnails gets one empty thumbnail per video Concept when it is opened (`addThumbnailAssets` in `db.ts`, idempotent); post statuses stay as they were, so a post finalized or published before then keeps its status. **Asset state** `empty | drafting | finalized`; the screen says **Not started / Drafting / Finalized** (the wire value `empty` is never shown). An asset also carries its finalized content reference, `finalizedAt` and a round counter for later tasks. Creating a Concept makes them all `empty`; the studio routes below move the script through `drafting` and `finalized`, using `setAssetState` in `concepts.ts`, which later tasks call too.
- **Post status** `draft` → `finalized` → `published`. `published` is set by the manual Publish below and left by Unpublish.

## Concepts and Posts

- **Concept**: title (1 to 200 characters), brief (0 to 5,000), createdAt, updatedAt, archived. Limits count characters, not UTF-16 units.
- **Post**: platform, format, `scheduledAt` (an instant; entered and shown in the Building time zone), status, note, createdAt. Several posts of one platform in one Concept are allowed. Only `scheduledAt` can change; a different platform or format is a new post (400 on a patch that names them).
- **Finalize post** is allowed only on a draft whose every needed asset is `finalized`; otherwise 409 `{ error, code, details: { missing: [assetKinds] } }`. **Back to draft** is allowed from `finalized`. A finalize of a non-draft, or a back-to-draft of a non-finalized post, is 409.
- An asset going back to `drafting` (through `setAssetState`) moves each finalized post that needs it back to `draft` and leaves a note, which the Overview shows under the status.
- **Deleting a post** is 409 when it is published (its session and files stay). Otherwise it first ends and removes the studio sessions of the post's own assets, then deletes the post, its assets and their drafts, and removes `<concept>/posts/<postId>/`. **Deleting a Concept** is allowed (the web asks first).
- `POST /concepts` may carry first `posts`; the create is atomic, one invalid post writes nothing.

## Concept view

An imported Concept has the Imported badge, the band with **Learn from this**, and read-only tabs (see Imported Concepts).

Header (task 36.001, modelled on the Tasks session header, reusing `DetailBackButton`, `HeaderIconButton`, `DetailLabel`, `TITLE_INDENT`): one row with Back, the Concept title (read-only `h3`), a status badge and a chevron, and a muted facts line `status · Created <RelativeTime> · N of M texts finalized · N posts`. The status comes from `conceptStatus` (`web/src/lib/contentView.ts`): Archived, else Draft (no posts or nothing finalized), else Ready (`needed > 0` and `finalized >= needed`), else In progress; `conceptFactParts` builds the rest. The chevron opens a section below the header holding the editable title (with an Edit title button) and the brief, both saving on blur; it is collapsed by default and starts collapsed again for each opened Concept (`ConceptBody` is keyed by `conceptId`). Then the tab bar **Overview, Script, Video, Thumbnail, Remotion, Images, Post content, Captions, Blog**, declared once as `CONCEPT_TABS` with the enable rule `conceptTabStates(posts, { scriptFinalized, compositionReady })` (pure, server and web copies): Captions needs an Instagram post, Blog a blog post, Post content a LinkedIn, X or Facebook post, Images an image or carousel post, Video a video or reel post **and a finalized script** (the tooltip and the line under the bar name whichever is missing, or both), Thumbnail a video or reel post (the script need not be finalized; the reason is "Add a video or reel post to use this tab"), Remotion a video or reel post **and the Concept's composition in the shared Remotion project** (`compositionReady`, from the Concept's `compositionId`; the reason is "Add a video or reel post to use this tab" first, then "Start the video in the Video tab first"). A tab that does not apply is shown disabled, with its reason as the tooltip only (the "Disabled tabs" text list was removed in 36.001) (and in place of the tab body if it was open when it became disabled). Overview, Script, Video, Thumbnail, Remotion, Images, Post content, Captions and Blog have content. The **Overview** has the posts table (platform, format, editable date and time, status, the assets it needs with their state, Finalize post / Back to draft with the 409 reason inline, delete), add post, and the Concept's script and video with their state, and for a Concept with a video or reel post its thumbnail (the row opens the Thumbnail tab).

## Content tab

Next to **New**, **Import past concept** opens the import session's view in place of the List (see Imported Concepts); it reads **Continue import** with a live dot while a session runs, and is disabled with the read-only title on a read-only Building. The filter row has the Imported filter.

- **List**: newest first, paged (default 50, maximum 200 and clamped; `limit` of 0, negative, fractional or not a number is 400). Rows show the title, posts as chips (platform icon, format, `RelativeTime`, status colour) and asset progress. Filters: post status (any post in that status), platform (any post on it), archived, and text search on title and brief (case-insensitive; `%` and `_` are literal). `archived=true` lists only archived Concepts; the default lists only the others.
- **New** dialog: title, brief, and a checkbox per platform with a checkbox per format; every ticked format is one post ("Will create N posts"). One date and time field plus **Apply to all platforms** copies it into each ticked platform's own field, which stays editable. Each platform's last ticked choices are remembered in the browser (`localStorage`, wrapped in try/catch, saved only after a successful create) and come back ticked. Several posts of one platform with different dates are made on the Overview with Add post.
- **Calendar**: a Monday-first month grid with previous, next and Today; each Post on its day **in the Building time zone** as a chip (platform icon, Concept title, status colour); more than 3 in a day shows "+N more". A chip opens its Concept. A week view is not built.

## Knowledge tab (Business knowledge)

Text sections are Markdown files in `<building>/knowledge/`: About the business (`about.md`), Audience, Products and offers, Facts and numbers, Links, Do's and don'ts, plus up to 20 owner-added sections (`custom-<slug>.md`, listed in `sections.json`; name 1 to 80 characters, unique ignoring case against every section, else 409; the 21st is 400; the built-in sections cannot be deleted, 400). A section is at most 50,000 characters (400).

- **Brand files** go in `knowledge/files/` as raw bytes (not base64 JSON): at most 50 MB each and 100 files. The route reads a body of 51 MB, so a file over 50 MB up to that is 400 and a bigger body is 413. A file name is a plain name (no folder parts, no control characters, no leading dot; 400), and a name already used is 409. Downloads are `application/octet-stream`, `attachment`, `nosniff`, so a stored SVG or HTML file never renders on the app's origin. Images preview in the web.
- **Colours** are a JSON list `[{ name, hex }]` in `knowledge/colours.json` (at most 20; `#RRGGBB`, stored upper-case; names 1 to 40 characters, unique ignoring case; 400 otherwise). A hand-edited file reads back; a corrupt file reads as an empty list.
- **Agents may edit the files directly.** Every read returns a `version` (a hash of the content) and "Last changed" (the file's modified time). A save with a stale version is 409 `{ error: "Changed by an agent since you opened it", code, details: { current } }` and writes nothing; the web shows that text with **Reload** (take the file) and **Overwrite** (send mine against `details.current`). A save is written through a temporary file and a rename, so an agent never reads half a document.
- `knowledge/README.md` is written by the daemon (at creation and when a custom section is added or removed) and tells agents what each file is, including `insights.md` (see Performance below). It is not a section and cannot be read or written through the section routes.

## Writing style tab

One Markdown file `knowledge/writing-style.md` with the headings General, LinkedIn, Instagram, X, Facebook, Blog and Video script, saved with the same version rule and a 50,000 character limit. The tab shows, top to bottom: **Pending proposals** from the retro (below; the tab label carries their count as a badge, hidden at 0, "99+" past 99), a collapsed **Retro log**, the editor, and **Change history**. The read returns the pending proposals as `proposals`. **Change history** lists the newest 50 saves: who (Person, Agent or Retro, a retro entry applied without review tagged "auto-applied"), when, and a short diff ("+2 lines, -1 line", "No changes"). An edit an agent made on disk is noticed at the next web save (the file's hash differs from the last one the daemon recorded) and logged as an `agent` entry before the person's own entry; there is no folder watcher, and a GET never writes.

## Settings tab

Name (renames the Building through the same `renameProject` as Settings → General, so the same 1 to 80 character rule, `updatedAt` and live `project` event apply), time zone (a dropdown), **Apply retro changes without review** (`autoApplyRetro`, a checkbox, default off; only `true` or `false`, anything else is 400 field `autoApplyRetro`, nothing saved), **Writing skill file** (an absolute path to an existing readable file, at most 4,096 characters, `~` is not expanded; empty or `null` clears it back to the default; any other value is 400 field `writingSkillFile`, nothing saved; the default path is shown as the placeholder) **Judge a post after N days** (`evaluationDays`, a whole number 1 to 90, default 7; anything else is 400 field `evaluationDays`, nothing saved), **Speaking speed (words per minute)** (37.006: a whole number 20 to 400, default 150, stored in the content meta table under `speakingWpm`; GET returns `speakingSpeed: { speakingWpm, source }` with `source` `default` (no row, or a corrupt one) or `manual` (any saved value, 150 included); PATCH takes a top-level `speakingWpm`, and anything else, `null` included, is 400 field `speakingWpm` with nothing saved, so there is no reset to the default; a Default / Set by you chip shows the source, and the form sends `speakingWpm` only when it changed, so saving other fields never marks it manual; 37.007 adds the `detected` source: see "Detected speaking speed" below; `speakingSpeed` is now `{ speakingWpm, source, sampleCount }`), and a read-only line with the Building folder path. This is the one place the absolute data path appears in a response; the settings panel guards its own read-only state.

## Read-only Buildings

A Building that is read-only (type unavailable, newer data, failed migration) answers **409 `{ error }`** on every write route (except Remotion Studio's `start`, `stop` and `heartbeat`, see [Remotion tab](#remotion-tab-task-32008)) and 200 on every read route, including the history; the web disables every changing control and keeps lists, files and history readable. Every panel takes a `readOnly` prop and none is drawn inside the platform's read-only wrapper (each tab declares `selfGuarded`, see the layout rules in `.docs/blueprint.md`).

## Studio pane and the Script tab

Every content tab of a Concept works the same way: an AI coding agent on the left, the result on the right. The pane is shared (`web/src/ui/content/StudioPaneView.tsx`, wired by `StudioPane.tsx`; server `content/studioSessions.ts`); a tab is an entry in `content/studioTabs.ts` (job, writing-style section, tool names). Script is the first: asset `script` of the Concept, job "write the spoken script for a short-form video of this Concept".

- **Left half:** the real interactive CLI terminal (the same `TaskTerminal` the Agent sessions use) for the current round. **Right half:** the newest saved draft labelled "Draft · round N · saved <relative time>", or "No draft yet. Ask the agent to write one.". **Copy** is at the top right of the result pane (clipboard, then a toast; a refused clipboard shows an error toast). The result pane's pinned footer has **Finalize** (enabled only when a draft exists) and **Start a new session** on the right.
- **Script stats (37.006, Script tab only):** on the left of the same footer row, always visible while the script scrolls: the word count ("1 word", "1,234 words"), the estimated length `~m:ss` and the speed, `179 words · Length ~1:12 · Speed [150] wpm · default`. Words are the shown text (the current draft, or the finalized text once finalized) split on Unicode whitespace, empty pieces dropped (a zero-width space does not split); the line numbers and comments are not counted. Length = words / speed, rounded to the nearest second with a floor of `~0:01` and no cap on the minutes; with no draft the footer shows "0 words" and length "—". The speed is the Building setting (Settings tab), shown with its source ("default", "set by you", "average of 3 recordings" or "from 1 recording"), and is editable inline: Enter or blur saves (`PATCH settings { speakingWpm }`), Esc puts the saved value back. A value that is not ASCII digits from 20 to 400 keeps the typed text, marks the field invalid and says "Use a whole number from 20 to 400. Nothing was saved."; a failed save keeps the value and shows the error with "· not saved". It is disabled with the read-only title in a read-only Building and stays editable on a finalized script. The formulas are in `web/src/lib/contentScript.ts`; the other tabs have no stats. The pane shows them only when `isScriptAsset(concept.assets, assetId)` finds a `script` asset: post texts and articles are not in `concept.assets` (they hang off `posts[].needs`), and `StudioPane`'s `assetKind` lookup falls back to `script` for an id it cannot find, so that lookup cannot gate script-only UI.
- **Opening the tab** with an `empty` or `drafting` asset and no session starts round 1 by itself (the asset becomes `drafting`), unless the daemon already tried to start it and was refused. A Building that is read-only starts nothing and says so. With no usable default agent the left pane shows the reason (409 `{ error }`), how to set one and a **Start** button (disabled in a read-only Building); there is no per-tab picker. The view carries the kept reason as `blockedReason` (null once a session exists), so a reason from an automatic start (below) shows the same way on the Post content, Captions, Blog and Images tabs, wraps when long and never replaces the Images tab's Remotion setup note. The pane shows no link: the global Settings panel cannot be opened from a Building, so it points to the footer's default-agent dot. This is an accepted deviation from the spec's "link to set one".
- **Automatic starts (dependency table).** `server/src/content/studioDependencies.ts` lists which asset kinds start after which asset is finalized (`START_RULES`). Finalizing the script starts round 1 of every asset of the Concept that has a pane and is still `empty` with no session: the video and the thumbnail (when a video or reel post needs them, so the thumbnail is designed in parallel with the video), each post's text (Post content, Captions), each blog article and each image or carousel post's image set. Finalizing the video starts the thumbnail under the same rule (it matters only for a thumbnail that never started, for example after a refused start). Drafting, finalized and already-started assets (even an ended one, which offers Resume) are left alone, so finalizing the script again after a reopen restarts nothing; an existing video session only gets the "script changed" flag. The starts run in the background, one at a time through the Building's write queue, after the finalize has answered; a refusal (no usable agent, a failed Remotion install) never fails the finalize and is kept per asset as its `blockedReason`, published as a `studioAsset` event like every started session. Each start re-checks in the queue and is skipped for an archived or deleted Concept or a post deleted meanwhile; a read-only Building cannot finalize at all. The video, image sets and thumbnail wait for the one shared Remotion install. Finalizing a text asset, an image set or the thumbnail starts nothing.
- **Finalize is a state, not a save:** the asset becomes `finalized` with the newest draft as its content, the CLI session ends, the left pane closes and the result takes the full width ("Finalized <relative time>", Copy). **Reopen** sets the asset back to `drafting`, starts round N+1 whose agent receives the finalized text as its starting point (the one case where earlier content carries over) and moves each finalized post that needs the asset back to draft (the rule above). Finalizing the script enables the Video tab, writes the text to `concepts/<conceptId>/script/script.md` and starts the dependent sessions (video, post text, article, image sets; see Automatic starts above).
- **Start a new session** (confirm: "End round N and start round N+1? Nothing from this round carries over.") ends the session and starts round N+1 with a fresh conversation. Nothing from earlier rounds is given to the new agent. **Layout (36.001, edge to edge since 37.006):** on an agent tab (Script, Post content, Captions, Blog, Images, Thumbnail) the Concept page is a full-height flex column: header and tab bar take their natural height, and the terminal and result panes fill exactly the rest with no outer page scroll. The panes have no outer padding, border, radius or gap: they touch the workspace's edges under a 1px line, split by one 1px divider (beside each other from 1024 px, under the terminal when stacked). Below 1024 px they stack, the terminal taking 2 parts and the result 3 (at least 12rem and 16rem), and only then can the panes area scroll. The result pane pins its heading (with Copy) at the top and its footer (stats on Script, the actions, the finalize hint, retro status) at the bottom, and only its body scrolls; text inside keeps its own padding. The post tabs' switcher and context line, the Images and Thumbnail read-only note and the skill warning are full-width padded strips above the panes. The Video tab keeps its own padded layout (see its Layout below). Overview and Remotion scroll normally. Earlier rounds' drafts stay in a collapsed "Previous rounds" list (inside the scrolling result body) (round, last draft, date, each with its own Copy), read-only.
- **Session ended** (restart, crash, the agent exited): the left pane says "Session ended" with **Resume** (relaunches the same conversation: Claude `--resume`, Codex `resume`; when the agent no longer has it, a fresh start in the same round with the round's last draft as context) and Start a new session.
- **Skill warning:** when the writing skill file cannot be read at session start the session still starts and the pane shows "Writing skill not found at <path>".
- Finalize has no confirm dialog (Reopen is cheap).
- **Line comments (36.002, Script tab only):** the draft shows one row per line with a muted line-number gutter; Copy still copies the plain text. Each non-blank line has a comment button (shown on hover or focus, always on touch screens, labelled "Comment on line N"). It opens a box under the line: textarea, counter "0 / 2,000", Cancel and Send (Ctrl/Cmd+Enter sends, Esc cancels, focus returns to the line's button). Several boxes can be open at once. Send calls `POST session/comment`; a refusal shows inside the box and keeps the text. A sent comment shows under its line as "Sent · <time>" with the comment, and a hint under the heading counts them; the notes clear when the agent saves a new draft (line numbers may have changed). An unsent box stays on its line number with its text; when that line's text changed it shows the new text, and when the line is gone it says "Line N is no longer in the draft." and Send is disabled. With no live session the buttons are disabled with "Comments go to the live agent session. Press Resume to comment."; on a read-only Building with the read-only title; a finalized script shows no comments. Post content, Captions and Blog draw their text their own way, so they have no line comments.
- A draft save, Finalize and a start all run in the Building's write queue (`ctx.exclusive`), one at a time; that queue, not a per-call lock, is what keeps a late `save_draft` from landing after Finalize. A `rev` of a view starts from the clock, so it stays ordered across daemon restarts.

### Session kind (server)

The import session is separate from these records (see Imported Concepts).

A "studio session" is one record per round (Script and Video tabs), in `studio-sessions.json`: Building id, Concept id, asset id, tab, round, executor id, the agent's conversation id, the launch setup (system prompt, binary, environment), state `running | ended`, timestamps, and the skill warning text. It is not a Task. A daemon restart marks running ones ended; deleting a Concept or the Building ends and removes its sessions. The asset's `round` counter is the current round (first open makes it 1; a new session and a reopen add 1). A script or post-text agent runs in `<building>/concepts/<conceptId>/`, a video, images or thumbnail agent in `<building>/remotion/`, with the same `auto` permissions as Agent sessions and `reportHooks: false`. **One live session per asset**: a second start while one runs, or a start on a round whose session ended, is 409.

- **Web view** (`StudioView`): `rev`, Concept and asset ids, the asset state/round/finalized time/finalized text, the current session as a DTO (id, conceptId, assetId, tab, round, state, executorId, timestamps), every round with its newest draft, and `skillWarning`. Never the conversation id, environment, token or a folder path. `rev` grows with every view the daemon builds, so the web drops an older one that arrives late.
- **Live updates** go over the existing `/ws` as `{ type: 'studioAsset', buildingId, view }`, on start, new round, resume, every saved draft, finalize, reopen and when the CLI ends.
- **Instructions** (system prompt, the same text for Claude and Codex): 1. the tab's job (Script: ask the owner about length, hook and call to action if unclear; and, since 37.006, the script-only rule below); 2. the Concept title, brief and its posts (platform, format, date); 3. the `<building>/knowledge/` path (the agent may edit those files when the owner tells it new facts and must say so in the chat) and `knowledge/writing-style.md` (General plus the tab's section, "Video script" for Script); 4. the **human-content-writing skill**: the daemon reads the file at session start and puts its full text into the instructions. The path is `~/.claude/skills/human-content-writing-skill/SKILL.md` unless the Building's "Writing skill file" setting names another; this applies to every text-writing tab, the Video tab decides its own; 5. save every complete draft with `save_draft`.
- **Script-only drafts (37.006).** The script is copied straight into a teleprompter or voice-over and its words set the estimated length, so the script job (`SCRIPT_ONLY_RULE` in `studioTabs.ts`, the same text for Claude and Codex) says the saved draft must be only the spoken script as plain paragraphs: no title or headings (no lines starting with `#`), no labels such as "Hook:", "Intro:", "Scene 1" or "CTA:", no bracketed or parenthesised stage or camera directions ([pause], (show screen)), no timestamps, no word-count or duration notes, no notes to the owner, no "Here is the script" preface, no markdown emphasis, bullets or code fences, and no emoji unless spoken. Questions, notes, assumptions and alternatives go in the chat. It also tells the agent to end a spoken lead-in with a full stop and keep an aside inside its sentence, since the guard below refuses those lines.
- **`save_draft` refusals for a script (37.006, `server/src/content/scriptDraftRules.ts`).** Only for the `script` asset (never post texts, articles or alt text), after the empty and length checks, `save_draft` refuses a draft with 400 `{ error, field: 'text' }`, handed back to the agent as a tool error like the length refusal, when a line (trimmed) is: a markdown heading (`^#{1,6}\s`); a code fence (starts with three backticks or `~~~`); only a label ending in `:` of at most 40 code points, colon included (`Hook:`, `हुक:`); only bracketed directions (`[pause]`, `(show screen)`, `[pause] (smile)`); or, on the first line only, a preface starting with "Here is" / "Here's" (any case, either apostrophe) that names script, draft or version or ends with `:`. The message names the first problem by line, counted on the trimmed text (`\r\n` counts as one line break), and the fix, for example "Remove the heading on line 1 and save only the spoken script". A sentence that merely contains a colon or brackets, a `#hashtag`, and "Here's why your sales dropped." are accepted. Known limit: a short spoken lead-in ending in `:` and a line that is only a parenthesised aside are refused.
- **Tools** (`bin/studio-session-mcp.mjs`, server name `agent_visual_os_studio`, authenticated with the CLI hook token plus the session id, relayed to `POST /api/studio-session/draft` and `GET /api/studio-session/concept`): `save_draft({ text })` (counted in code points after trim: the script 1 to 50,000 characters, a post's text or article its platform's limits below; empty or over is 400 `{ error, field: 'text' }` with a message naming the limit, which the tool hands back to the agent as a tool error so it can shorten and save again; stored trimmed as the round's newest draft, every call keeps its history; a session deleted while the call waited for the write queue is 404) and `get_concept()` (the Concept, its posts and the asset states). Refusals: bad token 401, no session id 400, unknown session 404, ended session or finalized asset 409. The tab entry names its tools, so later tabs add tools without changing the server. The session gets no task, testing or bug tools.

### Platform limits

One table, `server/src/content/platformLimits.ts`, duplicated in `web/src/lib/contentLimits.ts` with the thread and hashtag rules and pinned by `server/tests/platformLimits.test.ts` (U02, with shared cases in `web/tests/fixtures/contentTextCases.json`). The platform limit replaces the general 50,000-character draft cap for post texts and articles; the script keeps 1 to 50,000.

| Post | Rule enforced on `save_draft` |
|---|---|
| LinkedIn post | at most 3,000 characters |
| X tweet | at most 280 characters; a thread of at most 25 tweets, each at most 280 |
| Facebook post | at most 63,206 characters |
| Instagram caption | at most 2,200 characters and at most 30 hashtags |
| Blog article | first line `# <title>`; 300 to 50,000 characters |

- **Thread format:** a line whose only content, ignoring spaces, tabs and `\r`, is `---` separates tweets (`----`, `---x` and an inline `---` do not). Tweets are trimmed and empty ones dropped, so a leading, trailing or doubled separator adds nothing; a draft of only separators is empty (400). A thread is stored as the raw trimmed text, not normalised.
- **Hashtag:** `#` followed by letters, digits or `_` (`#[\p{L}\p{N}_]+`); `##tag` counts once, `#a#b` twice.
- **Blog title:** the first line after trimming must be `# ` followed by a title (`#Title`, `## Title` and an empty title are refused).
- Refusal messages name the limit and the actual count (and the tweet number in a thread), for example "The text is 3,001 characters; the limit is 3,000 characters. Shorten it and save again."

**Simplifications** (recorded on purpose): characters are Unicode code points, so an emoji with a variation selector (🏘️) counts 2; X's own counting (a URL as 23 characters, some characters as 2) is not modelled; a `#word` inside a URL (`https://a.b/#top`) counts as a hashtag. The web counts the same way, so the counters agree with the refusals.

## Imported Concepts (task 37.009)

An imported Concept is one the owner made outside this system: already written and usually already posted. It exists so agents can read it as an example and so its numbers count in results and Insights. It is stored in the same tables as any Concept, with `concepts.imported = 1`, and shows in the normal list and calendar.

**How it gets in.** There is no form and no `POST concepts/import` route (decided in UI planning, replacing the task's dialog). **Import past concept** in the List opens the **import session**: a live agent the owner gives text, links, file paths, exports and numbers. The agent reads them, checks `get_reference_content` for duplicates, lists what it found with what it inferred, asks, and only then saves with `save_imported_concept`. Files reach it as pasted text or paths; there is no upload control. The view replaces the List: the terminal on the left, **Imported in this session** on the right, a toast `Imported: <title>` per save. It stays open after a save, because opening the Concept would interrupt a batch. The owner can leave: the session keeps running and the button reads **Continue import**.

**The import session** is not a studio session: it has no Concept or asset, so it has its own records in `import-sessions.json` (`content/importSessions.ts`): Building id, executor id, conversation id, launch setup, state, timestamps. Saved Concepts carry `concepts.importSessionId`. One runs per Building (a second start is 409). It works in the Building's folder and has exactly two tools. Opening the view with no session starts one; a refused start (no usable agent) shows its reason and **Start** and is not retried by itself. An ended session offers **Resume** (a lost conversation restarts fresh under the same record, keeping its list) and **Start a new session** (a new record and an empty list; earlier Concepts stay in the Content list). A daemon restart marks it ended; deleting the Building removes it. Live updates go over `/ws` as `{ type: 'contentImportSession', buildingId, view }` on start, save and end. The view (`rev`, `session`, `saved`, `blockedReason`) never carries the conversation id, the environment or a folder path.

**`save_imported_concept({ title, brief?, script?, posts[] })`** (`POST /api/studio-session/imported-concept`, CLI hook token plus session id; `content/importedConcepts.ts`). One Concept per call, all or nothing: a fault anywhere, a script file that cannot be written or a failed row leaves no rows and no folder. Answers 201 `{ conceptId, title, posts: [{ postId, platform, format }] }`. Refusals are 400 and name the field in `field` and in the message, like `posts[1].text` or `posts[0].stats[0].capturedAt`. An ended session is 409, an id that is no import session 404, a Building that turned read-only 409.

| Field | Rule |
|---|---|
| `title` | 1 to 200 characters |
| `brief` | 0 to 5,000; omitted or null is empty |
| `script` | 1 to 50,000 after trim; omitted or null is none, blank is refused. Stored as the finalized script asset and in `concepts/<id>/script/script.md` |
| `posts` | 1 to 20 |
| `platform`, `format` | A valid pair (Closed sets) |
| `text` | The platform's limits (Platform limits), also for image, carousel, video and reel captions. Omitted, empty or blank is no text, even on a blog |
| `publishedAt`, `scheduledAt` | ISO instants. Each defaults to the other, both to now. The published time may be at most 5 minutes ahead; a future `scheduledAt` with no `publishedAt` is refused on `publishedAt` |
| `liveUrl` | Optional, http or https, 2,000 characters |
| `note` | Optional, 1,000 characters; kept through unpublish and publish |
| `stats` | Optional list of snapshots under the stats rules: `capturedAt` not before `publishedAt`, at least one count, watch time on video and reel only |
| `externalAssets` | Optional, 2,000 characters: free text about images or video that exist elsewhere, per post. Shown in that post's Needs cell and read-only tabs |

**Resulting state.** Every asset with content is `finalized`, every post `published`, so it counts in stats, Insights, results and the evaluation window. Assets not provided stay as normal empty rows but are never required: `postNeeds` (`rules.ts`, mirrored in `web/src/lib/contentRules.ts`) lists only an imported post's finalized assets, so `post.needs` and `progress` never show a missing asset. No studio session, auto-start or retro runs. Each save starts the debounced Insights refresh.

**Read-only rules.** These answer 409 `Imported content is read-only; delete and import again` (`IMPORTED_READ_ONLY`): session start, new round and resume, finalize (asset and post), Back to draft, reopen, line comment, Run retro, add post, and media upload, rename and delete. Still open: title, brief, archive, the post date, Unpublish, edit publish details, stats, delete. After Unpublish a post offers Publish and delete, never Back to draft. `GET` of an asset's session stays a plain read.

**Web.** List rows and the Concept header show an **Imported** badge (icon and text); rows show no asset progress. The filter *Imported or not / Imported only / Not imported* maps to `imported=` (absent, `true`, `false`; anything else is 400), and *Imported only* with no rows offers the import. The header status reads `Published` while a post is published, else `Ready`, and the facts line reads `Published · Imported <when> · N posts · Script`. A band under the header says what the Concept is and holds **Learn from this** and **Delete Concept** (a confirm step, disabled with the read-only title on a read-only Building, back to the List on success), because delete and import again is the only way to correct imported text. The Overview shows published state, URL and stats, Publish actions only, the Elsewhere note, `Not imported` for Concept assets without content, and no Add post. Script, Post content, Captions, Blog, Video, Thumbnail and Images show `Imported content is read-only. Agents read it as reference.` with the text or the Elsewhere lines (post tabs keep their switcher) and never start a session. Video needs no finalized script here. Remotion is disabled with `Imported content has no Remotion project`.

**Reference content.** Every session's instructions (script, post text, caption, blog, images, video, thumbnail) carry this section (`referenceSection`), always, `(none yet)` when empty: imported Concepts are the owner's earlier work, to read for voice, structure, hooks and length before writing, never to copy. It lists up to 10 newest imported Concepts with a published post on the session's platforms (a Concept with no posts matches all; archived ones count): title, platform and format, published date, the first 200 characters of the post text, else of the script.

**`get_reference_content({ platform?, format?, limit? })`** (`GET /api/studio-session/reference-content`): every session kind, the import session included, with the same auth and refusals as `get_performance`. `limit` is 1 to 50, default 10, and above 50 is 400. Answers `{ concepts: [{ conceptId, title, brief, script, posts: [{ postId, platform, format, text, liveUrl, publishedAt, stats, results, externalAssets }] }] }`, newest published first, with full texts. With a filter, each Concept lists only its matching posts. `stats` is null without snapshots.

**Insights.** The data file also holds imported published posts without stats (`stats: null`), and every post carries `imported`. A refresh with only such posts runs. `get_performance` stays posts with stats, with `imported` added.

**Learn from this** (`POST concepts/:cid/learn`, 202; `GET concepts/:cid/learn`, the last status or `null`): a one-shot retro-style agent over the Concept's script and post texts against the current `writing-style.md`. The prompt holds the title and texts, never a path or id; the answer shape, parsing, timeout and auto-apply are the retro's. There are no drafts, so `retroSkipped` does not apply. The run is stored on the Concept's script asset (`retros.assetId` is required) with `retros.sourceKind = 'imported'`, and proposals and log entries report `source.kind`. Writing style shows such a source as **Imported** with no drafts line. 409 for a non-imported Concept, one with no text, or while one runs for that Concept. The web shows `Learning…`, then the link to Writing style › Pending proposals, or what happened instead (nothing to learn, failed).

## Publish (manual) and stats

The owner posts by hand (no platform APIs or logins) and records it here. This is task 32.003.

### Publish rules

- A **finalized** post offers **Publish** on the Overview and on its Concept's row in the Content list. A `draft` or `published` post answers 409 `{ error }`.
- The Publish dialog shows the platform and format, the finalized text with **Copy**, and the finalized media: each image with its own download and **Download all (zip)**, or the video and, under it, the **Thumbnail** with its own Download (video and reel posts only). A media file gone from disk reads "File missing" and **Mark as published** still works.
- **Live post URL** is optional: `http` or `https`, at most 2,000 characters, else 400 field `liveUrl`. **Published at** is an ISO instant (entered in the Building zone, default now), at most 5 minutes in the future, else 400 field `publishedAt`. Mark as published sets status `published`.
- A published post shows its URL (a link) and its time (`RelativeTime`). **Edit publish details** (`PATCH publish`) changes URL (`null` clears it) and time; the time cannot move after a snapshot that was already captured (400 `publishedAt`). **Unpublish** (inline confirm) returns it to `finalized`, clears URL and time and **keeps its stats** (they show again on the next publish). A published post cannot be deleted, finalized again or sent back to draft (409).
- **Reopen block:** an asset a published post uses cannot be reopened: the studio `reopen` route answers 409 "Used by a published post" (`usedByPublishedPost`, web `reopenBlockReason`), and the web disables Reopen with that reason. The post-text, image-set and article of a published post and the Concept video and thumbnail of a published video or reel post are blocked; the script is never needed by a post, so it is never blocked. Unpublishing lifts the block. Every asset kind now has a pane, so the route answers this 409 for each of them.
- The **Calendar** puts a published post on its **published** day in the Building zone and any other post on its scheduled day (the month query uses the same rule).
- **Where the media comes from.** The post-text and article assets hold their text. The image-set asset's `content` is a JSON list of file paths, the thumbnail's a JSON list of one path (`["thumbnail/round-<n>/thumb-NN.png"]`) and the video asset's `content` is meant to give its file, all relative to the Concept's folder (the Images, Thumbnail and Video tasks write them). A path that leaves the folder reads as missing. **Known defect (since 37.002, open):** Finalize now stores the final render's **id** as the video's `content` (`commitFinalize(ctx, t, renderId)` in `studioSessions.ts`; `finalizedVideo()` in `videoStudio.ts` reads it that way), but `postMedia.ts` still reads it as a path, so for a video finalized since 37.002 the dialog's Video row shows "File missing" and `media/video` is 404. The Publish tests pass only because they set a path by hand. Downloads are `attachment`, `nosniff` and `Content-Security-Policy: sandbox`. The zip stores its entries uncompressed, leaves out a missing file, names entries by file name (repeats become `a (2).png`) and is 404 when no image is present.

### Stats snapshots

A published post has a **Stats** section on its Overview row (expandable panel under the row) with **Add stats**. Snapshots are only added, edited and deleted while the post is published (409 otherwise); listing is a read.

- **Captured at**: ISO instant (entered in the Building zone, form default now), required, at most 5 minutes in the future and not before the post's published time (equal is fine); either is 400 `{ error, field: 'capturedAt' }`. Several snapshots may share a captured time.
- **Counts**, each optional: `impressions`, `reach`, `views`, `likes`, `comments`, `shares`, `saves`, `linkClicks`, `profileVisits`, `followersGained`. A whole number from 0 to 10^12, else 400 field `counts.<name>`; an unknown name is 400 too. **At least one count** is required (400 field `counts`). **An empty count is `null` ("—"), never 0.** On a patch an omitted count is kept and an explicit `null` clears it.
- **Average watch time** (`watchTime`): seconds from 0 to 86,400 with at most 1 decimal, for `video` and `reel` posts only (400 field `watchTime`; the task set no upper limit, 86,400 is this task's choice). **Note**: 0 to 1,000 characters, stored trimmed.
- **Fields per platform** (the form shows these, under the platform's own labels; the server accepts every field for every platform): LinkedIn impressions, Reactions (`likes`), comments, Reposts (`shares`), Clicks (`linkClicks`), followers gained. Instagram reach, views, likes, comments, shares, saves, profile visits, followers gained. X Views (`impressions`), likes, Replies (`comments`), Reposts (`shares`), Bookmarks (`saves`), link clicks, profile visits. Facebook reach, views, Reactions (`likes`), comments, shares, link clicks. Blog views, link clicks, comments. The list is `PLATFORM_STAT_FIELDS` in `server/src/content/stats.ts`, copied in `web/src/lib/contentStats.ts` and pinned by `contentPublishStatsHelpers.test.mjs` (WU04).
- **Order:** newest captured first, ties by entry time, then insertion order. The post (and Concept) view carries `stats: { count, latest, delta }`: the latest snapshot and its change since the **previous snapshot in order** (not the previous non-empty value); the change is `null` for a count that is empty on either side, and `delta` is `null` with one snapshot.
- **Most views** (`GET concepts?sort=views`; `sort=newest` is the default; another value is 400 field `sort`): a Concept ranks by its best published post's latest `views`, or `impressions` when `views` is empty (X reports its views as impressions). Concepts without stats come last, newest first; paging and filters apply as usual.
- Snapshots keep their sources (below). Deleting a snapshot, a post (after unpublish), a Concept or the Building removes them; Unpublish keeps them.

### Fill from text or screenshots (extraction)

The Add stats form has a **Fill from text or screenshots** area (a text box and an image picker or drop zone). **Extract** runs an agent and **pre-fills the form**; nothing is saved until Save. Pre-filled fields carry a "from agent" mark that goes away when the owner edits the field. If the text or a screenshot shows when the numbers were read, Captured at is filled too, otherwise it keeps the form's value. The agent lists what it could not map and the form shows "Not used: ...".

- **Route:** one multipart request, `POST .../stats/extractions` with a `text` field (up to 20,000 characters) and `images` files (0 to 10, PNG, JPEG or WebP judged by their bytes, at most 10 MB each, raw bytes, not base64). Something to read is required (text or an image). 400 field `text` or `images` for a wrong type, too many, too long or an empty request; an image over 10 MB inside the window is 400; a body over the window (10 images plus 2 MB, about 102 MB, `EXTRACT_BODY_WINDOW`; the whole body is held in memory while it is read, which is acceptable for a single-user daemon) is 413; an unknown post 404; a post that is not published or a read-only Building 409, all before the agent runs.
- **Answer:** 200 `{ ok: true, extractionId, counts, capturedAt, unused }` or 200 `{ ok: false, reason }`. The form shows `Could not read the stats: <reason>` and stays usable by hand. There is no retry and no notification. The staged files of a failed run are removed.
- **The agent:** the default coding agent (the same rule as the studio sessions; none set, or a kind other than Claude or Codex CLI, means `ok: false` with a reason), one headless run, 120 seconds (`EXTRACTION_TIMEOUT_MS`, then the process is stopped). It gets the prompt (platform, format, the platform's fields with their labels, the strict answer shape and the pasted text between markers, as data) and read access to the uploaded image files (Claude's Read is scoped to its working folder), which sit in the extraction's own folder (`<building>/extractions/<id>/`) that is its working folder. Claude runs `-p <prompt> --output-format text --permission-mode dontAsk --allowedTools "Read(./**)" --disallowed-tools Bash,Edit,Write,NotebookEdit,WebFetch,WebSearch,Task`; Codex runs `exec --skip-git-repo-check --ephemeral --sandbox read-only -C <folder> -i <image>... -- <prompt>`. **These flags were chosen from the CLIs' help and never run against a real agent** (see the manual checks). The call is injectable (`ApiRouterOptions.extraction`).
- **Answer shape:** exactly `{ "counts": { "<field>": number|null }, "capturedAt": ISO string|null, "unused": string[] }` as bare JSON. A fenced answer, prose around it, an extra or missing key, an unknown field or a field the platform does not offer, a fraction, a negative number, a number as text ("1.2K") or a bad `capturedAt` is refused with its reason. Turning "1.2K", "3,4 M" and "12,345" into whole numbers is the agent's job; a value it cannot read is `null`, never guessed.
- **The agent runs outside the Building's write queue** (it can take two minutes): staging and the final check run in it, and a post that was unpublished or deleted meanwhile discards the result (409, no files left).
- **Sources as evidence.** Saving a snapshot with `extractionId` moves the screenshots and the pasted text (`pasted-text.txt`) into `concepts/<cid>/posts/<pid>/stats/<statId>/` and the snapshot lists them (`id`, `kind`, `name`, `size`, `contentType`); `GET .../stats/:statId/sources/:sourceId` serves one (found by id, never by a client name; `nosniff`, `sandbox`). An unknown or another post's `extractionId` is 404, a malformed one 400, and a failed save leaves the extraction in place. **Discard:** `DELETE .../stats/extractions/:eid` (404 when unknown or already used); the form discards an unsaved extraction when it closes, and an extraction older than 24 hours is removed the next time any extraction or snapshot save runs in that Building (there is no timer).
- All of these are 409 on a read-only Building, like every write.

## Detected speaking speed (task 37.007)

The video agent measures how fast the owner speaks in an uploaded facecam clip or voice-over, and the average becomes the speaking speed that the Script footer uses.

- **Building-wide, not per Concept.** One speed serves every Concept's Script tab; samples from all Concepts are averaged.
- **Table `speaking_rate_samples`** (content.sqlite, created on open for older databases): `id`, `mediaId` (unique, foreign key to `media` with cascade), `conceptId` (cascade), `wordsPerMinute` (real), `words`, `durationSeconds`, `createdAt`, `source` (`agent`), `seq`. Deleting a media file or a Concept deletes its samples; one sample per media file.
- **Tool `report_speaking_rate({ mediaId, words, durationSeconds })`** (video sessions only; relayed to `POST /api/studio-session/speaking-rate` with the same token and refusals as `set_checklist`; 409 for a session of another kind or an ended or finalized one). The server computes `words / (durationSeconds / 60)`. 400 naming the field: `mediaId` (missing, not a string, over 100 characters, not this Concept's video or audio file), `words` (not a whole number, or under 5), `durationSeconds` (under 3 or over 7,200), `wordsPerMinute` (outside 40 to 400). A second report for the same media replaces the sample and keeps its id. Upsert and delete run in the Building's write queue (`ctx.exclusive`). A report publishes the video view, so the web refreshes. `list_media` now also returns each file's `id`.
- **Agent instructions** (`videoInstructions.ts`): for new video or audio with the owner's speech (not music or b-roll), transcribe or count the words with the tools available, call the tool once per file, never guess a count (tell the owner instead). The checklist is not affected.
- **Effective speed** `{ speakingWpm, source, sampleCount }`: a saved manual value stays `manual` and wins; otherwise with samples it is `detected` = round(sum words / sum minutes), not the mean of the rates; otherwise `default` 150. `DELETE settings/speaking-speed` clears the manual value (200, also when none is set) and returns the speed; `PATCH` is unchanged. Editing the field while the source is detected makes the value manual.
- **Web:** the footer reads `Speaking speed 142 wpm · average of 3 recordings` (the field label stays "Speed") and offers "Use detected speed" only when the value is manual and recordings exist. The Settings tab lists the recordings (name, rate, words, duration) with an immediate Delete each (no undo; a deleted recording returns only when the agent measures that file again), an empty state, and scrolls from 12 rows. ### Flow

1. **Finalizing the script** of a Concept with a video or reel post starts video round 1 by itself (one rule of the dependency table under Studio pane), so it is ready when the owner opens the tab. If it cannot start (no usable default CLI agent), the reason is kept and the tab shows it with **Start**. Opening the tab never starts a session (unlike the Script tab).
2. The agent works out which media it needs and publishes a **checklist** with `set_checklist`. It must not build the video yet.
3. The owner drops media into the media column and **ticks** each item (provided, or not needed), optionally **linking** files to it.
4. When every item is ticked, **Confirm assets** is enabled. Confirming locks the checklist and types this into the agent's terminal, as if the owner wrote it: `All assets are provided. Media folder: public/concepts/<conceptId>/media. Files: <name> (<kind>, <m:ss or size>); …. Checklist: <label> → <linked names or (no file linked)>; …. Start building the video.` (one line; the wording is neutral, it never says "Not needed"). **Injection mechanism** (`server/src/content/typeIntoSession.ts`, shared with line comments): the daemon writes the text to the session's PTY as one bracketed paste (`ESC[200~` text `ESC[201~`, a single `write`), waits `submitDelayMs` (300 ms) and then writes a lone `\r`, so the Enter is never part of the paste. Before pasting, line breaks and tabs become spaces and escape sequences and control characters are dropped, so the text cannot end the paste, press Enter early or send Ctrl-C. Without the paste markers, text over one 1,024-byte terminal read reached Claude Code in two reads: it took the first as a paste and the rest as typed text, and 2.1.317 submitted only the typed tail (bug 36.002.001). Confirm is 409 when an item is unticked, the list is empty or already confirmed, or the session has ended (nothing is written or stored; resume first).
5. The agent builds the video in the Remotion project and never renders it. The right pane switches from the checklist to the **live preview**: the Building's Remotion Studio embedded at this Concept's composition (the Remotion tab's hook starts it when the pane shows, with the same heartbeats), which hot-reloads the agent's edits. The owner iterates there; no render happens while building.
6. Media can be dropped at any time, in every state, including after Finalize; the agent sees new files the next time it calls `list_media`.
7. **Finalize** renders the final video, once: it queues the Concept's composition on the Building's render queue (a `render` job, "Video render" in the footer, with progress and **Stop** in the pane) and answers at once with the view; the request does not wait for the render. When the render succeeds, the asset is finalized with that render (its id is the asset's content), the session ends and the agent column goes (the preview takes its space; the media column stays). If the render fails or is stopped, the asset stays drafting, the session keeps running and the error is shown above the preview; Finalize can be pressed again. Finalize also works after the agent's session ended, because the render needs the project and not the agent.

If the script is reopened and finalized again while a video session exists, no session starts and the tab shows "The script changed after this session started" (`scriptChanged` on the round); the script path is the same, so the owner can ask the agent to re-read it.

### Checklist

- `set_checklist({ items: [{ id, label, detail? }] })`: 1 to 30 items; `id` 1 to 40 characters of `[a-z0-9-]`, unique; `label` one line of 1 to 200 code points (no newline or control character, so the confirm message stays one line); `detail` 0 to 1,000. Anything else is 400. A repeat call before confirmation replaces the list and keeps the ticks and links of ids that stay; after confirmation any call, valid or not, is 409 "Checklist is confirmed".
- The owner's `PATCH video/checklist/:itemId` takes `ticked` (boolean) and `mediaIds` (this Concept's media; de-duplicated; anything else 400); an unknown item is 404; after confirmation, or once finalized, 409.
- Until confirmed, Finalize is 409 "Waiting for the owner to confirm assets".
- A new round (Discard) starts with an empty checklist. **Reopen** copies the finalized round's list with its ticks and links, **not confirmed**: the owner confirms again and the message is sent again. Deleting a media file unlinks it from the items of every round.

### Media storage and limits

- Media belongs to the Concept, not a round. Files are in `<building>/remotion/public/concepts/<conceptId>/media/<name>` (the full Concept id), so compositions load them with `staticFile('concepts/<conceptId>/media/<name>')`; the agent is told the folder relative to its working folder. Rows are in `media`; poster frames in `<building>/concepts/<conceptId>/media-thumbs/`.
- **Upload** (`POST media?name=`) streams the raw body to `<building>/remotion/.uploads/<uuid>.part` (never base64 JSON, never held in memory; `server.ts` keeps every body parser off this path), sniffs the first 8 KB, then in the write queue checks the count, picks the name and renames the file into place. Limit **2 GiB = 2,147,483,648 bytes** per file: a declared `Content-Length` over it (or not a safe whole number) is **400** before any byte is written; a body that streams past it is **413** and the partial file is deleted; an aborted upload leaves nothing. At most **200** files per Concept (400; two uploads racing for the last slot give one 201 and one 400). Node's HTTP server ends any request that takes longer than **5 minutes** (`requestTimeout`, left at its default because the daemon listens on every interface), so a 2 GB upload over a slow network link can end as "The upload was interrupted"; on the same machine it takes seconds.
- **Types** by extension and content: video mp4, mov, webm; image png, jpg/jpeg, webp, gif, svg; audio mp3, wav, m4a, aac. mp4, mov and m4a share the ISO base media check; SVG must have an `<svg` root after any BOM, XML declaration, comments or doctype; mp3 is ID3 or an MPEG frame header, aac ADTS. Anything else, a mismatch or an empty file is 400 "Unsupported file type" (empty: "The file is empty").
- **Names on upload are cleaned, not refused:** characters other than letters, digits, space, `.`, `_` and `-` become `-`, leading dots go, an empty base becomes `file`, the name is trimmed to 120 characters keeping its extension, and a name already used (ignoring case) gets `-2`, `-3` and so on. **Rename** (`PATCH media/:mediaId` `{ name }`) sends the full name and refuses instead: 1 to 120 characters, safe characters only, no leading dot, the same extension (ignoring case) else 400; a name another file has (ignoring case) is 409. The rename moves the file.
- **Thumbnails and durations** come from Remotion's bundled ffprobe/ffmpeg (`remotion ffprobe`, `remotion ffmpeg`), read right after upload when the project is installed. A file uploaded before that is read once the setup finishes. A failure only hides the thumbnail. An image is its own thumbnail; audio has none (404).
- `GET media/:mediaId/file` sends the file with its type, `nosniff`, `inline`, and Range support (206, 416) for the players; an SVG gets `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`.

### Session and tool

- **Instructions** (`imagesSystemPrompt`): the shared parts of the writing tabs' instructions (the knowledge folder the agent may edit and must say so, `writing-style.md` with its General and platform section, the writing skill below) plus the job; the Concept; the post's platform, format, scheduled time, default size and count rule; the post's text (finalized, else its latest draft, else "No post text yet"); the finalized script's path or "No finalized script yet"; the knowledge folder with its brand file names and colours (copy a logo or font into `public/brand/` and load it with `staticFile`); the shared `src/brand/` warning; the Concept's media and `list_media`; no network requests; where to edit and the id rule; render only with `render_images`; alt text with `save_draft`; and the **human-content-writing skill** (images carry text), with the skill warning when its file is missing. All of it is a snapshot taken at session start.
- **Tools:** `get_concept`, `save_draft`, `list_media`, `render_images` (`studioTabs.ts` entry `images`). An images session calling `set_checklist`, and a script, post-text or video session calling `render_images`, is 409.
- **`save_draft` saves alt text:** one line per image (split on `\n` or `\r\n`, each trimmed), at most 20 lines of at most 1,000 code points each; empty or over is 400 naming the line and the limit. The number of lines need not match the number of images.
- **`render_images({ compositionIds, width?, height? })`** (relayed to `POST /api/studio-session/images`): 1 to 20 distinct ids, each one of this post's own stills (case-sensitive; else 400 field `compositionIds` naming the id). Checked in the Building's write queue, where the round's old images are deleted and the call recorded; then each still is rendered in order to `<concept>/posts/<postId>/images/round-<n>/image-01.png` … `image-20.png`. Limits: 60 seconds per image and 5 minutes per call (`STILL_TIMEOUT_MS`, `IMAGES_CALL_TIMEOUT_MS`; injectable as `imageLimits`); a timeout fails the call with "image 5 (<id>) timed out after 60 seconds" or "the render_images call ran over 5 minutes while rendering image 5 (<id>)". The answer is `{ round, images: [{ index, compositionId, width, height }], queued }`, or 409 "Render failed: …" or "The render was stopped". Refusals: 401 bad token, 400 no session id, 404 unknown session, 409 ended session, finalized asset, old round, or a call already running or waiting for that asset. The relay waits up to 62 minutes (a call may queue behind a video render), so it goes over `node:http`.

## Remotion tab (task 32.008)

Remotion Studio for the Building's shared Remotion project, at the tab's full width, so the owner can scrub the timeline, change props and watch the video update while the Video tab's agent edits the code. Server: `content/remotionStudio.ts` (the process, its job and events), `content/studioLoopback.cjs` (the bind preload), routes in `api/remotionStudioRoutes.ts`. Web: `ui/content/RemotionTab.tsx` (wired), `RemotionTabView.tsx`, rules in `lib/contentRemotion.ts`.

- **Enabled** when the Concept has a video or reel post and its composition exists: `ConceptView.compositionId` is the composition id once `remotion/src/concepts/<conceptId>/index.tsx` exists (the Video tab's session scaffolds it; Discard's fresh scaffold keeps it), else null. The web also learns it from the video pane's live view, so the tab enables without a reload when the session starts.
- **One Studio per Building**, shared by its Concepts. Opening the tab reads Studio, then `POST start`, which starts it or reuses the one starting or running. The iframe opens `<url>/<compositionId>`; another Concept reuses the same process at its own composition.
- **The process:** `remotion studio src/index.ts --port=<port> --no-open --force-new` in `<building>/remotion/`, in its own process group (Stop also ends the bundler it starts), on a free port that the daemon finds by binding port 0 on 127.0.0.1. Remotion 4.0.529 Studio has no host option and binds every interface (`0.0.0.0` or `::`), so the daemon preloads `studioLoopback.cjs` through `NODE_OPTIONS=--require`, which binds every server Studio opens to **127.0.0.1**. `--force-new` keeps Studio from handing over to another Studio already serving the project. It is running once it prints `Server ready … http://localhost:<port>` for that port; the url is `http://127.0.0.1:<port>`. No ready line within 2 minutes (`STUDIO_START_TIMEOUT_MS`) kills it and fails.
- **States** `stopped | starting | running | failed` (`GET` view: `{ state, url, error, log, waitingForSetup }`; "waiting for setup" is `starting` with `waitingForSetup: true`). The log keeps the newest 200 lines (`STUDIO_LOG_LINES`), each cut to 2,000 characters, colours removed; it is Studio's own output and may name project paths. Nothing else in the view or its events carries a folder path, pid, environment or command line.
- **The install:** if the project's install (Video tab, Shared Remotion project) is not done, a writable Building runs it, or waits for the one running, and Studio starts when it succeeds; a failed install fails Studio with the setup's message. In practice the composition only exists once an install succeeded, so this matters only when the marker file is gone.
- **Tracked job** `remotion-studio` in the status footer's running list as "Remotion Studio · <Building>" with "starting…" while it starts and **Stop** (`POST stop`); the starting-to-running change is sent at once, past the 1-second progress throttle. It is in `GET /api/content/jobs/running` and the `contentJob` event while it starts or runs.
- **It stops** on Stop (tab header or footer), when no Remotion tab of the Building has sent a heartbeat for **10 minutes** (`STUDIO_IDLE_MS`; the web sends `POST heartbeat` at once and every 60 s while the page is visible, none while hidden; the server owns the timer, which each start and heartbeat restart), on Building deletion, and on daemon shutdown (the `exit` handler kills every Studio's process group). Nothing is stored, so a daemon restart leaves none running. A daemon killed with SIGKILL (or by the OS) skips the `exit` handler, so its Studio, in its own process group, keeps running until killed by hand. Deleting a Concept leaves Studio running. A crash after it was running is `failed` with the exit code; Retry starts it again. After an idle stop the tab shows "Remotion Studio is not running." with **Start Studio**; becoming visible again only sends a heartbeat, it never restarts Studio.
- **Live state** over `/ws`: event `remotionStudio` `{ type, buildingId, studio }` on every state change, and at most once a second for new log lines alone. Known limit: the web store puts the answer of `start`, `stop` and `heartbeat` over the Building's view with no ordering check, so an answer read after a newer `/ws` event can show a stale state ("running" after a footer Stop) until the next heartbeat, up to 60 s.
- **Edits:** Studio hot-reloads the agent's code changes through Remotion's own bundler. A prop the owner saves in Studio writes the project's code as Remotion does; the video agent's instructions already say the owner may change props in Studio. The app renders only through the Video tab, but Studio's own Render button is not turned off; whether it renders from inside the tab is unchecked (manual checks).
- **Embedding:** the header always has **Open in a new browser tab** (the same url; disabled with "Available while Studio is running" until there is one) and Stop while it starts or runs. Remotion 4.0.529's Studio server sends no `X-Frame-Options` or `frame-ancestors` header (only `Cross-Origin-Opener-Policy`/`Embedder-Policy`, and only with cross-site isolation turned on, which the daemon does not), so the iframe is used (`STUDIO_EMBEDDABLE` in `lib/contentRemotion.ts`; `false` switches the tab to the fallback card "Studio can't be shown inside this app" with the url and the new-tab button). Checked in a real Chrome during Development (2026-10-27) against Remotion 4.0.529 installed from the scaffold, started by the daemon's own spawner: Studio showed inside a cross-origin iframe at `/<compositionId>`, hot reload repainted the preview within seconds of an edit to the Concept's `index.tsx`, pointing the same iframe at another composition switched to it, `lsof` showed it listening on 127.0.0.1 only (the LAN address did not answer), and stopping it left no process behind. Because the url is 127.0.0.1, Studio only shows in a browser on the daemon's own machine. Below 640 px the tab suggests the new browser tab.
- **Read-only Building (decision):** the tab is available and Studio may start, stop and heartbeat there (viewing changes no data; the global read-only guard exempts these three routes), but `POST start` is 409 "Studio can't start: this Building is read-only and the Remotion project still needs its packages installed." when the install is not done, and no install runs. ## Performance: targets, results and Insights (task 32.009)

Published posts get stats snapshots (above). This section judges them against **targets** set per platform and keeps a living **Insights** document that every content agent reads.

### Targets tab

A Building tab after Writing style (declared once in `CONTENT_TABS`, self-guarded). One card per platform (LinkedIn, Instagram, X, Facebook, Blog), each with a Save of its own, seven optional fields: views, likes, comments, shares, saves, engagement rate (percent) and followers gained. A field left empty is "Not set". There are no per-post overrides and no period goals.

- **Values.** Counts are whole numbers from 0 to 10^12; the engagement rate is 0 to 100 with up to 2 decimals. Anything else, a non-number, or an unknown field is 400 `{ error, field }` and nothing is saved. `PUT targets/:platform` keeps an omitted field and clears a field sent as `null`; an empty body changes nothing. An unknown platform path is 400 (`field: "platform"`).
- **Views rule.** LinkedIn and X count `impressions` as views; Instagram, Facebook and Blog use `views`. The tab labels the field "Impressions" on LinkedIn and X and "Views" elsewhere.
- **Edits apply to every post of the platform, including past ones**, because results are computed on read, never stored. `GET targets/history` lists the newest 50 changes (who, when, old and new values; only the web changes targets, so who is always Person). A save that changes nothing adds no entry.
- **Engagement** is likes + comments + shares + saves, leaving out empty values (null when all four are empty). **Engagement rate** is engagement / views x 100, rounded to 2 decimals, and `null` ("—") without views, with 0 views or without engagement, never 0 or infinite. The rule is a pure helper (`server/src/content/targetRules.ts`) duplicated in `web/src/lib/contentTargets.ts` and pinned by a test on one shared table.
- **Evaluation window.** Settings has **Judge a post after N days** (1 to 90, default 7).

### Results

A published post is judged on its newest snapshot captured at least N days after it was published (a snapshot exactly N days after counts):

- per set target field: **Hit** (value >= target, so a target of 0 always hits), **Missed** (value < target) or **No data** (the value is null). The engagement-rate field is judged on the derived rate after rounding to 2 decimals;
- overall: **On target** (every set field hit), **Partly** (some hit), **Below target** (none hit, including every set field having no data) or **No target** (the platform has no field set, which outranks Too early);
- **Too early**: no snapshot is that old yet, or the post has no snapshot at all. The result then carries `progress` (day of N, the judge date and the latest values) when there is a snapshot.

Every post in a Concept or post response has `result` (null while not published) with `overall`, `fields`, `judgedFrom`, `progress` and the latest snapshot's `engagementRate`. The post row shows an icon and a word per field plus the overall badge. The Content list has an **Overall result** filter (`result=on-target|partly|below-target|too-early|no-target`, 400 otherwise; a Concept matches when any of its posts does) and one summary line per platform with published posts ("LinkedIn: 4 of 9 judged posts on target"), counted over all matching Concepts, not only the page.

### Insights document

`knowledge/insights.md` is written by the app, never by hand: the **Owner notes** (the one thing the person edits, stored apart from the generated text and kept across refreshes) on top, then the generated text. An agent's edit of the file on disk is replaced at the next write. The file is created when a session starts if it is missing.

- **Generated by a headless one-shot agent**: the default coding agent, read-only (every tool disallowed except Read), in a throwaway folder, 5 minute timeout, injectable for tests. It reads a data file the daemon writes for the run and removes afterwards.
- **Input.** The newest 200 published posts that have stats. Per post: Concept title and brief; platform, format, published weekday and hour in the Building time zone; the finalized text (first 1,000 characters) and its length; the script's first 3 lines (the hook) and its start; video seconds or image count where present; the latest snapshot's counts and engagement rate; the target results. The file also carries the current targets, the evaluation window, the previous `insights.md` text and the owner notes. It holds no absolute path.
- **Output.** Strict JSON `{ "markdown": string }` (a surrounding json code fence is tolerated), non-empty, at most 30,000 characters (counted as code points). Sections: Summary, What works, What does not work, Hooks, Formats and length, Timing, Per platform, Open questions. Every claim names its evidence (post count and an example Concept title); a platform with fewer than 5 judged posts says "Not enough data yet (N posts)".
- **When it refreshes.** 10 minutes after the last stats save, edit or delete, an unpublish, a published-details edit or a window change (debounced: a burst gives one run, on the Building's own timer, nothing is carried across a restart); immediately after a target change; on **Refresh insights** (`POST insights/refresh`, 202). A refresh is 409 while one is running, and 409 with "nothing to learn from" when no published post has stats. An event during a run gives exactly one follow-up run. A due timer on a read-only Building does nothing, and a refresh or a notes save there is 409. Reads stay open.
- **Running state.** A run is a running item of kind `insights` in the status footer (the background-job plumbing of the Video tab) and can be stopped there or with `POST insights/stop` (409 when none runs). A stop is not an error and keeps the previous document.
- **Failure.** An invalid, over-long, late or thrown answer keeps the previous document, adds no version and sets `lastError { reason, at }` ("Last refresh failed: <reason>" in the tab, state `failed`). No notification is raised. A later success clears it.
- **History.** The newest 20 versions (time, trigger `stats`, `targets` or `manual`, post count, text) are kept; the tab shows a diff to the previous version with + and − marks.
- **Owner notes.** `PUT insights/notes` takes `{ content, version }` (the `notesVersion` of the last read) with the rule used for knowledge files: a stale version is 409 with `details.current` and nothing is saved. At most 50,000 characters.
- `GET insights` returns `state` (`never-run`, `ready`, `running`, `failed`), the generated `markdown`, `notes`, `notesVersion`, `lastError`, `updatedAt`, `postCount` and `nextRefreshAt` (when the debounce will fire, else null).

### What content agents get

The shared session instructions of every kind (script, post text, caption, blog, images, video) and the retro's instructions carry a **Targets and Insights** section: the targets of the platform or platforms the asset is for (a Concept-level asset uses every platform of its posts; a platform with none says "no targets set"), the path of `knowledge/insights.md` and the sentence "Read the Insights before proposing anything. Prefer what works, avoid what does not, and say which insight a choice follows." The retro agent has no tools and runs outside the Building's folder, so it gets the file as `knowledge/insights.md` plus the Insights text inline.

Every studio session (not the import session) also has the tool **`get_performance({ platform?, format?, result?, limit? })`** (`GET /api/studio-session/performance`): published posts with stats, newest published first, each with its latest counts and engagement rate, target results, finalized text (first 1,000 characters), hook and script excerpt. `platform`, `format` and `result` use the closed wire values (400 otherwise); `limit` is 1 to 100, default 20, and above 100 is 400, not clamped. Refusals: 401 bad token, 404 unknown session, 409 ended session. It does not require the session's asset to be unfinalized.

## Writing-style retro

Every time a written asset (`script`, `post-text` or `article`; never `image-set` or `video`) is finalized, a **retro** compares the agent's drafts with the finalized text and proposes changes to `writing-style.md`. Code: pure rules in `content/retroRules.ts`, rows in `content/retroStore.ts`, the agent in `content/retroAgent.ts`, the service in `content/retros.ts`; web helpers in `web/src/lib/contentRetro.ts`.

- **Trigger:** every finalize calls the shared hook `retros.assetFinalized(ctx, assetId)` (the studio finalize does, so the Script, Post content, Captions and Blog tabs all trigger it; a later tab with its own finalize must call it too). The finalize answers at once; the retro runs after it, in the background, and never fails or delays it. **Run retro** on a finalized text's pane (next to Reopen) runs one on demand.
- **Skip:** no drafts, or exactly one draft whose text equals the finalized text, is recorded as `skipped` ("Nothing to learn") with no agent call.
- **Input:** every draft of every round, oldest first with its round number, the finalized text, the label ("Video script" for a script, "<Platform> · <format>" otherwise) and the current writing style. All of it goes through secret redaction. **Decision:** the CLI chat transcripts are not read, nor any folder path or session id; the drafts and the finalized text are what the owner actually changed.
- **Agent:** a one-shot headless turn of the default agent in a throwaway folder, every tool disallowed, the CRM-agent pattern (injectable for tests). Its instructions include the human-content-writing skill text by the Script tab's rule (the "Writing skill file" setting, else the default path; a missing file runs without it). The wait is 60 seconds and runs outside the Building's write queue; only recording the outcome and applying go through `ctx.exclusive`.
- **Answer:** the turn's `text` must be exactly `{ "summary": string, "changes": [ { "section", "action": "add" | "replace" | "remove", "find"?, "text"?, "reason" } ] }` once surrounding whitespace is trimmed. No code fence, no words around it, no extra fields. Rules:
  - at most 10 changes;
  - `section` is one of the seven headings, case-sensitive;
  - `find` is required and non-empty for replace and remove, and not allowed on add. It must occur exactly once, case-sensitively, in that section's body (the heading line excluded, overlapping matches counted);
  - `text` is required for add and replace, not allowed on remove, at most 2,000 characters (code points), and never contains a line starting with `## ` (that would split the document into a new section);
  - `summary` and `reason` are non-empty text;
  - a change for a section whose heading is gone fails.
- **Outcomes:** an empty `changes` list is `nothing` ("Nothing to learn"). Anything else wrong is `failed` with a reason shown as "Retro failed: <reason>": "The answer was not the expected JSON (<why>).", "The agent did not answer within 60 seconds.", "No agent is available…", or the agent's own error, redacted and cut to 200 characters. A failed retro is never retried by itself; Run retro tries again. Valid changes become a **proposal**.
- **Applying** (`add` appends on a new line after the section's last line, or becomes the body of an empty section; `remove` of a whole line takes its newline; changes apply in order, each checked against the document as the earlier ones left it): a `find` that no longer occurs exactly once (the document changed since the proposal was made) or a result past 50,000 characters refuses the whole apply with **409 `{ error, code: 'content-conflict', details: { failed: [{ id, section, action, reason }] } }`** and writes nothing. An apply writes a history entry (who `retro`, summary "<proposal summary> (<diff summary>)"), logging an agent's on-disk edit first exactly as a person's save does, and records the new style version.
- **Proposals** (Writing style → Pending proposals, newest first): source (kind, platform and format, the Concept title as a link that opens it, time, "from N drafts in M rounds"), summary, and each change with a checkbox (ticked), its reason and a diff against the current section text (one line of context each side, `−` find, `+` text, a note when the section is empty or the `find` is gone). **Accept N changes** (or "Accept 2 of 3 changes"; disabled with a hint at 0), **Edit** (the `find` and `text` of each change as editable text; section and action stay fixed; **Apply edited changes** or Cancel), **Discard** (no confirm; a toast says Run retro gets a new one). A refused apply shows an alert listing each failing change and tags it "Can't apply"; leaving it out or editing its `find` lets the rest apply. After a manual accept, a writing-style editor without unsaved edits reloads; one with edits meets the stale-version banner on its next save.
- **Auto-apply:** with the setting on, a valid proposal is applied at once (history tagged "auto-applied"). One that cannot apply stays pending with "Auto-apply was refused, so this waits for you." and the reasons. Known gap: an auto-apply does not reload an open Writing style editor or its Change history (the `contentRetro` event refetches only proposals and the log); reopening the tab shows the new text, and a save from the stale editor meets the stale-version banner.
- **Retro log:** a closed "Retro log (N)" under the proposals: the newest 50 `failed`, `nothing` and `skipped` retros, newest first, each saying failed or Nothing to learn in words (the dot colour is extra). Proposals and applied retros are never listed there.
- **Status on the finalized text:** the studio view (`GET session` and each `studioAsset` message) carries `retro: { status: running | proposal | applied | discarded | nothing | skipped | failed, reason?, proposalId?, changeCount?, at } | null`, shown as a polite status line under the action bar with a link to the Writing style tab for a proposal or an applied one. A retro ending sends `{ type: 'contentRetro', buildingId, conceptId, assetId }` over `/ws` plus a fresh `studioAsset` view for an asset with a pane; the web refetches the proposals (badge) and the log.
- **Running** is kept in memory only (the 60-second wait stops waiting but does not stop the agent process, so after a timeout Run retro can start a second agent while the first is still finishing): a retro still running when the daemon stops is never recorded. One running for an asset makes Run retro 409; a finalize while one runs (after a Reopen) starts none. A retro whose Concept or Building is deleted while it runs records nothing; deleting a Concept removes its retros and proposals.
- **Read-only Building:** no retro runs; Run retro, accept, discard and the settings change are 409; every read is 200.

## Decisions pinned where the spec was open

- Omitted time zone at create is `UTC`; a zone must be spelled as `Intl` lists it (`europe/berlin`, `UTC+2` and offsets are 400).
- `scheduledAt` on the wire is an ISO instant with `Z` or an offset; the web converts the `datetime-local` text using the Building zone (a time in a daylight-saving gap lands just after the gap, a repeated hour reads as its later occurrence).
- The calendar week starts on Monday.
- Platform and format are fixed on a post; deleting a built-in section and a duplicate file name are refused (400, 409).
- Which Concept id is open, the List/Calendar choice and the Concept tab are not persisted.
- Video tab (32.007): the confirm message is neutral (each item with its linked files or "(no file linked)"; the approved mockup's "Not needed" list is not used); upload names are cleaned and suffixed while rename refuses; a rename keeps the extension; Retry setup is a repeat `POST session`; Finalize is 409 while a render runs or waits (and disabled in the web after the session ended); Reopen's checklist is pre-ticked but not confirmed; Confirm with an ended session is 409 and is not kept for Resume; only `h264`; checklist labels are single-line; media files also answer Range requests and an SVG is sandboxed; the Enter of the confirm message is a separate write 300 ms after the text.
- Video live preview (37.002): the preview is the embedded Remotion Studio (compositions are agent-written code only Remotion can bundle, so no custom player); there is exactly one render, started by Finalize, and the asset finalizes only when it succeeds. `POST finalize` of a video answers at once with the queued render and the outcome arrives through the published view (a render takes minutes, too long for one request). Finalize is allowed after the session ended while the Remotion project is ready, and a drafting round lists no non-final renders (a failure shows only as the alert). Renders the agent made before this change stay in the data; one that is a finalized video's content still plays and downloads in the Video tab (Publish does not serve it: see the known defect under [Publish rules](#publish-rules)). Known limits: the `done` render is published just before the finalize commit, so for a moment Finalize looks enabled and a fast second click would queue one redundant render (its finalize is a no-op); a failed finalize commit after a good render leaves the asset drafting with no error shown.
- Automatic starts (37.003): a reason the daemon kept is not retried when the tab opens; the owner presses **Start**, so a failed start never loops. The starts run after the finalize answers (the finalize route already holds the write queue), so right after finalizing a script the dependent tabs briefly show "starting". Known limits: the Concept tab strip has no per-tab state badge (the approved mockup's "Blocked" dot was not built; the post switcher chips and the pane follow `studioAsset` events); opening a tab right after finalize can race the queued start, and the loser's "already running" conflict may flash until the `studioAsset` event arrives; a Building switched to read-only between finalize and a queued start is not re-checked. Not covered by tests: the retry on Start after a failed Remotion install, and that an existing video session only gets the "script changed" flag.
- Images tab (32.006): a call clears its round's old images when it is accepted; a stopped or failed call keeps the images it made, but only a newest call that finished in full can be finalized; Start a new session archives the still code and Reopen keeps it; an omitted width or height falls back to the default on its own; duplicate ids in one call are 400; alt text is at most 20 lines and an empty draft is 400; a second call for the same set while one runs or waits is 409; output files are `image-NN.png`; still ids are `still-<post hex>-<file name>`; the image routes are found by asset id; the footer's Stop for an image render uses the images stop route.
- Thumbnail (37.004): a thumbnail is required for every video and reel post (in the Finalize post 409 `missing` list after the video); it is one asset per Concept, created with the first video post and kept when the last one is deleted; its calls reuse the `image_renders` table; it starts with the script (in parallel with the video) and after the video; it needs no finalized script; its style section is General; the pick is a file name from the current round's newest finished call (`{ file }`), so an earlier round's thumbnail cannot be chosen without rendering it again; Concept tabs and `conceptTabStates` are unchanged until the web tab task. Known limits: no web tab yet, so a session is started only by the automatic starts (or the routes), and the owner cannot pick the final thumbnail in the app yet.
- Remotion tab (32.008): Stop is in the tab header as well as the footer; the stopped text is the same after Stop and after the idle stop (no stop reason is sent); Studio never restarts by itself; the server, not the web, waits for a running install; a heartbeat on a stopped Studio starts nothing; the old `withComingSoon` helper is removed and Images keeps its post rule.
- Line comments (36.002): comments are on the Script tab only (the post tabs' result is not plain text); read-only disables the comment buttons with the read-only title while finalized hides them; the daemon checks the line's exact text and answers 409 when it changed; sent notes live only in the open pane (not stored) and clear on a new draft.
- Script footer and script-only drafts (37.006): the actions moved into the result pane's footer on every agent tab (the task allowed keeping the old bar; the approved mockup moved them); the speed has no reset to the default once saved; a corrupt stored speed reads as the default; the footer and the Settings field accept only ASCII digits (`0150` is 150; `+150`, `1e2` and Devanagari digits are refused); only the first problem of a refused script is reported.
- The New dialog differs from the first spec text on purpose (approved in UI planning): platform and format checkboxes with one date per platform and remembered choices per browser, instead of free post rows.

- Imported Concepts (37.009): the task's Import dialog and `POST concepts/import` were replaced in UI planning by an agent-led import session, on the owner's instruction, and the route was dropped, so only the session tool saves; files reach the agent as pasted text or paths; saving needs the owner's yes in the chat. Schema: `concepts.imported`, `concepts.importSessionId`, `posts.externalAssets`, `retros.sourceKind`. Import sessions have their own file because studio records need a Concept and asset. Learn is stored on the script asset because `retros.assetId` and `style_proposals.assetId` are required. Normal asset rows are kept and left out of `needs`. Blank post text means no text; a blank script is refused. There is no server duplicate check: the agent checks with `get_reference_content`. The real tab bar and post chips stay (not the mockup's per-platform text tabs). A text-less post on a read-only tab reads `No text was imported.`. After a save the session view stays open.
