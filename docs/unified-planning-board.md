# Unified Planning board

Planning and execution share the Tasks board. Projects open on Tasks, whose columns are Planning, Running, Needs you, and Completed. The Planning header starts a numbered **Plan & bugs** session (see [Plan & bugs](#plan--bugs)) or a standalone task with **Task**, and its play button starts several pending tasks at once (see [Starting several pending tasks](#starting-several-pending-tasks)). The earlier **Plan** and **Report bug** buttons are gone; sessions created with them stay as they were.

A planning conversation is shown as a tinted, explicitly labelled Planning group. Tasks created by that conversation remain nested beneath it while they are unstarted, in the order the user arranged them; tasks without a saved position, including ones the conversation creates later, follow at the end in creation order. Idle groups start collapsed; active conversations and conversations waiting for input start expanded. The task-count expander can be toggled independently of opening the conversation. The group summary reports ready work; its history counts started work that is neither ready nor completed, completed work, archived unfinished work, and removed tasks separately. The same history appears in the conversation detail, including after completion. Planning groups and standalone tasks share one persisted top-level order. A nested task can be dragged, or moved with Alt+Up/Down, within its own group only; dropping it at the top level or in another group cancels the move. The group order is saved by the daemon and is a run plan only: task numbers, titles, branch names, and stacking (which follows task numbers) do not change. A group's ready tasks can be chained so each waits for the previous one to be merged (**Chain tasks**; see [dependent tasks](dependent-tasks.md)); that sets dependencies only and changes none of those. A task waiting for its parents keeps its Planning slot and leaves it only when its run is accepted.

Dragging a ready task to Running opens the normal worker, workflow, and branch choices. The task remains in its exact Planning position until the start is accepted. A start refused by the quick checks (unknown agent, busy project folder, task limit and similar) does not change the board or planning-completion eligibility. Once a start is accepted the card moves to Running at once, showing **Starting** and the current set-up step (such as "Creating worktree"); the worktree, hooks and agent launch then run in the background. If a set-up step fails, the card moves to Needs you as Failed with the step and its reason, and Retry sets it up again.

## Starting several pending tasks

The play button (accessible name "Start pending tasks") sits first in the Planning column header and in the header of the **Pending only** view. It opens the **Start pending tasks** dialog, which lists every card the column can start, in board order: standalone tasks, tasks nested under a planning or Plan & bugs session, and bugs under a reference card, including those in collapsed groups. Sessions, reference cards, and tasks that are waiting, queued, running or stopped are not listed. With nothing to start, the button stays focusable but disabled, with the title "No pending task can be started from this column". Below 24rem of column width, **Plan & bugs** and **Task** show their icons only and keep their names as label and tooltip.

- **Rows.** Each row is a checkbox, checked by default, with the Task or Bug badge and number, "Needs more info" for such a bug, the title (two lines, full title on hover), and "Waits for #37.003" when the daemon reports unmerged parents (the Start task dialog's lookup; a failed lookup shows nothing). A task with workflows enabled but none preselected is listed unchecked and locked with "No default workflow · open the task to choose one", and is never sent. "5 of 7 selected", **Select all** and **Select none** count only the rows that can be checked.
- **Coding agent.** **Coding agent for all** preselects like the Start task dialog. Each row's picker starts at "Same as all · <agent>" and follows the common agent until the row picks its own; a row's own pick stays when the common agent changes. A pick that runs out of quota or is removed falls back to the common agent.
- **Auto-merge.** When the Building has a linked repository, **Auto-merge for all** sits under the common agent and is on every time the dialog opens; a task's own saved Auto-merge setting is not the default here. Each row has its own Auto-merge switch that follows the common one until the row is toggled; a toggled row keeps its value when the common switch changes, is shown in bold, and has **Same as all** to follow the common switch again. Each start sends the row's value, and the daemon saves it as the task's Auto-merge setting when the start is accepted, so a bulk start turns Auto-merge on for every started task whose row was not switched off. Without a repository neither switch is shown and no Auto-merge is sent. The switches lock with the agent pickers: while starts are sent, and afterwards except on a refused row, whose value Retry reads when it sends.
- **Options.** Nothing else is asked: each task starts with its default or Bug Fix workflow as the Start task dialog would preselect it, every step, and a separate branch when the Building has a repository. The dialog says so.
- **Start N tasks.** Starts the checked rows one by one, in board order, through the same request as the Start task dialog, so the next start is sent only after the previous one is answered and the waiting list fills in board order. Unchecked rows are not touched. A start at the task limit is queued as usual; a task with unmerged parents waits for them without a second confirmation; a refusal marks its row and the others carry on. Start is disabled with nothing selected, with no usable coding agent, or while parent lookups run, and a double click sends nothing twice.
- **Results.** Each row reads "Next in line…", "Starting…", then "✓ Started", "Queued (position N)" (its place in the Project's waiting list), "Waiting · starts by itself once its parents are merged", or "✕ Not started: <the daemon's reason>" in red. Unchecked rows read "Not selected · left as it is". The dialog cannot be closed while starts are being sent and never closes by itself afterwards; a summary line counts the outcomes, and **Retry failed (N)** sends only the refused rows again, with the agent and Auto-merge each one now has.

## Completing planning

A conversation becomes eligible for automatic completion after it creates its first task. Once none of its linked tasks remain ready in Planning, an idle conversation completes and moves to Archived. If the conversation is live, this check waits until the turn settles and reads the latest linked-task state again.

On a browser viewport wider than 1200px, the conversation detail opened from the Tasks board shows a task panel to the right of the CLI (30% of the width by default; see the swap control below) instead of the history strip above it. The panel header carries the same history counts. Below it the panel lists every linked task that is ready, started, or completed (archived completed tasks included; archived unfinished and removed tasks are left out), in the order the conversation created them, which never changes when a task's status or board position changes. Each row shows the task number, title, and a status badge: Ready, the board's own Running / Needs you / Stopped / Failed, or Completed. Before the conversation has created a task the panel reads "Tasks this session creates will appear here." Clicking a ready row expands it in place to the full task description and a Start button; several rows can be open at once, and they close again when the detail view is left. Start opens the same guarded Start task dialog as the board, and the person stays on the conversation: an accepted start changes the row's badge, a cancelled one changes nothing, and a refused one shows its reason in the dialog. Clicking a started or completed row opens that task's normal detail view, whose Back control returns to the conversation, including when starting its last ready task has just completed and archived it (or to the board if the conversation was deleted meanwhile). The panel header carries a swap control (a columns icon button, "Widen tasks" / "Widen CLI" as its tooltip and accessible name, with a pressed state). One click swaps the two widths exactly: CLI 70% / tasks 30% becomes CLI 30% / tasks 70%, and a second click swaps back. The CLI stays on the left and the list on the right, the CLI session is not restarted and refits to its new width, and expanded rows, list scroll position and keyboard focus on the control are kept. The control shows whenever the panel does, including with an empty list. The choice is held by the open project popup and applies to every conversation viewed in it: it survives Back, opening a task and returning, switching popup tabs, and the viewport dropping to 1200px or narrower and widening again. It resets to CLI-wide when the popup is closed and reopened, switched to another project, or the page is reloaded; it is not saved in browser storage or sent to the daemon. Open limit: the swap has been checked against the source and unit tests only, not yet in a real browser with a live CLI session (refit, no restart, no horizontal overflow just above 1200px with the CLI at 30%). At 1200px or narrower there is no panel and the history strip shows as before; resizing across the breakpoint swaps them without reconnecting the CLI. Reordering, editing, archiving, and deleting tasks stay on the board and in the task's own detail view.

An idle conversation can also be completed explicitly from its detail view. Any ready linked tasks then remain as standalone Planning cards at the former group's position, in the group's order, and keep their provenance. Their queue positions are saved independently, so deleting the completed conversation does not reorder them. A conversation that never created a task is never completed automatically.

## Archive and restoration

Archived is shared by tasks and completed planning conversations. Planning cards carry a visible Planning badge. Completing planning does not archive its linked tasks. Restoring planning makes the conversation resumable and regroups only linked tasks that are still unstarted in Planning, in their saved group order. Running, Needs you, Completed, archived, and deleted tasks remain in their actual states and appear only in the conversation history.

Card actions live in the corresponding detail view. Board and archive cards open details directly and do not have overflow menus.

Planning cards show a Planning status while the agent works and Needs you while it waits for input; an idle conversation has no status badge. Task cards show Running, Needs you, Failed, Stopped, or Completed when those states apply. The Planning type label stays visible independently of status and color.

## Bugs

A bug is a task of type `bug`. Every task has a type, `task` or `bug`, set when it is created and never changed; a task stored before types existed reads as `task`. **Task** and plain planning sessions always create a `task`. Only a Plan & bugs session, an earlier bug report session and a coding agent's bug-filing tool create a `bug`. There is no Bugs tab and no separate tracker: a bug is listed, started, archived and deleted like any task.

A bug card is a task card with a **Bug** badge in text. It is never a Planning card. It also shows a severity badge when one is set ("High severity"), a "Needs more info" badge, or "Enough info" as plain footer text. Its status badge is the board's own (Running, Needs you, Stopped, Failed, Completed; none before it starts), in every column and in Archived. Outside its group a bug card carries an "Introduced by <task>" link to the introducing task, or plain text once that task is gone.

A bug's extra attributes, shown on the card and in its detail view:

| Attribute | Values |
| --- | --- |
| Severity | `critical`, `high`, `medium`, `low`, or unset |
| Info status | `enough` or `needs-more-info`. Advisory: it never blocks filing or starting. The person can flip it in the detail view while the bug has not started (`PATCH /api/plan-items/:id` with `infoStatus`: 400 for a bad value or an ordinary task, 409 once the bug has started; a refused call saves no other field it carried) |
| Introduced by | The introducing task's id, with its number and title copied when the bug was filed, and the commit when found. Empty when unknown. A commit sent with no introducing task is dropped |
| Suspected location | Free text |
| Found while working on | Agent-found bugs only: the task whose run hit the failing test |

The description always has the same five sections: Summary, Expected vs actual, Steps to reproduce, Suspected location, Introduced by. A section nobody filled in reads "Unknown".

**Numbering.** A bug under a numbered task is `<task number>.<NNN>`, counted per introducing task: the first bug against `4.002` is `4.002.001`. A bug with no introducing task, or whose introducing task has no number, is `B.<NNN>`, counted per Project. A bug introduced by a bug appends another part (`4.002.001.001`). Numbers are never reused after a delete, and changing a bug's introducing task does not renumber it. Bug report sessions take their number from the same sequence as planning sessions. A bug's branch name does not carry its number: `4.002.001: Crash on save` started with Bug Fix runs on `bugfix/crash-on-save`.

**Limits**, in characters after trimming: title 200, description 20,000 (the composed five-section text; a coding agent's own failure description is limited to 18,000 so that it always fits once the sections and test ids are added), suspected location 500, commit 64, test case id 500, test suite and action ids 200. A value over its limit is refused with 400 and never cut.

### Where ready bugs sit

A ready (not started, not archived) bug waits in Planning. Ready bugs are grouped under an introducing-task reference card: a dashed card captioned "Introducing task" with that task's number, title and current status badge. It has no drag handle, is never draggable, starts nothing, and opens the task's normal detail view on click, Enter or Space. It shows for as long as at least one ready bug is nested beneath it, whatever the task's state (Completed, archived, Running, Needs you, Stopped, Failed). If the task was deleted, the card shows the stored number and title struck through with a "Removed" badge, and it cannot be focused or opened; the bugs and their "Introduced by" text stay.

If the planning conversation that created the introducing task is on the board, the reference card sits inside that conversation's group, after its ready tasks, and the conversation's expander reads "Planning · 1 task ready · 2 bugs" (the bug part is left out at zero). A collapsed conversation hides the card and its bugs. Otherwise the reference card sits at the top level of the column. A bug with no known introducing task is a standalone, draggable bug card at the top level. A bug leaves its group the moment its start is accepted.

Each group has its own expander, "Bugs · N ready", where N is the number of cards beneath it. A group starts expanded while its introducing task is Running or Needs you and collapsed otherwise. A toggle lasts for as long as the board stays mounted.

The Planning column's header counts top-level entries: a conversation, a Plan & bugs or bug report session (started or not), a top-level reference card, a standalone bug and a standalone task each count 1. A reference card under a conversation counts 0.

**Order.** Bugs under one reference card reorder by drag or Alt+Up/Down within that group only; a drop at the top level or in another group cancels. Unpositioned bugs follow the positioned ones in creation order. `PUT /api/projects/:id/planning-queue/bugs/:introducerId/order` saves it with `{ ids }`, which must be exactly the group's current ready bugs: 400 malformed, 404 for an unknown or other-Project task or bug, 409 for a stale or conflicting set. The group stays reorderable after its introducing task is deleted. Top-level reference cards and standalone bugs take part in the shared top-level order: `PUT /api/projects/:id/planning-queue/order` accepts a third entry kind, `reference`, whose id is the introducing task's id. A reference under a conversation is not a top-level entry (sending it is 409), and neither is a bug inside a group (404). A failed write restores the prior order. Reordering never changes numbers, titles, branches or stacking.

### Plan & bugs

**Plan & bugs** is the one entry point for talking work through with an agent. Its dialog takes the person's first description; the draft is kept per Project, apart from the Task draft. Sending starts a numbered session (`planningPurpose: 'plan-and-bugs'`, numbered from the same Project sequence as planning sessions): an interactive, read-only CLI session with no branch, worktree or coding slot, as for planning. With no coding agent available the button reads **Create session** and the session is created with no CLI, exactly as described for bug report sessions below. `POST /api/projects/:id/plan-and-bugs` replaces `POST .../bug-reports`; `POST .../chat` without `skipPlanning` now starts a Plan & bugs session too, so no new session of the two earlier kinds can be created. Existing planning and bug report sessions keep their tools, instructions, board appearance and resume behaviour; a follow-up stays the kind it continues. There is no migration.

The session has the union of the two earlier kinds' tools: `list_tasks`, `create_task`, `update_task`, `delete_task`, `create_bug`, `update_bug`, `delete_bug`, `reopen_bug`, and a new `set_dependencies`, with the same rules, limits, ownership and statuses as for a bug report session (it changes only items it filed that have not started: another session's item is 404, a wrong-kind id 409, a started item 409). Its tasks are numbered `<session>.<NNN>` and nest under its card like a planning session's; its bugs follow the bug numbering and placement rules.

**Dependencies.** `set_dependencies` takes `{ itemId, dependsOn, uiPlanningWaitsForParent? }` (`PUT /api/agent-bugs/:itemId/dependencies?taskId=`) and returns the updated item; `[]` clears. `uiPlanningWaitsForParent` (boolean, 400 otherwise; left out keeps the stored value) is the item's [UI planning waits for parent](dependent-tasks.md#early-ui-planning) setting; the session proposes it per dependent item and confirms it with the owner. The item must be a task or bug the session filed that has not started. Parents may be any task or bug of the Project that is ready, or started but not finished or merged; a merged, archived, failed, stopped, PR-conflict or testing-setup parent is 409. The existing limits apply unchanged (no cycle or self-dependency, 20 parents, chains of at most 10) with the same statuses: 400 malformed, 404 unknown, foreign or other-Project items, 409 for a cycle, depth, self-dependency, a started item or a Project without a linked repository. Only a Plan & bugs session may call it (an earlier bug report session or a plain planning session gets 409). See [dependent tasks](dependent-tasks.md).

**Merge or separate.** The session's instructions tell it: when one piece of work needs another's changes, and both serve the same purpose (the second is only a part of the first), merge them into ONE task; when they serve different purposes and one merely consumes the other, create two items and set the dependency so they run in order. It must explain its choice to the person. This is guidance only; the daemon does not enforce it.

**Interview and confirmation.** As in a planning session, the instructions require an interview before any task, bug or dependency is filed, even for a short request (one decision at a time, a recommended answer for each, facts from the code and git history), then a summary of scope, decisions and open assumptions and an explicit go-ahead before the first `create_bug`, `create_task` or `set_dependencies`. Each task, and each bug where it applies, carries the specification completeness checklist: testing expectations, schemas and API contracts, environment and baseline, UI decisions, wording that must stay, and criteria verifiable in this environment. A thin bug is still filed after the confirmation round, never refused. Like the merge-or-separate rule, this is prompt guidance; the tools do not enforce it.

**On the board.** The card is labelled "Plan & bugs" (lightbulb and bug icons), with the status "Planning" while the agent works, "Needs you" while it waits, none between turns, or "CLI not started". Its expander reads "N tasks ready · M bugs"; tasks nest under the card, and bugs sit under their introducing-task reference card or alone. Its detail view lists tasks and bugs in the **Session bugs and tasks** panel with a Task or Bug tag, the state badge, "Depends on" chips, expand-to-start and open behaviour; it is read-only for the person. Completion follows the planning rules over both kinds: eligible after its first task or bug, completed once idle with none left ready, never when it filed nothing; manual complete, archive, restore and delete work as for planning. The footer and sessions popover count it as a planning-type session (its ready count adds tasks and bugs); the Archived panel and the 3D village treat it likewise.

### Bug report sessions (earlier kind)

Sessions created with the removed **Report bug** button keep working as described here. The button opened a dialog for the person's first description of the defect. Its draft is kept per Project, apart from the Plan and Task drafts. Sending starts a numbered bug report session: an interactive, read-only CLI session with no branch or worktree that uses no coding slot. Claude CLI denies shell and file-editing tools and Codex runs in a read-only sandbox, as for planning.

If no coding agent is available, the dialog still accepts the description and its button reads **Create session**. The session is created with no CLI ("CLI not started"). Its screen shows the description, still editable, the shared coding-agent dropdown (unavailable agents listed but disabled), and **Start session**, which starts the CLI with the description as its first message. This replaces the earlier rule that an unavailable CLI gives the same refusal as Plan; the Plan dialog itself is unchanged. A not-started session survives a daemon restart, holds no slot, is never completed automatically, and can be archived or deleted by hand. Its number is taken when it is created, and its description is stored with the session on the daemon.

Routes (the create route is now `POST /api/projects/:id/plan-and-bugs`, same body):  `{ description, executorId? }` answers 201; without `executorId` the session is created not started. `PATCH /api/tasks/:taskId/description` saves an edit and `POST /api/tasks/:taskId/start-session` with `{ executorId }` starts the CLI. A blank description or one over 20,000 characters is 400, a missing `executorId` on start is 400, an unknown agent is 404 and an agent that is not an interactive CLI is 422 (the statuses Plan gives), and either call on a session whose CLI has started is 409. A refused start leaves the session not started.

On the board the session is a session card labelled "Bug report", with the status "Reporting" while the agent works, "Needs you" while it waits, none between turns, or "CLI not started". Its bugs are not nested under it: a line under the card says how many bugs are ready and how many tasks it filed ("2 bugs ready, 1 task filed"). Its detail view lists its bugs and tasks in a **Session bugs and tasks** panel (or the history strip at 1200px or narrower) with the same badges, expand-to-start and open behaviour as a planning session's tasks. A row shows its link to the bug or task it was filed with, and a started row carries a "Started – locked" chip; the panel is read-only, with no Edit or Delete buttons for the person. It follows the planning rules for completion, archive and restore, over the bugs and tasks it filed (a ready task keeps it open like a ready bug): eligible after its first bug, completed once idle with no ready bug left, never completed if it filed nothing. Bug report sessions are not counted as Planning conversations in the footer or anywhere else, and bugs never change a planning conversation's history counts.

The session has eight tools: `list_tasks` (every task and bug of the Project, with type and status), `create_bug`, `update_bug` and `delete_bug`, `reopen_bug` ([Reporting a regression](#reporting-a-regression)) and the task tools below. Only a running bug report session can use them, in its own Project, and apart from `reopen_bug` it can change only bugs it filed that have not started (a started one is 409, another session's or another Project's 404, and a task id passed to a bug tool 409). `create_bug` needs a title and an Info status; an introducing task that is unknown or in another Project is 404, and one that has never started is 400 with the reason. With `update_bug`, a commit stays with its introducing task: naming a different task drops the old commit unless a new one is sent, and `commit: null` clears it. A resumed or followed-up session is still a bug report session, with the same tools. A planning session's `list_tasks` shows bugs, but its `update_task` and `delete_task` refuse a bug with 409.

**Tasks from a report session.** Investigating a defect can show that part of the work is new capability or an improvement, not a defect. The session files that part with `create_task` (`POST /api/agent-bugs/tasks`): a title (at most 200 characters, optional when a description can stand in, in which case the background titler names it as on the Tasks board), a `description` that is the full brief (required, at most 20,000 characters; the coding agent sees nothing else) and an optional `relatedBugId`. There is no priority: plan items have none, and a stray `priority` is ignored. The task is created exactly as the Tasks board's create flow creates one (plain title with no number prefix, no bug number spent, the Project's default workflow when it is later started), appears in the Unstarted column like any task, and is **never started automatically**. `relatedBugId` must name a bug filed by the same session (any status); anything else is 400 and nothing is created. The link is a copy of the bug's number and title stored on the task (`relatedBug`), so it survives the bug's deletion, and the task records its filing session (`reportSessionNumber`). Both cards show it: the task reads "Related to 10.010.003: title" and the bug lists "Related task: title" for each task pointing at it; a removed bug shows struck through and is not clickable, and a deleted or archived task drops off the bug's card. `update_task` (title, description, `relatedBugId`, where `null` clears the link) and `delete_task` work only on a task the session filed that has not started (not pending, or any run or workflow run, makes it started): a started task is 409, another session's, a manual or a planning task, or one in another Project is 404, a bug id is 409. The session stays read-only for project files; only bugs and tasks are written. Its prompt tells it to file defects as bugs, use a task only for new capability or improvement, say which it chose and why, and never turn a defect into a task to avoid reporting it.

### Bugs found by a coding agent

A coding session files a bug with `report_unrelated_test_failure` when a test it ran failed and it judges the failure unrelated to its task. The tool comes with the testing tools: execute Tasks and workflow steps that may edit code get it; read-only steps, planning sessions and bug report sessions do not. The caller must be `developing` and in its Project's active set, so a settled or reopened session is refused with 409. It can only create. It sends a title, the suite id, action id and case id, and a description with the failure output (at most 18,000 characters). The bug is created "Needs more info", standalone, with "Found while working on" set to the caller's task. If an open bug (not completed, not archived) already exists in the Project for the same suite, action and case, the call answers 200 with `existing: true` and creates nothing; a new bug is 201.

### Starting a bug

The Start task dialog (see [default coding agent](default-coding-agent.md#start-task-dialog) for its field order, collapsed Steps and Auto-merge switch) preselects the workflow of the Software type's "Fix a bug" slot (Bug Fix by default) for a bug; any other workflow can be picked. If that workflow is disabled or missing, the Project's default is selected and a line says so. A "Needs more info" bug shows a warning line and Start stays enabled. Started without a workflow id, the daemon applies the same rule. Everything else is the normal run model. Filing a bug raises no notification.

### Reporting a regression

A bug is Completed once its Bug Fix run finishes, but the fix sometimes does not cure the problem. Instead of filing a new bug and losing the earlier investigation, the person (or a bug report session) reports a **regression** on the completed bug with a reason. The same bug goes back to work and every step of its workflow runs again as the next round, each step continuing from its own earlier conversation.

**Same bug.** Its number, title, type, introducing task and description do not change. Its card moves from Completed to Running with the board's normal running status, and returns to Completed when it finishes again; it can be reopened again. Archived and Completed counts as completed: reopening it unarchives it and returns it to the board. A task (not a bug) and a bug that is not Completed (not started, running, waiting, stopped, failed) cannot be reported; those already have Start, Retry or Resume.

**Round 2 on every step.** The reopen starts a new workflow run of the bug (the workflow its last run used while it is still enabled; otherwise the Start-a-bug rule: the bug workflow, else the Project's default, and the response says so in `workflowNote`). Every step of that workflow runs in order from the first, so nothing in it is hard-coded to RCA. A step shows the next round after the highest round it reached in the bug's earlier runs: Round 2 after one regression, Round 3 after the next. The run stores that as `regression.roundOffsets` (per step id), and the run view's round list and stepper badge add it to the run's own round count. The run view's round list for a step shows the earlier runs' rounds first (read-only: summary and session, no Quick look or commands, since they have no live working copy), then this run's, so Round 1 stays reachable from the bug (`getWorkflowRunDetail` returns them as `earlierRounds`, each with its `displayRound`). A step removed from the workflow since round 1 does not run; a step added since runs as its first round. Review and loop-back rules apply as normal inside the new round, and approval steps pause for the person again; reopening needs no approval of its own.

**Previous context.** A step resumes its own earlier conversation when that conversation can be resumed (its session file still exists and the same agent runs the step) and is sent the regression message only. Otherwise it starts a new conversation with the full briefing, its own latest output from the earlier run (saved under the new run's output folder, so the step may read it) and the same message. The message says plainly that this is a regression: the previous fix did not resolve the issue, the reasons are listed oldest first with date and reporter, and the earlier output is the starting point, not the answer. Reasons are quoted data in a fenced block longer than any backtick run inside the reason, so reason text such as markdown or "ignore previous instructions" is evidence for the agent, never an instruction.

**Fresh branch.** Round 2 always starts on a new branch and working copy created from the Project's current base branch, never stacked on another task's unmerged branch and never reusing the earlier run's branch name. The earlier run's code changes are not carried over: they are on the new branch only if they already reached the base branch, for example through a merged PR. The new round's Complete stage commits, pushes and raises a new PR like any run. The dialog says so in one line.

**The list.** Each report is stored on the bug as `regressions`: `{ reason, reportedAt, reporter }`, where `reporter` is `{ kind: 'person' }` or `{ kind: 'report-session', sessionNumber }`. It is append-only (never edited or removed) and oldest first on the wire; the detail view shows it newest first under **Regressions** with the date and who reported it ("You" or "Bug report session N"), and the card shows a "Regressed ×N" badge. It is returned wherever the bug's attributes are (`bug.regressions`, `[]` for a bug stored before this existed) and travels in the normal live plan-item events. The description is never changed.

**Reason.** Required: text, non-blank after trimming, at most 20,000 characters after trimming; a longer one is refused with 400 and never cut.

**Entry points.** Both start round 2 immediately.

- The person: **Report regression** in a Completed bug's detail view (also an archived one) opens a dialog styled like Reject step: the reason (with a counter, Submit disabled when blank or over the limit), a note that each step resumes its earlier conversation with the same agent, and a note that round 2 starts on a new branch, so an earlier unmerged fix is not on it. There is no agent choice: each step keeps the agent it had so its conversation can be resumed. A refused start shows its reason in the dialog, which stays open. `POST /api/plan-items/:id/regression` with `{ reason }` answers 201 with `{ item, run, workflowNote }`; anything else sent in the body is ignored.
- A bug report session: `reopen_bug` with `{ bugId, reason }` (`POST /api/agent-bugs/:itemId/reopen?taskId=`), for any completed bug of the session's own Project, with the previous run's agent (the default coding agent when it is gone). Only a running bug report session may use it (the same 401 and 409 as its other tools); coding agents in execute tasks and steps and planning sessions do not get it.

**Statuses.** 400 for a blank, over-long or non-text reason or a malformed body; 404 for an unknown bug or (tool) a bug of another Project; 409 for a task, a bug that is not Completed, or a second reopen while the first is running (the second finds the bug already running; the Project lock makes the check and the start one step). A start the Project refuses uses the Start task statuses (task limit reached 409, folder busy 409, unusable agent): the bug stays Completed, nothing is recorded and the archive flag is unchanged, because the reason, the unarchive and the new run are written together once the start is accepted and restored if it fails.

**Open limits.** Nothing here has been run against the real Claude or Codex CLI: that the read-only report session and the new tools are accepted without a prompt, and that an agent files only unrelated failures and sets Info status honestly, are manual checks the person owns. Resuming a conversation from a different working directory was not verified against the real Claude or Codex CLI, and neither was `reopen_bug` in a live report session or the Report regression dialog in a browser; the manual checks are the person's. The new run's working copy is created at the path the earlier run used, which should keep a step's saved conversation findable, but that is an assumption until checked; if it is not, the step starts a new conversation with its earlier output, as described above. Real simultaneity of two reopens is tested by firing both at once against the Project lock, and git branch and working-copy creation without a real repository (the accepted run's branch and startup steps are asserted, the git steps themselves fail in the test). A start-up that fails after the start was accepted (the worktree or the agent launch) ends the run Failed like any Start task, with the reason already recorded on the bug; only refusals before acceptance (task limit, no usable agent, workflow missing) keep the bug Completed with nothing recorded. A busy or missing Project folder can only be refused after the task limit on a Project without a repository, and a repository-backed run works in its own working copy, so that refusal is not separately reachable. The cards, the three-level nesting, drag, focus after a keyboard move and screen-reader announcements have been checked against the source and pure helpers only, not in a browser. A keyboard move announces "Moved bug up within its introducing task's group." (or "down"). Not built: a boundary announcement when Alt+Up/Down is pressed at the end of a group (nothing is announced, as for nested planning tasks), a spoken announcement when a reorder is refused (the prior order returns and the board's alert shows the reason), a link to the introducing task from the bug's detail view (its rows are plain text; the card's "Introduced by" link opens the task), and the Session bugs and tasks panel beside a not-started session is the ordinary empty panel. Also not built for tasks: a link line on Completed or Archived task cards (only the open board cards show it), and a task-to-several-bugs link (one task names one bug). A task's stored link text is a snapshot, so renaming a bug with `update_bug` leaves the task's link text stale. A task that is only waiting for its parents still counts as not started and can be edited or deleted by its session. The race between a person's Start and the session's `update_task` is serialised by the Project's planning lock but was only tested in sequence.
