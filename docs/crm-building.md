# CRM Building

The CRM Building (type id `crm`, `server/src/buildings/types/crm.ts`, code in `server/src/crm/`, routes in `server/src/api/crmRoutes.ts`, web in `web/src/ui/CrmWorkspace.tsx` and `web/src/ui/crm/`) manages **one sales pipeline for one owner**: cold outreach to very many prospects over several channels, disciplined followups, a calendar that turns due work into a daily agenda, meeting notes (MOM), customers with the other Buildings they use, and reports.

Tabs, first to last: **Calendar** (includes Today), **Prospects**, **Customers**, **Lost**, **Import**, **Merge**, **Notes (MOM)**, **Reports**, **Settings**. The contact opens in place of the tab area that listed it, with a back button, never as a tab. Prospects opens on a **Board** (one kanban column per stage; a card moves with a drag or its "Move to…" menu, with an optimistic move and an Undo toast) with a **List** alternative; Customers is a directory of person cards with a Grid/Table toggle. Every tab starts with a `PageHeader` and a KPI row counted from existing endpoints (see docs/design-language.md). `CRM_TABS` (server `crm/limits.ts`, web `lib/crmWorkspace.ts`) is the one declaration of the order.

## Creating one, storage, deletion

`POST /api/projects` with `typeId: "crm"` and a name (at most 80 characters). The type has no repository, no workflow slots and no capabilities.

- **Own database.** All data lives in `<data>/buildings/<id>/crm.sqlite` (SQLite through `better-sqlite3`, WAL mode), opened on first use by `crm/runtime.ts`. MOM attachments and audio are files in `<data>/buildings/<id>/crm-files/<momId>/<fileId>`. Deleting the Building closes the database (`onDeleting`) and removes the folder, including the secrets file.
- **Why not the bulk layer.** The generic bulk store (`docs/architecture.md#bulk-data-layer`) is insert-only with roll-ups; the CRM needs row updates, a unique normalised handle that moves during merge and undo, and multi-step transactions (merge, undo, segment moves, import commits). So the CRM keeps its own file and runs it **in the daemon's main thread**. This is a decision with a cost: a long synchronous write stalls the event loop. The only long write is an import commit; see [Limits and benchmark](#limits-and-benchmark).
- **One writer at a time per Building.** Every write route runs through `ctx.exclusive` (a promise queue per Building), so an import commit and a manual edit on one contact serialise. Tests force the second write at that gate.
- **Schema** (`crm/db.ts`): `contacts`, `channels` (unique on type, label, normalised handle), `timeline`, `followups`, `batches`, `merges`, `dismissed_pairs`, `moms`, `mom_files`, `building_links`, `slot_days`, `block_days`, `email_sends`, `meta` (settings JSON, SMTP status).

## Contacts and channels

A **contact** is a person with many **channels**: phone, email, Instagram, Facebook, LinkedIn and "other" (with a label). A contact is exactly one of **prospect**, **customer**, **lost prospect**, **lost customer**. Prospect stages are New, Contacted, Engaged, Meeting set, Proposal. Fields: name, company, job title (each at most 300 characters), tags, source (batch, "pasted list" or "added by hand") and custom text fields.

- **Handles are normalised** (`crm/normalize.ts`) so the same handle on the same channel type can exist on only one contact: emails are trimmed and lower-cased; phones may contain only digits, an optional leading `+` or `00` and the separators space, `-`, `.`, `(`, `)` and `/` (letters or other text, such as a name before the number, is "Invalid phone") and are reduced to digits (a leading `+` or `00` is an international prefix; otherwise the Settings default country code is added after one national leading 0 is dropped; with no country code set the bare digits are kept; more than 15 digits is invalid; full-width digits count); Instagram, Facebook and LinkedIn handles are lower-cased with the profile URL, `www.`/`m.` and a leading `@` removed (LinkedIn keeps `in/` or `company/` so the two never collide); "other" needs a label and the same handle under another label is a different handle. Phone handles saved before this rule that contain text ("Tarun Gera, +919910166500") are repaired once when the CRM database opens: the number run at the end becomes the handle and is re-normalised with the current country code, an empty contact name is set from the text before it, and a `channel_changed` timeline entry is written. A repaired number that already belongs to another channel is left unchanged and logged (`console.warn`) so the owner can merge by hand; nothing is merged or deleted automatically. A merge undo can restore an old row, which the next open repairs. A refused handle is 409 with `details.ownerId` and, when the owner is lost, `details.offerReopen: true`.
- **Custom fields.** Defined in Settings: name unique ignoring case (a duplicate is 409), at most 20 (the 21st is 400), values at most 500 characters (counted in code points). A contact stored before a field existed reads it as `""`. Deleting a field that holds values is **blocked with 409 and the count** (`details.inUse`); clear the values first. Deleting an unused field is 204.
- **Lost** keeps a reason from the Settings list (defaults: Not interested, No response, Wrong fit, Bought elsewhere, Do not contact, Other) and the date. Deleting a reason in use is **blocked with 409 and the count**; renaming one updates the contacts. **Reopen** returns a lost prospect to prospect (stage New, or the stage in the request) and a lost customer to customer.
- **Stage** moves automatically (reachout marked sent → Contacted; response interested → Engaged; a meeting or appointment created → Meeting set) and never backwards; by hand it can move anywhere, and Proposal is reachable only by hand.
- **Do-not-contact** per contact and per channel blocks every send (409), cancels that contact's open followups (all channels for the contact flag, that channel's chain for a channel flag) and writes a timeline entry. Clearing the flag does not bring cancelled followups back. A followup that falls due while do-not-contact is cancelled with the reason (not sent, not delayed). A channel can also be marked invalid.
- A contact needs **at least one channel**.

## Import (Import tab)

Three ways in: a **CSV file**, a **pasted list** (lines of one or more columns, mapped like a CSV) and **one contact by hand**.

- **CSV is two-phase.** `POST …/crm/import/csv/preview` saves nothing and answers the counts; `…/csv/commit` takes the same body again and recomputes (no token). The body is JSON `{ fileName, contentBase64, mapping, batchName?, tags? }`: 15 MB becomes about 20 MB of base64, which fits the daemon's 25 MB JSON limit. `mapping` is `{ channels: [{ column, type, label? }], name?, company?, title?, tags?, custom?: { fieldId: column } }`; one column per channel type, an unknown column is 400. Tags in a cell are split on `;` or `,`.
- **A pasted list detects the columns and suggests a mapping.** The owner pastes text and presses **Detect columns**, which calls `POST …/crm/import/paste/suggest` with `{ text, separator?, hasHeader? }` and answers `{ separator, hasHeader, rows, columns: [{ name, samples, byAgent }], mapping, agentUsed, agentError? }`. It saves nothing, so it is allowed on a read-only Building (the web still disables the whole Paste mode there, like CSV mode). Detection (`crm/pasteColumns.ts`):
  - The **separator** is tab, comma, semicolon or pipe, whichever splits the first 20 lines into the most consistent column count above one (a tie goes in that order); otherwise `none`, one column per line. Quoted cells are read the CSV way.
  - The first line is a **header** when its cells are distinct, non-empty names that are not handles, and a later line holds a handle or one of the names is a known header word. Without a header the columns are "Column 1", "Column 2", ….
  - The owner can override the separator (`tab`, `comma`, `semicolon`, `pipe`, `none`) and the header; the suggestion then runs again.
  - **Rules first.** Header names map the way the CSV header guess does (and a header equal to a custom field name maps to that field). Otherwise a column where more than half of the values normalise as emails, phones (5 digits or more) or Instagram, Facebook or LinkedIn profile URLs is that channel; a text column with a company marker (Pvt Ltd, Inc, LLC, GmbH, …) is the company, and the one remaining text column is the name. An empty column is ignored. A second column of a channel already taken, a bare `@name`, or two text columns the rules cannot tell apart are left **open**.
  - **The agent fills only open columns.** When a column is open, the header and at most 5 sample lines (stored secrets removed) go to the CRM agent (kind `mapping`, no tools), which must answer exactly `{ columns: [{ index, role, channelType?, label? }] }` with known roles and column indexes. A role the rules already gave another column is skipped. If the agent is unavailable, fails, takes over 60 seconds (`PASTE_AGENT_TIMEOUT_MS`) or answers anything else, the rule suggestion stands and the web shows "Suggested without the agent". The agent never blocks an import, and preview and commit never call it.
  - The owner checks the suggestion in the same mapping grid as CSV (plus the Other channel with its label), then previews and imports. `POST …/crm/import/paste` takes `{ text, mapping, separator?, hasHeader?, batchName?, tags?, commit? }` and goes through the same plan and atomic commit as CSV: `commit: false` is a preview (200, saves nothing), otherwise it commits (201) and recomputes from the same body. Both are 409 on a read-only Building. A line with a different column count is rejected as "Wrong column count"; at most 50,000 data lines (the header does not count). The batch is named `Pasted list <date>` by default (the date is the day in the Building timezone) with source "pasted list". The older body `{ text, channel, label? }` still works and reads each line as one handle of that channel; sending both `channel` and `mapping` is 400.
- **Import button never greys out for a missing step.** It is disabled only for a read-only Building or while busy. Clicking it checks `commitBlocker` (`web/src/lib/crmImport.ts`) and shows the first reason in the tab's error note: still reading the file, no channel column mapped, not previewed yet (changing a mapping needs a new preview), or the preview found nothing importable. Preview shares the channel check (`channelBlocker`). A pasted list follows the same rules ("Preview the list first, then Import."), and also needs its columns detected again after the text changes (`pasteBlocker`).
- **Limits** (named in `crm/limits.ts`): `CSV_MAX_BYTES` 15 MB (1 MB = 1,048,576 bytes) and `CSV_MAX_ROWS` 50,000 data rows per file; over either is 400 and nothing is saved. A UTF-8 byte-order mark is accepted; other encodings and binary files are 400. **Row numbers follow the source line**; a multi-line quoted cell is one row; blank lines are skipped but still counted.
- **The result** counts **added, already existing** (matched an existing handle), **duplicates inside the file** and **rejected** rows (line and reason; the list is capped at 1,000 with `rejectedTruncated`). An existing handle is not overwritten; the batch's tags and source go on the existing contact's timeline as "imported again". A match with a lost contact is reported in `reopenOffers`. A row with one handle seen earlier in the file and a new one adds the new channel to the first contact (and counts as a duplicate); against a contact already in the database no channel is added.
- **Every import is a named batch** (default `<file name> <date>`, the date being the day in the Building timezone; names are not unique). Lists and Reports filter by batch (`?batch=<id>`; an unknown batch in a query is 400).
- **Atomic commit.** A file is planned (parsed, normalised and matched against the database in chunks of 2,000 rows, yielding to the event loop) and then written in **one transaction**: either the whole batch lands or none of it.
- A cell starting with `=`, `+`, `-` or `@` is stored as plain text and gets a leading apostrophe on CSV export.

## Timeline and comments

Every contact has one timeline, newest first (ties broken by id), paged. Kinds are a closed list (`TIMELINE_KINDS` in `crm/timeline.ts`): added, imported again, stage changes, reachouts and followups (planned, approved, sent, failed, retried, cancelled, done, delayed), responses, comments, MOMs, merges and unmerges, segment moves, Buildings attached or detached, **Building work** (see below), do-not-contact changes, channel changes. Entries are append-only except comments: the owner can add a comment (at most 5,000 characters), edit it and delete it; an edit or delete writes its own entry, and a deleted comment shows as deleted. Editing any other entry is 409.

A reachout or followup **planned** entry reads `<title> planned` and stores its due time in `data.dueAt` (milliseconds); the web shows "<title> planned for <relative time>" in the Building timezone, exact time on hover. Planned entries written before this rule kept a UTC ISO time in their text ("… planned for 2026-10-26T09:30:00.000Z"); opening the database moves that time into `data.dueAt` once (`repairPlannedText` in `crm/db.ts`). That in-place rewrite is the only exception to append-only, and it writes no new entry.

## Merge (Merge tab)

**Manual merge** of two contacts (`POST …/crm/merge` with `firstId`, `secondId`, optional `keepSegmentOf: first|second`) and **suggested duplicates by name**: same name ignoring case and accents, and the same company when both have one. Suggestions are paged (`limit` default 50, max 200) and the scan stops at 5,000 pairs; a name shared by more than 20 contacts is read for its first 20. A dismissed pair (either order) is not suggested again.

- The merged contact keeps the first-picked contact's row and id. It has all channels of both (a handle never twice), the union of tags, the first-picked contact's custom value where both have one (the other's is kept as a "kept value" timeline entry), and a timeline **interleaved by time** with a "merged" entry. A customer beats a prospect and an active contact beats a lost one unless the owner chooses.
- Open chains are re-evaluated: if the result is not a prospect, either side is do-not-contact, or either side logged a stopping reply, every open chain is cancelled.
- A contact that was already merged away is 409.
- **Undo** (`POST …/crm/merge/:id/undo`, optional `assignLaterEntries: merged|first|second`) restores both contacts, their channels, flags and their own timeline entries, followups, MOMs and attached Buildings. Entries made after the merge stay with the merged contact or go where the owner assigns. It is **409 with `details.reason`** when one of the restored handles now belongs to a different contact (`handle in use`), when already undone, or when a newer merge involves either contact (undo that first).

## Reachouts and followups (the outreach engine)

A **reachout** is the first message to a contact on one channel (step 0); followups are steps 1 to N. **Chains are per channel, and a reply logged on any channel stops every chain.** Cadence defaults: followup 1 two days after the reachout was sent, followup 2 four days after followup 1 was sent (gaps count whole days in the Building timezone, from the actual sent time, and keep the local wall time across a daylight-saving change); both gaps (0 to 365), the number of followups (0 to 10, default 2), the retry delay (default 2 hours) and tries (default 3) are in Settings. A message-type item is drafted from the **template** for its channel and step (`email:0`, `instagram:2`, …; fields `{name}`, `{company}`, `{title}` and custom fields, matched ignoring case). An unknown field stays visible and is reported in `unknownFields`; a known field with no value renders empty. The owner edits the final message before sending.

- **Followup types:** call, message, email, DM, online meeting, in-person meeting, appointment, other. Only the message types carry a message (a message on a call, meeting or appointment is 400).
- **States:** planned → pending (due; waiting for the owner or for approval) → approved → sent, plus failed (retry later or in the catch-up), cancelled and done. An illegal move (approving a sent item) is 409.
- **The chain ends** when the last followup was sent and the last gap has passed with no reply (with 0 followups: the first gap after the reachout). The contact **stays a prospect, flagged "No response"**. With "auto-mark lost after the chain" on (default off) it moves to Lost with the reason No response. `resurfaceAt` is the chain end plus the resurface days (default 30; 0 turns it off); the contact then shows in the Expand Today series. A reply after the chain ended is accepted, applies its outcome and clears the flag.
- **Response logging** (`POST …/contacts/:id/responses`): `interested` (stops every chain, stage Engaged, needs a next action: a followup type and time), `not_interested` (stops chains, Lost with a listed reason), `later` (stops chains, stores the call-back date, which must be in the future, and schedules a call), `wrong_number` (marks that channel invalid and cancels its chain; if no valid channel is left the answer has `needsLostDecision: true` and nothing moves until the owner chooses), `no_response_yet` (the chain continues; the item leaves the catch-up for today), `became_customer`. A refused response changes nothing.
- **Non-message items (call, online or in-person meeting, appointment, other)** have no message and no reachout popup. The contact panel's "Waiting for you" list, the Calendar card and Expand Today (overdue group) offer **Mark done** (`POST …/followups/:id/complete`: state `done`, a `followup_done` timeline entry, counted in on-time reporting; only for planned, pending or approved items) and, on the contact panel and Calendar, **Notes** (the MOM dialog, `MomDialog`). The rule lives in `isMessageType` and `canMarkDone` (`web/src/lib/crmCalendar.ts`; `isMessageType` mirrors server `MESSAGE_TYPES`). Both controls follow `crmControlsDisabled`. The Prospects "Pending reachout" flag, the Pending reachouts KPI and the approval count (`PENDING_SQL`, `APPROVAL_SQL` in `server/src/crm/contacts.ts`) count message-type items only, so a pending call raises none of them (a phone-channel reachout is type `call`).
- **Manual flow** for message-type items on every channel except email: the Prospects row shows **Pending reachout**; its action opens a popup with the message, **Copy**, and a radio group (**Sent message on <platform>** with the platform pre-selected from the channel and changeable; **Message sending failed, I'll try again**; **Stop the followups**) and **Submit** (disabled until a choice is made). Sent marks it sent now, schedules the next followup by cadence and sets the stage Contacted. Failed returns it after 2 hours, up to 3 tries; the third failure puts it in the catch-up where the owner can **change channel**, **keep trying** or **stop**. Stop cancels that channel's remaining followups with an entry. Routes: `POST …/followups/:id/submit`, `…/catch-up`. A resolved item is 409; two simultaneous submits give one 200 and one 409.
- **Approval.** Email is the one integrated channel. By default every email waits for approval (`POST …/followups/:id/approve` sends, `…/reject` cancels). Settings → approval has a per-channel "send without approval" switch (email only has an effect; other channels always use the popup). Switching it on does **not** release items already waiting.
- **Agent drafting** (`POST …/followups/:id/draft`): by default the result is a **draft** stored beside the message; `…/draft/accept` (optionally with edited text) makes it the message, `DELETE …/draft` discards it. A Settings switch per kind (message drafts, MOMs) applies results without review (default off; the two switches are independent). An agent failure comes back in place as `agentError` and never blocks sending the template message.
- **The tick.** A daemon timer runs once a minute (`startCrmTicker`, unref'd, stopped with the server) and `POST …/crm/tick` runs the same work on demand (the web calls it when the Calendar or Expand Today opens, unless the Building is read-only): due items become pending (or approved for email with no approval needed), retries return, chains end, and approved emails are sent. **Reads never tick:** `GET …/calendar` and `GET …/expand-today` send no mail and write nothing. Ticks are idempotent and state is in the database, so a restart loses nothing. An approved email whose connection is not set up stays approved and shows "Email is not set up…" once (one timeline entry); an unexpected error is logged and the tick goes on. With "send without approval" on and no connection, `POST …/reachouts` is 409 before anything is created.
- **Changing the number of followups** mid-chain: open steps beyond the new count are cancelled (with an entry), and a chain whose last step was sent and not yet closed gets its next step when the count is raised. A chain that already ended (flagged No response) is not revived.
- **A send holds the Building's write queue.** The SMTP call (up to 15 s per protocol step) runs inside the per-Building queue, so a slow mail server delays other writes on that Building until it answers. Known limit, accepted for one owner per Building.

## Email over SMTP (the one real integrated channel)

`crm/smtpClient.ts` is a small SMTP client (EHLO, STARTTLS or implicit TLS or none, AUTH PLAIN, one message per connection) written without a new dependency. TLS certificates are checked. Settings → Connections holds host, port (1 to 65,535), security mode (`starttls`, `ssl`, `none`), user, from address, a **write-only password** and a test-send action.

- **The password** is stored in the Building's `SecretsStore`. `GET …/settings` returns only `smtp.status.passwordSaved`. A `PATCH` that omits `smtp.password` keeps the saved one; `""` clears it. The value never appears in a response, error body, log line, notification, timeline entry or the database file (the secrets file holds it, owner-only).
- **Status:** `not_connected` (no host, from address or password saved, or never tested or sent), `connected` (after a successful test or send), `needs_attention` with the reason (after a failed send that points at the connection: login refused, TLS failure, server unreachable, timeout). The next success clears it.
- **Limits** (editable): **50 emails per day** (the calendar date in the Building timezone) and **60 seconds apart**. An email beyond the cap waits for the next day and shows **"delayed by daily cap"**; one inside the gap shows "waiting between sends". `delayed` entries are written once.
- **Cold emails** (every email to a prospect, including followups; customers get none) end with the **editable opt-out footer** from Settings, added once. An empty footer adds nothing. A message may start with `Subject: …` on its first line; otherwise the subject is "Hello" for a reachout and "Following up" for a followup.
- **A send failure** shows its reason (a fixed phrase plus the server's own words, with secrets removed), uses the retry rules above, and for connection failures raises the notification `crm.connection_needs_attention` (severity `warning`, subject type `project`, one per Building until a send succeeds). A refused SMTP or third-party call on a request the owner made (the test send) is **502** `{ error }`; an unset connection is 409.
- SMTP gives no replies, so replies are logged by hand. Bounce detection is not built.

## Calendar (Calendar tab)

Default view: **Today, Tomorrow, Day after** in three columns, paged by day only (`GET …/calendar?from=YYYY-MM-DD`; `view`, `week` or `month` parameters are 400). "Today" is the calendar date in the Building timezone. **Overdue items lead Today**, oldest first, marked overdue.

- **Durations** (editable per type and per item): online meeting 30 min, in-person meeting 60, appointment 60, call 2, message 1.
- **Sessions:** due message-type items are grouped into blocks of **40 messages per 30 minutes**, due calls into blocks of **15 calls per 30 minutes** (both editable, never mixed). A block is one calendar item that expands to its items (the response carries the items; at most 60 blocks per day are returned, with `moreSessions` for the rest).
- **Working hours** (per weekday, plus timezone) bound the free time; fixed items (meetings, appointments) take their slots; remaining free time is filled with **suggested session blocks** that the owner accepts, moves (`POST …/calendar/blocks/:day/:key` with `action` `accept|move|skip`; a move onto another item or outside the hours is 409) or skips for that day.
- **Daily slots** (Settings; defaults "Reachouts" 60 min and "Finding new prospects" 60 min, each with a fixed start or "anywhere in free time"). A slot can be resized, moved or skipped for one day (`PUT …/calendar/slots/:day/:slotId`) without changing the default. An "anywhere" slot longer than the free time is flagged **no room** (it is not placed partly); a fixed-start slot over a meeting is flagged as a conflict.
- **Expand Today** (`GET …/expand-today`): cards one by one, in this order: (1) **sent items with no response logged** (older than the first followup gap and within the last 30 days), (2) **overdue followups**, (3) **items awaiting approval**, (4) **failed items whose retry is due and ones that used all tries**, (5) today's agenda with the free time allocated. An item appears in the first group it matches. A failed item waiting for its retry is not flagged overdue. The response carries each group's empty-state text and the total; "3 of 12" and Skip are client-side (Skip changes no state).
- The calendar shows Shorter, Longer and Skip-today buttons for slots; dragging a slot with the mouse is not built (the pixel/minute helpers in `web/src/lib/crmCalendar.ts` exist and are tested, but no handler uses them yet).

## Notes (MOM) tab

A **MOM** attaches to exactly one followup, meeting or appointment (`followupId`, `meetingId` or `appointmentId`; none or two is 400; a second MOM on the same target is 409) and appears on the contact timeline. It holds typed notes, a transcript, attendees (existing contacts), **attachments** (documents) and **audio notes** (saved as files), and action items that become followups in one click (a second click returns the same followup).

- **Files** upload as raw bytes (`POST …/moms/:id/files?kind=attachment|audio&name=…`, not base64 JSON, because 20 MB would be about 26.7 MB of base64 and break the 25 MB JSON limit). At most **20 MB each** and **10 attachments per MOM** (audio notes do not count); a file of 20 MB + 1 byte is 400; the route's body window is 21 MB, beyond which the answer is 413. Names are reduced to a plain file name; downloads go through the database id, so a path never leaves the Building folder.
- **Agent analysis** (`POST …/moms/:id/analyse`) turns notes, transcript and attachments into Summary, Decisions and Action items. The result is a **draft** (accept with optional edits, or discard) unless "apply without review" is on for MOMs. Failure is returned in place; typed notes still save.
- **Audio is best effort.** The file is saved and `POST …/moms/:id/transcribe` tells an agent to transcribe it with any tool available on the machine. If that cannot be done, the owner can paste a transcript, or the MOM is built from typed notes only. Each MOM shows its transcript status: none, automatic (agent) or pasted. **Whether a real transcription works has not been verified** (see Manual checks).
- The tab lists MOMs across contacts, paged, searchable by text (notes, summary, decisions, transcript), contact and date range.

## Customers, Lost and attached Buildings

**Mark as customer** is a manual action on a prospect (also available from response logging): it moves the contact to Customers, cancels open chains and stamps the date. A customer can have **several Buildings attached** (any other Building; the CRM Building itself is 400, an unknown one 404, a repeat 409, a prospect 409). Each attached Building shows name, type and status; for an SEO Building the latest report ("Latest report: …" or "No report saved yet") and for a Software Building the count of open tasks appear, read by calling the type's own read capability handler (`get-latest-report`, `get-open-tasks`) directly (not through a Building link, which would need a grant); other types show the basics only. A removed or type-unavailable Building reads as **unavailable** (never as empty); a read that is refused or fails marks that Building `read_failed` with its reason and never fails the page. Attach and detach are on the timeline. Each attached Building row also has a **Work log** (see Work updates from attached Buildings). The **Lost** tab has two sections, each with reason, date and Reopen, paged.

## Work updates from attached Buildings

Every task (board plan item) run on a Building that is attached to a customer leaves a plain-language update on that customer's card. It is an **internal record for the owner only**: nothing is sent to the customer, no follow-up is created, and Counts and Reports do not change.

- **Start and finish.** When a task's first run starts, a "Started: <task> on <Building>" entry is posted, using the task title only (no agent call). When its run completes, a "Finished: <task> on <Building>" entry is posted with a short summary. A failed, stopped or needs-attention run posts nothing; a later retry or resume posts only the "finished" entry, never a second "started". A task that started before the Building was attached posts "finished" only. After a detach nothing new posts and earlier entries stay. If the same Building is attached to several customers, each gets its own entries. Only current customers with the Building attached get entries.
- **The summary** is written by the CRM's own agent (the one used for message drafts and MOMs, with no tools and no new setting) from the task title and the run's final summary only, with stored secrets removed. If the agent is unavailable, fails, times out (60 seconds) or answers with nothing, the entry is still posted at once with the title plus the run's own final summary and marked **Not rewritten**. It is never retried. Titles are capped at 200 characters and summaries at 1,000; a task with no title shows "Untitled task".
- **Backfill.** Attaching a Building posts "finished" entries for tasks that completed in the **last 30 days** (inclusive), one per task, dated by when each finished and marked **Backfilled**, with the same summary rules and no "started" entries. It runs after the attach has answered, and a failure never fails the attach. Re-attaching never duplicates an entry.
- **No duplicates.** Each entry has a work key (customer, Building, task, phase) with a unique index on the timeline table (a nullable `workKey` column added by an in-place migration), so repeated events, a daemon restart or a backfill racing a live finish give one entry.
- **Work log.** The customers list returns, for each attached Building, its own started and finished entries newest first (the newest 50, `workLog`) and the total (`workLogTotal`). It stays readable when the Building is unavailable.
- **Read-only.** A read-only CRM Building (type unavailable, failed migration, newer data) writes nothing: no updates and no backfill. A missing Building or an unwritable database is logged and never affects the task.
- **Entries are permanent.** Editing or deleting a Building-work entry is 409, like every kind except comments.

## Reports (Reports tab)

`GET …/reports?period=day|week|month&date=YYYY-MM-DD&batch=<id>`: the period (ISO week with Monday start; month; day) by the Building timezone with the previous period for comparison. Numbers: prospects added, reachouts sent, followups sent, **on time vs delayed followups** (on time = completed within **30 minutes** of the due time, editable; delayed records its delay, and the longest is reported), lost prospects, lost customers, new customers. Breakdowns by channel and by batch or source. `GET …/reports/export?table=summary|by-channel|by-source` is CSV (`text/csv`; formula-looking cells get a leading apostrophe).

- Counts come from the stored timeline events, so they do not change when a contact later changes segment.
- **A metric with no recorded event in the period is `null` ("no data"), never 0.** A period before the first record says so (`beforeFirstRecord`, `firstRecordDay`: "No records before <date>"). This is read per metric: a real zero and "no data" are not told apart when nothing of that kind was recorded.

## Settings (Settings tab)

Cadence (gaps, number of followups, retry delay and tries, auto-lost, resurface), the SMTP connection, approval per channel, agent "apply without review" switches, templates, durations, session sizes, working hours and timezone, daily slots, lost reasons, custom fields, default country code (1 to 3 digits, with or without `+`), email footer and caps, on-time window. `PATCH …/settings` validates each field (400 `{ error, field }`), keeps the rest on a partial change, and is 409 on a read-only Building. Number fields refuse NaN, fractions, strings and values past a safe integer.

## Read-only Buildings

A read-only Building (type unavailable, migration failed, newer data) answers **409 `{ error: <reason> }`** on every write route and writes nothing; every read route still answers 200. The generic `readOnlyGuard` (`server/src/api/buildingRoutes.ts`) refuses every non-GET route before the CRM handler runs, so a POST that writes nothing (`import/paste/suggest`) works there only because it is listed in `MUTATION_EXEMPT`. The web disables every changing control through `crmControlsDisabled` (history stays readable).

## Errors and routes

Routes follow `{ error }` with 400 for invalid input, 404 for an unknown Building, contact or item (and for a CRM route on a Building of another type), 409 for a conflict or a read-only Building (with `code` and `details` when the refusal carries data), 413 for an over-large raw body and 502 for a refused SMTP call. All routes are under `/api/projects/:id/crm/`: `contacts` (list, create, read, patch; `channels`, `dnc`, `stage`, `lost`, `reopen`, `customer`, `responses`, `timeline`, `reachouts`, `followups`, `buildings`, `merges`), `followups` (list, read, `message`, `submit`, `catch-up`, `approve`, `reject`, `complete`, `draft`), `customers`, `lost`, `buildings`, `import/csv/preview`, `import/csv/commit`, `import/paste`, `import/paste/suggest` (allowed on a read-only Building), `batches`, `merge`, `merge/suggestions`, `merge/:id/undo`, `tick` (POST), `calendar`, `expand-today`, `moms`, `reports`, `reports/export`, `settings`.

## Decisions pinned where the spec was open

**How times show in the web.** Due and planned times, timeline entries, the MOM date, the lost date, "Customer since" and the Prospects "resurfaces" date are relative labels (`RelativeTime`, see [design language](design-language.md#components)) in the Building timezone, with the exact time on hover. Calendar session starts, working hours and the Expand Today agenda show clock times through `formatExactTime(…, false)`. Until `GET …/settings` has loaded, labels and the Work log use the browser's zone, never UTC. The Log response form's default "next action" or call-back time is now + 24 hours in the browser's local time (`localDateTimeInputValue` in `web/src/lib/crmOutreach.ts`), since a `datetime-local` input reads local wall time. Source checks in `web/tests/relativeTime.test.mjs` (S01–S02) keep `Intl.DateTimeFormat` out of `web/src/ui/crm/` and allow `toISOString` there only for API payloads and input values.

Chain end (above); footer on every email to a prospect; email gap minimum 0 and cap minimum 1; a duplicate custom field name is 409 and the 21st field 400; CRM routes on another type are 404; one MOM per target; batch names are not unique; a batch filter by an unknown id in a query is 400; a message on a call is 400; an active contact beats a lost one in a merge; undo is allowed only for the newest merge involving a contact; an empty-string password clears the saved one; a CSV travels as base64 JSON (fits the 25 MB limit) while MOM files travel raw; the notification kind and subject for a failing connection are named above. No length limit is enforced on templates beyond 20,000 characters, tags or batch names beyond 120 characters.

## Not yet implemented

- **Out of scope for this task:** providers other than SMTP (WhatsApp, SMS, call dialling, Instagram, Facebook and LinkedIn sending), reply or bounce detection, in-app audio recording, a built-in transcription provider, week or month calendar views, multiple users or teams, invoicing.
- Thinner screens: a slot is resized with Shorter and Longer buttons, not by dragging; the Notes tab creates a MOM from a calendar item's Notes button only. (Merge picks contacts by search and has a keep-segment choice for manual merges and accepted suggestions; Reopen has a stage choice for a lost prospect.)
