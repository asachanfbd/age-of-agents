# SEO Building

The SEO Building (type id `seo`, `server/src/buildings/types/seo.ts`) manages the SEO of **one site**. Several sites mean several SEO Buildings. The shell, Settings → Connections, Settings → Data and the daily snapshot store came first; the Pages, Sitemaps, Keywords, Backlinks, Internal links, Tasks and Reports tabs are described below. Every tab now has its own panel; the earlier "not set up yet" placeholder is gone.

## Creating one

`POST /api/projects` with `typeId: "seo"` and `siteUrl`. The site URL is normalised: http or https only, lowercase host, trailing dot, default port, query, fragment and trailing slash dropped, at most 2048 characters, no user name or password. `www.` is kept because it is a different Search Console property. An invalid URL is a 400 naming `siteUrl`. The name is optional and defaults to the host. The type has no repository; its non-secret settings live in `<data>/buildings/<id>/seo.json` and its secrets in the Building's secrets file; the Google OAuth client is shared by every SEO Building and lives in `<data>/secrets.json`. Deleting the Building removes its data folder (database, settings, secrets); a running sync is stopped first and a failed cleanup is logged without blocking.

## Data model

All data lives in the Building's own SQLite file (the bulk layer, `docs/architecture.md#bulk-data-layer`), never in the central JSON store, and every list is paged server side.

| Table | One row per | Notes |
| --- | --- | --- |
| `gsc_rows` | property, day, page, query | clicks, impressions, and `positionImpressions` (position × impressions) |
| `ga4_rows` | property, day, page | sessions, key events |
| `fetch_ledger` | dataset, property, day | whether the day was fetched, whether Google had finalised it, and its row count |
| `seo_keywords` | normalised keyword | only keywords the person, an import, research or a clustering run touched: display text, non-Search-Console sources, status, pinned, cluster, target page |
| `seo_clusters` | cluster | name, normalised name, pinned (renamed or created by hand) |
| `seo_keyword_volumes` | normalised keyword | Google Ads volume: `exact` or `range`, low, high, the day fetched |
| `seo_keyword_proposals` | research idea | pending, accepted or rejected, with its source (agent or Ads) and volume |
| `seo_cluster_suggestions` | suggested move | what a clustering run would do to a keyword the person placed by hand |
| `seo_keyword_runs` | clustering or research run | status, progress, notices, error, result |

- **`property` is part of every key and roll-up.** Changing property never merges two properties' totals; the old rows stay and are listed as the previous property.
- **Roll-ups** (`gsc_daily/weekly/monthly`, `gsc_page_day`, `gsc_page_month`, `gsc_query_month`, `ga4_daily/weekly/monthly`) are maintained in the same transaction as the raw rows. They only add, so average position is stored as Σ(position × impressions) and read as Σ(position × impressions) / Σ impressions; CTR is Σ clicks / Σ impressions; zero impressions reads as no value, not 0. Week keys are ISO weeks (UTC).
- **Atomic days.** A day is written with one `replaceRows` call: delete the day's rows (subtracting them from the roll-ups), insert the new rows, and update the ledger, in one transaction. A failure (disk full, crash) leaves the day as it was. A corrected day replaces the old one and the roll-ups stay equal to a rebuild from the rows.
- **Gaps are not zeros.** A day with no ledger row is "no data" (null). A fetched day with no rows is a real zero (CTR and position still null). `GET /api/projects/:id/seo/series?dataset=gsc|ga4&from&to&grain=day|week|month` returns this; a dataset that is not connected answers `connected: false` and no points.

## Retention: 12 months

Search and analytics rows (and their fetch records) dated **more than 12 months ago are discarded**. The window is a per-Building setting (1 to 36 whole months, default 12). Discarded detail is not kept as aggregates; the roll-ups are reduced to match. **Comparisons older than the window, such as year-over-year beyond it, are not available.** Settings → Data states this and shows the oldest data held.

- **Notice first.** Nothing is discarded, automatically or on demand, until the person has seen the preview (`GET …/seo/data/discard/preview`: counts and the cutoff) and acknowledged it (`POST …/discard/acknowledge`). Before that, the automatic job raises a notification instead of deleting, and `POST …/seo/data/discard` answers 409. Shrinking the window requires a new acknowledgement; growing it does not.
- **Automatic** retention is the platform's six-hourly maintenance, gated by the type's `retentionPlan`. **On demand** is `POST …/seo/data/discard` (202, a storage job; it also compacts the file so the size drops).
- The day exactly at the cutoff is kept; one day older is discarded.
- Syncing, discarding and property changes for a Building run one at a time (a second answers 409).

Settings → Data (`GET/PATCH …/seo/data`) shows storage size, a configurable size-warning threshold, rows per dataset, oldest data, the latest sync/backfill state, and the rule.

## Syncing

- **Backfill** on the first sync fetches up to the retention window (Search Console serves about 16 months, so the effective start is the smaller of the two), oldest day first. It is a background job with visible progress, throttled with a pause between days, and respects quotas. The ledger makes it resumable: after a restart only days that are not yet committed are fetched, with no duplicates.
- **Incomplete days.** Days Google still marks incomplete (Search Console's `first_incomplete_date`; Analytics days newer than two days) are stored with `final = 0` and refetched at every sync until final.
- **Daily refresh.** The platform scheduler runs agent workflows, not code, so SEO has its own hourly timer that syncs a Building whose last success is older than 20 hours, plus **Sync now** (`POST …/seo/sync`, 202; 409 if one is running) and an on-open sync (`POST …/seo/sync/on-open`, skipped when the last sync is under six hours old). The same timer resumes a backfill a restart interrupted.
- **Sync status.** A sync in which any dataset could not finish ends as **failed** (with the reason in Settings → Data and on the connection card), never "done"; days written before the failure are kept.
- **Failures** (expired sign-in, property access removed, quota, network) show in Connections as needs attention with the reason, raise a notification, keep previous data, and are retried at the next sync. Quota errors back off (1 s doubling to 15 min, or the service's `Retry-After` if longer); if the quota does not clear, the connection is left alone for 15 minutes.

## Connections (Settings → Connections)

Each connection is one of: not connected, connected (account, property), needs attention (reason), syncing (progress). Secrets are write-only: after saving, the browser sees only a "saved" flag; tokens and keys are not logged or kept anywhere but the Building's secrets file, and the Google client only in the app-wide `<data>/secrets.json`.

- **Google client (global Settings > Google (SEO)).** The person creates their own Google Cloud OAuth client of type **Desktop app** (loopback redirects need no registration) and saves its id and secret once, in the app-wide **Settings > Google (SEO)** tab. Every SEO Building signs in with that one client; a Building's own Settings no longer asks for it. Connections shows "Google client not set up yet. Add it in Settings > Google (SEO)." with an **Open Settings** button (it opens Settings on that tab) until a client is saved, and "Using the Google client from Settings." afterwards. Connect and Reconnect for Search Console, Analytics and Ads stay disabled, with that notice as the reason, until the client is saved. Saving again replaces both values; **Remove** (after a confirm) deletes them, which leaves existing connections in place but their next refresh asks to connect again. Both values are stored only in the app-wide secrets file `<data>/secrets.json` (owner-only permissions, registered for log redaction at startup) and are never returned or logged: `GET /api/settings/google-oauth-client` answers `{ saved }`, `PUT` takes `{ clientId, clientSecret }` (both non-empty strings, trimmed; anything else is a 400 `clientId and clientSecret are required`, with no length limit) and answers `{ saved: true }`, and `DELETE` answers 204, also when nothing is saved.
- **Moving off per-Building clients.** Before this setting, each SEO Building kept its own client id and secret. On startup the daemon copies the **oldest** SEO Building's full pair (by creation time, ties by id) into `<data>/secrets.json` when no app-wide client is saved yet, then deletes the client id and secret from **every** SEO Building, whether it matched or not; tokens, the Ads developer token, the Bing key and the IndexNow key stay. Running it again changes nothing. A Building whose sign-in was issued to a different client is refused by Google on its next token refresh (`unauthorized_client`, like `invalid_grant`, counts as an expired sign-in), so its card reads "Search Console no longer accepts the saved sign-in. Connect it again." (or Analytics); reconnecting with the app-wide client fixes it.
- **Google sign-in.** The app starts the consent flow per service; the redirect is `http://127.0.0.1:<daemon port>/api/seo/oauth/callback`, taken from the socket the request arrived on (not the Host header). The state is single use and expires after 10 minutes. Access tokens are refreshed automatically (two minutes before expiry; concurrent refreshes share one call). A revoked refresh token (`invalid_grant`) puts the connection in needs attention. **Disconnect** stops syncing, deletes the tokens and keeps the data. Multi-user Google app verification is deferred: until the OAuth app is verified, Google may show an "unverified app" screen and expire refresh tokens of a test-mode app after 7 days.
- **Google Search Console (GSC).** Scope `webmasters.readonly`. Dates are in **Pacific time**, so "today" for the sync is the Pacific calendar date and the newest fetched day is yesterday (Pacific). Pick the property from the list the account can see (`sc-domain:` and URL-prefix properties both appear). Changing property needs confirmation.
- **Google Analytics 4 (GA4).** Scope `analytics.readonly`; per-page sessions and key events per day (`keyEvents` is GA4's current name for conversions). Optional: without it the GA4 columns read "Not connected", never 0.
- **Google Ads (Keyword Planner), optional.** Needs an Ads account, a **developer token** Google has approved for standard access, a customer id and OAuth with the `adwords` scope. Low-spend accounts get volume **ranges** instead of exact numbers; the check reports `exact`, `range` or `unknown` and the UI labels it. The API version is a named constant (`ADS_API_VERSION` in `googleServices.ts`, currently v24; Google sunsets a major roughly 12 months after release, so it needs bumping from time to time) and a 404 from that endpoint is reported as an unsupported version or wrong customer id, not as refused access. Whether a volume is a range is a **heuristic**: volumes that are exactly 10, 100, 1,000 … are treated as ranges, so an account that truly returned such a number exactly is labelled "may be ranges". No range field was confirmed in the API; the check and the pinned version are unverified against a real account.
- **Bing Webmaster, optional.** API key only; the check confirms the key can see this site.
- **IndexNow.** A key of 8 to 128 letters, digits or dashes (generated if none is sent). It is public by design (the person publishes it as a text file on the site, see Sitemaps) but is still never logged and never returned by the API: the Sitemaps tab shows only a shortened key file name. Paid SEO tools are not connected; backlink data comes from CSV import.

## API summary

All under `/api/projects/:id/seo` and answering `{ error }` with 400 (invalid input), 404 (unknown or non-SEO Building) or 409 (state conflict): `connections` (GET; `googleClientSaved` reflects the app-wide client), `connections/:service/connect` (POST), `connections/:service/properties` (GET; 502 if the service refuses), `connections/:service/property` (PUT, `confirm`), `connections/ads|bing|indexnow` (PUT), `connections/:service` (DELETE), `sync` (GET, POST), `sync/on-open`, `data` (GET, PATCH), `data/discard/preview|acknowledge`, `data/discard`, `series`, `pages`, `pages/detail`, `sitemaps`, `sitemaps/read|reread`, `sitemaps/urls`, `sitemaps/urls/inspect`, `sitemaps/bing-check`, `indexnow/key-check`, `indexnow/submit`, `indexnow/log`, and the Backlinks routes listed in its section (a rate-limited action answers 429 with `details.retryAt`). The OAuth redirect target is `GET /api/seo/oauth/callback`. The Google client is app-wide: `GET`, `PUT` and `DELETE /api/settings/google-oauth-client` (see Connections).

## Pages tab

`GET /pages` lists every known page for a date range and the same-length range before it; `GET /pages/detail?url=` drills into one.

- **Pages.** The union of pages with Search Console data in either window, GA4 pages, and every URL in a read sitemap (crawled pages are not a separate source: a crawl adds link counts and the crawler-seen title and meta to pages that already exist). A page with no data in a window is not listed unless a sitemap or GA4 has it.
- **Range.** Default: the 28 days ending at the last final Search Console day (yesterday, Pacific time, when nothing is stored), compared with the 28 before. `from`/`to` (at most 400 days, not in the future, real dates) and `compare=none` override it.
- **Maths.** CTR is total clicks over total impressions; position is weighted by impressions; change is absolute and relative, `new` when the previous value was 0 and none when both are 0 or either side has no data. A window with no fetched day shows `null` ("no data"), never 0; a window with some missing days is flagged `partial` and totals cover only the days present. A page with no rows in a fully fetched window has 0.
- **Filters and sort.** Sort by path, clicks, impressions, CTR, position, sessions, key events (no-data rows always last); search is a case-insensitive substring of the URL; the path prefix is literal text; `no-clicks` means impressions above 0 and clicks 0; `no-impressions` means 0 impressions (pages with no data are in neither); `changed` keeps pages whose clicks changed and ranks them by relative change. Limits: page size 1 to 500 (default 50), offset up to 10,000,000, search and prefix up to 500 characters; anything else is a 400.
- **Drill-down.** Daily trend for both windows (gap days `null`), the top 100 queries for the page in the current window (`showingFirst` says when there are more), `crawl` (always `available: false` for now), sitemap membership and the last inspection. Queries only cover what Search Console reports per query: rare, anonymised queries are not in the data, so a page's queries can add up to less than its totals.
- **Reading cost.** Totals are summed in the storage worker (`groupSums`, capped at 500,000 groups per call, `capped: true` when hit) from the page roll-up (Search Console) and the raw rows (GA4). Drill-down looks Search Console up under the spellings it may have stored (both protocols, with and without a trailing slash, encoded or not); unusual spellings such as extra parameters are not matched.

### URL normalisation

One rule set (`server/src/seo/urls.ts`, `normalizePageUrl`) makes variants one page: `https` (http and https merge), lowercase host, fragment dropped, ports 80 and 443 dropped, trailing slash dropped except the root, tracking parameters (`utm_*`, `gclid`, `fbclid`, `msclkid`) removed, the other parameters kept and sorted, percent escapes upper-cased with unreserved characters decoded, path case kept, at most 2,048 characters. `www.` and the bare domain are **not** merged. Anything that is not an absolute http(s) address is rejected. A domain property (`sc-domain:`) covers its subdomains; a URL-prefix property covers its exact host and path.

## Sitemaps tab

- **Discovery.** `POST /sitemaps/read` finds sitemaps submitted in Search Console, listed in robots.txt (`Sitemap:` lines) and at `/sitemap.xml` (listed only when something is there), reads each, follows indexes (3 levels, 200 files per run) and stores the result in the Building's database (`seo_sitemaps`, `seo_sitemap_urls`). `POST /sitemaps/reread {sitemap}` re-reads one. Sitemaps no longer found are removed, except those known only through Search Console when it could not be reached, or only through robots.txt when robots.txt could not be read (a 404 means "none"; any other failure means "unknown"). Relative `Sitemap:` lines in robots.txt are ignored and shown as a note above the list.
- **Limits.** 50,000 URLs and 50 MB (uncompressed) per file; more shows "Showing first N". Fetches stop at the size cap while streaming, time out after 20 s and refuse redirects to another host. Gzip is detected by content, so `.gz` files, mislabelled files and `Content-Encoding: gzip` all work; a gzip that expands past the cap is refused. DOCTYPE and entity declarations are refused. URLs on other hosts, invalid or duplicate `<loc>` values are warnings and are not counted.
- **Coalescing.** The same action on the same sitemap shares one run; a different action on a busy sitemap (or any action during a whole-Building read) is a 409.
- **Fields.** URL, type, source, last read, URL count, warnings, Search Console errors, warnings, submitted and indexed counts (the indexed count is `null`, "no data", when Google does not send it) and last submitted and downloaded times. Without Search Console the tab still lists what could be read.

### URL inspection

`POST /sitemaps/urls/inspect {urls}` (1 to 200 addresses of the property) and a background pass run after the daily sync. Google allows 2,000 inspections per property per day, reset at Pacific midnight. **The last 200 are reserved for manual requests:** the background pass stops at 1,800 and works in this order: URLs the person asked for that are still waiting, never-inspected URLs, URLs whose `lastmod` is newer than their last inspection, then inspections older than 7 days (oldest first). The count is raised before the call to Google and written to disk first, so a crash can over-count but never under-count. If sign-in fails mid-request, the inspections claimed for URLs that were never sent are given back; a Google quota error marks the whole day used. A manual batch larger than what is left inspects what fits; the rest show "waiting for quota" and the background pass takes them first the next day. A Google quota error marks the day used up. Statuses are labelled as possibly hours or days old.

### IndexNow and Bing

- `POST /indexnow/submit` with `mode` `selected` (up to 10,000 URLs), `sitemap` (every URL, split into requests of 10,000; for an index, the URLs of all sitemaps below it) or `new-or-changed` (URLs first seen after the previous read of their sitemap and not yet accepted, plus URLs whose `lastmod` is later than their last accepted submission). It is only ever started by a person; sync, opening a tab, reading sitemaps, inspection and restarts never submit.
- URLs must be on the key's host. One submission per minute per Building (429 with `details.retryAt`). Identical concurrent requests share one run; a different selection is its own run and is refused with the rate-limit 429 rather than answered with the first run's result. A 429 from IndexNow stops the remaining batches; nothing is retried automatically. Answers are mapped to plain reasons (400, 403, 422, 429, 5xx); 200 and 202 mean "received", never "indexed", and the UI says so. IndexNow has no indexed status.
- The log (`GET /indexnow/log`) has one row per URL per submission (time, endpoint host, HTTP status, result, message), newest first (ordered by time, batch, URL so paging is stable), and keeps 50,000 rows (oldest whole submissions are pruned).
- `GET /indexnow/key-check` (`POST` forces a fresh check; cached 30 s) fetches `/<key>.txt` from the site and reports reachable, mismatch, not found, redirected, a web page, timeout or too large. An unreachable file warns but does not block a submission. The response and log never contain the key, only a shortened file name.
- Bing: the tab's "Check Bing" button (selected rows, up to 50) calls `POST /sitemaps/bing-check {urls}` asks Bing Webmaster `GetUrlInfo` and keeps the answers in memory; the column shows "Not connected" until Bing is connected, and a failure marks only that URL "Unavailable".

## Keywords tab

Keywords are shown in **clusters**. A collapsed row is a cluster; expanding it lists its keywords; opening a keyword shows the pages that receive impressions for it. Version 2 of the type adds the keyword tables (the migration has no SQL of its own: opening the database creates missing tables, after a backup).

- **Keyword universe.** Every query Search Console has reported (read from the `gsc_query_month` roll-up, so it is cheap), plus keywords added by hand (source `manual`), imported from CSV (`import`) or accepted from research (`research`). A keyword has a stored record only once something is done to it; until then it is implied by its Search Console data and is unclustered. A keyword that disappears from Search Console data keeps its record, cluster and (for the retained months) its history. A query that is empty or longer than 500 characters is skipped and counted (`skippedQueries`); it never fails a sync.
- **One keyword, one spelling.** `normalizeKeyword` applies Unicode compatibility form (full-width letters become plain), lower case, accent removal, collapses every run of whitespace (tab, newline, no-break space) to one space and trims. Punctuation is kept (`c++` is not `c`). Text that is not a string, is empty after trimming or is over 500 characters is refused. The first text seen is the display text. `Café`, `cafe` and ` CAFE ` are one keyword with all their sources.
- **Cluster rows (collapsed).** Name, keyword count, combined clicks and impressions, CTR (combined clicks over combined impressions, never averaged), position weighted by impressions, change in clicks against the previous period (the same `deltaOf` as Pages: relative, `new` from 0, none when both are 0), the best keyword (most clicks, then impressions, then alphabetical; none when the cluster had no impressions), the number of distinct associated pages (a union) and the volume sum. **Ignored keywords are counted** in every sum; status does not change the maths. A range with no fetched Search Console day shows `null` for every number (never 0); a partly covered range is flagged `partial` and the sums cover only the fetched days. Keywords in no cluster are the virtual cluster **Unclustered** (id `null`). An empty cluster in a covered range shows 0 clicks and 0 impressions with no CTR or position (the same as a keyword with no rows), not null.
- **Expanded rows.** Each keyword with the same metrics, its volume, target page, status (`tracking`, `target`, `ignored`), sources, whether it is pinned, and whether it is cannibalised. A keyword with a covered range but no rows has 0 clicks and no CTR or position.
- **Volume.** Google Ads Keyword Planner volumes are stored per keyword with their precision and the day fetched. A volume that is a power of ten (10, 100 ... 10,000,000) is Google's bucket for accounts with little spend and is stored as a **range** (the number up to ten times it); anything else is **exact**; a value that is negative, not a number, or above 1,000,000,000 is treated as unknown. A cluster's sum is **exact** only when every volume in it is; with any range the sum is a range (low and high are summed), and keywords without a volume are counted as `missing`. Without Ads the cell says "Connect Google Ads for volume"; with Ads connected but no volume for a keyword it is a dash.
- **Cannibalisation.** A keyword is cannibalised when **two or more pages each received at least 5 impressions for it in the range** (`CANNIBALISATION_MIN_PAGES`, `CANNIBALISATION_MIN_IMPRESSIONS` in `keywordRules.ts`). Pages are compared by normalised address, so `/a/`, `/a?utm_source=x` and `http://A.com/a` are one page. It is flagged in the list (and the `cannibalised` filter), on the cluster row (a count) and in the drill-down, which states the rule and lists the competing pages. Dismissing the warning in the drill-down is only state in that panel.
- **Drill-down** (`GET /keywords/detail?key=`). Pages for the keyword in the range with their own metrics (up to 100, by clicks; `pagesTotal` says if there are more), a day-by-day trend for both periods (days never fetched are `null`), the intended target page (the person's choice, marked on its row), status, volume and the cannibalisation block.
- **Range, sort, search, filters.** The range and comparison work as on Pages (default 28 days against the 28 before; `from`, `to`, `compare=none`; at most 400 days). The `tracking`, `target` and `ignored` filters apply to the keyword list only; cluster rows always combine every keyword in the cluster (status never changes the maths), so a filtered expanded list can show fewer keywords than the row's count. `GET /keywords/clusters` pages cluster rows (sort by name, keywords, clicks, impressions, CTR, position, change, volume or pages; filter `all`, `pinned`, `cannibalised`, `unclustered`; search matches a cluster name or any keyword in it). `GET /keywords` pages keywords (`cluster=<id>` or `cluster=unclustered` for one group, none for all; sort by keyword or the same measures; filter `all`, `tracking`, `target`, `ignored`, `pinned`, `cannibalised`, `no-cluster`; no-data and no-volume rows sort last). `limit` is 1 to 500 (default 50), `offset` 0 to 10,000,000, `search` at most 500 characters. The web list is windowed (only the visible rows are drawn) and asks for the next page near its end.
- **Export** (`GET /keywords/export`, same range and filters, **all** matching keywords, not one page): CSV with keyword, cluster, status, pinned, sources, clicks, impressions, CTR, position, change, pages, cannibalised, volume low, volume high, volume precision, target page. No data is an empty cell, not 0; text starting with `=`, `+`, `-` or `@` gets a leading apostrophe so a spreadsheet does not run it as a formula.
- **Import** (`POST /keywords/import`, `{ csv }`, at most 5 MB and 50,000 rows): a header row with a `keyword` column (also `query`, `term`) and optionally `cluster`, `status` and `target page`. The reply counts `added`, `existing`, `duplicates` (repeats inside the file) and `rejected` rows with their line and reason. A named cluster is created if missing and pins the keyword.
- **Limits chosen here** (the spec did not give them): keyword and cluster name 500 characters, 500 keywords per bulk move or split, 10 competitor domains, a competitor host of at most 253 characters, 500 keywords per clustering run, 100 per agent request, 5 minutes per agent request, 200 proposals per research run.

### Clusters you can edit, and pinning

A keyword belongs to exactly one cluster or none. Edits are applied all or nothing, one at a time per Building: **rename** (pins the name), **create**, **merge** (moves the keywords and keeps their pins; the target keeps its name), **split** (selected keywords go to a new cluster; refused when nothing, or every keyword, is selected), **delete** (the keywords go to Unclustered and are unpinned, so a later run can place them) and **move** (to a cluster or to Unclustered). Moving or splitting **pins** the keywords. A duplicate cluster name (compared without case, accents or spacing) is a 409.

### Clustering by an agent

`POST /keywords/cluster-run` starts a run (202) over the keywords; `GET` gives its status (`queued`, `running`, `succeeded`, `failed`, `stopped`, with progress and notices); `POST .../stop` stops it (409 when none is running). One run at a time per Building (409).

- **Cost and cap.** The agent is one headless claude/codex turn per batch (the same executor choice as task naming), so cost is LLM usage. A run sends at most **500 keywords** in batches of 100: keywords nobody has placed come first, then placed ones the person has not pinned, then pinned ones (the agent may only comment on those), each group by impressions, highest first. When more exist, the run says "Processed 500 of 600 keywords this run ... Run again to place the rest."
- **Nothing changes until every batch answered.** A failed, stopped, timed-out or malformed batch leaves the clusters exactly as they were. Output is checked (`{ clusters: [{ name, keywords }] }`, names 1 to 500 characters); keywords the agent was not sent are ignored, a keyword listed twice is placed by its first group, an omitted keyword stays where it is, and a name matching an existing cluster (without case) reuses it.
- **Manual edits are never overwritten.** The result is applied at the end against the state *at that moment*: a pinned keyword is never moved, even one pinned while the run was working. Where the agent would move a pinned keyword, the run records a **suggestion**; `GET /keywords/suggestions`, `POST /keywords/suggestions/:id/apply` (moves the keyword and keeps its pin; a suggestion whose keyword has since moved is dropped with a 409) and `.../dismiss`. A pinned cluster name is never changed by a run. A run left "running" by a daemon restart is closed as failed.

### Keyword research

`POST /keywords/research-run` with optional `competitors` (domains or URLs; `https://Rival.com/path` becomes `rival.com`; localhost, IP addresses, other schemes and more than 10 are refused). The agent gets the top queries, the site's top pages, the competitors and the keywords already known, and proposes ideas. When Google Ads works and a language and location are set (`PUT /keywords/market`, numeric Ads ids such as 1000 and 2840; the web sets them under Settings → Connections → Google Ads, and `GET /connections` returns them as `keywordMarket`), Keyword Planner ideas and volumes are added. Ideas already tracked, pending or rejected (compared by normalised keyword) are not proposed again. Proposals wait in a review list (`GET /keywords/proposals`): **Accept** adds an unpinned, unclustered keyword with source `research`; **Accept into cluster** places and pins it; **Reject** keeps it from being proposed again. Accepting twice is harmless. Nothing is tracked until accepted. `POST /keywords/volumes/refresh` refreshes volumes for up to 1,000 tracked keywords.

- **Without Ads** the run still proposes keywords and the response and UI say "Connect Google Ads for volume". A missing language or location says so and asks no volumes.
- **Ads quota, access or sign-in errors** do not fail the run: the agent's proposals are kept, the run shows `adsError`, the Ads card in Settings → Connections shows the same text as "needs attention", and stored volumes are untouched. A later good run clears the message. A failed refresh keeps the old volumes.

### Safety

A read-only Building refuses every keyword change (409) but can still be read. No credential, token or key is returned or logged; agent and Ads messages shown to the person never include a response body.

## Backlinks tab

Backlinks come from **manual CSV import** only; no paid source is connected. The storage (`seo_backlinks`, `seo_backlink_batches`, `seo_backlink_mappings`, added by version 3 of the type) holds normalised links, so a paid provider could write the same rows later without changing the tab. Without data the tab says so and offers the import.

- **Import wizard** (a dialog): pick a file, choose a format and say whether it is a **full export** or a **partial update** (no default: a wrong guess would mark links lost). Formats are the presets **Ahrefs**, **Semrush**, **Moz** and **Google Search Console**, a saved mapping, or **manual mapping** (every field is chosen by hand and can be remembered under a name; a saved mapping that names a column the new file lacks is refused with that column). The preview shows how rows map, counts, a sample, problems with row numbers (header is row 1; blank lines are dropped before numbering, so a row after a blank line is numbered one lower than its line in the file) and, for a full export, how many links would be marked lost. **Nothing is saved until the person confirms**; if there are problem rows the button reads "Import N valid rows" and the server refuses the commit without `confirm: true`.
- **Presets are unverified.** Their header names were written from the tools' documented exports and checked only against fixtures; a real export may need the manual mapping. Header matching ignores case, spacing and punctuation. Semrush's "Page ascore" is read as the source DR and Moz's Domain/Page Authority as DR/UR. The Search Console links report has no DR, so its preset maps only source, target and a date.
- **Files:** `.csv`, `.tsv` and `.txt`. Encoding is detected (UTF-8, UTF-8 with BOM, UTF-16 with BOM, otherwise Windows-1252), and so is the delimiter (comma, semicolon, tab, pipe). Binary files and zip-based formats (`.xlsx`) are refused. The cap is **15 MB** (`limits.backlinkFileBytes`; 500,000 rows): the file travels as base64 inside the daemon's 25 MB JSON body, so the 100 MB shown in the mockup is not reachable. The file is split into cells in one pass, then its rows are checked in chunks (`limits.backlinkChunkRows`, 5,000) with a yield to other requests after each, so a large import does not hold the daemon. A file over the cap is refused with 413 and a message naming the limit.
- **Row rules** (named constants in `backlinkRows.ts`): source URL must be a full http(s) address of at most 2,048 characters; a relative target (`/pricing`) resolves against the site address; a target on another host is **kept and flagged** `otherHost`; DR and UR are 0 to 100 (decimals, or a decimal comma, allowed); traffic is a whole number (a thousands separator such as `12,400` is read); non-numeric text in a metric column is a row error, a blank is null. Dates are ISO (`2026-10-01`, with or without time or offset), from 1990-01-01 to tomorrow; `10/01/2026` is refused as ambiguous; first seen after last seen is an error; missing dates are the import date. Link type is follow, nofollow, sponsored or ugc (several allowed, `dofollow` means follow); anything else is a row error. The anchor is trimmed and whitespace-collapsed (case is kept) and at most 1,000 characters. Columns no field uses are kept as extras (at most 50 columns, 500 characters each). Values are stored raw; formula-like text is escaped only on CSV export.
- **Identity and updates.** A link is the normalised source URL + normalised target URL + anchor. Duplicates inside a file keep the first row and list "Duplicate of row N". Re-importing updates matches: a value the file leaves empty never overwrites a stored one, first seen keeps the earliest date and last seen the latest, notes are kept.
- **Lost links.** Only a **full export** marks stored, not-yet-lost links absent from the file as lost (with the day); a **partial update** never does. A row that is invalid but still names a link does not mark it lost. A lost link listed again is live again (not new). A full export with no valid rows is refused. **Status** is `new` for links first brought in by the latest import, `lost`, or `live`.
- **Atomic.** Links, the batch record and a remembered mapping are written in one storage step, serialised per Building, so a failure leaves the previous state intact. Deleting a batch is not possible; a single link can be deleted after a confirm click in the detail panel (the server's DELETE takes no confirm flag).
- **Views and numbers.** Table (source, target, anchor, type, first and last seen, status, DR, UR, source traffic, linking-page metrics in the detail panel, extras), **New in period** (first seen within the period) and **Lost in period** (the day a full export marked it lost), **referring domains** (links, best DR, total source traffic: the sum over the domain's links, so a tool that repeats domain traffic on every row inflates it), **target pages** (links, referring domains, best DR). Periods are 7, 28 or 90 days ending today (UTC), the first day included. Rollups and the summary count live and new links only. The summary shows total backlinks, referring domains, new and lost in the period, and the average DR (mean of each domain's best DR, over domains that have one, one decimal) with "n of m links have DR". `www.` and subdomains are separate domains. Filters: status, link type, DR range (links without DR are excluded when a bound is set), domain, target page, search (literal text in source, anchor and target), sort (empty values last either way) and CSV export that honours them.
- **A missing metric is `null` in the API and a dash in the UI, never 0.** The first column set is Source URL, Source domain, Target URL, Anchor, Link type, First seen, Last seen, Status, Lost on, DR, UR, Source traffic, Page DR, Page UR, Page traffic, Other host, Note, then the extras.
- **API** (all under `/api/projects/:id/seo/backlinks`): `GET /` (filters, sort, `limit`, `offset`), `GET /overview`, `/domains`, `/targets`, `/batches`, `/mappings`, `/export`, `POST /import/preview` and `POST /import` (body `{ fileName, content (base64), format, mapping, mode, confirm, rememberAs }`), `PUT /:uid/note`, `DELETE /:uid`. The list route reads all of a Building's links and filters in memory (the same approach as Keywords); a very large link set is slower than the Pages and Keywords lists.
- **Create tracking task** opens the Tasks panel's New task form prefilled for the backlink (`prefill.backlink` in `web/src/lib/seoTasks.ts`); the task is linked to the backlink and shows on its detail.

## Tasks tab

One list for everything done on the site: **manual** tasks a person tracks, **scheduled** data fetches and **agent** tasks. Code: `server/src/seo/` (`taskRules.ts`, `taskStore.ts`, `tasks.ts`, `agentTasks.ts`, `proposalRules.ts`, `scheduledActions.ts`, `taskPorts.ts`), `server/src/api/seoTaskRoutes.ts`, `web/src/ui/SeoTasks.tsx` and the files beside it.

- **Statuses.** Five groups: Not started, Running, Needs approval, Done, Failed / Blocked. A manual task's status is set by the person (to do, in progress, blocked, done, cancelled; cancelled counts as Done and is labelled so). An agent task takes its status from its workflow run, then from what happened to the approved proposal (handed off is Done, a failed handoff is Failed). A scheduled fetch takes it from its job and newest history entry (never run, running, last run OK, last run failed, paused, turned off after failures). Setting a status by hand on an agent or scheduled task is a 400.
- **Overdue** means a manual task with a due date before today (a plain calendar day in the Building's timezone, else the host's) that is not done or cancelled. One `seo.tasks_overdue` notification (warning) per Building lists them; it is raised when the set or a due date changes, not on every check, and resolved when none is left. It is re-checked on every task write and hourly.
- **Linked items.** A task may link to a page, keyword, cluster, backlink or sitemap. The link must exist when the task is made (a page only has to be on the site) and the task keeps a text snapshot, so it still reads sensibly if the item leaves the data; the detail and the related-tasks block flag it "no longer in data". Related tasks (`GET /tasks/related?type=&ref=`) include done ones and show on the Pages, Keywords and Backlinks drill-downs.
- **Limits** (`TASK_LIMITS` in `taskRules.ts`): title 500 characters, notes 20,000, 20 evidence links of at most 2,048 characters (http or https, no user name or password), due date `YYYY-MM-DD` from 2000-01-01 to 2100-12-31, 100 pages per agent run, list `limit` 1 to 500 and `offset` up to 10,000,000. Unknown request fields are ignored; optional fields are `null` when empty. The default order is newest updated first.
- **API** (under `/api/projects/:id/seo`): `GET /tasks` (filters `kind`, `group`, `owner`, `due`, `linkType`, `search`), `POST /tasks` (201), `GET /tasks/related`, `GET|PATCH|DELETE /tasks/:taskId`, `GET /tasks/:taskId/csv`; `POST /agent-tasks` (202), `POST /agent-tasks/:id/stop|approve|refresh`, `GET /agent-tasks/:id/proposal` and `proposal.csv`, `PUT /agent-tasks/:id/proposal/rows/:rowId`, `POST .../proposal/decide-all`, `POST .../handoff/retry|manual`; `GET|POST /schedules`, `GET /schedules/cron-preview`, `PATCH|DELETE /schedules/:jobId`, `POST /schedules/:jobId/run`, `GET /schedules/:jobId/history`. Errors are `{ error }`: 400 invalid input, 404 unknown task or Building, 409 conflicting state (deleting an agent or scheduled task through the task route, approving with nothing accepted or twice, editing a running agent task).
- **Scheduled fetches** are scheduler jobs whose target is `{ kind: 'action', actionId }` (see `docs/scheduler.md`). The six actions are `sync` (waits for the sync), `sitemaps` (refresh plus URL-inspection pass), `crawl`, `indexnow` (new and changed URLs), and `report-weekly` / `report-monthly` (save the last full week or month as a report; see the Reports tab). Cron, history, overlap, failure counting and auto-disable are the scheduler's. A run refused because a sync or crawl is already going, or because of the IndexNow one-per-minute limit, is recorded as skipped and does not count toward auto-disable.
- **Agent tasks** start a normal workflow run of one of five slots of the SEO type, so they also show on the global board with the Building's name: `seo-keyword-research`, `seo-keyword-clustering`, `seo-title-meta`, `seo-content`, `seo-audit`. The Catalog decides which workflow fills each slot; defaults are `catalog/workflows/seo-*.json`. Title/meta, content and audit end at an approval step. **Research and clustering answers are applied to the Keywords tab automatically once the run succeeds** (research as proposals to review, clustering as placements and suggestions); they have no approval step because they change no site content. The in-process runs started from the Keywords tab are unchanged. The agent's answer is read from the run's step output as JSON.
- **Proposal review.** Current against proposed title and meta per page, with counters (title 30 to 60, meta 70 to 160 characters, counted as code points), Accept, Edit and Reject per row (editing without choosing accepts the row; an edit is capped at 500 and 1,000 characters). Approve needs at least one accepted row; pending rows are left out. Approving also approves the run's waiting step.
- **Handoff.** With the Building linked to a Software building that grants `start-planning-session`, the accepted rows go into the call's `prompt` (a call is made as a person, so Connections may hold it for approval; the task then shows "Handoff waiting for approval" and follows the call). The session id and its status are recorded on the task, and one manual follow-up task ("Publish: …") is made. With no usable link, or a prompt over 10,000 characters (never truncated), the accepted rows become one manual task with a CSV. A failed handoff shows its error and offers Retry (one session) and the manual task (one). A handoff claim cut off by a restart is closed as failed. Mockup 4 said the proposal is "attached as a document"; the capability takes only a text prompt, so the text is embedded.
- **The SEO Building never edits the website.**

## Internal links tab

A **crawler and a link graph** for the one site. Code: `server/src/seo/crawl/` (`runner.ts`, `fetchPage.ts`, `parse.ts`, `robots.ts`, `analysis.ts`, `views.ts`, `store.ts`, `rules.ts`, `site.ts`), `web/src/lib/seoInternalLinks.ts`, `web/src/ui/SeoInternalLinks.tsx` and the Graph, Matrix, Compare and Crawl log views beside it (the log: `server/src/seo/crawl/crawlLog.ts`, `web/src/ui/SeoCrawlLogView.tsx`).

### Libraries

| Job | Library | Why |
| --- | --- | --- |
| HTML parsing | `cheerio` | Maintained, tolerant of broken HTML. Anchors, title, meta, canonical, `<base>`. |
| robots.txt | `robots-parser` | Group choice, `Allow`/`Disallow` precedence, `*` and `$` wildcards, `Crawl-delay`. |
| Graph drawing | `sigma` 3 (WebGL) with `graphology` and `graphology-layout-forceatlas2` | WebGL draws a few thousand nodes; the ForceAtlas2 layout runs in a worker for a time that shrinks with graph size (`layoutBudget`), then stops. Above 400 nodes labels are off; above 800 edges are thinned. |

Fetching is Node's own `fetch`, with redirects handled by hand.

### Crawl rules (stated on screen next to **Crawl site**)

- **Discovery.** Seeded with the home page and every sitemap URL already read (Sitemaps tab). **First run:** creating an SEO Building starts a background first run (`server/src/seo/firstRun.ts`, called from `seoLifecycle.created` without awaiting): it reads the sitemaps, then starts the first crawl. Errors are logged, never thrown; `deleting` calls `forgetFirstRun` first so no crawl starts for a deleted Building (delete waits for an in-flight sitemap read, bounded by the fetch timeout). `seoDeps.firstRun` switches it off for tests. **Self-heal:** a fresh (non-resume) crawl, manual or scheduled, that finds no stored `seo_sitemap_urls` first calls `refreshSitemaps`, before `loadRobots`, so a robots.txt failure cannot block the sitemap fetch; a Stop during that fetch ends the run as stopped. A site that has no sitemap is therefore requested at `/sitemap.xml` on every crawl (the first run passes the internal `sitemapsChecked` option so creation fetches once; the HTTP route does not expose it). If the fetch finds nothing, only the home page seeds the crawl, the snapshot says so (`seededFrom: 'home'`) and the tab shows a "No sitemap was loaded" note for that snapshot. Then anchors are followed breadth first. **No JavaScript is run**; a site whose links appear only after scripts run shows few links and is flagged "may be incomplete" (HTML pages average under 1 internal link, with at least 3 pages).
- **Same site only.** The Building's `siteUrl` host is the site; `www.` and the bare host are one site, written as the Building's own host. Every other host (and subdomain) is *external*: links to it are counted per page, never requested. A redirect to another host is recorded, not followed. A redirect that only switches `http`/`https`, `www.`/bare host or adds/removes a trailing slash is the site's own: the crawl learns the origin from the first scheme or `www.` redirect (per run, relearned on resume), requests every later address there, and re-requests the page that redirected. Without this every page would read as a redirect to itself and the snapshot would hold 0 pages and 0 links. `mailto:`, `tel:`, `javascript:`, `data:` and bare `#fragment` links are skipped.
- **Politeness.** Defaults and allowed ranges (`rules.ts`): page cap 3,000 (1 to 10,000), 2 requests per second (0.1 to 10), 15 s timeout (1 to 60), 2 MB per page (0.1 to 10). One request at a time. robots.txt is always obeyed (it follows the same own-host redirect, and its rules apply to the whole site whichever origin is requested; a disallowed address is never requested and shows as blocked); `Crawl-delay` slows the crawl, capped at 10 s. A missing robots.txt (4xx) allows everything; a 5xx or no answer **refuses the crawl** and says why. A 429 (or 503 with `Retry-After`) is retried up to 3 times, waiting `Retry-After` or 1, 2, 4 s, never more than 60 s; then that page is marked rate-limited and the crawl goes on.
- **Endless URL spaces.** Addresses are normalised as everywhere else (`normalizePageUrl`: tracking parameters and fragments dropped, parameters sorted). Then an address is skipped (counted as "skipped: URL space") if it has more than 3 parameters, more than 10 path segments, a path segment repeated 3 times, or the path already has 20 different query strings.
- **Size and type.** The body is cut off at the size limit while it streams (a declared `Content-Length` over it is refused up front); the page is recorded as too large and not parsed. Only `text/html` and `application/xhtml+xml` are parsed; other types are recorded and their links are not followed. gzip/deflate are decoded by `fetch`.
- **Never credentials.** Requests carry only a user agent (`agent-visual-os-seo`) and an `Accept` header: no cookies, no `Authorization`, no Google token. Links with a user name or password are dropped.
- **Redirects.** Each hop is a recorded page. A link to a redirecting address is attributed to the **final page** and keeps the address it pointed at (`via`), so it can be flagged "redirect link". A loop or more than 10 hops marks the first address failed. A page that redirects to its own key (same key after normalising: a scheme, `www.` or trailing-slash change) is re-requested at most twice, at the literal `Location` (`/about` to `/about/` is requested as `/about/`; page keys stay slash-less, relative links resolve against the real URL); a robots-disallowed target is not requested and the page shows as blocked. Anything else that comes back to the same address is a loop (`CrawlSite.sameKeyRedirect` decides). A link to a page that ends in 4xx/5xx (or failed) is flagged **broken**.
- **Counting.** Inbound = distinct linking pages (self-links excluded); outbound = distinct target pages; every occurrence stays a link row with its anchor, `nofollow` flag and location (nav, header, footer, body: footer beats nav beats header; no landmark is body). Nofollow links are still followed for discovery. Depth is the fewest clicks from the home page (home = 0; unreachable = none). **Orphan**: in a sitemap, not the home page, no inbound link. Links to pages the crawl never fetched (page cap, URL-space skips) are dropped and counted.
- **Run control.** `POST /internal-links/crawl` starts (202) or, with `{"resume": true}`, continues an interrupted run. A start while one runs is **409** with `code: "crawl-running"` and `details.runId`. Both starts are decided before the first `await`, so two simultaneous requests give one 202 and one 409. Stop (also during a pause for pacing or back-off) saves what was fetched, with the page being fetched kept on the queue, as a **partial** snapshot and keeps the queue so the run can resume; a run found marked running after a restart is reported as stopped and resumable. A failed run (for example robots.txt) keeps the previous snapshot.
- **Snapshots.** One file pair per crawl under the Building's `crawl/` folder (pages and links, plus a small meta file), dated, labelled Complete or Partial, with a "capped" note when the page cap ended the crawl. The newest 10 **complete** snapshots are kept, plus the newest 2 partial ones, so stopped runs never push out complete snapshots to compare against. A stopped or failed crawl never touches an earlier snapshot. Snapshot ids are validated before they reach a file name.

### Screens

- **Crawl bar**: Crawl site, progress (fetched, queued, failed), Stop, Resume, snapshot picker, settings form (robots.txt checkbox is always on), the rules line, and banners for partial, capped, "may be incomplete" and the crawl-quality warning (below).
- **Graph**: nodes are pages, sized by inbound links or clicks from home, coloured by section, status or indexing state. Filters: section, status, max clicks, min inbound, search (Enter selects the first match). Highlight chips (combine freely): orphans, deeper than 3 clicks, fewer than 2 inbound links (home excluded), broken links, redirect links. Click a page for who links to it and where it links, with anchors, location and nofollow, redirect and broken badges, its external link count and "Open in Pages tab". Without WebGL a message replaces the canvas.
- **Matrix**: rows and columns chosen by section or search, at most **30 each**; a cell shows the link count (anchors and locations on hover, click to pin); totals; **Export CSV** (`POST /internal-links/matrix/export`; cells starting `=`, `+`, `-`, `@` are prefixed with an apostrophe).
- **Crawl log** (fourth view, after Compare): for the selected snapshot, one row per address the crawler requested, **in request order** (redirecting, failed and robots-blocked addresses included). Columns: `#`, address with "from" under it (`sitemap`, the linking or redirecting page's address, `start page` for the home page of a crawl not seeded from a sitemap, `unknown` for snapshots saved before this view), status (a dash when no answer came), content type, redirect target (a "to itself" badge for a self-redirect), error (robots, network, timeout, too-large, rate-limited, redirect-loop, too-many-redirects) and the internal and external link counts. A summary line sits above: requested, OK, redirected, failed, links found. Each address is in one bucket: **failed** (any error or 4xx/5xx) beats **redirected** (has a target) beats **OK** (2xx, no error); so a self-redirect, which also carries `redirect-loop`, counts as failed. Anything else (for example a 304, or a 3xx without a target) is **other**, shown on the line only when it is not zero, so the buckets always add up to requested. Internal links = the raw internal links found on the page (duplicates, self links and links to addresses never crawled count; at most 500 per page); external = the existing `externalLinks`. Snapshots saved before this view fall back to unique outgoing pages for the internal count.
  - **Filters** (single choice, each chip shows its count): Redirects, 4xx/5xx, Errors, Self-redirects, Zero links found (the same test marks the amber count cells, via a `zeroLinks` flag on each row: a 2xx HTML page, no error, with no internal and no external link; non-HTML files, redirects and failures are not "zero links"). The address search (debounced by 250 ms) is a case-insensitive literal substring of the address and combines with the chip (AND). The detail closes when its row leaves the results and does not reappear. Filtering and search run on the server; the screen receives at most **1,000** matching rows (and says so), the export carries them all.
  - **Export CSV** (`GET /internal-links/log/export?snapshot=&filter=&q=`, file `crawl-log-<crawl date>.csv`) follows the current filter and search; cells starting `=`, `+`, `-`, `@` get a leading apostrophe.
  - **Row detail**: clicking a row opens a panel under the table with the internal links found on that page (target, anchor, location, nofollow; targets never crawled are marked "not crawled") and the crawled pages whose links point at that exact address (once each, self links excluded). When the stored link lists hit the cap the panel says that some linking pages may be missing. External links are counted but not stored per page, so they are not listed. A page whose list was not stored (older snapshot, or past the storage cap) says so.
  - **Storage.** `discoveredFrom` and `internalLinks` live on each page record; the raw per-page link list is `rawLinks` in the snapshot file, capped at 100,000 links in crawl order (about 12 MB; pages after the cap keep their counts but not their lists). The discoverer is kept in the run's saved state, so stop and resume keep it (work saved before this field shows "unknown", not "start page"); a first discoverer wins and a redirect target is discovered from the redirecting address.
- **Crawl-quality warning**: when more than half of the requested addresses are a **zero-links page or a self-redirect** (each counted once), the snapshot carries `warning: { affected, total }`, shown as an amber alert above every view with a button to the Crawl log, and the picker reads "Complete, with warning". The crawl still ends `complete`; the warning is decided when the snapshot is written, so snapshots saved before it show none. There is no minimum page count.
- **Compare**: two snapshots (default newest against the one before): pages added or removed, links added or removed (keyed by source, target and anchor) and status changes. With one snapshot the API answers 409.
- **Pages tab**: Inbound and Outbound columns (a dash before a crawl), an orphan marker, and in the drill-down an Internal links block (crawl date, status and depth, inbound, outbound, canonical, indexing) plus the crawler-seen title and meta. Without a crawl it says so and links to the Internal links tab.

### API (all under `/api/projects/:id/seo/internal-links`)

`GET /` (snapshots, latest run, settings with ranges and defaults, host), `PUT /settings`, `POST /crawl`, `GET /crawl`, `POST /crawl/stop`, `GET /graph?snapshot=`, `GET /page?snapshot=&url=`, `POST /matrix`, `POST /matrix/export`, `GET /compare?from=&to=`, `GET /log?snapshot=&filter=&q=`, `GET /log/page?snapshot=&url=`, `GET /log/export`. `filter` is one of `all`, `redirects`, `http-errors`, `errors`, `self-redirects`, `zero-links`; an unknown filter or a repeated parameter is a 400. ## Running jobs in the status footer

Long SEO jobs are listed in the footer's Commands group (and counted in its number) while they run, whether or not the Building is open. Each row shows the job name, elapsed time, the Building's name as its heading and, for a crawl, `N fetched, M queued`. Clicking a row opens the Building on the tab that owns the job.

| Job | Row name | Tab it opens | Stop |
|---|---|---|---|
| Internal links crawl | Internal links crawl | Internal links | Yes (the row's Stop button, same as the tab's) |
| Sitemap fetch | Sitemap fetch | Sitemaps | No |
| URL inspection pass | URL inspection | Sitemaps | No |
| Keyword research / clustering | Keyword research / Keyword clustering | Keywords | No |

- **Source.** The daemon keeps a registry of running jobs (`server/src/seo/jobs.ts`), broadcasts each start, progress and end as a `seoJob` event on `/ws`, and lists the running ones at `GET /api/seo/jobs/running`. The web loads that list on startup and on every `/ws` reconnect; a job missing from it is dropped, and a job whose end was already seen is never listed again.
- **Events.** Progress is sent at most once a second per job. The end event (`complete`, `stopped` or `failed`) is sent after the job has left the registry and is never held back.
- **One row per job.** A crawl that has to fetch the sitemaps first shows only the crawl row: the nested read is not a job of its own. Only the top-level sitemap reads (the Sitemaps tab, the scheduled action and the first run) are.
- **Failure.** A crawl that fails (robots.txt refused, or its state could not be saved) raises an `seo.crawl_failed` notification (warning) carrying the error, resolved by the next crawl that completes. A Stop raises none. Other jobs raise no notification.

## Reports tab

One scannable report of SEO progress for a chosen period against a comparison period. Code: `server/src/seo/` (`reportPeriod.ts` periods and retention, `reportBuild.ts` the maths and the report, `reportData.ts` reads the Building's data, `reportExport.ts` CSV/Markdown/print, `reportSummary.ts` the AI summary, `reports.ts` saved reports, scheduling and the capability, `reportTables.ts`), `server/src/api/seoReportRoutes.ts`, and in the web `lib/seoReports.ts`, `store/seoReportsStore.ts`, `ui/SeoReports.tsx`. The Reports tab replaces the earlier placeholder tab.

- **Periods.** Presets: this week vs last week, this month vs last month, last 28 days vs previous 28, and a custom range whose comparison is the previous period of equal length unless overridden. **Weeks start on Monday** (not configurable). A custom range may be 1 to 400 days and may not end after today (Pacific); an override comparison is not checked against the current range, so it may overlap. There is no year-over-year option.
- **Retention.** Search and analytics rows are kept for the Building's retention window (12 months by default, `retentionMonths` in Settings). A range that reaches before the oldest retained day (the retention cutoff, e.g. 2025-10-15 for a clock of 2026-10-15) is clipped and a note names that day; a comparison entirely before it is "no data". Saved reports are not part of the discard.
- **Partial days.** By default the current window ends at the last day the sync marked final; today (Pacific) and days Google still calls incomplete are left out, counted in `period.trimmedDays` and explained in a note. `includePartial=true` includes them and says so.
- **Scorecard.** Clicks, impressions, CTR, average position, sessions, key events, indexed pages (of submitted), keywords in the top 3 / 10 / 20 (cumulative, from each keyword's impression-weighted Search Console average position; labelled as not rank tracking), new and lost backlinks, referring domains, average DR and UR, tasks completed. Each tile has `state` (`ok`, `not-connected`, `not-available`, `no-data`, `hidden`), the value, the change in absolute and percent terms, and a `glyph` (▲ ▼ ■) plus `verdict` word (better, worse, flat), so the direction never relies on colour. Position and lost backlinks are "lower is better". A source that is not connected is "Not connected", never 0; a metric with data in only one period shows it and no change.
- **DR and UR.** Averages are over the links live at each period end that have a value (a DR of 0 counts, a missing one does not), shown with "n of m links have DR". The tiles are hidden when no live link has the value. They come from the Backlinks import (`sourceDr`, `sourceUr`).
- **Maths and rounding.** CTR is total clicks over total impressions; position is weighted by impressions; nothing is a mean of daily rates. Periods of different length compare totals **per day** (rates and snapshot counts compare directly) with a note. CTR is shown as a percentage to 2 decimals, position to 1, counts whole (1 decimal per day), percent changes to 1 decimal. Rounding is half away from zero on the unrounded value, changes use unrounded values, and a change that rounds to zero is "flat". Going from 0 to something is "new" with no percentage; 0 to 0 is flat.
- **Winners and losers.** Pages, keywords and clusters, the 10 biggest gains and 10 biggest losses in clicks (keywords also by position), counted only when a row had at least `minImpressions` (default 50, a whole number from 0) in **both** periods. Ties break on impressions (largest first), then alphabetically. A link first seen and lost in the same period counts as both new and lost.
- **Indexing changes.** New `seo_index_changes` table: every URL inspection that changes a URL's state (the first answer included) is logged, in the same transaction as the inspection (one row per url and time). The report reads the log plus a baseline: a URL inspected before the log existed has its `seo_inspections` state as its baseline, and a URL whose first logged change starts from a known state is taken to be in that state at the end of the day before. The earliest known state sets "known from"; a period ending before it shows **no data** for indexed pages (not 0) with a note. Newly indexed / excluded compare the state before the period with the state at its end, so a URL that goes out and back in shows in neither list, and a URL first inspected inside the period is a baseline, not a change. Indexed vs submitted at a period end uses the sitemap URLs first seen by then. Before the log began only the latest state of a URL inspected earlier is known.
- **Internal-link changes.** The newest complete crawl snapshot by the period end against the newest one before the period starts (the crawl keeps the last 10): links added and removed, orphan pages before and after, pages newly over 100 outgoing links. With fewer than two such crawls the section says "needs two crawls".
- **AI summary.** `POST /reports/summary` runs a tool-less agent turn (`KeywordAgent.summarise`) on demand and answers `{ paragraph, actions, generatedAt, periodKey, digest, label: 'AI-generated' }`. It is never started by viewing, saving or scheduling; a failure or timeout (`agentTimeoutMs`) leaves the report usable; a second request while one runs is 409. The agent is given the host, the period, one text line per metric and the biggest movers, never tokens, property ids or file paths. The page marks a summary stale when its `digest` no longer matches the report; saving attaches it only when the digest still matches.
- **Saved reports.** `POST /reports` (201) stores the period, the whole computed report and the summary as one JSON document in `seo_reports` (the list returns only name, source, dates and flags). A saved report is self-contained: it is read back byte for byte after new syncs, imports and the retention discard, and is never discarded. Names are trimmed, default to the dates, and are at most 80 characters. Saving an empty Building (nothing connected or imported) is 409.
- **Exports.** `GET /reports/live/export` and `GET /reports/:id/export?format=csv|md|html[&table=scorecard|pages|keywords|clusters|backlinks|indexing|internal-links|work]` (the backlinks table ends with the DR/UR coverage row; the print view and Markdown carry the same sections, including internal links and the "not available yet" messages). CSV cells that start with `=`, `+`, `-`, `@` get a leading apostrophe; "no data" and "Not connected" are text; the print view (`html`) escapes every value and is meant for the browser's Save as PDF.
- **Scheduling.** The `report-weekly` and `report-monthly` schedule actions save the last full Monday-to-Sunday week (or calendar month) against the one before, named "Week 41 2026" (ISO week) or "September 2026", then raise an `seo.report_published` notification (info) and publish the `report-published` event (`reportId`, `period`, `source`). A run on an empty Building, or for a period already saved, is skipped. `GET /reports/schedule` says whether the scheduler is running; without it the tab says reports are manual. Scheduled saving is what keeps history past the retention window.
- **Cross-Building.** The type declares the read capability **`get-latest-report`** (no approval, no inputs): outputs `found`, `markdown`, `period`, `savedAt` and `keyNumbers` (metric key to value; a metric with no data is left out). With no saved report it answers `found: false` and empty strings.
- **API** (under `/api/projects/:id/seo/reports`): `GET /live`, `GET /live/export`, `POST /summary`, `GET /schedule`, `GET /`, `POST /`, `GET|DELETE /:reportId`, `GET /:reportId/export`.

## Scale and benchmark

Targets: 10M metric rows and 1M list rows per Building; lists in 1 s, aggregates in 2 s. `node server/scripts/benchSeo.ts [--gsc N] [--ga4 N] [--runs N]` loads rows through the same insert path as a sync (roll-ups maintained in the same transaction) and prints a report. It is not part of `npm test`.

**Full run (10,000,000 Search Console rows, 1,000,000 Analytics rows, Node 25, Apple silicon, 9 runs per query):**

- Ingest: 10M Search Console rows in 517 s (about 19,400 rows/s), Analytics 1M rows in 27 s (about 37,300 rows/s). The database file is 3.5 GB with all indexes and roll-ups (about 320 bytes per row).
- The daemon's worst event-loop lag during ingest and queries was 33 ms (all database work is in the worker thread); daemon RSS peaked at 343 MB and ended at 229 MB, so memory does not grow with the data.
- Every list p95 is at most 58 ms against 1 s. Every aggregate p95 is at most 117 ms against 2 s; the slowest is the top-10 queries of a month (p50 86 ms) because that roll-up has one row per distinct query per month.
- Retention: discarding 904,200 rows (31 days of a 12-month window) took 277 s, in chunks of 20,000 rows with the roll-ups reduced to match. It runs in the worker and does not block the daemon, but it is slower than ingest, so a very large first discard (for example after shrinking the window) takes minutes.

**Why the raw table has so few indexes.** A first version with indexes on page, query, clicks, impressions and (property, page, day) slowed down as the table grew: inserting one day of 27,000 rows took 0.4 s at 270k rows and 5 s at 1.6M rows, and the run was abandoned. Profiling showed the cost was those random-insert B-trees (dropping the roll-ups did not help). Raw rows now keep only the unique key (property, day, page, query), which serves property and day lookups, and an index on `day`; after the change a day took a flat 0.3 to 0.5 s. Rankings and per-page history come from roll-ups instead: `gsc_page_month` and `gsc_query_month` for top pages and queries, `gsc_page_day` for one page's daily history. Raw rows can be listed by day and filtered (property, day, page, query) but not sorted by clicks.
