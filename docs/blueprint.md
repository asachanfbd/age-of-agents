# Blueprint

**What this document is**: a living snapshot of what currently exists in this repository — not a changelog. Every section below describes the present state only. When something changes, edit the relevant section in place; do not append history, "previously this worked differently," or migration narrative here. If a transition genuinely needs to be recorded (e.g. a deprecation still in progress), it belongs in the section it affects, clearly labeled as in-progress, and removed once the transition completes.

This is distinct from the per-project `Blueprint` defined in [`glossary.md`](glossary.md) (an agent-authored file written into a *managed* project's own `.docs/` folder at the end of a Task). This file is agent-visual-os's own status document, about itself.

For **why** things are built the way they are, see [`architecture.md`](architecture.md). For domain vocabulary, see [`glossary.md`](glossary.md). For phased scope, see [`roadmap.md`](roadmap.md) — the "Overall plan" section below only summarizes where this repo currently sits against that roadmap.

## What this repository currently is

A working two-part system: a background daemon (`server/`) that registers real Projects, spawns real `claude -p` Workers against them, runs an agent-driven planning phase alongside real coding execution, and persists everything in a file-based database; and a 3D visual frontend (`web/`) wired to that daemon over REST + WebSocket instead of dummy local state. Creating a Project through the running app creates a real, git-ignored folder under `projects/` at the repo root. **Phase 1 (MVP) is done** (see "Overall plan" below) — Manager Templates and a live PTY terminal remain out of scope for later phases; multiple concurrent Tasks per Project are now supported, in a small, scoped form (see "What's implemented" below).

## Stack and layout

Node.js/TypeScript throughout. `server/` runs on plain Node (Express + `ws`) with no build step — it executes `.ts` sources directly via Node's native TypeScript support. `web/` is Vite + React 19 + TypeScript, `three` + `@react-three/fiber` + `@react-three/drei` for the 3D scene, `zustand` for state. Both sides test with Node's built-in test runner (`server/tests/*.test.ts`, `web/tests/*.test.mjs`); no vitest/jest dependency anywhere in the repo.

## What's implemented

### The daemon (`server/`)

- **Testing setup** (`src/testing/setup.ts`, task 2.005): “Set up / Reconfigure / Repair testing” creates an ordinary PlanItem marked with `testingSetup: { mode }` and runs a built-in, code-defined two-step workflow. Discovery is read-only and produces a proposal that must be explicitly approved for its exact round before the implementation step can write. Revisions return to read-only discovery, rejection stops the setup, and completion is refused until the config is valid and every enabled primary test action has normalized agent-run evidence. Starts are deduplicated per Project; when another PlanItem holds the Project's setup queue, the item waits and auto-starts when that holder completes. REST is under `GET`/`POST /api/projects/:id/testing/setup` and `POST /api/testing-setup/:runId/{approve,revise,reject}`. The safety contract is detailed in [`architecture.md`](architecture.md#testing-setup-an-approval-gated-open-task).

- **File-based database** (`src/db/FileDatabase.ts`): one JSON file per collection (`projects.json`, `tasks.json`, `task-contexts.json`, `plan-items.json`, `workflow-runs.json`, `step-runs.json`), atomic writes (temp file + rename), mutations serialized per instance so concurrent callers never interleave a read-modify-write. No SQLite dependency — see the amended decision in [`architecture.md`](architecture.md#one-central-runtime-state-store-docs-stay-per-project).
- **Building Types and bulk data** (`src/buildings/`, task 10.003): a Building's type comes from a code-registered list (Software, plus the dev-only Notes skeleton); a type with large data gets its own SQLite file in a worker thread, queried and paginated in the store, with roll-ups, a retention rule, size warning and backup-protected migrations; per-type Catalog configuration of workflow slots; `SecretsStore`; owner and tenant fields. Software Projects are unchanged. See `docs/architecture.md` ("Building Types are coded, not configured", "Bulk data layer") for the design and the benchmark.
- **Projects** (`src/projects/projectService.ts`): `POST /api/projects` creates a real folder under `projects/<slug>/` (slug de-duplicated with a numeric suffix) with an empty `.docs/` folder (the `blueprint.md` and `plan/` stubs are restored on first read; no `notes/`, `decision-logs/`, `tasks/` or `milestones/` folders are made), plus the registry record — `id`, `name`, `slug`, `status`, `position`, `activeTaskId`, `activeTaskIds`, `taskCount`. Cloning a repository that already ships its own `.docs/` preserves it untouched. Position is opaque to the server (the frontend's plot layout owns it) but persisted, so a reload doesn't reshuffle buildings. `PATCH` updates position; `DELETE` removes the folder and the record (refused while a task is active).
- **Docs bootstrap** (`projectService.ts`'s `startDocsBootstrapTask`, called from `api/router.ts`): every new Project, blank or cloned, gets a first Tasks-breakdown item (`plan.ts`'s `DOCS_BOOTSTRAP_TITLE`/`DOCS_BOOTSTRAP_DESCRIPTION`), created before the response and started through `workerManager.enqueuePlanItemExecution` like a user-started task: it runs when a slot is free and waits in the plan-item queue at the task limit. It always runs the fixed one-step `DOCS_BOOTSTRAP_WORKFLOW` (`plan.ts`: `documentation-n-retro-agent` with `maintain-project-context` preloaded, passed as an already-resolved workflow and stored on the queue entry), not the Project's own workflow, so a documentation job never goes through planning, development and review. The skill decides between a bootstrap and a migrate run. The start only accepts the run and launches its start-up in the background, so project creation does not wait for the agent. A failed start never fails Project creation: the item stays on the board, not started, for the owner to start again. There is no start delay. Replaces the earlier bare Task (`startTask`, no workflow run) started 1.5 s after creation, and with it the board special case for runless cards and the early-window gap. See [`architecture.md`](architecture.md#cloning-a-repository-bootstraps-its-docs-from-what-already-exists).
- **Project plan** (`src/projects/plan.ts`, `src/projects/planItemService.ts`): five fixed Markdown documents per Project under `.docs/plan/` (Specifications, Requirements, Test Cases, End-to-End Testing, Performance Testing) are stubbed at creation, restored if missing, and read/written through `GET`/`PUT /api/projects/:id/plan[/docs/:key]`. Tasks are structured `PlanItemRecord` data in `plan-items.json`, not parsed from those documents. `POST/PATCH/DELETE /api/plan-items[/:id]` manage them; a description-only manual task receives a background-generated title. Each item retains its status, linked execution Tasks, and (when created by planning) its durable `planningRef`/planning Task provenance. The Tasks board has four columns in order: **Planning**, **Running**, **Needs you**, **Completed**. Numbered planning conversations and standalone unstarted tasks share the persisted `planningQueueOrder`; `PUT /api/projects/:id/planning-queue/order` reorders those top-level entries together, while ready children remain nested under their active conversation in creation order. `POST /api/plan-items/:id/execute` presents worker/workflow/branch choices and moves an item out of Planning only after an accepted start; a canceled or rejected start leaves its placement intact. `PATCH /api/plan-items/:id` can mark work done or archive it, and deleting a linked item also updates its conversation's completion eligibility. Once a conversation has created at least one task, it completes into the unified Archived view when its last ready child leaves and the session is idle; live turns defer that latest-state check. `POST /api/tasks/:taskId/planning-complete` manually completes an idle conversation, retaining ready children as standalone Planning cards with persisted queue slots and provenance. Restoring the conversation regroups only children still ready in Planning; it never moves other linked tasks. Archived mixes completed planning conversations with archived tasks, each openable and restorable from detail. See [`unified-planning-board.md`](unified-planning-board.md) for lifecycle details and [`architecture.md`](architecture.md#project-plan-documents-and-the-tasks-breakdown) for the structured-data rationale.
- **Milestones**: a Project's target states, one plain markdown file per milestone under `.docs/milestones/` (`milestone-1.md`, `milestone-2.md`, ...), written by hand (no stub is created at Project creation). `PlanItemRecord.milestoneId` can link an item to a milestone, but nothing sets it any more (items linked by older planning sessions keep theirs). No DB record, API route, or UI tab of its own yet — a milestone file is read the same way any other repo file is, through the Code tab. See [`architecture.md`](architecture.md#milestones-a-projects-target-states-broken-into-tasks).
- **Documents tab listing** (`src/projects/documents.ts`): `GET /api/projects/:id/documents` reads the blueprint file plus whatever's actually in `.docs/plan/` (a real `readdir`, not a hardcoded 5-key list) and reports each plan-dir file's `docKey` when it matches one of the fixed `PlanDocKey`s (so the existing plan-doc editor still opens it) or `null` for anything else found there, read-only via `GET /api/projects/:id/documents/plan/:name`.
- **Code tab file explorer** (`src/projects/fileTree.ts`): `GET /api/projects/:id/code/tree` returns `{ files, folders }` from `listProjectTree`. When the project is its own git repo, files come from `git ls-files` (tracked + untracked-but-not-ignored) and folders from a walk that prunes `.git`, anything `git ls-files --ignored --directory` reports, and symlinks, so empty folders still appear. Otherwise it is a plain recursive walk excluding `node_modules`/`.git`/build-output noise. `POST /api/projects/:id/code/entries` (`createCodeEntry` in `src/projects/codeFiles.ts`) creates an empty file or folder with the name exactly as typed; it refuses any path with a `.git` segment, compared case-insensitively because macOS/Windows filesystems treat `.GIT` as `.git`. It shares `createEntry`/`entryPathSegments` and the `EntryExistsError` (409) / `InvalidEntryPathError` (400) errors in `src/projects/projectEntries.ts` with the docs create route, which still appends `.md`. Creating inside folders the tree hides (`node_modules/`, gitignored folders) is allowed, so such a file opens but is not listed. `GET /api/projects/:id/code/file?path=` `GET /api/projects/:id/code/file?path=` reads one file read-only (text, or a `binary`/`too-large` marker instead of raw bytes for anything unsuitable to preview). Every requested path is resolved against the project's root and rejected (400) if it resolves outside it — `..` segments, an absolute path, and a symlink that escapes the root (checked via `realpath`) are all caught, never silently clamped. For a path that doesn't exist yet, `resolveSafePath` realpath-checks its nearest existing ancestor, so a create cannot write through a symlinked folder that points outside the project; a missing file still resolves, so reads 404. A path through an existing file (`package.json/x`) still surfaces ENOTDIR as a 500.
- **Catalog** (`src/catalog/`): full CRUD over agents (Templates) and skills, backed by this repo's own root-level `catalog/agents/` + `catalog/skills/` — a fully separate folder, never this repo's real `.claude/` nor the user's `~/.claude/` — with game-only metadata in a sidecar `catalog/catalog-index.json` (`catalogIndex.ts`). Every read (`listAgents`/`getAgent`/`listSkills`/`getSkill`) re-syncs that index against disk first (`syncCatalogIndex`): any `.md`/`SKILL.md` file not yet indexed gets a synthesized default entry (title-cased name, a default avatar, `enabled: true`), and any index entry whose backing file is gone is dropped — this is how a hand-dropped file, or anything dropped in externally (`npx skills add`), surfaces with no manual migration step. `frontmatter.ts` parses/serializes the `---\nname:\ndescription:\n---\n<body>` block without reordering unknown keys; every write forces the frontmatter `name:` to equal the id (the key Claude Code itself uses to invoke a subagent/skill, kept consistent even though this Catalog's own files are never actually loaded as one), independent of the sidecar's separate human-readable display `name`. `paths.ts` guards every filesystem write against path traversal (id pattern + a syntactic-then-realpath resolve, mirroring `projects/fileTree.ts`'s `resolveSafePath`). `skillZip.ts` extracts an uploaded zip with a two-pass zip-slip guard (path-escape and symlink-entry rejection, validated before anything is written; yauzl's own entry-name validation is a first layer, not a replacement). `skillInstall.ts` runs `npx skills add <owner/repo>` as a real subprocess (strict slug validation, `spawnFn`-injectable for tests, never `shell: true`) with `cwd` set to a fresh temp directory it creates and owns exclusively — since that CLI has no output-directory flag and always writes into whatever `.claude/skills/` it finds relative to its own cwd, this is what keeps it from ever touching this repo's real `.claude/`; once the process exits successfully, the installed skill folder(s) are copied from `<tmpdir>/.claude/skills/` into the real `catalog/skills/` (each id sanity-checked via `paths.ts` first) and the temp directory is removed regardless of outcome. Streams a running/log/settled event shape structurally parallel to `commands/commandRunner.ts`, broadcast over the same `/ws` channel. Two Templates ship seeded in `catalog-index.json`: `builder` (`catalog/agents/builder.md`), non-manager, `defaultAutonomy: 'auto'`; and `manager` (`catalog/agents/manager.md`), `manager: true`, `defaultAutonomy: 'auto'` — its persona instructs the Worker to delegate substantial sub-tasks to native Claude Code sub-agents via the Task tool rather than doing all the work directly, and to surface the sub-agent's question directly when one reports it needs clarification. Every Task now runs as a live interactive-CLI session rather than a structured headless turn, so that question simply appears in the Manager's own terminal (the project popup) for a person to answer directly — there is no longer a `blockedQuestion`/`answerTask`-mediated relay for it (that mechanism only ever existed for the removed structured/headless executor contract; `'blocked'` is now a `TaskStatus` a live Task can no longer reach at all) — while `resolveDisallowedTools` still guarantees the Task tool is never stripped from a manager-flagged Task, so the Manager can make its next delegated call once it has the answer. See [`architecture.md`](architecture.md#manager-and-sub-agent-flow-native-delegation-with-a-relay-for-questions) and [`architecture.md`](architecture.md#catalog-lives-in-its-own-repo-root-catalog-folder). A third Catalog kind, Workflows (task 3.012), lives the same way at `catalog/workflows/<id>.json` (`src/catalog/workflowService.ts` — one JSON file per `WorkflowRecord`, no sidecar index needed since a Workflow's game-only fields already live in its own file) via `GET/POST /api/catalog/workflows` + `GET/PUT/DELETE /api/catalog/workflows/:id`; validation checks every step id is unique, every `agentId`/`skillIds`/`executorId` resolves in the Catalog/executors config, and every `loopBack.toStepId` targets an earlier step with `maxRounds` 1–10. One Workflow, `software-development` (UI Planning → Test Case Planning → Development → Code Review [loops back to Development, max 3 rounds] → Human Code Review → Docs & Retro → the built-in Complete stage), ships seeded and is the Catalog default; `PATCH /api/projects/:id/workflow` sets a Project's own choice (`ProjectRecord.workflowId`, null = default).
- **Workflow run engine** (`src/worker/workerManager.ts`'s `startWorkflowRun`/`startStepTask`/`advanceWorkflowRun` and friends, `src/worker/workflowPrompt.ts`, `src/worker/workflowSummarizer.ts`, `src/terminal/stepTaskTool.ts` + `bin/step-task-mcp.mjs`): task 3.012 replaced running a Tasks-breakdown PlanItem as a bare execute Task with a `WorkflowRunRecord` — a frozen snapshot of the Project's resolved Workflow, one shared git worktree/branch (`<type>/<ref>-<slug>` — see `projects/branchName.ts`, no model call, off the Project's own branch) reused by every step's own `TaskRecord`/`StepRunRecord` (round-numbered; a request-changes or loop-issues reply resumes the step's prior CLI session with the new context as a new round when possible, otherwise starts fresh). A read-only step (`canEditCode: false`) gets the exact `PLAN_DISALLOWED_TOOLS` enforcement a planning session gets; a step may also set `canUseBrowser` (needs `canEditCode` or `canRunCommands`) to get a headless Playwright browser MCP server, installed and described in `architecture.md`'s "Workflow steps may use a headless browser" section (task 39.002); a step session reports its result and pages the branch's diff through its own MCP tools (`complete_step`/`skip_step`/`diff_summary`/`diff_file`, relayed via `/api/workflow-steps` — every step Task, now always an interactive CLI session, gets the MCP server, and closes that session itself the instant it reports an outcome, `endStepSession`). A step with `requiredOutputFormat: "html"` (the seeded UI Planning) has `complete_step` refused with a 422 nudge until it carries a real HTML mockup output (`src/worker/requiredOutputs.ts`; the round stays running so the agent retries in the same session, and `skip_step` is unaffected); the route also validates each output's shape and parses a stringified `outputs` array (`src/api/stepOutputs.ts`). `complete_step` takes an optional free-text `planningGap` (stored on that round's `StepRunRecord`) for an ambiguity planning should have resolved; every gap raised so far in the run is listed in each later step's prompt under "Planning gaps raised this run", and the seeded Docs & Retro step's instructions tell it to root-cause each one and write project-scoped fixes into `.docs/planning-notes.md` with no approval. A fix that belongs in a shared Catalog Workflow step or Skill is proposed to the person in the step's live session and applied only after an explicit "yes" via two more step MCP tools, `update_workflow_step({workflowId, stepId, instructions})` and `update_skill({skillId, body, description?})`, which the MCP script relays straight to the existing `GET`/`PUT /api/catalog/workflows/:id` and `PUT /api/catalog/skills/:id` routes (so `updateWorkflow`/`updateSkill` do the validation and persistence). That approval is enforced by instruction only: there is no proposal record, queue or UI. A step may also stop and ask the person a direct question in its own session when genuinely stuck. Approval (`POST /api/workflow-runs/:id/approve|request-changes`), loop exhaustion (`.../loop`), a step that ended without ever calling `complete_step`/`skip_step` (Task exit, Stop, or a daemon restart), and a manual `.../retry-step`/`.../stop` are all handled by the same run/PlanItem-status mapping (a stopped run is halted, not finished: its PlanItem goes `blocked`, and its worktree and step session are kept so `POST /api/workflow-runs/:id/resume` can start the current step's next round by resuming that same CLI session with a "Continue." message; re-executing a stopped item removes the old worktree first) and `workflow`-origin-feature Notifications (raised on `awaiting-approval`/`needs-attention`, resolved when the run leaves that state). The built-in Complete stage commits/pushes, raises (or reuses) the PR via `gh`, against the run's base branch, and completing the run regardless if `gh` is missing or the PR call fails — and stores a `completionReport` built by a headless summarizer turn (`workflowSummarizer.ts`, the same "one throwaway JSON turn on whichever executor has the least rate limit used" pattern `planItemTitler.ts` already established, now shared via `executors/leastUsedExecutor.ts`) with a stitched-together fallback if that turn fails. A settled step's (or round's) conversation can be reopened from the run view's "Resume session" control (`GET /api/tasks/:taskId/reopen-session/options` and `POST /api/tasks/:taskId/reopen-session`). The generic Task Resume and Follow-up routes reject workflow step Tasks, so this step-specific route remains the only ad hoc launch path. It retains its captured agent, skills, permissions and eligible step/testing tools; `complete_step` and `skip_step` still reject a settled round. Completed editable runs ask whether to reopen with permissions or read-only because the branch may already be merged. An existing run worktree is reused; when removed, the daemon restores the task branch into its recorded worktree path. A branch gone locally and remotely allows only a project-folder read-only session. A completed run's recreated copy is removed on a clean or read-only exit; after a writable exit with changes, the run stores a pending commit-and-push or discard decision until resolved (`POST /api/workflow-runs/:id/reopen-changes`). Reopened sessions take no Task concurrency slot, write no Task or StepRun record, leave run status unchanged, do not report lifecycle hooks and end after 15 seconds detached; a later round waits for an inspect process to exit before continuing that conversation, and no two Task records launch processes on one CLI session ID at once. This removed the old ad hoc completion flow entirely: `completeTerminalTask` now just settles a paused terminal Task `'done'` immediately, with no docs-and-retro Yes/No confirmation step (that pass is now the Workflow's own Docs & Retro step). **Regression reopen** (task 22.001): `workerManager.ts`'s `reopenBug` (`POST /api/plan-items/:id/regression`, session tool `reopen_bug` via `bugTracker.reopenCompletedBug`) reports a regression on a Completed bug and starts a new run of it at once: the reason is appended to the bug's `regressions` list in the same write that accepts the run (and unarchives the bug), so a refused start changes nothing. The run is a fresh run on a new branch from the base branch (never the earlier branch, never stacked) carrying `regression.roundOffsets`; `startStepTask` gives each step's first attempt the earlier run's latest round of that step as its prior, so it resumes that session (`continuableSession`) or starts fresh with its earlier output, and sends `workflowPrompt.ts`'s `buildRegressionMessage` (reasons quoted as data). Resuming from a different working directory is unverified against the real CLIs. See [Reporting a regression](unified-planning-board.md#reporting-a-regression).
- **Step progress labels** (`src/worker/stepProgress.ts`): each `report_progress` checklist item may carry an optional `short` label (1-2 words, e.g. "writing code"); a non-string is a 400 like `note`, and length is never refused: `trimShortLabel` keeps the first 2 words and at most 24 characters (by code point, ending in "…" when cut), and stores null when nothing is left. `summarizeProgress` copies the first in-progress item's label into `WorkflowRunRecord.currentStepProgress.currentLabel` (null when none is in progress or it has no label, and on progress stored before labels existed), broadcast with the run and reset with the rest of the summary when a new step round starts. The step prompt and `bin/step-task-mcp.mjs`'s schema ask agents for it; the 3D village's task tags show it.
- **Worker orchestration** (`src/worker/`): `claudeProcess.ts` spawns `claude -p --output-format stream-json --permission-mode <bypassPermissions|default> --json-schema <status contract> [--disallowed-tools <tools>] [--resume <id>] "<prompt>"`, parses the stream-json lines, and classifies the final result as `done` / `blocked` / `error` per the Phase 0 spike's confirmed mechanism (any extra top-level JSON fields on the final message, e.g. `planTasks`, are captured on `ClaudeTurnResult.extra`). `workerManager.ts` is a factory (`createWorkerManager`, with the real `runClaudeTurn` injected as the default) enforcing a small, per-Project concurrent-Task cap rather than a single global one — a git-backed Project's first active Task always runs directly in the Project's own working directory, and each Task beyond that (`assignTaskWorkspace`) gets its own isolated `git worktree` + branch (`task/<taskId>`, off whatever the Project's directory currently has checked out) up to `MAX_CONCURRENT_TASKS_PER_PROJECT`, instead of `startTask`/`followUpTask` refusing outright; a Project with no linked repository stays capped at one Task, since there is no git repo to isolate a worktree in. A settled worktree Task's directory is removed (`cleanupWorktree`) while its branch — and anything already pushed to it — is left for a human to review/merge, never auto-merged. `TaskRecord.worktreePath` records which directory a Task actually ran in (absent for the common non-worktree case); `ProjectRecord.activeTaskIds` holds the full active set, while `activeTaskId` keeps meaning "the most recently started still-active Task" for the existing single-Task UI. See [`architecture.md`](architecture.md#concurrent-tasks-per-project) for the full model and its rationale. The same `workerManager.ts` also relays blocked-task answers via `--resume`, resumes a *finished* Task's session for a follow-up instruction (`followUpTask`, a new linked TaskRecord — see [`architecture.md`](architecture.md#follow-up-tasks-continue-a-session-not-mutate-a-finished-one)), writes every turn to a Task's transcript, mirrors a linked PlanItem's status onto its Task, applies a `'plan'`-kind Task's proposed `planTasks` changes once it settles `'done'`, and broadcasts `WorkerEvent`s (`project` / `task` / `log` / `planItem` / `planItemDeleted` / `workflowRun` / `stepRun`) to subscribers. A Task's `manager` field is copied from its Template's `manager` flag at creation (`startTask`/`followUpTask`, the same pattern `autonomy` follows from `defaultAutonomy`) and persisted on the `TaskRecord`; `runTurn`'s `resolveDisallowedTools` uses it to guarantee the native delegation (`Task`) tool is never included in `--disallowed-tools` for a manager-flagged Task, regardless of `kind`. Today only a `'plan'`-kind Task sets `disallowedTools` at all (`PLAN_DISALLOWED_TOOLS`, which never includes `Task`), so an ordinary `'execute'` Task — what a Manager Template actually runs — already has no tool restrictions; the guarantee exists so that can't silently regress. `startTask` also accepts an optional `skillIds`, validated the same way an explicit `templateId` is (`catalogService.listSkills`/`listAgents`: must exist, `AgentNotFoundError`/`SkillNotFoundError`; must be `enabled`, `TemplateDisabledError`/`SkillDisabledError`) before the Task is ever persisted; `followUpTask` carries a prior Task's `skillIds` forward, same as `templateId`. `workerManager.ts`'s `buildAppendSystemPrompt` builds the Worker's `--append-system-prompt` as the Template persona (`readAgentPersona`) followed by the chosen Skills in skill-id order — deterministic regardless of the order `skillIds` was given in. By default a Skill loads **on demand**: one `## Available skills (read on demand)` section lists each skill's name, id, frontmatter description ("(no description)" when empty) and absolute `SKILL.md` path, with instructions to check descriptions against the work, Read an applicable `SKILL.md` in full, resolve relative paths against that skill's directory, skip skills that don't apply, and list the skills read in any summary. A Skill also named in the optional `preloadSkillIds` (a subset of `skillIds`, validated at Workflow save, in `startTask` and by the start-task API; absent or empty means all on demand) is "always load": its full `SKILL.md` body (`catalogService.readSkillBody`) goes under a `## Skill: <name> (<id>)` heading, preceded by a note (`skillSectionHeader`) saying it is already loaded and naming its absolute path. Catalog skills are never installed into the Project's own skill directories, so both forms say the skill is runner-supplied and not to be reported missing. `preloadSkillIds` is copied wherever `skillIds` is (step to step Task, follow-up), the completion docs Task preloads `maintain-project-context`, and the shipped Docs & Retro steps preload it too. A stored `sessionSetup` is never rebuilt: tasks started before this keep their full bodies. deliberately broader than `worker/projectFolderGuard.ts`'s folder-busy guard, since an app update affects every Project at once) decides when it's safe to apply a `server`-classified update. `appUpdateService.ts`'s stateful `AppUpdateStatus` machine (in-memory only, lost on restart by design) backs `GET /api/app-update` and `POST /api/app-update/{check,apply,cancel}`: `apply()` runs a `web-only` change immediately in-process (`webOnlyUpdateRunner.ts`: pull → install → build into `web/dist.new/`, swapped over `web/dist/` only on success, so a failed build never disturbs the already-running `vite preview`) with no daemon restart at all; ### Scene / visual layer (`web/src/scene/`)

- **Art direction**: a light, clean miniature town in the style of an isometric warehouse dashboard: a fresh green grass plain with soft patches, cream paved streets, fenced yards with yellow dashed bay lines, warehouses with tinted pitched roofs, trees, rocks and water, cardboard boxes, white robots and metal machines, with white info cards for tags. City Center keeps its two-story civic pavilion (1.1× visual scale) at the middle of the cross road.
- **Camera & controls** (`Scene.tsx`, rules in `cameraMath.ts`, driven by `cameraController.ts`): drei `MapControls` with pan (left-drag), zoom (wheel, pinch, middle-drag) and rotate/tilt (right-drag or Shift + left-drag). The target stays on the map (`MAP_HALF`, from the town layout), zoom is 8-90 units and elevation 20°-80°, so the camera never goes underground or flips. Zooming is a street walk: closer than the Home distance, the camera also drops toward 28°, so the yards on either side of a street are seen from the side; the user's own tilt is kept on top of that curve. **Keyboard rotation:** W/A/S/D work anywhere in the 3D view, no minimap focus needed. A and D orbit left and right (D raises azimuth), W and S tilt up and down (W raises elevation, clamped to the tilt limits), at 75°/s while held, per frame by elapsed time with a 0.1 s cap on a frame gap (`web/src/scene/cameraKeys.ts`, bound by `cameraController.bindKeyboard`). Keys are ignored with Ctrl/Meta/Alt, during IME composition, in input, textarea, select, contenteditable and the terminal (`[data-task-terminal]` or `.xterm`), while a popup disables controls, and while the scene is covered (`setCovered`, fed from `Scene`). A rotation key cancels a flight; starting Home or a minimap flight clears held keys, so the flight wins. Frames are requested only while a key is held. All camera input pauses while a Project is dragged (`controlsEnabled`). Camera state lives in the controller, not the world store, so moving the camera re-renders only the navigation card. `Scene` attaches the controller to the controls drei currently holds (`useThree((s) => s.controls)`, effect keyed on `[controls, invalidate]`), never a ref: `PerspectiveCamera makeDefault` makes drei rebuild `MapControls`, and a controller bound to the first instance moves only the minimap (bugfix 33.003.001).
- **Navigation card** (`ui/VillageNavigation.tsx`, `ui/VillageNavigationCard.tsx`, geometry in `scene/minimapMath.ts`): bottom-left, 16px above the status footer. A **Home** button flies (~700ms, ease-in-out) back to `DEFAULT_VIEW`, the one fixed Home view. A north-up minimap (200px, 140px on phones) shows streets, the Home building, each Project as a status-coloured dot, and the camera's ground footprint (a trapezoid that follows pan, zoom and rotation). Clicking it flies there (~450ms, zoom and rotation kept), dragging makes the camera follow, and arrow keys pan 5 units while the minimap has focus. Any user input cancels a flight; Home and the minimap are disabled during a Project drag.
- **Ground** (`Ground.tsx`, `Terrain.tsx`): a textured ground plane using a procedurally-painted canvas texture (fresh green grass with a soft gradient and a few large pale and deep patches; no soil, specks or haze) that fades into the sea at its edge, plus three still-water ponds with a pale foam ring on the outer edge of the map. Clicking empty ground (a real click, not a pan) deselects the current building.
- **Background and scenery** (`Backdrop.tsx`, `Terrain.tsx`, `scenery.ts`): the sea around the plain, with no hills. Trees (round and pine), rocks, fences, gate paths, kerbs and lamps are generated once from fixed seeds in `scenery.ts` (pure, unit-tested: none lands on a road, yard, City Center or water) and drawn as instanced meshes, so their number costs no extra draw calls. There are no per-plot lights or shadows. Not yet implemented: ambient animation (tree sway, chimney smoke, pond shimmer) from the approved mockup.
- **Day/night cycle** (`skyKeyframes.ts`, `Scene.tsx`): follows real IST time, with brighter neutral hemisphere fill and sunlight, full daylight held from 8 AM to 5 PM, sunrise around 6 AM, dusk around 7 PM, and night from 9 PM through 5 AM. Streetlamp emission and stylized light pools fade on at night. Daylight material colors are lighter and less metallic so shaded surfaces remain readable. A crescent moon (`Moon.tsx`) and starfield (`Stars.tsx`) fade in opposite the sun as it sets and fade back out as it rises, riding the same `sampleSky` sample (a `moonVisibility` keyframe field, plus moon elevation/azimuth derived as the sun's angle phase-shifted by half a day) rather than a second clock; a separate, world-anchored dim cool-white directional light follows the same arc so buildings/ground/trees stay gently visible at night instead of relying on ambient fill alone. The crescent shape itself is two overlapping spheres (a pale lit disc mostly covered by a slightly larger dark occluder sphere) rather than a custom shader. Unlike everything else in the scene, the visible moon mesh and starfield are mounted as children of the `PerspectiveCamera` and positioned in camera-local space (a yaw/pitch arc a few hundred units out, safely inside the camera's fixed field of view) rather than world space — the camera looks down at 20°-80° and only ever shows a narrow "open sky" band above the far edge of the screen, so a world-space placement falls out of view as the camera turns; riding along as a rigid camera child keeps them in that band at any tilt or rotation, and keeps them from visibly shifting as the camera pans or zooms, like real, astronomically distant objects. Both materials disable depth testing and fog so they always read as a distant, unoccluded backdrop.
- **Streets and plots** (`townLayout.ts`, `scenery.ts`, `TownStreets.tsx`, `lib/villageLayout.ts`): twelve north-south streets, each with a left and a right side of ten yards facing the road, 12 × 2 × 10 = 240 plots (`PROJECT_CAPACITY`), arranged in six columns (two streets per column, one on each side of a cross road through City Center). Streets are numbered outward from City Center, alternating north and south. A plot is a (street, side, slot) triple; positions are stored as plot coordinates, the daemon accepts only the 240 plots (`server/src/projects/townPlots.ts`, kept equal to the web generator by a drift test), and the scene draws plot (x, z) at (x, z) × `TOWN_SCALE` (3.2). Each yard is turned a quarter turn (`villageLayout.ts`'s `yardFacing`) so its door side faces the road, and no two yards, a yard and a road, or a yard and City Center overlap. The ground runs to ±60 world units (`WORLD_BOUND`); the default camera shows only a part of it, and the rest is explored with the camera controls. Positions saved on the earlier 32-plot block grid are moved once to the 32 street plots nearest City Center, in their old order (`migrateLegacyPosition`; the daemon at startup, the web app on load). An off-plot, invalid or doubled saved position is repaired to the nearest free plot by `lib/townGroups.ts`'s `repairPositions`. A yard-sized pad lies on every plot (so a free plot reads as a place to move a Project to). Decoration uses instanced meshes and does not intercept pointer events. Creation and movement call the same pure nearest-free-plot rule in the store. The top bar reads "N projects · 12 streets" and warns near and at capacity; the Create Project button disables at 240.

Wraparound glazed window bays, silver facade fins, a floating rounded roof, recessed skylight, cyan edge lighting, and a sheltered double-door entrance form its facade. The yard is turned a quarter turn so its front (door side) faces its street, so the same plan serves both sides of a street. ### Project Workspace — the Full-fledged Project Popover (`web/src/ui/ProjectWorkspaceModal.tsx`)

- **Vertical space is scarce — UI guideline**: the popup is short, so plan every new control around height. Prefer single-row controls; avoid stacked labels and multi-line inputs in always-visible bars; move rarely-used inputs into a dialog or a collapsible section (the run view's approval bar is one row until Reject is pressed, then expands an auto-growing reason box in the bar itself, `AutoGrowTextarea`, 1 to 5 lines then scrolling, so the stage content above stays visible while the reason is typed; Send rejection or Ctrl/Cmd+Enter sends, Cancel or Escape collapses it, and the typed reason is kept per run in browser storage until it is sent or the run leaves awaiting approval; the "review loop ran out of rounds" comment box uses the same textarea); combine tabs or toggles rather than adding rows; keep fixed headers and footers to one row; and let the main content (terminal, markdown) take the remaining height.
- **Header/toolbar redesign**: the header is a title row (project name, status `Badge`, close) stacked above a toolbar row — `ProjectCommandBar` (highlighted command buttons plus a shadcn `DropdownMenu` "⋯" for every non-highlighted command, always present so its "Run Custom Command" item stays reachable even with zero saved/non-highlighted commands) on one side, `BranchMenu.tsx` on the other when `project.repositoryUrl` is set. Status/agent labels throughout this file use shadcn's `Badge` (muted, in their own row under a row's title rather than crammed inline) and every action uses shadcn's `Button` (`size="sm"`/`"icon"`, `variant` per action kind — `destructive` for Stop/Delete/Remove) instead of the legacy `.status-pill`/`.btn` CSS classes, which other UI files (`SettingsPanel.tsx`, `AgentsSettings.tsx`, `TopBar.tsx`) still use. A Radix `Popover`/`DropdownMenu` rendered inside this modal needs an explicit `z-[20001]` on its content (`.modal-overlay`'s `z-index: 20000` otherwise sits above the portal's default `z-50`).
- **Branch popover** (`BranchMenu.tsx`, replacing the old inline `BranchPicker` text-input/datalist/checkbox form): a compact trigger showing the current branch name opens a `Popover` containing a searchable (`Command`/`CommandInput`, type-to-filter) list fed fresh from `serverApi.projectBranches` every time it opens (the server now fetches `origin` first — see `architecture.md`'s "Branch listing and checkout"), plus a Sync action in the popover's own header (a distinct "catch up to remote" action, not merged into branch switching). Selecting any listed branch (local or remote) checks it out via `serverApi.checkoutBranch`; typing a name matching nothing offers "Create branch" (`create: true`) instead of a separate checkbox. Sync and switching to an existing branch are disabled only while the Project's own folder is really busy — `lib/branchMenu.ts`'s `isProjectFolderBusy`, the same rule the daemon's `checkoutProjectBranch`/`runProjectSync` refuse on (`server/src/worker/projectFolderGuard.ts`), computed over the store's live `tasksById`/`workflowRunsByProject` rather than the Project's overall `status`: a running planning session, or a Task/WorkflowRun isolated in its own worktree, never disables them. Creating a branch stays enabled regardless.
- **Attention banner**: when the status dot's red 'error' state applies to the open project (`lib/buildingVisualStatus.ts`'s `buildingVisualStatus`/`describeAttention`, recomputed here from the same `lastTaskIdByProject`/`reviewedTaskIds`/`isOutOfSync(project.sync)` inputs the warehouse label's dot reads), a red banner between the header and the top-level tabs explains why — a failed latest task's reason, an out-of-sync branch's `describeSync` message, or both — so opening the popup because of that dot answers "why" immediately instead of requiring a hunt through tabs. This banner does not yet factor in an open Notification's severity the way the warehouse label's dot does (see "Status indicator" above) — it still only ever fires off a failed task/out-of-sync branch, a gap left for the Notification Center work (`docs/milestones/milestone-5-notification-system.md`) to close.
- **Documents/Code sidebar width**: `.workspace__tabs` gets the `workspace__tabs--file-tree` modifier (240px vs. the plain tab-button lists' 168px) whenever it's rendering a `FileTree` (Documents/Code tabs), since real file names get cramped at the narrower width; both variants collapse to `width: auto` under the existing 720px mobile breakpoint.
- **Opening it**: clicking a Project's warehouse calls `openWorkspace(projectId)` directly (`ProjectYard.tsx`'s `handlePointerUp`), setting `workspaceProjectId` in the store; `ProjectWorkspaceModal` renders as a centered full-screen overlay (`.modal-overlay`, the same pattern as the create-project dialog) whenever that's set, independent of `selectedId` and `catalogOpen` (`openWorkspace` closes the Catalog modal if it was open, and vice versa — see "Catalog modal" below). The topbar's project picker opens the same workspace for consistency; "Headquarters" in that picker calls `openCatalog()` the same way City Center's own click does. Its inner content is keyed by project id, so switching projects remounts it with a clean tab/detail-view state rather than an effect resetting it (see the `web-interaction-conventions` skill). A project that's already `developing`/`blocked` when opened lands straight on the Tasks tab with that Task's own Details view showing, not the Overview tab — preserving the wave-and-popover-into-chat flow's immediacy now that a building's click goes straight to the full workspace instead of a small quick-chat popup.
- **Top-level tabs** (`WorkspaceContent`): Tasks, Documents, Testing, Code, Settings, then **Archived** at the far right whenever archived tasks or completed planning conversations exist (`lib/projectTasks.ts#hasArchivedItems`). ## What's explicitly not implemented

- The Execute composer (`WorkspaceChat`'s non-planning instance, see "Persistent chat footer" above) is the only place to choose a Template or fold in Skills when starting a Task — `POST /api/projects/:id/tasks` accepts optional `templateId`/`skillIds` end to end (each validated to exist and be `enabled` in the Catalog — `AgentNotFoundError`/`SkillNotFoundError` 404, `TemplateDisabledError`/`SkillDisabledError` 422 — and, when given, folded into the spawned Worker's system prompt, Skills after the persona in skill-id order). The planning chat (`sendChatMessage`/`POST /chat`), the Tasks board's per-card Start (`executePlanItem`/`POST /api/plan-items/:id/execute`), and follow-ups (`followUpTask`, which carries a prior Task's own `templateId`/`skillIds` forward automatically) still have no picker of their own; each of those silently runs the Catalog's default Template with no Skills unless a caller passes these fields by hand.
- No live PTY terminal (deferred per the v1 scope decisions in `architecture.md`). Multiple concurrent Tasks per Project and git worktrees are implemented, but capped: 6 concurrent coding Tasks for a Project with a linked repository, 1 without one (live and waiting-for-input Tasks and starting runs count; planning sessions and conflict runs do not). A refused start shows its own message in place, listing the Tasks using the slots; archiving or completing a still-running planning session has its own message, and doing so to an already complete session is a quiet no-op; refused automatic starts raise one project-scoped notification — see [`architecture.md`](architecture.md#concurrent-tasks-per-project) — and no UI exists yet to show or manage more than one active Task on a Project at once: the existing single-Task UI (Tasks tab, footer counts, the chat composer's `idle`-only gating) is untouched, so it still cannot itself start a second concurrent Task; the capability is reachable today only by calling the API directly.
- No real pause on an approval-gated Task — `autonomy: 'approval'` runs the CLI's default permission mode, which denies a gated tool call rather than pausing for one. See `server/README.md`, "Known simplifications."
