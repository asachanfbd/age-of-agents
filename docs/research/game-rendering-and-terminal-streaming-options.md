# Game rendering and terminal-streaming options

This covers two separate technical questions for agent-visual-os's frontend: what to render the Age-of-Empires-style scene with, and how to get a worker process's output into the browser. All star and fork counts and last-push dates below came from direct GitHub API calls on 2026-09-12, not search-engine summaries, unless stated otherwise.

## Scene rendering

Three options were compared for the game scene: Phaser 3, PixiJS, and Three.js. Phaser 3 (40,298 stars, pushed 2026-08-21) is a full 2D game framework with built-in sprite animation, tilemaps, physics, and input handling, and Anthropic-adjacent official React and Vite starter templates exist for it. A directly relevant reference project, `twofactor/pogicity-demo` (429 stars, pushed 2026-09-01), already implements isometric city-builder mechanics, including four-direction walking character animation, on top of Phaser. PixiJS (48,142 stars, pushed 2026-09-08, the most active of the three) is a lower-level 2D renderer without Phaser's built-in scene, tilemap, or physics conventions, better suited to being one embedded component inside a larger app than to a full game built from scratch.

Both Phaser and PixiJS are fundamentally 2D, sprite-sheet-based renderers. agent-visual-os's actual requirement, decided during scoping, was a scene that reads as three-dimensional and clean rather than as 2D pixel art, which ruled both out regardless of art quality. Three.js (115,413 stars, pushed 2026-09-11, by far the largest and most active project considered) renders true 3D and was chosen instead, paired with React Three Fiber for the React integration layer. This has a steeper learning curve than a 2D framework and needs more manual setup for animation, but it is the only one of the three that can deliver a genuinely dimensional look.

Free, CC0-licensed asset packs exist that fit a project-and-worker visual metaphor without commissioning custom art: Kenney.nl publishes an "Isometric Blocks" pack and a "Medieval RTS" pack (120-plus structures, units, and tiles, explicitly built for town-building and strategy games), both usable as a starting point, though the medieval theme would need reskinning toward a software-project look. The Kenney "Game Assets All-in-1" bundle (60,000-plus assets, CC0) is the umbrella collection both come from. A widely used isometric plugin for Phaser, `phaser3-plugin-isometric`, was checked and found stale: its last published version dates to February 2023, per Snyk's package-health data, which is moot now that the scene is planned in Three.js rather than Phaser, but is recorded here since it was part of what was evaluated.

## Getting process output into the browser

The standard architecture for this, used by every off-the-shelf tool checked, is a server-side PTY whose stdout is piped over a WebSocket to a browser-side terminal emulator, most commonly `xterm.js`. `xterm.js` itself (21,163 stars, pushed 2026-09-11) is actively maintained, but its packages were renamed: the legacy `xterm` package on npm is deprecated in favor of the scoped `@xterm/xterm` plus official addons such as `@xterm/addon-fit`, which is worth knowing since older tutorials still reference the old package name. `node-pty` (Microsoft, 2,025 stars, pushed 2026-09-03, actively maintained and what VS Code's own integrated terminal uses) is the standard PTY-spawning library for Node, though it has a real, long-documented history of native-module friction inside Electron specifically (GitHub issue #728 and others), which does not directly apply here since agent-visual-os is a plain Node web server, not an Electron app.

Three off-the-shelf tools already package this exact PTY-to-WebSocket bridge as a standalone app: `ttyd` (C, 12,353 stars), `gotty` (Go, community-maintained fork at `sorenisanerd/gotty`, 2,545 stars), and `wetty` (Node.js, built on `xterm.js` and `node-pty` directly, 5,430 stars, pushed 2026-09-11). All three are built to expose one terminal session per connection, not several named panes embedded inside a larger custom app alongside a game canvas, so using one as-is would mean running a separate instance per worker rather than a single multi-session server. They are useful as reference implementations of the bridge, not as drop-in dependencies.

agent-visual-os's version 1 does not use any of this. The chosen approach renders the already-structured `stream-json` event stream as formatted text through `xterm.js` used purely as a display widget, with no real PTY behind it. A `node-pty`-backed, genuinely interactive terminal, allowing direct typed input into a worker's session, is recorded as a possible later addition, not part of the current plan; see [`../roadmap.md`](../roadmap.md#phase-4--not-committed), "Phase 4."

## Process management specifically for Claude Code agents

No actively maintained, purpose-built library for managing a pool of `claude -p` subprocesses with permission-prompt injection was found; see [`real-agent-orchestration-options.md`](real-agent-orchestration-options.md) for the detail on that search. The closest adjacent, well-maintained project is `smtg-ai/claude-squad` (8,469 stars, pushed 2026-08-20), which runs each agent in its own `tmux` session and isolated git worktree, but expects a human watching the terminal pane directly rather than a programmatic client parsing structured output. `stravu/crystal`, a similar multi-session tool with SQLite-backed persistence, appears to have been renamed and succeeded by a project called "Nimbalyst" as of February 2026, per its own repository description; that successor project's maturity was not independently checked in this research pass.
