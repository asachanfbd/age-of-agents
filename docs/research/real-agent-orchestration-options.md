# Real agent orchestration options

This compares two ways to programmatically run real Claude agents against real project folders: the Claude Agent SDK versus direct `claude` CLI subprocess management, covering what each supports for streaming status, pausing an agent to ask the user a question, and one agent spawning others. agent-visual-os ended up choosing direct CLI subprocess management, mainly to avoid separate API-key billing; this file records what the research found either way. Facts below are sourced from Anthropic's own documentation and, where noted, from GitHub issues on `anthropics/claude-code`; anything not independently confirmed is flagged as such rather than stated as fact.

## The SDK and the CLI are the same engine

The Claude Agent SDK, in both its Python and TypeScript packages, spawns the Claude Code CLI itself as a subprocess and talks to it over the same newline-delimited-JSON protocol the CLI exposes directly via `claude -p --output-format stream-json --input-format stream-json`. The SDK's `pathToClaudeCodeExecutable` and `executable` options, documented in Anthropic's own TypeScript reference, confirm this. So choosing between "use the SDK" and "shell out to the CLI" is not a choice between two different engines. It is a choice between typed message objects and callbacks (the SDK) versus parsing raw JSON lines and wiring hooks by hand (the CLI directly).

## What launching a scoped agent supports

`query()` in the SDK, or `claude -p` on the CLI, both take a working directory to scope file and shell tools to, a system prompt or persona, tool allow/deny lists, a permission mode (`default`, `plan`, `acceptEdits`, `bypassPermissions`, and others), a model choice, and session resume flags. Both stream structured events: assistant messages, tool-use blocks, a final result message with cost, and, when requested, token-level deltas. Every message carries a `parent_tool_use_id`, which is enough to attribute activity to a specific sub-agent for a live status view. Source: Anthropic's Agent SDK reference pages for TypeScript and Python, and the CLI's headless-mode documentation.

## Pausing to ask the user something

Claude Code has a built-in `AskUserQuestion` tool. In the SDK, calling it pauses execution genuinely, indefinitely, until a `canUseTool` callback returns an answer; Anthropic's own documentation states the callback can stay pending indefinitely. On the CLI side, the equivalent path is `--permission-prompt-tool`, which points Claude Code at an MCP tool that receives the same kind of request, or a `PreToolUse` hook returning a `defer` decision, which lets the process exit and resume later via `--resume <session_id>` once an answer is ready, without holding a process open the whole time a human is thinking. The `defer` decision was added in Claude Code v2.1.89, per its changelog.

One clear gap found in Anthropic's own documentation: `AskUserQuestion` is not available to sub-agents spawned through the built-in Agent/Task tool, only to the top-level process. A sub-agent that hits something it cannot resolve on its own has no native way to ask; getting a question out of a sub-agent requires either a custom tool the sub-agent calls, which the host application intercepts, or ending the sub-agent's turn and letting the top-level process (in this project's design, the manager) ask on its behalf.

A more specific, and less settled, finding: a closed GitHub issue on `anthropics/claude-code` (#12605, "AskUserQuestion Hook Support") states that, at the time it was filed, hooks could detect an `AskUserQuestion` call but could not programmatically supply an answer back to Claude Code in headless mode. The issue is closed, but no maintainer comment explaining why was retrievable during this research, so whether the later `defer` mechanism fully resolves this for `AskUserQuestion` specifically, as opposed to ordinary tool permissions, is not confirmed. This is exactly the assumption agent-visual-os's Phase 0 spike needed to test before anything else was built on top of it.

## One agent spawning others

The SDK supports native, in-process sub-agent delegation: passing an `agents` map to `query()` gives Claude a built-in Agent/Task tool it can use to delegate, nested up to a depth of 3 and up to 20 concurrent sub-agents by default, both configurable via environment variables. This happens inside one CLI subprocess; a sub-agent gets its own isolated context but is not a separate OS process, and by default the parent only sees its summarized result, not its full working transcript. Getting fully independent, separately killable agent processes instead of this in-process delegation is not something Claude Code provides out of the box; it means the host application spawning multiple independent `claude -p` processes itself and coordinating between them, which is architecturally a different thing from native delegation.

## Billing

This is a fact that applies identically whether an application uses the SDK or the CLI directly, since both share the same authentication layer. Anthropic's documented policy reserves OAuth or subscription login (Free, Pro, or Max plans) for ordinary individual use of Claude Code and Anthropic's other native apps, and states that developers building products or services on top of Claude, including through the Agent SDK, should authenticate with an API key through the Claude Console instead. The CLI's `--bare` flag, meant for scripted and SDK-driven use, enforces this mechanically: it does not read OAuth credentials at all, only an API key or a cloud-provider credential.

## Empirical spike, 2026-09-12

Everything above came from documentation and GitHub issues. This section is a direct test against the actual `claude` CLI available to this account (v2.1.269), run from a throwaway scratch directory, to check the assumption the rest of this plan depends on: that a headless session can pause on a question and be resumed with an answer.

First test: `claude -p "<task requiring a choice between Python and Node.js, instructed to use AskUserQuestion>" --output-format stream-json --verbose`. The session ran `ToolSearch` for `AskUserQuestion`, got back "No matching deferred tools found," and its own `system/init` event listed its available tools explicitly: no `AskUserQuestion` among them. It responded with "I don't have access to an interactive question tool in this session, so I'll ask directly here instead," stated the question as plain text, and ended the turn (`stop_reason: end_turn`, exit code 0). No file was written; nothing was left running or paused. This confirms, for this account's build, `AskUserQuestion` is genuinely not available in headless mode, not merely undocumented.

Second test: resumed that same session with `claude -p --resume <session_id> "Use Node.js." --output-format stream-json --verbose`. It picked the task back up correctly, remembering it had asked about Python versus Node.js, and proceeded to scaffold a Node.js project. This is the part that matters: the "ask, then resume with an answer" pattern works, it is just not a live pause of a running process. The first invocation runs to completion and exits; the question is the result of a normal, finished turn; resuming starts a new process that continues the same logical session.

Third test, checking whether this holds under a real autonomy setting rather than the CLI's default: repeated the first test with `--permission-mode bypassPermissions`. It still asked and stopped correctly, without attempting any file writes first. Resuming with the answer under the same flag then genuinely created the files (`package.json`, `index.js`, `.gitignore`), with `permission_denials: []` in the result. Worth noting what happened under the default permission mode instead, on the second test above run without `bypassPermissions`: the write attempts were silently denied, not paused or asked about, and the worker's own final message explained that its file creation had been refused. Default permission mode fails closed and silent; it does not behave like a pause. Whatever setting agent-visual-os uses for "full autonomy" needs to be an actual permission-mode flag passed to the process, not just an intention.

Fourth test: added `--json-schema '{"type":"object","properties":{"status":{"type":"string","enum":["blocked","done"]},"message":{"type":"string"}},"required":["status","message"]}'` to a fresh run of the first test. The result came back as valid, parseable JSON, `{"status":"blocked","message":"<the question>"}`, instead of free text. This is a more reliable detection signal than scanning prose for something that looks like a question, and is confirmed to work alongside `bypassPermissions`. The `"done"` branch of that same schema was not separately exercised in this spike; there is no specific reason to expect it behaves differently, but it has not been directly observed.

One incidental finding while reading `claude --help` during this spike, unrelated to the question above but relevant to the rest of the plan: this CLI build has native background-session management beyond `-p`/`--resume`, including `claude --bg`, `claude agents --json` (lists active sessions with pid, cwd, and status), `claude logs <id>`, `claude attach <id>`, `claude stop`/`rm <id>`, and a `-w`/`--worktree` flag that creates a git worktree for a session directly. None of this is covered in the sections above, since it did not surface in the public documentation and GitHub issues that research was based on. It was not exercised beyond confirming the commands exist and checking for stray sessions this spike left running. It is a strong candidate for reducing how much subprocess-pool and worktree-management code agent-visual-os needs to write by hand; see [`../architecture.md`](../architecture.md#a-finding-that-may-reduce-how-much-of-this-needs-to-be-hand-built) for the follow-up note.

## Prior art

Anthropic's own reference point for multi-agent orchestration is an engineering blog post, "How we built our multi-agent research system," describing the orchestrator-worker pattern behind Claude's Research feature: a lead agent plans and spins up three to five parallel sub-agents, then synthesizes their results. It is a description of the pattern, not a code reference, and it predates the Agent SDK's current sub-agent feature. No official Anthropic example of a web UI visualizing multiple concurrent agents was found.

Third-party projects that touch parts of this problem, all unofficial and of varying maturity: `patoles/agent-flow` (a passive observer of Claude Code's own hook events, does not spawn or manage processes itself), `hoangsonww/Claude-Code-Agent-Monitor` (a monitoring dashboard over session data), `disler/claude-code-hooks-multi-agent-observability` (relays hook events, including permission requests, to a dashboard for human review, but does not inject answers back into a paused session), and `Ngxba/claude-code-cli-ui` (built on the Agent SDK, has a PTY terminal view, but no documented structured flow for detecting and answering a blocked permission or question state). Two much smaller, single-digit-star projects come closer to the specific "detect blocked, inject an answer" pattern agent-visual-os needs: `raylin01/claude-client`, which parses `control_request` events and exposes methods to approve, deny, or answer a question directly; and `claw-army/claude-node`, which owns a long-lived stream-json subprocess and supports resuming by session ID. Both are proof-of-concept scale, not production-grade, and neither should be depended on as-is.
